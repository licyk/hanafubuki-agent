The model does its work through tools. Each tool comes from a plugin, which `disabledPlugins` can turn off as a whole (see the [Configuration reference](/docs/config-reference#general)). Which tools need an approval is in [Permissions and approvals](/docs/permissions#what-asks).

| Plugin         | Tools                                                                                                            |
| -------------- | ---------------------------------------------------------------------------------------------------------------- |
| `execution`    | `exec_command`, `write_stdin`, `resize_execution`                                                                |
| `workspace-fs` | `read_file`, `list_directory`, `search_text`, `apply_patch`, `move_path`, `delete_path`                          |
| `web`          | `web_search`, `fetch_web_page`                                                                                   |
| `view-image`   | `view_image` (only when the model takes images)                                                                  |
| `mcp`          | The MCP servers' tools, and `list_mcp_resources`, `list_mcp_resource_templates`, `read_mcp_resource`             |
| `skills`       | `skills_list`, `skills_read`, `enable_skill`, `disable_skill`                                                    |
| `memory`       | `list_agent_memories`, `search_agent_memories`, `read_agent_memory`, `append_agent_memory_note` (with memory on) |
| `goal`         | `get_goal`, `create_goal`, `update_goal`                                                                         |
| `subagents`    | `spawn_agent`, `send_message`, `followup_task`, `wait_agent`, `list_agents`, `interrupt_agent`                   |

A few tools are always there: `update_plan` (the task plan), `request_user_input` (asking you), `new_context` (a fresh context window), and `tool_search` when some tools are offered on demand.

## Commands and terminals [#commands]

`exec_command` runs a command in a shell:

| System       | Shell                                                                                                                 |
| ------------ | --------------------------------------------------------------------------------------------------------------------- |
| Linux, macOS | `/bin/bash` (or `/bin/sh` without it), as a login shell (`-lc`) by default                                            |
| Windows      | `pwsh` (or `powershell` without it), with UTF-8 output; on request `cmd.exe`, or the bash of Git for Windows or MSYS2 |

- **A POSIX shell on Windows**: when the model asks for one (`shell: "posix"`), the command runs in the bash (or, without it, the `sh`) of Git for Windows or MSYS2, as a login shell (`-lc`) by default, like on Linux; the default stays PowerShell. The shell is looked for in this order, bash before `sh` at each step:
  1. When the Agent itself runs in an MSYS2 or Git Bash shell (`MSYSTEM` is set), that environment's, through the Agent's `PATH`.
  2. On the command's `PATH`, leaving out the `bash.exe` in `System32` (and `SysWOW64`, `Sysnative`) and in a `WindowsApps` directory: those start WSL, not a shell of this machine.
  3. In `usr\bin` of `%ProgramFiles%\Git`, `%ProgramFiles(x86)%\Git`, `%LOCALAPPDATA%\Programs\Git` and `%SystemDrive%\msys64`.

  Git for Windows' `bin\bash.exe` only starts its `usr\bin\bash.exe` as a child of its own, so that one runs instead: a stop then ends the shell itself. Without a shell, the command is not run, and the model is told where it was looked for and that `power_shell` is there. The variables such a shell gets are in [Environment](/docs/environment#commands).
  - A program built on the MSYS runtime splits its command line itself, not as other Windows programs do, so the script is spelled for it there: a space in front of a script without a space or tab, and each run of backslashes not before a `"` doubled. The approval shows the script as written; the command line it binds is the spelled one.
  - The runtime cuts a command-line argument longer than 8186 characters short without a word (measured with Git for Windows' and MSYS2's runtimes, on text of the Basic Multilingual Plane), so a script of more than 8000 UTF-16 units (characters, for most text) is refused: the model is told to write it to a file and run that, or to use `power_shell`.
  - It does not start in the Windows [sandbox](/docs/permissions#sandbox): under its restricted token the MSYS runtime stops with `couldn't create signal pipe, Win32 error 5`.
  - A working directory longer than 247 bytes is handed to Windows in its verbatim form (`\\?\`); how the MSYS runtime takes one is untested.

- **Long-running commands**: a command is waited for up to 10 seconds by default (the model may ask for up to 30). One still running then goes on in the background, and the model reads its later output, or writes to it, with `write_stdin`.
- **Interactive terminals**: the model can ask for a pseudo-terminal (PTY), which takes any input and can be resized with `resize_execution`; otherwise only Ctrl-C can be sent.
- **Output**: each call returns the output since the previous one, up to the bound the model names (`max_output_bytes`: 64 KiB by default, at most 256 KiB). A session keeps the newest 4 MiB of its output for its calls, whatever their bound.
  - Past the bound, a call returns the output's head and tail, each cut at a line break, with a line `[… N bytes omitted …]` between them, and says `truncated`; it reads on from the end. A call that fell more than 4 MiB behind gets the marker, with what it missed, then the newest output. Of the bytes a session keeps, nothing is left out without the marker, and no line is glued to another.
  - Escape sequences are removed, and carriage returns, backspaces, moves along a line and erases are applied by cell, a wide (CJK) character taking two, so a progress line keeps only its last state. A sequence cut by the end of a call is read whole by the next. The model reads this plain text; the colours and attributes of the output's SGR sequences are kept beside it for a display only (the terminal interface's [command output](/docs/terminal-interface#rendering)), never in what the model reads, the history's tool output or an export.
  - In a pseudo-terminal, the output is replayed through a terminal screen of the PTY's size (`vt100`), with its resizes: each call returns the lines that scrolled off since the previous one, then the screen's rows from the first that changed, so repaints (ConPTY's above all), progress bars, cursor moves and erases land where a terminal would put them. A row still being written, such as a prompt, comes again, whole, once something is added to it. As on a terminal, rows that scroll inside a scroll region a program set are not kept, and a resize does not reflow the rows already written. The terminal interface's preview of a running command reads the screen the same way.
- **Time limits**: every process is stopped after 10 minutes. A tool that makes no progress for 10 minutes is stopped too.
- **Sandbox**: a command runs in the session's [sandbox](/docs/permissions#sandbox): by default on Linux and macOS it writes only in the workspace roots and the temporary directories, without the network; one whose sandbox this machine cannot give is not run.
- **Outside the sandbox**: the model can ask to run one command outside the sandbox, with the arguments `sandbox_permissions` (`"use_default"`, the default, or `"require_escalated"`) and `justification` (a question of at most 1024 bytes shown with the approval; only with `"require_escalated"`, else an error the model reads), as in Codex. Such a command needs an approval of its own, which the full-access mode never gives; see [Permissions](/docs/permissions#escalation).
- **Environment**: commands get a clean environment, without your shell's variables; see [Environment](/docs/environment#commands).
- **Text encoding**: output reaches the model as UTF-8.
  - PowerShell, 5.1 and 7 alike, starts by setting its console's output and input code pages, and the encoding of the text it pipes to programs (`$OutputEncoding`, ASCII in 5.1), to UTF-8 without a byte-order mark, and turns progress bars off (`$ProgressPreference = 'SilentlyContinue'`).
  - `cmd.exe` runs `chcp 65001` first, so the programs it starts that follow the console's code page write UTF-8. Its own built-ins (`dir`, `echo`, `type`) keep the code page `cmd.exe` started with, the console's (OEM) one, when they write to a pipe; in a pseudo-terminal, or run as `cmd /c …` from PowerShell, they arrive whole.
  - Python writes UTF-8 (`PYTHONUTF8=1`, `PYTHONIOENCODING=utf-8`).
  - What a program writes in another encoding anyway is decoded piece by piece, so one output can mix them: ASCII passes, each run of other bytes that is UTF-8 stays, and one that is not is read in Windows's ANSI code page (936, GBK, on Chinese Windows; 1252 on Western ones). Linux and macOS have no such fallback, since commands get `LANG=C.UTF-8`: bytes that are not UTF-8 show as `�`.
  - The fallback is the ANSI code page, not the console's (OEM) one. On Chinese, Japanese and Korean Windows the two are the same (936, 932, 949, 950), so `cmd.exe`'s built-ins are read right there. Elsewhere they differ (1252 and 437 or 850, 1251 and 866, 1253 and 737): a program that follows the console's code page writes UTF-8 after `chcp 65001` or PowerShell's settings, but the non-ASCII text of `cmd.exe`'s own built-ins on a pipe is read in the wrong code page.
  - In a pseudo-terminal, Windows's console host turns what a program writes into UTF-8 itself, reading it in the console's code page, which is UTF-8: a program there that writes the ANSI code page regardless still shows `�`.
- **Working directory**: a command runs in the directory the model names, a relative one taken from the first workspace root; when it names none, in the first workspace root: the working directory (`-C`), or the one it was changed to while the Agent runs.
- **Clean-up**: the Agent records the process groups it starts and ends them when it shuts down; after a crash, the next start cleans up what was left.

The terminal interface shows a running command as `• Running …` with its output as it streams ([Tool calls](/docs/terminal-interface#tools)); `exec --json` has its `execution_progress` events.

In a [review](/docs/sessions#reviews), only plain `git --no-pager` reads run; see [Permissions](/docs/permissions#review).

## Files [#files]

| Tool             | Does                                                                                       |
| ---------------- | ------------------------------------------------------------------------------------------ |
| `read_file`      | Reads a file, page by page, up to 256 KiB a page                                           |
| `list_directory` | Lists a directory                                                                          |
| `search_text`    | Searches text with a regular expression, honouring `.gitignore` and the other ignore files |
| `apply_patch`    | Creates, changes and deletes files as a patch                                              |
| `move_path`      | Moves or renames                                                                           |
| `delete_path`    | Deletes a file or a directory                                                              |

- A relative path is taken from the first workspace root.
- Reading is not limited to the workspace roots. A write, move or delete anywhere needs an approval; one that touches a path outside the workspace roots is critical, and its summary names those paths.
- `read_file` pages by bytes: `offset` is where its page starts and `nextOffset` where the next one does. Its result also counts the line the page starts on, `startLine` (from 1), so the lines it read can be numbered.
- In the terminal interface, `apply_patch`'s approval shows the diff it makes, and its result the files it changed, with the diff expanded ([Tool calls](/docs/terminal-interface#tools)), its rows numbered where the patch landed. The tool reports those positions beside its result, for the display only: the model reads the files it changed, as before.

## The web [#web]

`web_search` searches the web, and `fetch_web_page` reads a page's text. Neither needs an approval. `fetch_web_page` reads public pages only, and checks a page's address on this machine even through a proxy ([Web fetch and name resolution](/docs/network-logging#web-fetch-dns)).

`webSearchProvider` picks the search service:

| Value              | Does                                                                                                                  |
| ------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `"auto"` (default) | SearXNG first when `searxngBaseUrl` is set, then DuckDuckGo when SearXNG finds nothing or fails; otherwise DuckDuckGo |
| `"duckduckgo"`     | Always DuckDuckGo                                                                                                     |
| `"searxng"`        | Always SearXNG; needs `searxngBaseUrl`                                                                                |

```sh
hanafubuki-agent config set searxngBaseUrl https://searx.example.com
hanafubuki-agent config set webSearchProvider searxng
```

- A search returns at most 10 results, kept for 5 minutes.
- A fetch returns up to 50,000 bytes of text by default, and can continue page by page. It follows at most 5 redirects, 20 seconds each fetch.
- A fetch refuses private and loopback addresses and URLs with credentials.
- With `webFetchUseJinaReader = true`, a direct fetch that fails (refused, timed out, empty, an unsupported type) is retried through `https://r.jina.ai/`, which sends the URL to Jina.
- The web tools use `network.proxy`; see [Network and logging](/docs/network-logging#proxy-scope).

## Goals [#goals]

The `goal` plugin's tools work on the session's [goal](/docs/sessions#goals):

- `get_goal` reads it: the objective, status, budgets, the tokens and time used, and the tokens left of its budget.
- `create_goal` (`objective`, an optional `token_budget`) creates an active goal. The model is told to create one only when you, or instructions, ask for one; it fails while the session has an unfinished goal.
- `update_goal` (`status`: `complete`, `blocked` or `paused`) marks the goal complete once its objective is achieved and verified, blocked after the same blocker recurred for three goal turns, or paused at your request. It cannot resume a goal or lift a budget limit.

None needs an approval. In Plan mode only `get_goal` is offered; in a temporary session (a side conversation) they fail.

## Sub-agents [#subagents]

The model can hand a task to a sub-agent: a conversation of its own, a child of the session ([Sessions](/docs/sessions#children)), that runs in the background with the session's permission mode, and with its model and tools unless `spawn_agent`'s arguments or the sub-agent's [role](/docs/roles#subagents) say otherwise. The tools are Codex's (its second multi-agent tool set):

| Tool              | Arguments                                                                                                  | Does                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ----------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `spawn_agent`     | `task_name`, `message`, `fork_turns` (`all`/`none`), `agent_type`, `model`, `reasoning_effort`, `provider` | Creates a sub-agent named `task_name` (lowercase letters, digits, underscores) as the spawnable role `agent_type` (the session's own without it), on the model, reasoning effort and Provider given, and runs `message` as its first turn; `all` starts it from the conversation before the current turn, `none` from nothing. Returns its task name, its id and the Provider, model and reasoning effort it runs with (`null`: the Provider's default) |
| `send_message`    | `target`, `message`                                                                                        | A running sub-agent reads the message at its next step; an idle one with its next task. Starts no turn                                                                                                                                                                                                                                                                                                                                                  |
| `followup_task`   | `target`, `message`                                                                                        | Gives a sub-agent another task: a new turn when it is idle, otherwise added to the turn it runs                                                                                                                                                                                                                                                                                                                                                         |
| `wait_agent`      | `timeout_ms` (10 s to 5 min, 30 s by default)                                                              | Waits until a sub-agent finishes a turn, and returns the final answer (or the error) of each one that finished since the last wait                                                                                                                                                                                                                                                                                                                      |
| `list_agents`     |                                                                                                            | The session's sub-agents, with the status and the role of each                                                                                                                                                                                                                                                                                                                                                                                          |
| `interrupt_agent` | `target`                                                                                                   | Stops the sub-agent's turn; it keeps taking messages and tasks                                                                                                                                                                                                                                                                                                                                                                                          |

`target` is a sub-agent's task name or its session id.

- **Limits**: only a session that is not itself a child spawns, so a sub-agent cannot spawn its own; at most 3 sub-agents of a session run at once; a task name is used once per session.
- **Model, effort and Provider**: each is `spawn_agent`'s argument, else the role's, else the session's own. `provider` is an enabled Provider's id or, when exactly one enabled Provider has it, its display name (case aside); a Provider without `model` keeps the inherited model id there. Whatever is passed is checked before the sub-agent exists, and a refusal is an error naming the argument with what can be passed instead, so no sub-agent is made: a Provider that is not enabled (the error lists the enabled ones); a model that neither the Provider's recorded listing, its `models."<id>"` settings, the session's own model on its Provider nor the default model on the default Provider names (the error lists up to 20 of the known ids, those sharing the longest start with the one asked for first), when a listing is recorded, else any model is passed to the Provider as given; an effort the model is not known to take, when its levels are configured or reported (the error lists them, the default marked) or it is known to take none; `none`. An effort that is not passed is never checked, and a request narrows it as for any session ([Reasoning effort and thinking](/docs/providers-models#reasoning)). The parent's history (`fork_turns` `all`) goes to whichever Provider the sub-agent runs on. A follow-up task runs on the sub-agent's own model; `/model` while viewing it changes that.
- **Approvals**: the tools need none. A sub-agent's own tool calls are approved in its own conversation, under the permission mode it takes from the session at each task: one that needs your answer waits there until you open the sub-agent and answer it.
- **Guidance**: the model of a top-level session whose step offers `spawn_agent` (not in Plan mode, nor in a [role](/docs/roles#sessions) that leaves the tool out) also reads guidance on coordinating sub-agents (spawn only when asked to, run independent steps in parallel, wait for them before answering) and the roles it may give them ([Roles for sub-agents](/docs/roles#subagents)). Then, for `provider`, `model` and `reasoning_effort`, it reads its own model and the enabled Providers by id and name, its own first, then by name: under each, the models known of it (its own model, the `models."<id>"` settings, the default model on the default Provider, then the recorded listing by id), each with the reasoning efforts it takes, the default marked, or that it takes none, where that is known; a Provider without a recorded listing says any model id is passed to it as given. At most 8 Providers of 8 models each and 4 KiB in all; what is left out is said ("… and 3 more") and still accepted. Everything listed is accepted by a spawn and named as its errors name it; no token, header or base URL is shown. The list is read at every step without a request, so a Provider edited, a listing recorded with other models or levels, a model's reasoning refused by its Provider (for the 7 days that refusal is kept) or a `/model` change shows from the next step; so does the end of levels a Provider reported for a model its latest listing no longer names, 7 days after they were seen. Nothing else changes it. In Plan mode only `wait_agent` and `list_agents` are offered.
- A sub-agent is a session like any other: its turns and events are in its own history, and an interface lists a session's sub-agents through the `subagents` call ([Embedding the Agent](/docs/embedding#feature-calls)). `subagents` in `disabledPlugins` takes the tools and the guidance away.

## Workspace roots [#workspace]

The workspace roots tell the model which directories it works in, in this order:

1. the working directory: `-C DIR`, or the current directory;
2. the working directory's Git root;
3. each `--add-dir DIR`.

A directory inside an earlier one is dropped. The first root is what relative paths are taken from, and what `@` mentions and `/diff` use.

```sh
hanafubuki-agent -C ~/src/app --add-dir ~/src/shared-lib
```

## AGENTS.md [#agents-md]

At the start of each turn, the Agent reads these instruction files and gives them to the model:

1. your own: `AGENTS.override.md` in the data directory, or `AGENTS.md` without it (`~/.local/share/hanafubuki-agent/AGENTS.md` on Linux);
2. each workspace root's `AGENTS.override.md`, or its `AGENTS.md`.

Only the files in the roots themselves are read, not those in the directories between the Git root and the working directory. All the instructions together are capped at 32 KiB, 16 KiB a group.

With the `workspace-context` plugin turned off, the model sees neither these instructions nor the workspace roots and the environment.
