When the model wants to do something with side effects (run a command, change a file, call an MCP tool), the Agent first lets the **permission mode** decide whether it needs your approval.

## Permission modes [#modes]

| Mode             | `--permission-mode` | In `config.toml` | Does                                                                                  |
| ---------------- | ------------------- | ---------------- | ------------------------------------------------------------------------------------- |
| Manual (default) | `manual`            | `"manual"`       | Every operation that needs an approval waits for your answer                          |
| Automatic review | `auto-review`       | `"auto_review"`  | A model reviews each operation that needs an approval and decides, without asking you |
| Full access      | `full-access`       | `"full_access"`  | Every operation that needs an approval is allowed                                     |

To set it:

```sh
hanafubuki-agent config set permissionMode auto_review    # from now on
hanafubuki-agent --permission-mode full-access exec "…"   # for this run only
```

A profile can hold it too, such as `[profiles.review] permissionMode = "auto_review"`, selected with `-p review`. The mode is fixed when a turn starts. In the terminal interface, `/permissions` changes it for the session (below), and `/status` shows the mode in effect.

### One session's mode [#session-mode]

A session can run in another mode than the configured one, until it ends, without changing `permissionMode`. In the terminal interface `/permissions` sets it, with the session's sandbox as a [preset](#presets) or alone with `/permissions MODE` ([Terminal interface](/docs/terminal-interface#permissions)). An embedding host sets it with `set_session_permission_mode` ([Embedding the Agent](/docs/embedding#permissions)).

- It can be changed at any time. A running turn keeps the mode it started with; the session's next turn takes the new one.
- It belongs to that session only: other sessions, and a fork of it, keep the configured mode.
- It is kept in memory only: after a restart the session is back on `permissionMode`.

## The sandbox [#sandbox]

The permission mode decides who approves a command; the **sandbox** decides what an approved command can reach. The two are independent: a command the full-access mode runs without asking still runs in the sandbox.

| `sandboxMode`                                        | A command the model runs can                                                                                                                                                                                                                                       |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `"read-only"`                                        | read every file your user can; write nothing but `/dev/null` and `/dev/tty`; not use the network                                                                                                                                                                   |
| `"workspace-write"` (the default on Linux and macOS) | read every file; write under the [workspace roots](/docs/tools#workspace), `/tmp`, the Agent's temporary directory (`TMPDIR`, on Windows `TEMP`) and `sandboxWorkspaceWrite.writableRoots`; use the network only with `sandboxWorkspaceWrite.networkAccess = true` |
| `"full-access"` (the default on Windows)             | everything your user can: no sandbox                                                                                                                                                                                                                               |

```sh
hanafubuki-agent config set sandboxMode read-only
hanafubuki-agent config set sandboxWorkspaceWrite.networkAccess true
```

These are Codex's `sandbox_mode` and `[sandbox_workspace_write]`; its default preset is workspace-write without the network. The keys are in the [Configuration reference](/docs/config-reference#sandbox). A turn's sandbox is fixed when it starts, like its permission mode.

### Platforms [#sandbox-platforms]

- **Linux**: Landlock confines the filesystem (Linux 5.13 or later, with Landlock enabled) and seccomp the network (x86_64 and aarch64). A sandboxed command starts the `hanafubuki-agent` binary again as a helper, which confines itself and then becomes the command, so the command is still the process the Agent owns. This is Codex's Landlock pipeline; Codex itself now prefers bubblewrap, which needs user namespaces that many systems restrict, and a bundled `bwrap`.
- **macOS**: Seatbelt. A sandboxed command runs under `/usr/bin/sandbox-exec` (that path only, never one found on the `PATH`), which applies a policy that denies everything the mode does not allow and then becomes the command. The policy is Codex's. The writable roots are resolved first, so `/tmp` is `/private/tmp` and a symlinked root grants its target; a root that does not exist stays unwritable. Under a writable root, an existing `.git` (for a `.git` file, the repository it points to as well), `.agents` and `.hanafubuki-agent` stay read-only, as Codex keeps `.git`, `.agents` and `.codex`: a command could otherwise add a Git hook or change the project's `sandboxMode`.
- **Windows**: the sandbox is opt-in, as in Codex: `[windows] sandbox = "unelevated"` turns on Codex's unelevated sandbox, which needs no administrator. A sandboxed command starts the `hanafubuki-agent` binary again as a helper, which starts the command with a restricted token and waits for it: the command's writes must also be allowed to a capability SID of one of the writable roots, the logon session or Everyone, and each writable root grants its own SID, with an ACE added to its directory the first time (the ACEs stay, and adding one walks the whole tree once). Under a writable root an existing `.git` (for a `.git` file, the repository it points to as well), `.agents` and `.hanafubuki-agent` are denied to those SIDs, as on macOS. The command runs on a desktop of its own, so its windows and keystrokes never reach yours, and in a job that ends it, and whatever it started, when the helper ends. **The network is not blocked**: without network access the command only gets Codex's offline environment (`HTTP_PROXY` and the like pointing nowhere, `CARGO_NET_OFFLINE`, `NPM_CONFIG_OFFLINE`, `GIT_SSH_COMMAND` failing), which a program can ignore. Codex's elevated sandbox, which blocks the network with firewall rules for sandbox users an administrator creates, is not available yet (`windows.sandbox = "elevated"` refuses every sandboxed command, and [`/setup-default-sandbox`](/docs/terminal-interface#commands) says so). An unset `sandboxMode` stays full-access on Windows; with `[windows] sandbox` unset, any other mode makes every command fail, as below.

`hanafubuki-agent doctor` reports the sandbox mode in effect and whether this machine can give it.

### When it is unavailable [#sandbox-unavailable]

A command that asks for a sandbox this machine cannot give is **not run**: the Agent never runs it unconfined instead. The tool call fails before anyone is asked to approve it, and the model reads why:

```text
the command was not run: it needs the workspace-write sandbox, which is unavailable (this kernel has no Landlock (Linux 5.13 or later, with Landlock enabled)); set sandboxMode to "full-access" to run commands without a sandbox
```

On such a machine, set `sandboxMode = "full-access"` to run commands again, unconfined (on Windows, or turn the sandbox on with `[windows] sandbox = "unelevated"`). On Linux and Windows, a program that embeds the Agent must let its binary serve as the helper, or every sandboxed command fails the same way ([Embedding the Agent](/docs/embedding#sandbox-helper)). On macOS the sandbox is unavailable only without `/usr/bin/sandbox-exec`; but an Agent that itself runs inside a Seatbelt sandbox cannot start another, so its sandboxed commands fail as they start.

### Running one command outside the sandbox [#escalation]

As in Codex, the model can ask to run one command outside the sandbox: `exec_command` with `sandbox_permissions` set to `"require_escalated"` and a `justification`, a short question for you ([Tools](/docs/tools#commands)). It does so when a command needs more than the sandbox allows (writing outside the writable roots, the network when it is off), or failed because of the sandbox. Such a command needs an approval of its own, which says that it runs outside the sandbox and gives the justification:

```text
Run Posix command outside the sandbox in /home/me/project: npm install (reason: Do you want to download the project's dependencies?)
```

| Permission mode  | A command outside the sandbox                                                                       |
| ---------------- | --------------------------------------------------------------------------------------------------- |
| Manual           | waits for your answer                                                                               |
| Automatic review | is reviewed; the reviewer sees that it leaves the sandbox and the justification                     |
| Full access      | is refused, and the model reads why: a mode that asks no one cannot let a command leave the sandbox |

These follow Codex's approval policies: `on-request` asks you, an `auto_review` reviewer reviews the escalation, and `never` rejects it. Once approved, the command runs without the sandbox, with your user's rights; an approval of the same command inside the sandbox does not run it outside, nor the other way round. **Allow for the session** of a command outside the sandbox allows that same command (its text and directory) outside the sandbox again, and nothing else; the tool's own allowance does not cover commands outside the sandbox. When the session's sandbox is `full-access` the request changes nothing but the approval, since the command runs unconfined anyway.

A command the sandbox refuses fails as the operating system reports it (`Permission denied`, `Operation not permitted`, a failed DNS lookup); its output carries no hint, as in Codex: the model learns when to ask from the tool's description and the context below.

### What the model is told [#sandbox-context]

Each turn's world state has a `sandbox` section beside the permission mode, with the sandbox mode, whether the network is allowed, the writable roots (in workspace-write) and how a command may leave the sandbox in the turn's permission mode, as Codex's permissions instructions tell its model:

```json
{
  "escalation": "A command that needs more than the sandbox allows runs outside it with sandbox_permissions \"require_escalated\" and a justification question; the user approves or denies it.",
  "mode": "workspace-write",
  "networkAccess": false,
  "writableRoots": ["/home/me/project", "/tmp"]
}
```

In automatic review the escalation text says the reviewer decides, and asks the model to proceed only with a materially safer alternative after a denial; in full access it says not to ask; with no sandbox it says there is none. When the network is off but the sandbox in effect does not block it (Windows' unelevated sandbox, see [Platforms](#sandbox-platforms)), the section adds `"networkEnforced": false`, so the model is not told that the network is unreachable when it is not. The section changes, and is sent again, only when one of these does: the sandbox mode, the permission mode, the workspace roots or the configured roots.

### What it does not cover [#sandbox-limits]

- Only the commands the model runs (`exec_command`, and the terminals they leave running) are sandboxed. The file tools are bounded by the workspace roots and their approvals; MCP servers and [hooks](/docs/configuration#hooks), which you configure, run outside the sandbox.
- Reading is not restricted.
- On Linux nothing under a writable root stays read-only, `.git` included: Landlock only grants rights, so Codex's read-only `.git` inside the workspace is not ported there. On macOS it is, so in workspace-write `git commit`, and anything else that writes `.git`, fails: run it with full-access.
- On macOS a `.git`, `.agents` or `.hanafubuki-agent` that does not exist when the command starts is not protected: the command can create one.
- Without network access, on Linux every socket but a Unix one is refused, and so is connecting any socket, Unix ones included (an SSH agent, Docker's socket); with it, only VM sockets stay refused; either way `io_uring`, which could open a socket past the filter, is refused. On macOS, without network access no socket connects, Unix ones included; with it, every one does.
- On Windows the restricted token confines writes only: what the logon session or Everyone may write stays writable, the network is reachable (see [Platforms](#sandbox-platforms); the model is told so, see [What the model is told](#sandbox-context)), and a background process a command leaves behind ends with it.
- On Windows a [POSIX shell](/docs/tools#commands), the bash of Git for Windows or MSYS2, does not start in the sandbox: under the restricted token the MSYS runtime stops at once with `couldn't create signal pipe, Win32 error 5`. Run such a command in full-access, or outside the sandbox, or use PowerShell.
- In a terminal (PTY) command on Linux, `/dev/stdout` and `/dev/stderr` name the terminal's `/dev/pts` device, which is not writable: write to the output itself, or to `/dev/tty`, which is (the command's own terminal).
- On a Linux kernel older than 6.2, truncating a file outside the writable roots is not restricted (Landlock's ABI before version 3 cannot).

### One session's sandbox [#session-sandbox]

Like its permission mode, a session can have its own sandbox mode until it ends, without changing `sandboxMode` (`set_session_sandbox_mode`, see [Embedding the Agent](/docs/embedding#permissions)). The session's next turn takes it; it is kept in memory only; a fork starts without one, and a sub-agent takes its parent's. `sandboxWorkspaceWrite` still comes from the configuration.

### Presets [#presets]

The terminal interface's `/permissions` offers Codex's presets, each a permission mode with a sandbox mode, set for the session together ([Terminal interface](/docs/terminal-interface#permissions)):

| Preset      | Permission mode  | Sandbox mode      |
| ----------- | ---------------- | ----------------- |
| Read only   | Manual           | `read-only`       |
| Default     | Manual           | `workspace-write` |
| Auto-review | Automatic review | `workspace-write` |
| Full access | Full access      | `full-access`     |

Where this machine has no sandbox, the presets that need one cannot be chosen.

## What needs an approval [#what-asks]

| Operation                                                                   | Approval                                                       | Risk                                                |
| --------------------------------------------------------------------------- | -------------------------------------------------------------- | --------------------------------------------------- |
| Running a command (`exec_command`)                                          | Every time                                                     | Critical                                            |
| Writing to a running command, resizing its terminal                         | No                                                             |                                                     |
| Changing files (`apply_patch`)                                              | Yes                                                            | High; critical outside the workspace roots          |
| Moving or deleting files (`move_path`, `delete_path`)                       | Yes                                                            | High; critical for a recursive delete               |
| Reading files, listing directories, searching text                          | No                                                             |                                                     |
| Web search and fetch                                                        | No                                                             |                                                     |
| MCP tools                                                                   | By the server's approval policy; see [MCP](/docs/mcp#policies) | High; critical when the tool says it is destructive |
| Tools of a [code plugin](/docs/plugin-rules#guest-contributions)            | Yes, like an MCP tool that asks                                | High                                                |
| MCP resources, the memory tools, listing and reading Skills, viewing images | No                                                             |                                                     |
| Turning a Skill on or off                                                   | Always asks you                                                | Critical                                            |
| `git clone`                                                                 | Always asks you                                                | Critical                                            |

- There is no list of safe commands: even `ls` or `git status` asks.
- Reading is not limited to the workspace roots: the model can read any file your user can.
- The operations that **always ask you** (turning a Skill on or off, `git clone`) ask in automatic review and full access too, and can only be allowed once.
- A command you type yourself after `!` in the [terminal interface](/docs/terminal-interface#composer) is approved by your typing it, in every mode: it runs in the session's sandbox and no prompt asks, unless an approval rule that always wants a person applies.

## Answering an approval [#answering]

<Tabs items={["Terminal interface", "exec"]}>
  <Tab value="Terminal interface">
    The approval shows the kind of operation, its summary and its risk. `y` allows it once, `a`
    allows it for the session (when offered), and `n` or Esc denies it. Ctrl-C denies it and every
    request waiting behind it. See [Terminal interface](/docs/terminal-interface#approvals).
  </Tab>
  <Tab value="exec">
    `--approve` decides: `deny` (the default, every approval denied), `ask` (you are asked at the
    terminal) or `allow:TOOL[,TOOL…]` (those tools allowed, the others denied). See
    [exec](/docs/exec#approvals).
  </Tab>
</Tabs>

- **Allow once** allows this one operation.
- **Allow for the session** (`a`) stops the same tool from asking for the rest of the session, whatever the command or path; for a command [outside the sandbox](#escalation), only that same command outside the sandbox. It is kept in memory only: after a restart, or once the tool changes (an MCP server whose settings or credentials changed, say), it asks again; an MCP server that only reconnects keeps it. The operations that always ask you do not offer it.
- After a **denial** the model is told it was denied; usually it tries another way, or explains why it needs the operation.
- An approval waits at most 15 minutes; then it counts as denied.

## Automatic review [#auto-review]

In automatic review mode, an operation that needs an approval is reviewed by **the session's own model on its Provider**. The review request has no tools, only the operation and an excerpt of the conversation, and the model answers with a risk level, whether you asked for the operation, allow or deny, and why.

- Allowed, the operation runs; denied, the model is told why.
- Three denials in a row stop the turn, so the model does not keep trying.
- A review that times out (after 90 seconds) or fails denies the operation.
- The review is kept in the session's history; `exec --json` has it as the `permission_review_*` events.
- You can approve an operation a review denied; see below.

Automatic review costs extra model requests and relies on the model's judgement. It suits everyday work you can undo.

### Approving a denied operation [#approve-denied]

When a review denies an operation you did want, you can approve it: `/approve` in the terminal interface lists the session's denials to choose from ([Terminal interface](/docs/terminal-interface#permissions)), and an embedding host calls `approve_denied_action` ([Embedding the Agent](/docs/embedding#permissions)). Only one of the session's ten latest denials can be approved, and not while a turn or a compaction runs.

The approval does not run the operation and starts no turn. It adds a note to the session's history, which the model reads from its next request:

```text
The user has manually approved a specific action that automatic permission review previously denied.

Treat this as approval to perform that exact action in the same context in which it was originally requested.
Do not assume this also authorizes similar operations with different payloads.

Approved action:
<the operation's summary>
```

- The model sees the note as trusted context, so when you ask it to go on it can try the operation again.
- The retry is **still reviewed**. The reviewer sees the note among your own messages, labelled `user approval`, and is told it authorizes that exact operation and nothing else. A different operation, or the same one with other arguments, is judged as before.
- The note is kept in the session's history, also after a restart. A [compaction](/docs/providers-models#compaction) keeps neither the note nor the denials: after one, the approval is gone.

## Full access [#full-access]

In full-access mode, every operation that needs an approval is allowed without asking. What still applies:

- The [sandbox](#sandbox): a command runs as confined as `sandboxMode` says, and a request to run one [outside it](#escalation) is refused.
- The operations that always ask you (turning a Skill on or off, `git clone`).
- The calls refused outright: an MCP tool its server's policy denies, a command or path that cannot be resolved.
- [Plan mode](/docs/plan-mode) still offers read-only tools only.

## In a review [#review]

A [review](/docs/sessions#reviews) session is read-only, in place of the read-only sandbox Codex reviews in:

- Tools that only read (files, directories, text search, the web, images, MCP resources) run as anywhere else.
- A command runs only when it is `git --no-pager` with one of `status`, `diff`, `show`, `log`, `blame`, `rev-parse`, `merge-base` and `ls-files`, and plain arguments: no quotes, variables, redirections, pipes or second command, and no `--output` or `--ext-diff`. It runs through a POSIX shell or PowerShell, never `cmd.exe` (which would run a `git.cmd` from the working directory first). `--no-pager` is required so that no pager waits on a terminal for input.
- Everything else that needs an approval (other commands, file changes, MCP tools that ask, Skills) is **denied without asking**, with the reason as the tool's error. What needs none runs as anywhere else: an MCP tool its server's policy allows without asking (`allow`, not destructive), and the Agent's own tools such as the plan and goal tools.
- The review's turn runs in full access, so what is allowed runs without asking (Codex's "never ask"). A turn you start on the review session later runs in your mode, and stays read-only.
- The rule is the `review` plugin's: with the plugin off, no review starts, and a review session from before is not kept read-only.

## Other controls [#other-controls]

- The [sandbox](#sandbox) confines what an allowed command can write and reach.
- [Plan mode](/docs/plan-mode) gives the model read-only tools only, whatever the permission mode.
- MCP servers have their own approval policies (`allow`, `ask`, `deny`); see [MCP](/docs/mcp#policies).
- `disabledPlugins` removes a whole kind of tool: `["execution"]` leaves the model no way to run commands; see the [Configuration reference](/docs/config-reference#general).
- The model is told the permission mode and the [sandbox](#sandbox-context), so it can plan with them.
