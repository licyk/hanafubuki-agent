An installable plugin is a **package**: a directory with a manifest, which the Agent installs from a directory or a [marketplace](#publishing) ([Installed plugins](/docs/architecture#installed-plugins)). A plugin in Codex's, Claude Code's, Cursor's or the Agent Plugins format brings content (Skills, MCP servers, hooks) and needs no code. This page is about this project's own format, `.hanafubuki-plugin/plugin.json`, whose plugin can also carry **code**, the plugin's **guest**: a program that the Agent starts out of process, confined by the sandbox, or a [WebAssembly module](#wasm) that it runs within limits of fuel, time and memory. The Agent calls it for the tools, context sections, prompt fragments, hooks and observers its manifest declares ([Code plugins](/docs/architecture#code-plugins)). A guest that crashes or hangs costs only its own contributions.

## Start a plugin [#start]

`hanafubuki-agent plugins new NAME` writes a plugin with code, ready to build:

```sh
hanafubuki-agent plugins new my-plugin                  # Rust, in ./my-plugin
hanafubuki-agent plugins new my-plugin --target wasm    # Rust, compiled to WebAssembly
hanafubuki-agent plugins new my-plugin --lang python --dir plugins/my-plugin
```

```text
my-plugin/
├── Cargo.toml                          the guest's Cargo project (Rust), or plugin.py (Python)
├── src/main.rs                         (src/lib.rs for WebAssembly)
├── README.md                           how to build, check and run it
└── package/                            the plugin the Agent installs
    └── .hanafubuki-plugin/plugin.json
```

The Rust plugin contributes a tool (`greet`), a context section (`<name>_status`, which reads the workspace) and an observer (`turn_finished`); the WebAssembly one the same, but its section does not read the workspace, which a module cannot reach; the Python one a tool (`count_words`) and a prompt fragment. Each manifest also declares a `configSchema`, and a program's its permissions. The repository's [`examples/plugins/`](https://github.com/licyk/hanafubuki-agent/tree/main/examples/plugins) holds all three, as `plugins new` writes them (`hello-rust`, `hello-wasm`, `hello-python`).

`package/` is apart from the source on purpose: an install copies the whole package (all but `.git` and symbolic links) into the data directory and hashes it, and its guest starts only while the package still has that hash. A build tree (`target/`) inside the package would be copied and hashed at every install. The build puts the program or the module into `package/`:

```sh
cargo build --release && cp target/release/my-plugin package/                 # Rust
cargo build --release --target wasm32-unknown-unknown \
  && cp target/wasm32-unknown-unknown/release/my_plugin.wasm package/my-plugin.wasm  # WebAssembly
python3 -m pykardia.guest.export process plugin.py Plugin package/my-plugin.pyz  # Python
```

## The package [#package]

| Path                                                    | What it is                                                                                                                                                                           |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `.hanafubuki-plugin/plugin.json`                        | the [manifest](#manifest)                                                                                                                                                            |
| the guest's program or module                           | what `runtime.command` names (`./my-plugin`, `./my-plugin.pyz`), read-only to it, or what `runtime.module` names (`./my-plugin.wasm`)                                                |
| `skills/`, `.mcp.json`, `hooks/hooks.json`, `commands/` | content, as in Codex's and Claude Code's formats ([Skills](/docs/skills#sources), [Plugins' servers](/docs/mcp#plugin-servers), [Plugins' hooks](/docs/configuration#hooks-plugins)) |
| `agents/`                                               | content: role files ([Roles](#roles))                                                                                                                                                |

A plugin may have content, code or both. Its id is `<name>@<marketplace>`; one installed from a directory is `<name>@local`. While a program runs, its working directory is the plugin's own data directory (`PLUGIN_DATA`), the one place it writes, and `PLUGIN_ROOT` is the installed package; a module has neither.

## The manifest [#manifest]

```json
{
  "name": "my-plugin",
  "version": "0.1.0",
  "description": "What it does.",
  "runtime": { "type": "process", "command": ["./my-plugin"], "protocol": "kardia-guest/2" },
  "contributes": {
    "tools": [
      {
        "name": "greet",
        "description": "Greets someone by name.",
        "inputSchema": {
          "type": "object",
          "properties": { "name": { "type": "string" } },
          "required": ["name"],
          "additionalProperties": false
        },
        "timeout": 10
      }
    ],
    "contextSections": [{ "kind": "my_plugin_status" }],
    "prompt": { "slot": "capabilities" },
    "toolLifecycleHooks": false,
    "continuationHooks": false,
    "observers": ["turn_finished"]
  },
  "permissions": { "network": false, "workspace": "read", "env": [] },
  "configSchema": {
    "type": "object",
    "properties": { "greeting": { "type": "string" } },
    "additionalProperties": false
  }
}
```

The manifest is read as an external producer's: a field, or an entry of a list, that cannot be used is left out with an issue, and the rest is used. `plugins validate` lists every issue.

| Field                                                             | Meaning                                                                                                                                                                                                                                                                                                                                                                                              |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`                                                            | the plugin's name: its id's first part, the namespace of its tools and the name its guest declares                                                                                                                                                                                                                                                                                                   |
| `version`, `description`, `keywords`, `interface`                 | as in Codex's manifest; the version names the installed copy                                                                                                                                                                                                                                                                                                                                         |
| `skills`, `mcpServers`, `hooks`, `commands`, `agents`             | content, each a path that starts `./` and stays in the package (`mcpServers` and `hooks` may also be written inline); `agents` is a directory of role files or one file, or a list of them, in place of `agents/` ([Roles](#roles))                                                                                                                                                                  |
| `runtime.type`                                                    | `process` (a program) or `wasm` (a [WebAssembly module](#wasm))                                                                                                                                                                                                                                                                                                                                      |
| `runtime.command`                                                 | `process`: the program and its arguments; the program is a file in the package (`./…`), or, with `runtime.interpreter: true`, an interpreter (an absolute path, or a name on the Agent's `PATH`) with the package's files as arguments                                                                                                                                                               |
| `runtime.protocol`                                                | `process`: `kardia-guest/2`                                                                                                                                                                                                                                                                                                                                                                          |
| `runtime.module`                                                  | `wasm`: the module, a binary `.wasm` file in the package (`./…`)                                                                                                                                                                                                                                                                                                                                     |
| `runtime.limits`                                                  | `wasm`: what each call may use, each optional: `fuel` (about one unit per instruction; unset, none is counted), `timeoutMs` (at most 3600000; unset, its longest call: the 10 s call deadline or a longer tool `timeout`), `memoryBytes` (64 KiB to 4 GiB; 256 MiB)                                                                                                                                  |
| `contributes.tools[]`                                             | `name` (ASCII letters, digits, `_`, `-`), `description`, `inputSchema` (a JSON Schema object), `timeout` (seconds, above 0 and at most 3600; else the 10 s call deadline). The model sees `<plugin>__<name>`; every call asks for the user's approval. An interface shows a call's result by the [fallback](/docs/plugin-rules#tool-presenters): a structured result's top-level keys, else its text |
| `contributes.contextSections[]`                                   | `kind` (lowercase letters, digits and `_`, not one of the Agent's own); at most 7. A plugin's sections come after the Agent's and the host's in their slot, in kind order ([Context renderers](/docs/plugin-rules#context-renderers))                                                                                                                                                                |
| `contributes.prompt.slot`                                         | `instructions`, `worldState`, `capabilities` (the default) or `memory`                                                                                                                                                                                                                                                                                                                               |
| `contributes.toolLifecycleHooks`, `contributes.continuationHooks` | `true` to be asked before and after each tool call, and about each candidate final answer                                                                                                                                                                                                                                                                                                            |
| `contributes.observers`                                           | events to be told of: `turn_admitted`, `sampling_committed`, `turn_finished`, `memory_contribution_changed`, `session_archived`, `session_restored`                                                                                                                                                                                                                                                  |
| `permissions.network`                                             | `true` to reach the network (off by default). The three permissions are a program's: a module asks for none                                                                                                                                                                                                                                                                                          |
| `permissions.workspace`                                           | `none`, `read` (the default) or `write`                                                                                                                                                                                                                                                                                                                                                              |
| `permissions.env`                                                 | the names of the Agent's environment variables the guest receives                                                                                                                                                                                                                                                                                                                                    |
| `configSchema`                                                    | a JSON Schema of an object: the plugin's settings, lowered to options that `plugins settings` and `/plugins` check them against, and that its guest receives them checked by ([configSchema](#config-schema))                                                                                                                                                                                        |

What each declaration becomes, and its bounds, is in [What a guest contributes](/docs/plugin-rules#guest-contributions).

## Roles [#roles]

A plugin can bring [roles](/docs/roles): definitions of how the Agent works that only narrow it, which a session or a sub-agent then runs in. A plugin in this project's format keeps them as role files, the `.toml` files of `agents/` (its subdirectories too) or of the paths its manifest's `agents` names, with every key of a [role file](/docs/roles#keys):

```toml
# agents/reviewer.toml
description = "Reviews a change and lists the problems it finds; never edits."
extends = "explorer"
instructions = "List each problem with its file and line."
```

Each role is named `<plugin>:<role>`, after the plugin name of its id (`my-plugin:reviewer`); an `extends` names a role as the catalog does (`my-plugin:base` for one of the plugin's own). The roles are there while the plugin is on. What reading them leaves out is the plugin's issue: `plugins validate` lists it, and `plugins info` once the plugin is installed and on. Precedence, the merge and the sessions are in [Plugins' roles](/docs/roles#plugins).

### Claude Code agent files [#claude-agents]

A Claude Code plugin's agent files, the `.md` files of its `agents/` (or of its manifest's `agents`), are read as roles too. The frontmatter is read key by key, a key of the wrong type left out with an issue:

- `name`: the role's name, after the plugin's (`<plugin>:<name>`); one that cannot be a role's name, or none, gives way to the file's name.
- `description`: the role's description, which it needs.
- `tools`: the only tools the role may use, a comma-separated list (`Read, Grep, Glob`) or a YAML list, mapped by the tool table below. A name the table does not know is left out, with an issue; so a list of names it knows none of allows **no** tool. Without `tools`, the role narrows no tool. A `tools` that is neither text nor a list makes the role unusable, since leaving it out would allow every tool.
- `disallowedTools`: tools the role denies, written as `tools` is and mapped by the same table; a denied tool wins over an allowed one. A name the table does not know (`NotebookEdit`) is left out, with an issue: this Agent has no such tool to deny. A whole MCP server (`mcp__github`) denies every tool of it (`mcp__github__*`). A tool with a specifier (`Bash(git push:*)`) cannot be said here, since a role names tools, not their calls, so the **whole** tool is denied (`exec_command`), with an issue. An item that is not text is left out, with an issue; a `disallowedTools` that is neither text nor a list makes the role unusable.
- `permissionMode`: the role's `permissionModeCap`, by the mode table below. One that is not text makes the role unusable.
- `model`: `inherit` keeps the session's model. Any other value (`sonnet`, `opus`, `haiku`) names none of this Agent's models, so it is ignored, with an issue, and the model is inherited as well.
- the body after the frontmatter: the role's instructions.

Other keys (`color` and the like) are ignored. A file without frontmatter, or whose frontmatter is not YAML even with a plain value holding `: ` quoted, is left out with an issue.

| Claude Code                  | This Agent                            |
| ---------------------------- | ------------------------------------- |
| `Read`                       | `read_file`                           |
| `Grep`                       | `search_text`                         |
| `Glob`, `LS`                 | `list_directory`                      |
| `Edit`, `MultiEdit`, `Write` | `apply_patch`                         |
| `Bash`                       | `exec_command`                        |
| `WebFetch`                   | `fetch_web_page`                      |
| `WebSearch`                  | `web_search`                          |
| `mcp__<server>__<tool>`      | the same name, an MCP server's tool's |

| `permissionMode`    | The role                                                                           |
| ------------------- | ---------------------------------------------------------------------------------- |
| `default`           | capped at `manual`                                                                 |
| `acceptEdits`       | capped at `auto_review`                                                            |
| `bypassPermissions` | capped at `full_access`, which caps nothing                                        |
| `plan`              | capped at `manual`, and denies the write tools (below)                             |
| `dontAsk`           | capped at `manual`, with an issue: denying whatever it does not allow is not a cap |
| anything else       | capped at `manual`, with an issue                                                  |

`plan` denies what [Plan mode](/docs/plan-mode) removes from a default session, the Agent's own tools that are not read-only: `apply_patch`, `delete_path`, `move_path`, `exec_command`, `write_stdin`, `resize_execution`, `create_goal`, `update_goal`, `spawn_agent`, `followup_task`, `send_message`, `interrupt_agent`, `enable_skill`, `disable_skill` and `append_agent_memory_note`. The kernel's own (`update_plan`, `new_context`, `request_user_input`) stay, as a role never removes them. MCP tools are denied too (`mcp__*`) unless the agent has `tools`: then the role allows only the tools listed, an MCP tool listed included, and denying `mcp__*` would remove it. Unlike Plan mode, which keeps an MCP tool annotated read-only, `plan` keeps only the MCP tools `tools` lists, and it denies no other plugin's tools: a tool an installed plugin's code registers stays, writing or not, unless `tools` leaves it out.

A Codex package has no roles.

## The guest [#guest]

A guest is a program that speaks Kardia's guest protocol (`kardia-guest/2`) on its standard input and output: its metadata is exactly the manifest's `name` providing the one service `plugin`, its `apply` receives its settings and provides `plugin`, and the Agent calls `plugin`'s methods, one per kind of contribution: `tool`, `context`, `prompt`, `beforeToolUse`, `afterToolUse`, `continuation`, `observe`. The methods, their arguments and their answers are in [The guest protocol](/docs/plugin-rules#guest-protocol); what a guest may `view` (its workspace and its settings) is in [What a guest may reach](/docs/plugin-rules#guest-host-calls).

Its standard output is the protocol's: it must never print there. It logs to standard error or through the host's `log`; the Agent keeps the last 16 KiB of its standard error for its status and logs a guest's words only at `trace`.

### Rust [#rust]

[kardia-guest](https://crates.io/crates/kardia-guest) implements the protocol: implement its `Guest` trait and call `serve` from `main`.

```rust
use kardia_guest::{json, Guest, Host, Map, Meta, Request, Result, Value};

struct Plugin;

impl Guest for Plugin {
    type Config = Value;

    fn meta() -> Meta {
        Meta::plugin("my-plugin").provide("plugin")
    }

    fn apply(host: &Host, _settings: Value, _imports: Map<String, Value>) -> Result<Self> {
        host.provide("plugin", &json!({}))?;
        Ok(Plugin)
    }

    fn call(&mut self, _host: &Host, request: Request) -> Result<Value> {
        match request.method.as_str() {
            "tool" => {
                let name = request.args["arguments"]["name"].as_str().unwrap_or("world");
                Ok(json!(format!("Hello, {name}!")))
            }
            method => Err(format!("no method {method}").into()),
        }
    }
}

fn main() {
    kardia_guest::serve::<Plugin>();
}
```

A panic in a call is caught and becomes that call's error.

### Python [#python]

[pykardia](https://github.com/licyk/pykardia)'s guest SDK implements it in Python: subclass `pykardia.guest.Guest`, and export the class as a process guest, a zipapp that bundles the SDK and runs on any Python 3.10 or later:

```sh
python3 -m pip install git+https://github.com/licyk/pykardia
python3 -m pykardia.guest.export process plugin.py Plugin package/my-plugin.pyz
```

The manifest runs it with the interpreter on the Agent's `PATH`: `"command": ["python3", "./my-plugin.pyz"], "interpreter": true`. Under the sandbox a guest reads only the system's directories (`/usr`, `/lib`, …), its package and its interpreter's program, so the interpreter must be the system's: a virtual environment's or a version manager's Python under a home directory cannot read its own standard library there. The SDK speaks `kardia-guest/2` from its repository's `main` on; the 0.1.0 release on PyPI is older.

### The SDKs' licences [#licences]

kardia-guest and pykardia's guest SDK (`pykardia/guest/` and the modules an export bundles) are under **MIT OR Apache-2.0**, so a plugin that links or bundles them chooses its own licence; an exported zipapp carries their licence files. The rest of Kardia and pykardia, and the Agent itself, are GPL-3.0-only; a guest is a separate program, which the Agent runs and talks to over a pipe.

### WebAssembly [#wasm]

A guest may instead be a WebAssembly module (`"runtime": {"type": "wasm", "module": "./my-plugin.wasm"}`), which the Agent runs inside its own process with wasmtime. It speaks the same methods through the guest ABI's exports and host functions instead of a pipe, and the same Rust source builds it: in a `cdylib` crate, `kardia_guest::export!(Plugin)` takes the place of `main`, and `cargo build --target wasm32-unknown-unknown` builds it (`plugins new --target wasm` writes such a crate).

- **It reaches nothing outside itself.** The only functions it may import are the guest ABI's (`read`, `write`, `log`, `provide`, `view`, `invoke`, from the module `cordis` or `kardia`): no files, network, clock or environment. A module that imports anything else (WASI, say) does not load. So it asks for no permissions, needs no grant and no sandbox, and starts as soon as it is installed and on, on every platform; its `workspace` view reports `{"access": "none", "roots": []}`, and its `settings` view is its settings, as a program's.
- **Its limits bound each call** (`runtime.limits`): its fuel (instructions), its time (the call's own deadline, and at most `timeoutMs`) and its linear memory (`memoryBytes`, 256 MiB by default). A call that runs out of fuel or time, a memory that would grow past the limit, and any trap (a Rust guest's panic is one) fail that call and the guest's instance: the guest restarts, as a program that crashed. An error the guest reports itself is only the call's.
- **It is loaded once per version.** The module is compiled when its guest first starts, and nothing is instantiated then: its metadata is taken from the manifest. A restart takes a fresh instance (fresh memory) of the same compiled module. Each instance's metadata must be exactly the manifest's name providing `plugin`, or it does not start; other modules it declares (`deps`) are not loaded.
- **One file for every platform**, which a marketplace publishes as it is.

A module in another language exports the ABI itself: `memory`, `cordis_meta() -> i32`, `cordis_apply(len) -> i32`, `cordis_call(len) -> i32` and optionally `cordis_dispose()` (or the same named `kardia_*`). Each export's input is a message of `len` bytes that `read(ptr)` copies into its memory; it sets its result (or its error, with a status other than 0) with `write(ptr, len)`. The messages are the JSON of the process wire's exports ([Any other language](#other-languages)). pykardia can export a Python guest as a WASI module, which needs WASI and so does not load here.

### Any other language [#other-languages]

A guest in another language implements the wire itself. Every message is one JSON object on one line (at most 4 MiB): the Agent's on the guest's standard input, the guest's on its standard output.

1. The Agent opens with `{"export":"hello","input":{"protocol":"kardia-guest/2"}}`; the guest answers `{"ready":"kardia-guest/2"}`.
2. Each export carries an `id`: `{"export":"meta","id":1}`, `{"export":"apply","id":2,"input":{"config":{…},"imports":{}}}`, `{"export":"call","id":3,"input":{"key":"plugin","method":"tool","args":{…}}}`, and at the end `{"export":"dispose","id":4}`.
3. The guest answers an export with at most one `{"output":"<text>","id":…}` (the result as JSON text, or the error's message) and then `{"done":0,"id":…}`, or `{"done":1,"id":…}` when it failed. `meta`'s output is `{"deps":[],"plugin":{"name":"my-plugin","inject":[],"provide":["plugin"]}}`.
4. While an export runs, the guest may call the host with the export's `id`: `{"call":"provide","key":"plugin","value":{}}` (in `apply`; any other key is refused with an error), `{"call":"view","key":"workspace"}`, which the Agent answers `{"result":…}` or `{"error":"…"}`, and `{"call":"log","level":2,"text":"…"}` (0 error to 3 debug), which it does not answer.
5. At any time the Agent may send `{"ping":n}`, which the guest answers `{"pong":n}` at once, and `{"cancel":id}`, after which that export's result is dropped.

## Check it [#validate]

`hanafubuki-agent plugins validate DIR` reads the plugin as an install reads it and checks its code as the guest host would run it, without installing or starting anything:

- the manifest's issues (a field left out, a timeout out of range, an unknown contribution) and declared paths that do not exist;
- what its [roles](#roles) leave out: a role file's key, a Claude agent file's tool with no counterpart or its Claude `model`;
- the runtime: for a program, the protocol, a program in the package that exists (and is executable), or an interpreter on the `PATH`, and the package files its arguments name; for a module, a file in the package that is a binary WebAssembly module, and a tool `timeout` longer than `limits.timeoutMs`, which would stop it first;
- what registration would leave out: a tool name that is not one, a schema too large or too deep, a context kind that is not a plugin's, more than 7 kinds, a prompt slot that does not exist, an event no observer receives, names declared twice;
- a `configSchema` that does not describe an object, and each property of it that cannot be an option ([configSchema](#config-schema)).

With `--run` it then installs the plugin into a throwaway home (its own configuration and data directory, deleted afterwards), grants what the code asks for, starts its guest (a program under the sandbox; a module, which needs none, compiled and instantiated), and reports its state, what its start left out, its exit and its standard error: the handshake, the metadata and `apply` all happen as in the Agent. It fails (exit code 1) on any issue, or when the guest does not run; `--json` prints `{"validation": …, "started": …}`.

## Develop it [#dev]

`hanafubuki-agent plugins dev DIR` installs the plugin as `<name>@local`, turns it on, shows what its code asks for and grants it (after asking; `--grant` grants without asking), and prints its guest's state. Then it watches the directory: when its files have been quiet for a moment after a change (a new build or export), it installs the plugin again and its guest starts anew with the change, keeping its grant and settings; a change that asks for more permissions asks again. Ctrl+C stops it; the plugin stays installed (`plugins remove <name>@local` removes it).

`plugins dev` runs the Agent, which holds its data directory, so no other Agent runs on it meanwhile: stop it to try the plugin in the terminal interface or `exec`, where it stays installed. A scratch home keeps a plugin under development out of your own configuration and data: run `plugins dev` and then the terminal interface with the same [`HANAFUBUKI_AGENT_HOME`](/docs/environment#read).

### Link it [#link]

`hanafubuki-agent plugins link DIR` links the plugin instead: it is `<name>@local` (or under `--marketplace NAME`), turned on, and its directory is the package itself. Nothing is copied into the cache and no content hash pins it, so it needs no Agent kept running, as `plugins dev` does: the Agent you then run (the terminal interface, `exec`, a host) reads the directory as it is now. While its built-in `plugins` row runs, that Agent watches every linked plugin that is on; once a linked directory's files have been quiet for 500 ms after a change (reading a file is not one, nor a change in `.git`), it reloads the installed plugins: the plugin's Skills, MCP servers, hooks and roles are read again, and its code starts anew with the change.

A linked plugin is trusted exactly as an installed one: its code runs under the same grant and the same sandbox profile (its directory read-only), a change that asks for more permissions leaves it `blocked` until `plugins grant`, and its hooks wait to be trusted again after each change, as an installed plugin's do once its files change. `plugins list` shows its source as `linked DIR`. It is never updated: `plugins update` refuses it, and `plugins add` of the same id refuses until it is removed (as `link` refuses an id that is installed). The link is recorded in the data directory's `plugins/linked.json`, apart from the installed plugins' `install.json`, so an older build of the Agent, which rewrites `install.json` without knowing links, never drops it ([Data directory](/docs/data-directory)). `plugins remove <name>@local` unlinks it: its record and its `[plugins]` entry go, and the directory stays as it is (its data directory too, unless `--purge-data`). A link writes nothing into the directory, so its `commands/` do not become Skills (an install turns them), and a directory that is gone leaves the plugin listed with an issue.

## Settings and permissions [#settings-permissions]

- **Permissions** are granted by the user, never by the plugin: a program whose permissions are not granted is `blocked`. `plugins grant ID` grants what the manifest asks for, as does **Grant its permissions** on the plugin's page in `/plugins`. An update that asks for more waits for a new grant. A WebAssembly module asks for nothing and is never `blocked`.
- **The sandbox's plugin profile** confines a program: it reads the system's directories and its package, writes only its data directory, reaches the workspace as granted and the network only if granted, and starts with an empty environment but its granted `env`, `PLUGIN_ROOT` and `PLUGIN_DATA`. Linux and macOS enforce the reads; Windows cannot deny them, so there `workspace: "none"` is not enforced. Where there is no sandbox, a guest does not start.
- **Settings** are `[plugins."ID"].settings` in `config.toml`: `plugins settings ID --set '{"greeting": "Hi"}'` replaces them (checked against `configSchema`), `--set null` removes them, `plugins settings ID` prints them with the schema; `/plugins` and the settings center edit them too ([configSchema](#config-schema)). They are the configuration `apply` receives and the guest's `settings` view, and a change starts the guest again with them.

### configSchema [#config-schema]

The `configSchema` is enforced. When the package is read, each property of its `properties` is lowered to an option, which the options form in `/plugins` (`o` on the plugin) and the plugin's section of the [settings center](/docs/terminal-interface#config)'s Plugins tab show, and the settings are checked against. The keywords it reads:

| Keyword                                        | Becomes                                                                              |
| ---------------------------------------------- | ------------------------------------------------------------------------------------ |
| `type: "boolean"`                              | a toggle                                                                             |
| `type: "integer"`, `"number"`                  | a number, within `minimum` and `maximum` when they are given                         |
| `type: "string"`                               | a text, at most `maxLength` characters when it is given                              |
| `enum` of strings                              | a choice among them, each labelled by its value (with `type: "string"` or no `type`) |
| `type: "array"`, `items: { "type": "string" }` | a list of texts, at most `maxItems` items of at most the items' `maxLength`          |
| `default`                                      | the option's default, when it fits the option                                        |
| `title`                                        | the option's label (its key when there is none)                                      |
| `description`                                  | the option's description, its first line                                             |

Another keyword constrains nothing here, as for a tool's schema; `required` and `additionalProperties: false` are still checked when the settings are written. A `default` that does not fit its option is an issue of the package, and the option has none. Nothing makes an option secret. A property that is none of these (an object, a list of anything but strings, a union of types, a non-string or empty `enum`, a `minimum` above its `maximum`) is not an option: it is an issue of the package (`plugins validate` lists it), and its value reaches the guest unchecked. At most 64 properties are options.

The guest receives its settings checked against the options: a value that does not fit its option gets the option's `default`, or is left out when the schema gives none, and an integer or a number out of range is clamped; each is an issue of the package and a warning in the log, and `config.toml` keeps what was written. A key the settings leave out stays out (the guest's own default applies), and a key no option describes reaches the guest as it is. A write is strict: `plugins settings --set`, `set_package_settings` and the forms refuse settings that do not fit, with the reason, and write nothing.

So a plugin declares its settings with its `configSchema` alone, and needs no settings page: the options are settings of the Agent's [settings catalog](/docs/architecture#settings-catalog), a section per plugin (`plugins."ID".settings`, in the Plugins group) whose keys are `plugins."ID".settings.OPTION`. The settings center shows them as rows (`/config plugins."ID".settings`), and a host's settings page as it shows the Agent's; a write of them (`write_setting_values`, the key spelled by `package_setting_key`) puts the changed keys over the settings in the user's `config.toml`, removes a key it resets, is checked as `set_package_settings` checks, and restarts the guest. It holds one plugin's settings and nothing else. A value is shown as set by the user or as the default; no other layer is named for it.

## When it fails [#failures]

| What happens                                                     | What the Agent does                                                                                                                                                                 |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| a bad manifest or component                                      | that field or component is an issue, the rest loads; a guest whose runtime cannot run does not start                                                                                |
| the guest panics in a call                                       | the SDK returns it as the call's error: a tool error to the model, a section left out                                                                                               |
| a call outlives its deadline                                     | the guest is killed and restarts; the turn goes on without that contribution                                                                                                        |
| the guest exits, aborts or runs out of memory                    | its contributions retire at once and the guest restarts, which registers them again                                                                                                 |
| it breaks the protocol, or sends a line over 4 MiB               | as a crash: killed, restarted                                                                                                                                                       |
| a module traps, uses up its fuel or time, or outgrows its memory | the call's error; the guest's instance is dropped and the guest restarts with a new one                                                                                             |
| it keeps failing                                                 | restarts after 2 s, 10 s and 30 s; a fourth failure within 10 minutes leaves it `failed` until `plugins retry` (or **Retry plugin** in `/plugins`); a failed start is not restarted |
| its package's files change after the install                     | it does not start until it is installed again                                                                                                                                       |

The rest of the Agent, and a host that embeds it, is never affected: a program is another process, and a module runs in wasmtime's sandbox, where a trap or a limit stops only its own instance. `plugins info ID` shows the guest's state and error; `/plugins` shows its state and issues, and `/warnings` its issues and, until it is retried, its failure.

## Publish it [#publishing]

A plugin is published in a **marketplace**: a directory or a git repository with a `marketplace.json` that lists plugins (`.agents/plugins/marketplace.json`, or Claude Code's `.claude-plugin/marketplace.json`):

```json
{
  "name": "my-marketplace",
  "plugins": [
    { "name": "my-plugin", "source": "./plugins/my-plugin/package" },
    {
      "name": "other-plugin",
      "source": {
        "source": "git-subdir",
        "url": "https://github.com/me/other-plugin",
        "path": "package",
        "ref": "v1.0.0"
      }
    }
  ]
}
```

A source is a path in the marketplace (`./…`), `{"source": "local", "path": …}`, a git repository (`{"source": "url", "url": …}`) or a directory of one (`{"source": "git-subdir", "url": …, "path": …}`), with an optional `ref` or `sha`. Users add the marketplace and install from it:

```sh
hanafubuki-agent plugins marketplace add me/my-marketplace
hanafubuki-agent plugins add my-plugin@my-marketplace
hanafubuki-agent plugins grant my-plugin@my-marketplace
```

A plugin with a compiled program publishes that program inside its package, built for each platform it supports (a WebAssembly module is one file for all); nothing is signed, so users trust a marketplace as they trust its source. `plugins update` installs a new version, and `plugins marketplace upgrade` fetches a git marketplace's changes first. The commands are in [Command-line reference](/docs/cli-reference#plugins), the configuration in [Configuration reference](/docs/config-reference#plugins).
