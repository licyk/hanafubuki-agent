Every conversation is a session, kept in the data directory's `history/`: a conversation in the terminal interface, one continued with `resume`, and every `exec`. A session has a numeric id, which `sessions list` shows.

## Listing sessions [#list]

```sh
hanafubuki-agent sessions list
```

```text
2  2026-11-09 04:37  gpt-5.1  Explain what this repository does
1  2026-11-08 21:12  gpt-5.1  Fix the lint errors
```

Each line has the id, the last update (local time), the model and the title, the latest first. The title is made from the first message: at once the message itself, cut to 36 characters, then one the model writes from it. When that fails the first message stays the title, and the model is asked again at your next message, until it gives one or you rename the session. A session without a title shows `(untitled)`.

- `--archived` lists the archived sessions instead.
- `--json` prints one session summary per line as a JSON object (the id, model, Provider, mode, title, token use, creation and update times, the directory and Git branch it was created in as `cwd` and `branch`, its [role](/docs/roles#sessions) as `role` when it has one other than `default`, and more), for scripts.
- Only sessions without a parent are listed: a [child session](#children) is found under its parent.

<Callout>
  Every start of the terminal interface creates a session, even if you send no message. `sessions
  list` shows these empty sessions; the resume picker hides them.
</Callout>

## Reading a session [#show]

```sh
hanafubuki-agent sessions show 2
```

```text
session 2  gpt-5.1  Explain what this repository does
assistant: This is …
  done
→ exec_command
thought for 3s
user: Explain what this repository does
```

`show` prints the session's latest 200 items, the latest first: your messages (`user:`, or `user (steering):` for one sent while a turn ran), how long the model thought (`thought for 3s`, in whole seconds, rounded down; not its text), the model's answers (`assistant:`), its tool calls (`→ TOOL`) and their results (`done` or `failed`), the commands you ran with `!` (`user ran: COMMAND`, with `(exit N)` or `(failed)` when it did not succeed), and what the session's background work reported, a line per event (`background: …`, [Wake events](/docs/internals#wake-events)). Older items are left out, and `(older items are not shown)` says so first. Context only the model reads is not shown.

`--json` prints that page of the transcript as JSON, with every field of each item, the thinking's text included. The terminal interface shows the thinking too when you resume the session.

## Exporting [#export]

`/export` in the terminal interface copies a session's whole conversation as Markdown, or saves it into a file ([Terminal interface](/docs/terminal-interface#session-commands)); a host calls `export_session_markdown`. The export is read from the history, every page of it, oldest first:

```markdown
# Hanafubuki Agent conversation

## User

Explain what this repository does

## Activity

    exec_command({"cmd":"ls"})
    Cargo.toml
    crates

## Assistant

This is …
```

- Each message is a `## User` or `## Assistant` section, as written; a message sent during a turn is a `## User` too, and its images are named (`[Image #1]`). A plan the model proposed is a `## Plan`.
- Each tool call is a `## Activity` section, indented as a code block: the tool's name with its arguments on one line (cut after 200 characters), `· failed` when it failed, then the first 10 lines of its output and how many more there were. A command you ran with `!` ([Terminal interface](/docs/terminal-interface#composer)) is one too: `!` and the command, `· exit N` when it exited with another code than 0 or `· failed` when it did not finish, then its output the same way. A context compaction is `Context compacted`.
- What the session's background work reported (its sub-agents and background terminals) is a `## Background updates` section, a line per event.
- The model's thinking and the context only the model reads are left out. A session with nothing to show is not exported.

## Archiving and deleting [#archive-delete]

```sh
hanafubuki-agent sessions archive 2
hanafubuki-agent sessions delete 2
```

- **Archive**: the session leaves `sessions list` and the resume picker but is kept; `sessions list --archived` finds it. Its child sessions are archived with it.
- **Delete**: removes the session and its history for good, with its child sessions, archived or not. It is refused, with the reason as the error, while a fork or a quarantined session file still needs the session or one of its children; a child that cannot be deleted refuses the whole deletion.
- Either closes the session's [side conversation](#side). Restoring a session does not restore its children.
- In the terminal interface, `/archive` and `/delete` do the same for the session shown, after a confirmation, and then show no session. The resume picker lists the archived sessions under Tab, where Ctrl+A or Enter restores one, and Ctrl+A archives another session ([Terminal interface](/docs/terminal-interface#resume)).

## Editing an earlier message [#edit]

Editing one of your earlier messages (Esc twice in the [terminal interface](/docs/terminal-interface#edit); `edit_from_turn` for a [host](/docs/embedding#edit-from-turn)) does not rewrite the session's history:

- The session is forked before the turn the message started. The fork has everything before that message, records the session as its source (`forkedFromSessionId`), and gets the message back, its text and images, to edit and send.
- The original is archived, whole, children and all: `sessions list --archived` finds it and `sessions show` reads it. The fork is listed in its place.
- Files the Agent changed are not restored.
- It is refused while a turn runs in the session, and in a child session: a [side conversation](#side) is temporary.

## Worktrees [#worktrees]

A worktree is a separate checkout of the repository the working directory is in, which the Agent makes under the data directory's `worktrees/` (named `<repository>-<8 hex digits>`), detached at the repository's `HEAD`. It can belong to one session, recorded in the worktree's Git metadata.

- In the terminal interface, `/worktree` continues the conversation in a new worktree (a fork of the session goes on there and owns it) or starts a new conversation there (the session your next message creates owns it); in a Git repository `/fork` offers the first too. Either moves the working directory into the worktree. See [Terminal interface](/docs/terminal-interface#worktrees).
- `/worktree`'s Browse worktrees lists the repository's worktrees, with their commit, branch and session: it resumes a worktree's session, copies its path, or removes it.
- Removing a worktree deletes its checkout with its local changes and prunes the repository's record of it; its session stays. The worktree the working directory is in is not removed.
- A session records the directory it was created in (`cwd`): one created in a worktree records the worktree, a fork records its source's.
- With the `worktree` plugin off (`disabledPlugins`), worktrees are unavailable, and the interface says so.

## Roles [#roles]

Every session has a [role](/docs/roles#sessions): `default`, which narrows nothing, unless you start it with `--role NAME` or switch it between turns with `/role NAME`. The role's instructions, tools, plugins and permission-mode cap are kept with the session: editing or deleting the role file later changes no session that has it, and a resumed session keeps the role it had. `/status` shows it.

## Child sessions [#children]

A session can be the child of another, made for it rather than started by you: a [side conversation](#side), a [sub-agent](#subagents) or a [review](#reviews). A child records its parent (`parentSessionId` in its summary) and why it was made (`origin`: `side`, `subagent` or `review`), and works in its parent's directory, with its parent's model and settings (a sub-agent may be given another model, [below](#subagents)). It keeps its parent's [role](/docs/roles#sessions), and may only narrow it further: a child is never allowed more than its parent. A sub-agent may be given a narrower role of its own ([below](#subagents)). A fork keeps its source's role.

Every session records, when it is created, the workspace's primary directory (`cwd`) and the Git branch checked out there (`branch`, read from the repository's `HEAD`; none for a detached `HEAD` or outside a repository). A child, or a fork, takes its source's. A session from before these fields existed has none.

## Side conversations [#side]

A side conversation is a temporary conversation beside a session, for a question you want answered without disturbing the session's work.

- It starts with everything the session had at its last turn boundary: the whole conversation when no turn runs, and the conversation before the running turn otherwise, so you can ask while the session works. The session's history must have at least one turn.
- Its model is told it is in a side conversation: the inherited conversation is reference only, not instructions to carry on; it answers questions and explores without changing files, the workspace or settings unless you ask it to in the side conversation.
- It is **ephemeral**: kept in memory only, never written to the history, never listed, and gone when it is closed, when its session is archived or deleted, or when the Agent stops. Its transcript starts at the side conversation, not with the inherited history.
- A session has at most one; opening it again returns the open one. Closing it stops its running turn and its background terminals.
- **In the terminal interface**, `/side` (or `/btw`) opens it: in Fullscreen a pane beside the conversation, in Scrollback a switch to it; Esc returns and `/side close` closes it ([Terminal interface](/docs/terminal-interface#side)).

## Sub-agents [#subagents]

After a shutdown or restart, a sub-agent whose work was interrupted is reported as lost to its parent. When a nested subtree is lost, its highest sub-agent is reported once. The history remains available for a follow-up task. The report waits for the parent’s next turn; launching the Agent does not resume work automatically.

A sub-agent is a child the session's model spawns with `spawn_agent` to work on a task in the background ([Tools](/docs/tools#subagents)).

- It is **durable**: written to the history like any session, with `origin` `subagent` and the task name as its title. Session lists leave it out like every child; it is listed with its parent's children.
- It starts empty, or with its parent's conversation before the turn that spawned it, and runs with the permission mode its parent's next turn would have; its turns come from its parent's model, not from you.
- It has the [role](/docs/roles#subagents) `spawn_agent`'s `agent_type` names, one of the spawnable roles: its tools are its parent's narrowed by the role's, its instructions the role's, its model and reasoning effort the role's, else its parent's. Without `agent_type` it keeps its parent's role, model and reasoning effort. `list_agents` names each one's role.
- `spawn_agent`'s `model`, `reasoning_effort` and `provider` choose its model, effort and Provider over the role's and its parent's, each checked before the sub-agent is made ([Tools](/docs/tools#subagents)). A sub-agent on another model or Provider has that model's context window and image input, and keeps its model across its tasks and a restart.
- Its end (its final answer, or its error) and the messages it sends its parent (`send_message` to `parent`) are queued on the parent, durably: the parent's running turn reads them at its next step, and a parent that ended its turn is woken to read them, with `wakeOnBackgroundTasks` on ([Tools](/docs/tools#subagents)). The parent's `wait_agent` takes its final status from the same queue, also after a restart.
- Archiving or deleting the parent archives or deletes its sub-agents with it.
- Sub-agents nest two levels below the main conversation; side conversations and reviews cannot spawn them. By default 8 work across the whole tree (`maximumRunningAgents` in [`[pluginOptions.subagents]`](/docs/config-reference#plugin-options)), counting a parent waiting for its own children. A waiting child is woken by its children; its answer reaches its parent only after that work and its queued updates are settled.
- **In the terminal interface**, `/subagents` lists them with their status, model and reasoning effort and shows one in place of its parent, live while it runs; in Manual mode an approval a sub-agent waits on is shown in its parent, labelled with its title, and answered on it ([Terminal interface](/docs/terminal-interface#subagents)). `/agents` (or Left on an empty composer) lists every session without a parent, its status rolled up from its children's (a sub-agent waiting for an approval puts its parent under Needs input), to open, fork, rename, stop, archive or delete them ([Terminal interface](/docs/terminal-interface#agents)).

## Reviews [#reviews]

A review is a child that reviews the work in the session's repository and reports its findings back to the session: the facade's `start_review` ([Embedding the Agent](/docs/embedding#feature-calls)), Codex's `/review`.

- **What it reviews**: the uncommitted changes (staged, unstaged and untracked), the changes against a base branch (from the merge base of `HEAD` with that branch, which the review is given), one commit, or your own instructions. `review_targets` lists the working directory's branches, current branch and latest 100 commits to choose from.
- It is **durable**, with `origin` `review` and `Review: <target>` as its title, and starts empty: nothing of the session's conversation, only the request for its target as its first message. Its model is the session's, in Default mode whatever the session's mode, and it is told Codex's review guidelines, which ask for the findings as JSON (title, body, confidence, priority, file and lines, and an overall verdict).
- It is **read-only** ([Permissions](/docs/permissions#review)): it reads files and runs plain `git --no-pager` reads; anything else that needs an approval is denied without asking.
- It runs one turn, whose final answer is read as the findings: an answer that is not that JSON is kept whole as the explanation, and a finding that does not read is left out. Then the session is told, as context its model reads at its next turn, what the review found, or that it was interrupted (`cancel_review`) or failed. If the session runs a turn then, the note waits for it to end.
- The session must have had a turn: its history starts with one, so a session with none cannot be told. A review of it is refused.
- Archiving or deleting the session archives or deletes its reviews with it.
- **From the terminal interface**: `/review` picks the target, shows the review running (Esc cancels it), then its verdict and findings ([Terminal interface](/docs/terminal-interface#review)).

## Goals [#goals]

A session can have a goal: an objective it keeps working toward beyond one answer, until the objective is done or a budget is spent.

- **Setting one.** You set a goal through the facade (`set_goal`) or `/goal` in the terminal interface, or ask the model to and it calls `create_goal` ([Tools](/docs/tools#goals)). A goal you set replaces the session's, and its usage starts again; the model may only create one when the session has none or its goal is complete. The objective is at most 4,000 characters (a longer one is refused: put the instructions in a file and name it), and a goal may have a token budget and a time budget.
- **What keeps it going.** While the goal is `active`, a turn that ends with a final answer goes on: the model is told to continue toward the objective, once per final answer, until it marks the goal `complete` or `blocked`, you pause it, or a budget is spent. No turn starts by itself: resuming a goal, or setting one while the session is idle, takes effect at the session's next turn. A Plan-mode turn is not continued.
- **Budgets and usage.** While the goal is active it counts the model tokens the session spends (input and output, as the provider reports them or as estimated; the input is the prompt total, cache reads and writes included, on every protocol, so on Anthropic a budget fills faster than before 0.3) and the time spent in turns. Once a budget is spent the goal becomes `budget_limited`, and the turn gets one more answer, in which the model is told to wrap up. A goal without a budget still runs within each turn's own limits (tool calls, tokens and continuation context per turn): a turn that reaches one fails, and the goal stays active for the next turn.
- **Statuses**: `active`, `paused`, `blocked` (the model is at an impasse it cannot pass without you), `budget_limited` and `complete`. A spent budget outranks paused and blocked, and resuming a budget-limited goal leaves it budget-limited.
- **What the model sees.** Each turn starts with the goal in its context: the objective as quoted data (left out when its quoted form is over 700 bytes), who set it, its status and budgets. A goal you set or replace while a turn runs is announced at that turn's next final answer.
- **Where it is kept.** The goal is stored with the session's state in the history, so it survives a restart, a fork keeps it (status and usage too), and archiving and deleting the session carry it. A child session (a side conversation, a subagent) does not inherit its parent's goal, and a temporary session cannot have one.
- With the `goal` plugin off (`disabledPlugins`), the goal tools are gone, nothing is continued and the goal calls are unavailable; a goal already set stays stored.
- **From the terminal interface**: `/goal` shows the goal with its status, budgets and usage, and sets, replaces, edits, pauses, resumes and clears it ([Terminal interface](/docs/terminal-interface#goal)).

## Resuming a session [#resume]

Continue a session in the terminal interface:

```sh
hanafubuki-agent resume 2        # by id
hanafubuki-agent resume --last   # the latest session a turn ran in
hanafubuki-agent resume          # pick one from a list
```

The interface replays the session's latest 200 items, and your next message continues it. `/resume` in the terminal interface opens the same picker. See [Terminal interface](/docs/terminal-interface#resume).

`exec` always creates a new session and cannot continue one, but a session `exec` created can be continued with `resume ID`.

## Notes [#notes]

- Like `resume`, every `sessions` command starts the Agent, so it needs the data directory to itself: while another Agent process runs, it fails, as [Troubleshooting](/docs/troubleshooting#data-directory-in-use) explains.
- A session id is a number; anything else exits with code 2.
