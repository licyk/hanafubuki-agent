A release is a `v<version>` tag on `main`. The tag starts `.github/workflows/release.yml`, which publishes every crate but `xtask` to crates.io, builds the `hanafubuki-agent` binary for four targets and creates the GitHub release with the archives.

## Checklist [#checklist]

<Steps>
  <Step>
    **Bump the version** (skip this when the workspace already names the version you release):

    ```sh
    cargo xtask version patch        # or minor, major; --dry-run prints the next version
    git commit -am "chore(release): hanafubuki-agent 0.1.1"
    git push
    ```

    `version` raises `[workspace.package].version` and every internal requirement in `[workspace.dependencies]`, then refreshes `Cargo.lock`. When the requirement users write (`hanafubuki-agent = "0.3"`, for one) changes with it, it also updates the dependency snippets in `README.md` and the site's MDX pages. Before 1.0 a minor release may break, so a release that removes or changes public API (the `exec --json` events included) bumps the minor version.

  </Step>
  <Step>
    **Wait for CI to pass** on the pushed commit on all three systems. The release reuses that run rather than testing again, and runs `ci.yml` itself when the commit has no usable run (a docs-only commit CI skipped, for one).
  </Step>
  <Step>
    **Tag and push:**

    ```sh
    cargo xtask tag --dry-run        # prints the tag it would make: v<version>
    cargo xtask tag --push
    ```

    `tag` makes the annotated tag on a clean `HEAD` and pushes it (it also takes `--version`, `--name`, `--message` and `--remote`).

  </Step>
  <Step>
    **Watch the release:** `gh run watch -R licyk/hanafubuki-agent` (or the Actions tab). The jobs are below.
  </Step>
  <Step>
    **Check the result:** the crates on crates.io (`cargo install hanafubuki-agent-cli` works), and the release's eight files.
  </Step>
</Steps>

## The release workflow's jobs [#the-release-workflows-jobs]

| Job              | What it does                                                                                                                                                                                                                                                                                                                   |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `plan`           | reads the workspace version; on a tag, fails unless the tag names it                                                                                                                                                                                                                                                           |
| `ci-result`      | finds CI's run of the commit and waits for it; a failed run stops the release                                                                                                                                                                                                                                                  |
| `checks`         | runs `ci.yml` when `ci-result` found no usable run                                                                                                                                                                                                                                                                             |
| `publish`        | `cargo publish --workspace`, in dependency order, skipping versions already on crates.io and waiting out crates.io's rate limit                                                                                                                                                                                                |
| `licenses`       | generates `THIRD-PARTY-LICENSES.txt` with `cargo-about` (`about.toml`, `about.hbs`) and appends `crates/tui/syntax-licenses.txt`                                                                                                                                                                                               |
| `binaries`       | builds `hanafubuki-agent` with `--release --locked` for `x86_64-unknown-linux-gnu`, `x86_64-apple-darwin`, `aarch64-apple-darwin` and `x86_64-pc-windows-msvc`, and packages `hanafubuki-agent-<version>-<target>.tar.gz` (`.zip` on Windows, with the binary, LICENSE, NOTICE and the third-party licences) and its `.sha256` |
| `github-release` | creates the release with notes generated from the previous `v*` tag, and uploads the archives and their sums                                                                                                                                                                                                                   |

`publish` and `github-release` run only on a tag.

## The asset names are a contract [#asset-contract]

From the version that ships `hanafubuki-agent update` on, a released binary updates itself from the latest release's archives, so what `binaries` and `github-release` make is read by every version already installed, not only by the one being released:

| What                 | Read as                                                                                                                              |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| The targets          | `x86_64-unknown-linux-gnu`, `x86_64-apple-darwin`, `aarch64-apple-darwin`, `x86_64-pc-windows-msvc`; any other build has no release  |
| The archive          | `hanafubuki-agent-<version>-<target>.tar.gz`, `.zip` for Windows                                                                     |
| The executable in it | `hanafubuki-agent-<version>-<target>/hanafubuki-agent`, `.exe` for Windows                                                           |
| The release          | the tag `v<version>`, neither a draft nor a pre-release (GitHub's latest release), each archive with the SHA-256 digest GitHub gives |

Renaming an archive, moving the executable inside it, adding or dropping a target, or marking a release as a pre-release strands the self-update of every version before the change: those installations are updated by hand once. `crates/update/tests/release_contract.rs` reads `release.yml` and `about.toml` and fails when their targets or packaging lines drift from the updater's table (`RELEASE_TARGETS`, `asset_name` and `entry_path` in `crates/update/src/target.rs`): change both together, and only on purpose. A resumed release ([below](#resuming-a-release-that-stopped)) replaces archives while lookups may be reading them; an update that meets a missing archive or a digest that no longer matches stops and changes nothing.

## The first release and crates.io's rate limit [#the-first-release-and-cratesios-rate-limit]

crates.io lets an account create a few new crates at once and then one every ten minutes. The first release creates all 24 crates, so `publish` publishes the first few, then one crate every ten minutes or so: about three and a half hours in all. The job retries up to 30 times and is allowed 330 minutes; `github-release` waits for it. Later releases only add versions of existing crates, which crates.io limits far less, and take minutes. A release that adds a crate (as the self-update added `hanafubuki-agent-update`) creates it within the few crates.io allows at once: still minutes.

## Resuming a release that stopped [#resuming-a-release-that-stopped]

A run that stopped part-way (the publish timed out or failed, a binary did not build, the runner went away) is resumed with a manual run **on the tag**:

```sh
gh workflow run release.yml -R licyk/hanafubuki-agent --ref v0.1.0
```

Every job is safe to repeat: `publish` skips each crate version already on crates.io, the binaries are built again, and `github-release` uploads the archives over an existing release's (`--clobber`) instead of creating it again.

## Rehearsing [#rehearsing]

A manual run on a branch builds and packages the binaries (and the third-party licences) and publishes nothing: `publish` and `github-release` run only on a tag. Rehearse before a release that changes the workflow or the build, and look at the archives the run uploads as artifacts:

```sh
gh workflow run release.yml -R licyk/hanafubuki-agent --ref main
```

If a fix is needed in the code, a published version cannot be replaced: fix it on `main`, bump the version, and release the new one.

## Secrets [#secrets]

- `CARGO_REGISTRY_TOKEN`: a crates.io token with the `publish-new` and `publish-update` scopes, set as a repository secret. Only `publish` sees it.
- `GITHUB_TOKEN`: the workflow's own token, with `contents: write` only on `github-release`.
