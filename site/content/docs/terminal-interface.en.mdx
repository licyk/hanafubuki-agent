`hanafubuki-agent` with no command opens the terminal interface. Text after it is sent as the first message:

```sh
hanafubuki-agent
hanafubuki-agent "Find the modules in this project that no test covers"
```

The interface starts with no session: your first message creates it, as does a command that needs one (`/model`, `/effort`, `/mode`, `/compact`, `/status`, `/context`). Starting and quitting leaves no empty session behind. With no default Provider or no model chosen, the interface opens the [setup](#setup) instead of letting the first message fail. When the session cannot be created for another reason, the conversation says why in red and the interface stays open; the next message tries again.

The interface needs a terminal on both standard input and standard output; in a pipe or a redirection it points you to [exec](/docs/exec) and exits with code 2. `-m`, `-C`, `--add-dir`, `--permission-mode` and the other [global flags](/docs/cli-reference#global-flags) apply as usual.

## Fullscreen and Scrollback [#modes]

The interface shows the conversation one of two ways, chosen when it starts and kept until it quits:

- **Fullscreen** (the default): the interface takes the terminal's alternate screen and draws the conversation itself, above the bottom area. You scroll, select, search and copy inside it (see [Reading the conversation](#reading)), and it does not stay in the terminal after you quit.
- **Scrollback**: the interface takes the lower part of the terminal, and the conversation is written into the terminal's own scrollback above it, so you scroll back through it, select and copy like any other output, and it stays in the terminal after you quit. Its newest entries stay in the part the interface draws, the tail, where they change and expand in place as in Fullscreen until they are written ([Reading the conversation](#reading)).

It starts in Fullscreen unless one of these says otherwise, the first that applies winning:

1. `--no-alt-screen` on the command line: Scrollback for this run.
2. `tui.alternateScreen = "never"`: Scrollback. `"auto"` (the default) is Scrollback in an SSH session (`SSH_TTY` or `SSH_CONNECTION` set), `"always"` never.
3. `tui.fullscreenTranscript = false`: Scrollback. `/tui` opens it in the [settings center](#config).

The keys are in the [Configuration reference](/docs/config-reference#tui).

Resizing the terminal lays the conversation out again for the new width in either: Fullscreen at once, Scrollback once the size has held for a moment, by writing the conversation into the terminal again ([Reading the conversation](#reading), [Rendering](#rendering)).

## Layout [#layout]

In Fullscreen the conversation fills the screen above the bottom area. In Scrollback the interface draws the bottom area and, above it, the conversation's newest entries (the tail); the rest of the conversation is in the scrollback above them.

At the start (and after `/new` or a resume) a box shows the version, the model and the working directory. Before a session exists, the model is the one it will get: `-m`'s, else the configured one. The bottom area holds, from the top:

1. **The status line**: during a turn, `• Working 25s • esc to interrupt` with the elapsed time; once the turn has thought, `• Working 25s (Thinking 20.7s) • esc to interrupt`, with the time the whole turn has thought so far, which runs on only while the model thinks ([Thinking](#thinking)). While a model request is retried it reads `Reconnecting 1/3: reason`. The working timer pauses while an approval or a question waits for you. It stays for the whole turn, also while the answer streams.
2. **The messages waiting** for the turn, while there are any ([below](#composer)). During a turn the rows they took stay, blank, once the turn has read them, until it ends, so the conversation above does not move each time.
3. **The composer**, starting with `›`.
4. **The footer**: the [status line](#status-line), by default the model and its reasoning effort, the working directory and the session's title, while the composer is empty or holds a draft with no turn running; `? for shortcuts` when it shows no item. On an empty composer, `← for agents` follows when Left opens the [command center](#agents). A draft written during a turn shows `tab to queue message` instead. When a newer release exists, the right of the same row says so, `Update available: 0.3.0 · hanafubuki-agent update` ([Updates](#updates)).

An approval, a question and the `/model` and `/mode` lists take the place of the status line and the composer while they are open. A list stays open when a turn ends; `/model`'s opens before any Provider has answered and fills in as each does ([The model list](#model-list)). The settings, `/providers` and `/mcp` among them, are the [settings center](#config)'s, over the whole screen.

In the conversation your messages start with `›`; a tool call is `• Running TOOL: SUBJECT` where it starts (`• Running COMMAND` for a command; the subject is what it acts on: the command line, the path, the query), and changes there in place into what it did, collapsed: `• Ran cargo test` with the output's last lines, `• Edited src/lib.rs (+12 -3)`, `• Read src/lib.rs (lines 1–120)`, `• Called TOOL` with the first lines of what it returned ([Tool calls](#tools)); a thinking is `• Thinking 3.4s`, then `• Thought · 20.7s` ([Thinking](#thinking)); the task plan is `• Updated Plan · 1/5 complete` with its steps; errors start with a red `■`. After a stretch of tool calls, a `─ Worked for 1m 05s ─` rule comes before the answer, `─ Worked for 1m 05s · thought for 20.7s ─` when the turn thought.

Fullscreen has the conversation's keys too: Page Up/Page Down, F3, F4, Ctrl-Space and the others in [Reading the conversation](#reading); in Scrollback, F4 reaches the tail's activities.

These are the default keys. [The keymap](#keymap) changes the keys of its actions (Enter, Tab to queue, Shift+Left to edit a queued message, the history and its search, pasting an image, the editor, Esc to interrupt, Ctrl-T, Ctrl-O, `?`, Shift+Tab, Alt+, and Alt+., Alt+Left and Alt+Right, the editing keys, the conversation's and the pagers' keys, the command center's session actions); Ctrl-C, Ctrl-D and the keys of popups and lists (Tab's completion among them) stay as they are.

The composer has the usual Emacs-style editing keys: Ctrl-A/E for the start and end of the line, Ctrl-W to delete the previous word, Ctrl-U/K to delete to the start or end of the line, Alt-B/F to move by word, and so on.

<Callout>
  Esc interrupts the turn whatever it is doing, also while the answer streams. It never sends the
  draft in the composer: with steering messages waiting it sends them as the next turn, otherwise
  what waited goes back into the composer (below).
</Callout>

### The shortcuts [#shortcuts]

`?` on an empty composer shows the keys under it in three groups, side by side when the window is wide enough, else in two columns or one; `?` again hides them, and so does a key the composer takes (typing, Enter, the arrows). Each key is the one [the keymap](#keymap) gives its action now: a key you rebind shows as rebound, and an action you unbind (or bind only to a chord) is left out.

```text
  Keyboard shortcuts

  Compose                        Session                                        Transcript (open first)
  /         Commands             tab                Send message                ctrl + t                           Open transcript
  @         Mention files        shift + tab        Change mode                 f3                                 Find text
  !         Shell command        alt + ,            Less reasoning              pgup / pgdn                        Scroll
  ctrl + j  New line             alt + .            More reasoning              ctrl + space                       Start selection
  ctrl + v  Paste image          ←                  Agents (empty prompt)       ctrl + home / ctrl + end           Top / latest
  ctrl + g  External editor      alt + ← / alt + →  Subagents (empty prompt)    shift + alt + , / shift + alt + .  Top / latest
  ctrl + r  Search history       f4                 Inspect activity
  esc esc   Edit last message    ctrl + c           Quit

  /keymap customize
```

- **Compose**: `!` runs a shell command, Ctrl+V attaches the clipboard's image (`ctrl + alt + v` under WSL, whose terminal pastes text with Ctrl+V), Ctrl+G edits the draft in your editor and Ctrl+R searches the messages sent ([below](#composer)); the new line is Shift+Enter where the terminal reports it. **Session**: Tab says `Queue message` and Ctrl+C `Interrupt` while a turn runs. **Transcript**: the conversation's keys ([Reading the conversation](#reading)), in Fullscreen beside the composer, in Scrollback once Ctrl+T has opened the transcript.
- In a [side conversation](#side) or a [subagent](#subagents) shown, the mode, the effort and editing an earlier message are the main conversation's, and are left out.
- When the screen is too short for them all, the list is cut and says `… more: /keymap`; `/keymap` lists every action.
- Shift+Tab is refused during a turn, as `/mode` is. Alt+, and Alt+. step through the levels `/effort` offers ([below](#effort)). Alt+Left and Alt+Right go round the session and its subagents ([below](#subagents)).

## The composer [#composer]

- **Pasting**: a paste of more than 1000 characters shows as a `[Pasted Content 1234 chars]` placeholder, expanded when you send; deleting the placeholder deletes the paste.
- **Images** (Codex's): Ctrl-V attaches the image on the clipboard to the message, at the cursor, as `[Image #1]`, then `[Image #2]` and so on; under WSL it is Ctrl-Alt-V, Ctrl-V being the terminal's paste there. An image file copied in a file manager is attached where it is; an image itself (a screenshot, an image copied in a browser) is saved as a PNG, `clipboard-1.png` and on, in a directory the interface creates in the system's temporary directory. Under WSL, where the clipboard Linux sees is not Windows', the image Windows holds is asked of PowerShell (`powershell.exe`, then `pwsh`). A paste that is one image file's path (quoted, with escaped spaces, a `file://` URL, or a Windows path, which WSL reads as its `/mnt/c/…` one) attaches the file too, followed by a space; a path to anything else stays text. A message may be images alone. The placeholder is one piece: Backspace deletes it whole, which drops its image (and removes its PNG), and the images after it are renumbered. The message the model reads keeps the labels where you put them, its images after it in their order, so `compare [Image #1] with [Image #2]` names them; the conversation shows the message with a `[Image #1: clipboard-1.png]` row for each image. The Agent reads each image when the message is sent and keeps its own copy: the PNG is removed once the turn has started, or, for a steering message, once the model has read it, and the directory with what is left in it when the interface exits. Only PNG, JPEG, GIF and WebP images can be attached, at most 20 MiB and 40 million pixels each and 8 to a message; one beyond that is refused at once with the reason (`photo.bmp is not a PNG, JPEG, GIF or WebP image, the formats a model is sent.`, `… is too large to attach: …`, `A message carries at most 8 images; remove one first.`), and a path stays text. A clipboard with text and no image pastes the text, as the terminal's paste would; with neither, Ctrl-V says `There is no image on the clipboard.`; with no clipboard to read (no display, a terminal over SSH, whose clipboard is the other machine's) it says `The clipboard cannot be read (…); save the image to a file and paste its path instead.` An empty paste, which some terminals send for an image, attaches the clipboard's image too, and says nothing when there is none. Ctrl-V does nothing while a popup or the history search is open, and a `!` command takes no image (``A `!` command takes no images.``). When the session's model is known not to read images, a message with one stays in the composer (`This model does not read images (reported); remove the image or switch with /model.`; [Images](/docs/providers-models#images)); while nothing says, it is sent. Up and Down and Ctrl-R bring a message of this run back with its images, those whose PNG has been removed left out with their labels; a message of an earlier session comes back without its labels, its images not being read back. Messages put back into the composer, or sent together as one, keep their images, renumbered in order. Ctrl-G gives the editor the labels as they are: a label left in place, or moved, keeps its image, a label deleted drops it, and the rest are renumbered. `composer.paste_image` in [the keymap](#keymap) rebinds Ctrl-V and Ctrl-Alt-V; Ctrl-Alt-V does not paste on Windows, where it is AltGr.
- **History**: Up and Down go through the messages sent in this run (drafts cleared with Ctrl-C included), not the earlier messages of a resumed session; Ctrl-R searches those too.
- **Searching the history**: Ctrl-R turns the row under the composer into `reverse-i-search:` (Codex's). Type, or paste, what to look for: case does not matter, and the composer shows the newest message holding it, the text found highlighted, in place of your draft. The search goes through the messages sent in this run, then what you sent in the Agent's sessions, the latest first: messages, steering messages and `!` commands as typed, the latest 1,000, each text once; a subagent's session is left out. Those are read once, at the first Ctrl-R, and until they come the row says `searching`. Ctrl-R or Up shows an older match, Ctrl-S or Down a newer one, and at an end the match shown stays. Enter takes the match into the composer to edit, without sending it; Esc or Ctrl-C closes the search and puts your draft back as it was, also while a turn runs, which goes on. With nothing found the row says `no match` and your draft shows. Backspace deletes a character of the search, Ctrl-U all of it. A message given back to the composer meanwhile (an interrupted turn's) goes into the draft Esc puts back. `composer.history_search` in [the keymap](#keymap) rebinds Ctrl-R; the other keys of the search stay as they are.
- **Editing in your editor**: Ctrl-G opens the draft in your editor (Codex's): the command in `VISUAL`, else in `EDITOR`, as they were when the interface started; one set to nothing counts as unset. It may have arguments and quotes, such as `code --wait`: on Windows it is read by the Windows command line's rules, where a backslash is part of a path, and the program is looked up on `PATH` with its extensions, so `code` finds `code.cmd`. The draft, its large pastes written out, goes into a temporary `.md` file, and the interface hands the terminal to the editor and waits for it to exit: it leaves Fullscreen's screen and the terminal's modes meanwhile, and takes them back after. The row under the composer reads `Save and close external editor to continue.`, which shows in Scrollback while an editor in another window has the draft; such an editor must wait for its window to close (`code --wait`). When the editor exits successfully, what it saved is the draft, its trailing blank lines dropped, and a large paste that comes back unchanged is its placeholder again (one edited stays text). With no editor set, the interface says `Set VISUAL or EDITOR to edit the message in an editor.`; an editor that is not found, cannot start or exits with an error, or a file that is no longer text, is named in the conversation, and the draft stays as it was. Ctrl-G does nothing while a popup or the history search is open. It works while a turn runs: the turn goes on, and the conversation shows what it did once the editor is closed. While an editor in another window has the draft, the terminal is in its normal mode: Ctrl-C there stops the interface, as it stops any program the shell runs. `composer.external_editor` in [the keymap](#keymap) rebinds Ctrl-G.
- **Steering a running turn**: a message you send with Enter while a turn runs goes to that turn, and the model reads it at its next step: once the tool calls it is making have run, or after its answer, and the turn goes on. Until then it waits above the composer under `Messages to be submitted after next tool call (press esc to interrupt and send immediately)`; it is written into the conversation once the model has read it. Several are sent in order. Enter before the turn has started queues the message instead (below).
- **Queueing a message**: Tab while a turn runs queues the message under `Queued follow-up inputs`; with nothing running, Tab sends it as Enter does. A command typed with Tab runs at once, as with Enter. When the turn ends, each queued message starts a turn of its own, the oldest first, one after another, also after a failed turn. Shift+Left (or Alt+Up) puts the last queued message back in the composer, before your draft, to change it.
- **Nothing is lost**: a steering message the turn did not read (it ended first, it failed, or the Agent refused the message) is sent when it ends, under `Messages to be submitted at end of turn`; several go together as one message, before the queued ones.
- **Interrupting**: Esc with steering messages waiting interrupts the turn and sends them at once, together, as the next turn (`Model interrupted to submit steer instructions.`); the queue stays, and so does your draft. Ctrl-C, or Esc with no steering message waiting, interrupts and sends nothing: what waited (steering, held and queued messages) goes back into the composer, one per line, before your draft.
- **Shell commands**: a message that starts with `!` runs the rest as a shell command, in a turn of its own that asks no model (Codex's). It runs through the `exec_command` tool, in the session's [sandbox](/docs/permissions#sandbox) and the working directory, until it exits, at most the shortest of the [command timeout](/docs/tools#commands) (`pluginOptions.execution.commandTimeoutMinutes`), the tool timeout (`toolIdleTimeoutSeconds`), each 10 minutes unless configured, and the turn's 30 minutes, so raising the command timeout alone does not let it run longer; Esc stops it: its process is terminated. While the draft starts with `!`, the row under the composer reads `! shell command · runs in the session's sandbox`. Typing it is its approval, so no prompt asks, whatever the permission mode; an approval rule of a plugin that always wants a person still asks. `git clone`'s rule ([What needs an approval](/docs/permissions#what-asks)) reads a command's program and arguments, not a shell script, so `!git clone …` runs without asking. It shows as `• You ran ls` with what it printed ([Tool calls](#tools)). With no model to ask for a way out, a command the sandbox blocks (an install with the network off, a write outside the writable roots) just fails, and a failed one adds a row saying that `!` commands run in the session's sandbox (`/permissions`). The model reads it from your next message on: the command, its exit code, how long it took and its output. `!` alone says how (`Prefix a command with ! to run it locally`). While a turn runs a command is refused (`A turn is running; wait for it or interrupt it first.`) and stays in the composer; it is refused in Plan mode too. A message sent while one runs waits for it, as Tab queues it. Up and Down recall it as typed, and Ctrl-R finds it, in later runs too.
- **Each conversation has its own**: the main conversation, a [side conversation](#side) and a [subagent](#subagents) shown queue apart, and a conversation in the background goes on with its queue. What waits is dropped with a side conversation closed or a subagent left. Moving the conversation to another session (`/new`, `/resume`, editing an earlier message) is refused while a turn runs or a message waits.

## The model list [#model-list]

`/model` opens its list at once, before any Provider has answered. The session's model comes first, with what is already known of it (its own settings, what a refusal taught, the last listing, models.dev when it is on, the built-in window; nothing is requested for it), then one row per enabled Provider saying `listing…`. Each Provider is listed by a request of its own, and its models take its row's place as soon as it answers, in a fixed order: the Providers by name, each one's models in its listing's order. So a slow or unreachable Provider holds up no other. Under the list, `• Listing models… 3 of 6 Providers answered · 4s` counts the Providers that have answered, listed or failed, and how long the list has waited; it goes once every Provider has answered. With no Provider enabled it says `No Provider is enabled: /providers adds one.` Rows that arrive keep what you typed in the search, the selected row and its line on the screen: the rows around it move, it does not.

Each model's row shows its id, its Provider and three columns under a header:

```text
                                                     Context  Thinking  Vision
› claude-sonnet-4-5 (current)            Anthropic      200K  yes       yes
  gpt-5.1                                OpenAI         272K  ?         ?
  meta-llama/llama-3.1-405b-instruct:f…  OpenRouter     131K  no        no
  Team gateway                           listing…
  Work proxy                             not listed: 401 Unauthorized
```

- **Context** is the model's window (`200K`, `1.05M`), **Thinking** whether it reasons, **Vision** whether it reads images: `yes`, `no`, or `?` when nothing says. They are the model's own facts, named as `/status` and `doctor --online` name them ([The model](/docs/providers-models#model)). The model policy's `contextWindowTokens` and `imageInput = "disabled"` apply to whichever model a session runs, so the list says them once, under its title (`The model policy sets every session's window to 128K; images are never sent.`).
- A long id is cut with `…` in its row, the Provider's name first down to 10 columns. Under about 51 columns each row stacks: the id, with the Provider when both fit, and under it `context 200K · thinking yes · vision yes`.
- Under the list, the selected model's facts, each with its source: `claude-sonnet-4-5 · Anthropic: context 200K (reported) · max output 64K (reported) · thinking low, medium, high (reported) · vision yes (reported)`; or `context not known (compacts on the Provider's error)`, `thinking yes, levels not known (models.dev)`, `thinking no (learned: the Provider refused it)`, `vision not known`.
- The keys under it end with `? not known`; with [models.dev](/docs/providers-models#models-dev) off (the default) and a row at `?`, they add `models.dev can fill these: /config modelMetadata`.

Typing searches the ids, the models' names as their listings give them, and the Providers' names (`openrouter`, `Sonnet`). Up and Down skip the Providers still listing. Enter on a model makes it the session's and closes the list, even while other Providers are still listing. Enter on a Provider whose listing failed (`not listed: …`, the whole error under the list; the keys say `enter lists again`) lists it again. Esc closes the list at any time: the listings still running finish, and what they report of the models is kept as when the Agent lists by itself, but their answers find no list and are dropped; a second `/model` starts a list of its own. Every list is read live: nothing is shown from an earlier listing.

## Session commands [#session-commands]

- **`/rename`** opens a one-line prompt with the session's title. While it is open the session's model is asked for a title for the conversation as it stands: it shows under the field (`Suggested: …`), and Tab puts it into the field. Enter renames, Esc cancels. With the `titles` plugin off, or nothing to suggest from, the prompt says `No title suggestion`. `/rename NAME` renames at once. Without a session, `/rename` creates one first.
- **`/archive`** and **`/delete`** ask first (the "No" choice is selected). Then the interface shows no session, as after `/new`. An archived session is found again in the resume picker's archived list (Tab), and Ctrl+A or Enter there restores it. Deletion cannot be undone, and deletes the session's child sessions too. See [Sessions](/docs/sessions#archive-delete).
- **`/fork [name]`** forks the session at its latest committed item: the copy has the whole conversation, and the interface continues in it; the original is kept as it was. With a name the copy is renamed. When the working directory is in a Git repository and the `worktree` plugin runs, it first asks where the copy runs: Fork here, or Fork into a new worktree, which is `/worktree`'s Continue this conversation ([below](#worktrees)).
- **`/clear [name]`** clears the terminal's scrollback and screen in Scrollback, or the conversation in Fullscreen, and leaves the session as `/new` does. With a name, the session your next message creates gets it.
- **`/export`** offers Copy to clipboard or Save to file. Save asks for a file name, filled with `hanafubuki-agent-session-ID.md` in the first workspace root. `/export PATH` saves there at once. A relative path is read against the first workspace root (`~` is not expanded), and an existing file is not replaced: the export fails instead. The format is described in [Sessions](/docs/sessions#export).
- **`/copy`** offers the last answer whole (as Markdown), each fenced code block (as written, without the fence), and each quote (without its `>`); in Fullscreen also Select in the transcript: a caret in the conversation, which the arrows move; v or Space starts a selection, y or Enter copies it, Esc or q leaves. The answer is read from the session's history, so a resumed session's last answer is offered too.
- **`/ps`** writes the session's background terminals into the conversation: each command, its state (and exit code), its directory and its last three lines of output. **`/stop`** (or `/clean`) asks first, then stops them all and says how many it stopped; one that would not stop is reported.
- **`/recap`** writes `Writing a recap…`, then the recap: what the conversation is about and where it stands, and `Next:` with an open question or the agreed next step when there is one. It reads the latest exchanges, without tool output, and commits nothing to the session. On a Provider or gateway that refuses structured output it still works: the request is asked again with a forced tool, then as plain text ([Providers and models](/docs/providers-models#forget)). With the `recap` plugin off, it says recaps are unavailable and why.
- **`/init`** sends a fixed prompt as your message: write `AGENTS.md`, a short contributor guide for the repository (structure, commands, style, tests, commit conventions), and leave an existing `AGENTS.md` unchanged. The prompt is Codex's.

## Roles [#role]

A session's [role](/docs/roles#sessions) narrows what it may use: its tools, the plugins that contribute to it, the most permissive permission mode. A new session has the role `--role` named, else `default`.

- **`/role NAME`** gives the session that role before its next turn: its instructions, its model and reasoning effort if it sets them, and its narrowing. The conversation says `Role set to NAME`. A role no source defines, or one that cannot be used, is refused with the usable roles named. **`/role default`** takes every narrowing away again.
- **`/role`** alone lists the usable roles with the first line of their description, the session's marked; the one chosen is set as `/role NAME` sets it.
- It is not available during a turn. Without a session, `/role` creates one first.
- The role shows in `/status`, and in the status line with the `role` item.

## Reasoning effort [#effort]

**`/effort`** lists the reasoning efforts the session's model can be given, the current one marked `(current)`; the one chosen applies from the next turn, and the conversation says `Reasoning effort set to LEVEL`:

```text
  Select Reasoning Effort
  The reasoning effort of gpt-5 in this session.

  1. low
  2. medium (model default)
› 3. high (current)
  4. Default                 unset: the Provider's default
  5. Custom…                 type an effort
```

- The levels are those of the model's own `reasoningEfforts`, else those its Provider's catalog names; levels from models.dev are not offered ([Reasoning effort and thinking](/docs/providers-models#reasoning)). With no level known there are only **Default** and **Custom**; a model that takes no reasoning says so in the subtitle, and `The Provider refused the reasoning parameter` when a refusal taught it.
- **Default** unsets it: the Provider's default applies. **Custom** opens a one-line prompt, filled with the current effort when it is a custom one; Enter checks it first, and one that is refused (`none`, say) stays in the field with why. A current effort the list does not have shows as `Custom: max (current)`.
- **`/effort LEVEL`** sets any effort at once (narrowed to the model's levels when sent), **`/effort default`** unsets it.
- It is not available during a turn: it says `Change the effort after this turn, or interrupt it.` Without a session, `/effort` creates one first.
- **Alt+, and Alt+.** lower or raise the effort a level among the levels above, under the same conditions. An unset effort, or one off the levels, starts from the model's default, else the first level; past an end it stays and says `Reasoning is already at the highest level (High).` With no level known they say `No reasoning levels are known for this model; use /effort to type one.`
- The effort shows in `/status`, and in the status line's `model-with-reasoning` item (shown by default). The model policy's reasoning effort row in the settings center offers the same options, for the effort new sessions take ([Settings](#config)).

## Permissions [#permissions]

The permission mode starts as the configuration's (`permissionMode`, or `--permission-mode`); see [Permissions](/docs/permissions#modes).

- **`/permissions`** lists Codex's [presets](/docs/permissions#presets), each a permission mode with a sandbox mode: Read only (Manual, `read-only`), Default (Manual, `workspace-write`), Auto-review (Automatic review, `workspace-write`) and Full access (Full access, no sandbox). The one in effect is selected: the session's own modes, else the configured ones; when they make no preset, none is. Full access asks first (Cancel is selected). Where this machine has no sandbox, the presets that need one cannot be chosen. Choosing one sets both modes for the session. Without a session, `/permissions` creates one first.
- **`/permissions read-only`** or **`/permissions default`** sets that preset at once. **`/permissions manual`**, **`/permissions auto-review`** or **`/permissions full-access`** (`auto_review` and `full_access` too) sets the permission mode alone, at once and without asking, and keeps the sandbox: a mode's name is never a preset's.
- The modes are the session's only, until the interface quits: `permissionMode` and `sandboxMode` stay as they are, other sessions and forks keep the configured modes, and a turn already running keeps the modes it started with. See [One session's mode](/docs/permissions#session-mode) and [One session's sandbox](/docs/permissions#session-sandbox).
- **`/approve`** lists the actions automatic review denied in this session, the latest first: each with its summary and the review's rationale, searchable. The interface keeps the latest ten of each session, from the time it opened it, so a resumed session lists none of its earlier ones. The one chosen is approved: the model sees the approval from its next request, and a retry is still reviewed ([Approving a denied operation](/docs/permissions#approve-denied)). With none, it says `No denied actions to approve.` While a turn runs the Agent refuses the approval, and the conversation says why.

## Working directory and worktrees [#worktrees]

- **`/cd [path]`** makes `path` the working directory: the first workspace root, with its Git root and the `--add-dir` directories after it. A relative path is read against the current working directory; `~` and `~/…` are your home directory, as is `/cd` alone. The session goes on there: its next turn works in the new roots. The Agent refuses while a turn, a compaction or a background terminal runs, and a directory that does not exist; the conversation says why, and nothing changes.
- The project configuration does not follow `/cd`: its trust level and the project's `config.toml` stay the ones read when the interface started, until you start it again.
- **`/worktree`** opens a menu, when the working directory is in a Git repository and the `worktree` plugin runs (otherwise it says why there is none):
  - **Continue this conversation** makes a new worktree, forks the session into it ([Worktrees](/docs/sessions#worktrees)), changes the working directory to it, and continues in the fork. Without a conversation yet, this row cannot be chosen.
  - **Start a new conversation** makes a new worktree and changes the working directory to it, with no session: the session your next message creates belongs to the worktree.
  - **Browse worktrees** lists the repository's worktrees, each with its commit, its branch (`detached` for a new one) and its session. Choosing one offers Resume session N, Copy path and Remove worktree; removing asks first (Cancel is selected), deletes the checkout with its local changes and keeps the session. The worktree the working directory is in is not removed: `/cd` out of it first.
- When a step after the worktree was made fails (the fork, the change of directory), the worktree is kept, and the conversation says where; Browse worktrees removes it.

## First-run setup [#setup]

When the interface starts with no default Provider (none is configured, or none is enabled), or with no model chosen for new sessions and none given with `-m`, it opens the [settings center](#config) at the Providers instead of letting the first message fail:

- With no Provider: `a` adds one. Fill in its name, protocol, base URL and token, then **Add a Provider**: the first one is the default. Enter on it opens its record, whose **List models** tests it and whose **Choose the model** lists its models: the one you pick, on that Provider, is the one new sessions run.
- With Providers but none enabled: turn one's **Enabled** on, or add one.
- With a default Provider but no model: its **Choose the model**.

Esc goes back a page and closes the center from the tabs; the composer is yours again. A message sent before the setup is done stays in the composer, a line says why, and the center opens again. Once a model is chosen, the next message creates the session. `/new` checks again, as a start does.

## Forms [#forms]

The forms of the settings center's pages (a plugin's options and settings, a preset, a model id typed in) take these keys:

| Key                | Does                                             |
| ------------------ | ------------------------------------------------ |
| Tab, Down          | The next field; from the last, the first         |
| Shift+Tab, Up      | The previous field; from the first, the last     |
| Enter              | The next field; on an action (**Save**), runs it |
| Space, Left, Right | Switches a choice or a toggle (`[x]`)            |
| Esc                | Back                                             |

- Text fields have the composer's editing keys. Each field keeps its own kill buffer (Ctrl-K, Ctrl-U, Ctrl-W, then Ctrl-Y), so text deleted from a secret cannot be yanked into another field.
- A secret value is drawn as dots, its last character shown only while you type it. A paste goes into the field that has the focus, without its line breaks.
- What is wrong with a field is said in red under it, and the focus goes there. What the Agent refuses on saving is said under the form, whose entries are kept.

## Providers [#providers]

`/providers` opens the [settings center](#config) at the Providers: each with its protocol and base URL, `default` beside the default one and `off` beside a disabled one. A Provider's record has its fields (the token shown as `••••` when it is set, never the token), and the actions **Make default**, **List models** (which tests it), **Choose the model** and **Delete**. **Choose the model** shows the loading line while the Provider answers, then its models in the columns of [the model list](#model-list), with the selected one's facts under them. `/providers policy` opens the model policy. The fields and the model page are in [Providers and models](/docs/providers-models#interface).

## Plugins [#plugins]

`/plugins` opens the plugin browser (Codex's plugin catalog), a page of the [settings center](#config) (Plugin browser, in Plugins), on three tabs, switched with ←/→: **Installed**, **Marketplaces** and **Built-in**. Each change is saved at once; while it runs, the page says so (`Installing…`), and everything is read again after it. The commands' equivalents are in [Command-line reference](/docs/cli-reference#plugins).

- **Installed** lists the [installed plugins](/docs/cli-reference#plugins): each with its state, version, hooks that need review and issues. Space turns the highlighted one on or off; Enter opens it (its source, version, format, Skills, MCP servers, hooks, [roles](/docs/roles#plugins) and issues); `o` opens a code plugin's options, when its `configSchema` lowers to some (the generic options form below; saving writes its settings, keys the options do not describe kept, and starts its code again); **Install from a directory…** asks for a plugin's directory, which is installed as `<name>@local`.
- A plugin's page offers **Disable plugin** or **Enable plugin**, **Trust its N hook(s)** while some wait, **Grant its permissions** while a code plugin's are not granted (it says what its code may reach; a **Code** row shows its guest's state), **Settings** for a code plugin (a form with its settings as one JSON object, checked against its manifest's `configSchema`; empty removes them; its code starts again with them), **Update plugin** (again from its marketplace or directory), **Retry plugin** (load it again, and start a failed guest again) and **Uninstall plugin**, which asks whether to keep its data directory. Below them: its source, version, format, Skills, MCP servers, hooks and issues.
- **Marketplaces** lists the added marketplaces, each with its source and how many of its plugins are installed. Enter opens one: its plugins, each **Available**, **Installed**, **Disabled** or **Not installable**; Enter on one that is not installed shows **Install plugin**. Ctrl+U upgrades a git marketplace, Ctrl+R removes one after asking. **Add a marketplace…** asks for a source: `owner/repo`, a git URL, or a local marketplace directory.
- After an install, a plugin with hooks lists their commands and asks to trust them (**Trust them**, or **Not now**: `/hooks` and the plugin's page trust them later). A hook runs only once trusted.
- **Built-in** lists the plugins compiled into the Agent (and the host's), with their state and summary: Space or Enter turns one on or off (`disabledPlugins`; the core ones cannot be), `r` starts a failed one again, and `o` opens the options of one that has some (`[pluginOptions.NAME]`).
- The **options form** is generic: a field per option of the plugin, labelled with its summary and key, as a toggle, a number (its bounds as the placeholder), a choice, a text (masked when it is secret) or a list of texts separated by commas. Save checks every value as the write does and shows the reason under a field that does not fit; only the values changed are written, into the user's `config.toml` (a built-in plugin's [`[pluginOptions.NAME]`](/docs/config-reference#plugin-options), a code plugin's [`[plugins."ID"].settings`](/docs/config-reference#plugins)), and the plugin takes them at once. The same options are the rows of the plugin's own section in the center's Plugins tab.

Esc goes back a page, and from a tab back to the center. Started with `--safe-mode`, the browser says no installed plugin is loaded.

## MCP servers [#mcp]

`/mcp` opens the [settings center](#config) at the MCP servers (in Tools): each with its command or URL, its connection phase, its number of tools once connected, and its last error. A server's record has its transport, environment or headers, protocol mode and policies, per-tool ones included, and the actions **Delete**, **Connect**, **Disconnect**, **Refresh**, **Log out** and **Log in**, which opens its OAuth login. Its secrets are the **MCP secrets** beside it. The servers the enabled installed plugins run are the **Plugins' MCP servers**, beside them too: each with its plugin, connection phase and tools, which you turn on or off and narrow to some tools or away from some (`[plugins."ID".mcpServers.NAME]`, [Plugins](/docs/config-reference#plugins)); how one runs stays its plugin's, and `/mcp verbose` lists them as well. See [MCP](/docs/mcp#interface).

## Reviews [#review]

`/review` opens a picker of what to review: **Review uncommitted changes** (staged, unstaged and untracked), **Review against a base branch** (the repository's local branches, the current one marked `(current)`, searchable), **Review a commit** (the latest 100 commits, searchable by subject or hash) and **Custom review instructions** (a one-line prompt). Esc on a list goes back to the presets. Outside a Git repository the branch and the commit are unavailable and say why. `/review INSTRUCTIONS` reviews with your instructions at once. How a review runs is in [Sessions](/docs/sessions#reviews).

- A review reports back into the conversation, so the session must have had a turn: before your first message `/review` says `Send a message first; a review reports back into a conversation.` It does not start during a turn, nor while another review runs.
- While it runs, the conversation shows `>> Code review started: … <<` and the status line `Reviewing …`. Esc, Ctrl-C or `/review cancel` cancels it (`<< Code review cancelled >>`). A message you send meanwhile waits above the composer under `Messages to be submitted at end of turn` and is sent when the review ends, so the turn it starts reads what the review found. While one waits, Esc does not cancel the review (it says so): Ctrl-C does, and puts the message back in the composer.
- When it ends, `<< Code review finished >>` is followed by the verdict and its confidence, the explanation, and each finding: its priority and title, its file and lines, and its body.
- With the `review` plugin off, `/review` says reviews are unavailable and why.

## Goals [#goal]

`/goal OBJECTIVE` gives the session a goal ([Sessions](/docs/sessions#goals)); `/goal --tokens N OBJECTIVE` gives it a token budget too (`200000`, `200k`, `2m`). When the session's goal is not complete, a question asks first, **Replace goal?**, with keeping the current goal selected. The Agent pursues the goal from your next message; one set during a turn is taken up at that turn's next answer.

- `/goal` alone shows the goal: its objective, status, tokens used (of the budget) and time used, with what can be done: **Pause goal** (an active goal) or **Resume goal** (a paused or blocked one), **Edit objective**, **Set token budget** and **Clear goal**. Without a goal it says so, with the usage.
- `/goal pause`, `/goal resume` and `/goal clear` act at once; `/goal edit` opens a prompt filled with the objective. Editing the objective, or setting the budget, sets the goal again: its usage starts from zero.
- Without a session, `/goal` creates one first. With the `goal` plugin off, it says goals are unavailable and why.
- The [status line](#status-line)'s `goal` item shows the goal: read when a session opens, then updated by every `/goal` and, during a turn, by the session's events.

## Hooks [#hooks]

`/hooks` opens the hooks browser, a page of the [settings center](#config) (Hook review, in Tools): it lists the [hook](/docs/configuration#hooks) events, each with how many hooks it has, how many run (trusted and on) and how many need review, above what in the configuration was skipped and why. Enter opens an event: each hook with its matcher and command, its trust (`trusted`, `new, review required` or `modified since trusted, review required`), whether it is on, the file it is configured in and its timeout. Space or Enter turns the highlighted hook on or off, `t` trusts it, Esc goes back, and from the events back to the center. On the events, `t` trusts every hook that needs review, after a question. Each change is saved at once, as the Hooks collection's actions (Tools tab, where each hook's record shows its whole definition: command, timeout, status message and where it is written), and the hooks are read again. A hook is defined in its file, never in the center.

When the interface starts with hooks that need review (new, or modified since they were trusted), the conversation says `N hooks need review: /hooks`, and the warning is kept; nothing waits for you.

## Side conversations [#side]

`/side` (or `/btw`) opens the session's [side conversation](/docs/sessions#side): a temporary conversation beside it, for a quick question that should not disturb the session's work. `/side QUESTION` opens it and sends the question there. The session must have had a turn: before your first message `/side` says `'/side' is unavailable until the current conversation has started.` It is refused too while a [review](#review) runs or while the session's context is being compacted.

- **Fullscreen**: the side conversation is a pane docked on the right of the conversation, with its own transcript, composer and status line; a title row tops each pane and a divider separates them. The pane opens focused. Its messages go to the side session, the main conversation's to the main session, and both stay live: a turn in one goes on while you type in the other. Narrower than 100 columns, or zoomed (`leader z`), the focused conversation fills the screen under its title. Drag the divider with the pointer, or use `leader <` and `leader >`, to resize the panes; `leader =` makes them equal; a click in the other pane focuses it.
- **Scrollback**: the interface switches to the side conversation: `Side conversation · Esc returns · /side close closes it` is written into the scrollback, then the side conversation. What the main conversation writes meanwhile waits, and is written when you return to it.
- **Returning and closing**: Esc on an empty composer with nothing running (the `chat.edit_previous` key), or `leader left`, returns to the main conversation. The side conversation stays open: `/side`, `leader right` or `leader tab` shows it again, with its transcript and its draft. `/side close`, or `leader x`, closes it: its running turn is interrupted and the session is dropped (`Side conversation closed.`). It is closed too when the main conversation moves to another session (`/new`, `/resume`, `/fork` and the like).
- **Commands** in a side conversation are those Codex allows there: `/copy`, `/agents`, `/export`, `/raw`, `/diff`, `/mention`, `/status`, `/warnings`, `/pwd` and `/side`. The popup lists only those; another says `'/x' is unavailable here; Esc returns to the main conversation.` An earlier message of a side conversation is not edited.

The panes' keys are [keymap](#keymap) actions, by default the leader (Ctrl-X) then a key:

| Key      | Action                                                  | Does                                                       |
| -------- | ------------------------------------------------------- | ---------------------------------------------------------- |
| `left`   | `global.focus_pane_left`                                | Returns to the main conversation                           |
| `right`  | `global.focus_pane_right`                               | Focuses the side conversation                              |
| `tab`    | `global.toggle_side_conversation`                       | Switches to the other conversation                         |
| `<`, `>` | `global.move_divider_left`, `global.move_divider_right` | Moves the divider (Fullscreen)                             |
| `=`      | `global.equalize_pane_widths`                           | Gives the panes equal widths (Fullscreen)                  |
| `z`      | `global.toggle_pane_zoom`                               | The focused pane alone, or both again (Fullscreen)         |
| `x`      | `global.hide_pane`                                      | Closes the side conversation, or leaves the subagent shown |

In Fullscreen, while the leader waits for its second key with a second conversation open, a box in the focused pane lists them.

## Subagents [#subagents]

`/subagents` writes the session's [subagents](/docs/sessions#subagents) into the conversation, each with its status (`running`, `idle` or `failed`), the model it runs on and its reasoning effort (`default` when it takes its Provider's), as in `counter  idle · gpt-5.4-mini · low`, and the start of its latest answer, then opens a list of them, each entry described the same way (`idle · gpt-5.4-mini · low`, then the answer's start); while one runs, the list follows their statuses. Enter shows the one selected in place of the session, under `Subagent NAME · from PARENT · Esc or ctrl-x left returns`: its transcript as `/resume` shows it and, while it runs, its turn as it goes on (its answer streams, its tool calls show, an approval it waits on is asked there, including one it asked for before it was shown, and Esc interrupts it). A message you send there goes to the subagent.

- Esc on an empty composer with nothing running, `leader left` or `leader x` returns to the session, whose own turn went on meanwhile.
- **Alt+Right and Alt+Left** on an empty composer step through the session and its subagents, in this list's order and round: from the session to its first subagent, from the last back to the session. With none they say `This session has no subagents.`; while a side conversation is open they say to close it first.
- In Fullscreen the subagent fills the screen; in Scrollback the interface switches to it, as to a [side conversation](#side). Its commands are a side conversation's. While a side conversation is open, a subagent is not shown: close it first.
- **A subagent's approvals**: a subagent runs in its parent's permission mode, so in Manual mode its tool calls wait for you. While the session's subagents run (or its turn does), the interface reads them about every 0.4 seconds and shows an approval a subagent waits on as an ordinary [approval](#approvals) whose summary starts `Subagent NAME:`; your answer goes to the subagent. It stays open when the session's own turn ends, and closes once it is answered elsewhere (in the subagent shown) or the subagent's turn ends. While a side conversation has the focus, it waits in the main conversation: in Fullscreen its pane shows it, in Scrollback you see it when you return.

## The command center [#agents]

`/agents`, Left on an empty composer (the footer then says `← for agents`) or `global.open_agents` (no default key) opens the command center over the whole screen (the alternate screen in Scrollback). Left opens it while the composer has the keys and is empty, no popup is open, `/agents` runs in that conversation, and Left is still `editor.move_left`'s key; otherwise Left moves the cursor as before.

It lists the sessions without a parent, as the resume picker does, each with a status that is the most urgent of its own and its children's (subagents and reviews):

- **Needs input** (red `●`): the session, or one of its children, waits for an [approval](#approvals) or the answer to a [question](#questions).
- **Error** (red `!`): its own last turn failed.
- **Working** (green `●`): a turn runs.
- **Ready** (cyan `○`): its last turn completed.
- **Inactive** (dim `○`): its last turn was interrupted or cancelled. A child whose turn failed counts as inactive: its failure asks nothing of you.

The sessions are under headings with their count (`2 of 5` when the filter hides some): the project, the directory, the status or the model, as `tui.agentsGrouping` says. A project is the directory within the repository's main checkout, so a session in one of the repository's worktrees falls under the checkout the worktree was made from. Under a heading the latest session comes first. The session shown is marked `(shown)` and selected when the center opens. More sessions are read as you scroll.

- **Pinned**: the sessions you pin (`p`) come first, under `Pinned`, whatever the grouping, among the sessions read so far.
- **Unread**: a session that changed, itself or one of its children, since it was last shown has a bold title, and a blue `●` while it asks nothing of you. A session is shown while the main conversation shows it, and when the center opens on it; one never shown here is never unread, and a rename or a restore made from the center is no news.
- **Hidden**: `h` hides a session from every tab. A search lists it again, marked `(hidden)`, and opening it shows it again.

The pins, the hidden sessions and when each session was last shown are the interface's own, kept in the data directory's `tui-state.json` ([Data directory](/docs/data-directory#contents)); the sessions know nothing of them.

From 90 columns, a details pane beside the list says more of the session selected: its title and status, its model and reasoning effort, the branch and the tokens used, its directory; its children (subagents and reviews) with their status; what the most urgent of it and its children waits on you for (an approval's subject or the question) and what it does now; its latest answer (`Last message`) and the message that asked for it (`Prompt`). `c` gives the keys to its children: Up and Down choose, Enter or Right shows the child beside its parent as [`/subagents`](#subagents) does, `x` interrupts the child's turn (a subagent's through the subagents' own interrupt, so that it still takes follow-up tasks), and Esc, Left or `c` return to the sessions. Narrower than 90 columns, the details take the list's place while a child has the keys.

| Key                           | Does                                                                                                                                      |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Up, Down (`k`, `j`)           | Moves the selection; past an end, to the other end                                                                                        |
| Page Up, Page Down, Home, End | Moves a page, or to the first or last session                                                                                             |
| Enter, Right                  | Opens the session in place of the one shown. Under Archived, restores it                                                                  |
| Tab, Shift-Tab, `1`–`6`       | The filter: All, Needs you, Working, Ready, Inactive, Archived, each but Archived with its count                                          |
| `/`, F3                       | Searches the titles: what you type narrows the list, Enter opens the session selected, Esc ends the search                                |
| `n`                           | Leaves the session shown: the next message starts a new one                                                                               |
| `w`                           | Moves into a new worktree, as `/worktree`'s "Start a new conversation": the next message starts a session there ([worktrees](#worktrees)) |
| `f`                           | Forks the session at its head and continues in the copy                                                                                   |
| `r`                           | Renames the session: its title is edited in place, Enter saves it, Esc cancels                                                            |
| `x`                           | Interrupts the session's turn                                                                                                             |
| `p`                           | Pins the session, or unpins it                                                                                                            |
| `h`                           | Hides the session                                                                                                                         |
| `c`                           | Gives the keys to the session's children in the details pane (above)                                                                      |

A confirmation starts on Cancel: Up or Down chooses, Enter confirms, Esc cancels. The keys of the session actions (`/`, F3, `n`, `w`, `f`, `r`, `x`, `p`, `h`, `c`, `a`, Backspace and `g`) are the keymap's `agents` context ([below](#keymap)); the others stay as they are.

Opening, starting (in a worktree too) and forking move the main conversation, so they wait while its turn runs. The session shown is archived and deleted with `/archive` and `/delete`, not from here. The center never waits for a read: the sessions, their children and the selected one's latest exchange are read on a thread of its own, at the start, as you scroll and after each action. While it is open, that thread also watches the sessions the Agent holds, four times a second: each one's changes, an approval or a question it waits on, and what it does. What changed is read again, and the center follows it with no key pressed: the list for a session without a parent, a parent's children for a child, the details for the session selected. The facade has no event stream for every session, so the watch reads them as they are, as [the subagents' watch](#subagents) does; a session the Agent does not hold does not change.

## @ file mentions [#mentions]

`@` followed by a few characters opens a popup of up to 20 files in the workspace roots that match them fuzzily. `.gitignore` and the other ignore files are honoured, even outside a Git repository. Tab or Enter replaces the `@…` with the file's path: relative for a file in the first workspace root, whole for one in another root, and quoted when it has spaces.

Only the path is sent; the model reads the file with its tools.

## Reading the conversation [#reading]

In Fullscreen the conversation follows the latest output until you scroll. Scrolled up, it stays where you are while the turn goes on, and a `↓ Back to bottom · esc` control above the composer (`New activity · …` when something was added below) brings you back.

| Key or gesture                         | Does                                                                                                                                                              |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Mouse wheel                            | Scrolls three lines                                                                                                                                               |
| Page Up/Page Down                      | Scrolls one page                                                                                                                                                  |
| Ctrl-Home, Ctrl-End (Alt-`<`, Alt-`>`) | To the start of the session (loading its earlier messages) or to the latest output                                                                                |
| Esc, a click on the control            | Back to the latest output                                                                                                                                         |
| Enter on an empty composer             | Back to the latest output                                                                                                                                         |
| Drag                                   | Selects; a double click selects a word, a triple click a line, Shift-click extends the selection                                                                  |
| Ctrl-Space                             | Starts a selection with the keyboard; arrows and Shift-arrows move it                                                                                             |
| Ctrl-X `[`                             | Select mode: a cursor in the conversation, moved with the keys, to select and copy                                                                                |
| Ctrl-C, Ctrl-Shift-C, Ctrl-Insert      | With a selection: copies it                                                                                                                                       |
| Enter                                  | With a selection: copies it and goes back to the latest output                                                                                                    |
| Right click                            | Copies the selection                                                                                                                                              |
| Esc                                    | With a selection: clears it                                                                                                                                       |
| F3                                     | Finds text: type the query, Enter accepts the match, Ctrl-P/Ctrl-N go to the older or newer one, Esc cancels                                                      |
| Click on an entry's control or header  | Shows or hides its details: a press and a release on the same cell of the header, so a drag that starts there still selects (below)                               |
| F4                                     | Focuses the latest activity (a tool call, a thinking, a plan, a long message): Up/Down move between them, Enter or a click shows or hides its details, Esc leaves |
| Ctrl-T                                 | Shows the whole conversation in detail (every thinking's text, a tool call's whole output), in place; Ctrl-T or Esc goes back                                     |

An entry with more to show has a control on its own row below it: a thinking (its text), a tool call with more than its collapsed rows show (`+ 12 lines` for lines of output, `+ Show details` otherwise; [Tool calls](#tools)), a task plan with a note or more than three steps (collapsed to three steps: those in progress, then those pending, then those done), and a message of yours longer than 12 rows (its first 12, `+ 8 lines`). Expanded, the control reads `− Hide details` or `− Show less`. An entry with nothing more to show has no control. Its header is its first row of text (a message's first line): a click there toggles it too, and a quick second click toggles it back rather than select a word. Expanding or collapsing an entry whose header is on the screen keeps the header on its row. Each entry expands on its own, and a running one keeps its state when it completes.

The footer under the conversation shows the keys of a selection, a search or a focused activity while it lasts. A copy goes to the system clipboard; where there is none (over SSH, say) it is sent to the terminal (OSC 52), which most terminals put on their clipboard, and the interface says it is unconfirmed. A copy's result shows above the composer for a few seconds.

While an approval, a question or a list is open, the keys are its own; the mouse still scrolls and selects, and Ctrl-C copies a selection.

Fullscreen captures the mouse, so the terminal's own selection usually needs Shift held while you drag. To copy with the terminal's selection, `/raw` shows the conversation without its styles.

In Scrollback the terminal holds the conversation: you scroll, select and copy it with the terminal. Its newest entries stay in the tail above the bottom area, laid out as in Fullscreen: a thinking or a tool call changes there in place, and an entry's control (`+ 12 lines`, `+ Show details`) shows or hides its details.

- When the tail would take more than 60% of the screen (at least 8 rows), its oldest completed entries are written into the scrollback as they are shown; one collapsed with more to show ends with `ctrl + t to expand`. An answer is written line by line as it passes the limit, the rows it committed only: what may still change (a table arriving, the line still arriving) stays in the tail. A running entry is never written: one taller than the tail shows its first line and its latest ones.
- When you send your next message, the tail is written first, whole, so a finished turn's entries stay expandable until then. A session opened in its place (`/new`, a resume) and switching to the other conversation write it too, and quitting writes what is left.
- During a turn the tail does not get shorter: collapsing an entry leaves blank rows until the next write. Expanding one uses them first; past them, the tail grows upward from the bottom area, so the entries above, its header too, move up by the rows it gained.
- A click on a control or on an entry's header shows or hides the details, and so does F4 then Enter (Up/Down move between the tail's activities, Esc leaves).
- To take the click, the interface captures the mouse while the tail shows a control. The first turn of the wheel gives it back to the terminal, which scrolls from the next turn on, until your next key or the next entry. Shift-drag still selects with the terminal. With `tui.scrollbackMouse = "off"` the mouse is never captured; the keys and the [transcript](#transcript) still work.
- Entries already written expand in the [transcript](#transcript) (Ctrl-T).
- After a resize, once the size has held for 75 ms, the interface clears the terminal's scrollback and screen and writes the conversation again for the new width, each entry as it was written (an expanded one stays expanded); the tail stays as it is. It writes about what a terminal's scrollback keeps: the last 1,000 rows (9,001 in Windows Terminal, 3,500 in WezTerm, 10,000 in Alacritty), under `Earlier messages are available — press ctrl + t to view the full transcript` when it leaves earlier ones out; the [transcript](#transcript) has them all. The clear takes everything above the bottom area: what the shell printed before the interface started, an earlier session's rows, the other conversation's and the lines between them. A terminal or multiplexer that does not clear its scrollback for the sequence (`CSI 3 J`) keeps the old rows above the new ones. While the transcript, the settings center or another full-screen view is open, the rewrite waits until it closes.
- An answer that streams through a resize goes on at the new width, the rows it had committed staying at the old one; when it ends, the conversation is written again once more, the answer laid out for the new width.

Each time the session's context is compacted, the conversation shows `• Context compacted` where it happened: after `/compact`, when a turn compacts it (at the threshold, when the model asks for a new context, after the Provider's context-window error), and when a turn installs a compaction that ran [in the background](/docs/config-reference#compaction). A resumed session shows its earlier compactions the same way. When a compaction a turn runs fails, the conversation shows a warning, `⚠ Context compaction failed: …` with the error, and [`/warnings`](#warnings) keeps it; a failed `/compact` says so in its reply instead (`the conversation was not compacted: …`). A cancelled compaction shows nothing. When the Provider refuses a request as too long and the session takes the window it taught ([The context window and compaction](/docs/providers-models#compaction)), the conversation says so once, before the compaction that follows: `• The Provider refused the request as too long; this model's window is taken as 131072 from now on.`

## Hierarchical compression [#compression]

Under the `hierarchical` [compaction strategy](/docs/configuration#compaction) the model folds stretches of the conversation into summaries it writes, with its `compress` tool. A `compress` call shows folded: its header names the ranges it folded and their topics (`• Called compress: m00002–m00005 Setup`), and below it is the first line of its receipt (`[Compressed m00002–m00005 → 1 block(s), ~8000 tokens saved.]`). The summaries the model wrote and the rest of the receipt are its details, which the [transcript](#transcript), Ctrl-T in Fullscreen and F4 show. A resumed session shows its `compress` calls the same way.

`/compression` reads the session's compression without changing it or asking the model:

- **The panel** (billion-context's): the context against the window, what is sent after compression and how it splits, the reminder to fold and the ranges it offers, and each active block with its tier, the tokens it replaced, its summary's size and its topic. Below it come the counters (the `compress` calls applied, the tokens compressed and absorbed, the tool results stored and retrieved) and, while `contentStore` is on, the content store's size.
- **`/compression cache`** shows the cache report: the last request's tokens and each fold, with what the folds saved. The cached tokens are the cache reads the Provider reported; one that reports none shows none cached.
- A session that never ran the strategy says it is not using hierarchical compression.

The [status line](#status-line)'s `compression` item shows the active blocks and the tokens folded away.

If the compression fails for a request (its algorithm panicked), the conversation shows a warning, `⚠ Context compression failed; this turn goes on with the full history: …`, and the rest of the turn runs as `standard`; [`/warnings`](#warnings) keeps it.

## The context [#context]

`/context` shows what the session's last request held, without changing the session or asking the model. It reads a snapshot, so it works during a turn too, where it shows the request the turn sent last. For example, with some rows left out:

```
/context

  Last request: about 75k tokens (estimated: about 4 bytes a token) · the Provider counted 74k
  Context window: 200k

  Instructions                 █░░░░░░░░░░░░░░░░░░░   3%   6.2k
  Tools (15)                   █░░░░░░░░░░░░░░░░░░░   5%    10k
  MCP/plugin tools (3)         ░░░░░░░░░░░░░░░░░░░░   1%   2.1k
  Context sections             ░░░░░░░░░░░░░░░░░░░░   2%   4.3k
    environment                ░░░░░░░░░░░░░░░░░░░░   0%    450
    skill_catalog              ░░░░░░░░░░░░░░░░░░░░   2%   3.9k
  User messages                ░░░░░░░░░░░░░░░░░░░░   2%   4.1k
  Assistant messages           █░░░░░░░░░░░░░░░░░░░   6%    13k
  Tool calls and outputs       ███░░░░░░░░░░░░░░░░░  16%    31k
  Free                         ████████████░░░░░░░░  62%   125k

  Cached tokens: last 61k · session 300k
  Uncached tokens: last 13k · session 110k
  Cache hit rate: last 82.4% · session 73.2% — 300k of 410k prompt tokens from cache (6 requests)
```

- **The groups**, laid out as billion-context's panel lays out its breakdown: a row each, with a bar of its share of the window, the percent and the tokens. They are the instructions; the tools, `Tools (N)` for the Agent's and its built-in plugins' and `MCP/plugin tools (N)` for MCP servers' and installed plugins'; the context sections, each by its kind under their total; user messages, assistant messages, the reasoning sent back, tool calls and outputs, continuation context and compaction summaries; images, with their count; the rest of the request (`Other request fields`: the model, the settings, the request's own framing); and `Free`, the window less the request. A group that holds nothing is left out. With no window known, each share is of the request and there is no `Free` row.
- **The figures are estimates**: the Agent's own, about four bytes a token of the request as it is serialized and an image by its own rule, the estimate every check of a request against the window counts with. The groups add up to the request's. The heading says so, with the prompt the Provider counted beside it once the response is back (`no count from the Provider` before then, or when it reports none).
- **Before any request** of this run, or after a compaction replaced the history, it shows an estimate of the next request, built as a compaction checks it: no tool runs and no model is called. Built outside a sampling step, it leaves out what plugins prepare for one, and outside a turn the context sections; the heading says so. When even that cannot be built, it says why.
- **The prompt cache**: `Cached tokens`, read from the Provider's cache, `Uncached tokens`, the rest of the prompt, and `Cache hit rate`, each for the last request and for the session, then how many of the session's prompt tokens came from the cache and over how many requests that reported a cache figure. The session's rate is over all of its prompt tokens, a response that reported none included. A Provider that reports no cache figure shows `not reported`, never 0%.
- At a narrow width the bars narrow and long labels are cut with `…`; it shows the same in Fullscreen and Scrollback.

## The transcript [#transcript]

In Scrollback, Ctrl-T opens the whole session's transcript (`T R A N S C R I P T`) on the terminal's alternate screen, in the compact presentation, where an entry's control shows its details (a click on the control or the header, or F4 then Enter, as in [Reading the conversation](#reading); Ctrl-O every thinking); a second Ctrl-T shows every entry in detail, and a third closes it. `/diff` shows its diff the same way. In Fullscreen, Ctrl-T shows the conversation in detail in place instead (above), and `/diff` covers the screen until you close it.

| Key                                 | Does                                          |
| ----------------------------------- | --------------------------------------------- |
| Up/Down (`k`/`j`)                   | Scrolls one line                              |
| Page Up/Page Down (Space, Ctrl-B/F) | Scrolls one page                              |
| Ctrl-U/Ctrl-D                       | Scrolls half a page                           |
| Home/End                            | To the start or the end                       |
| `q`, Esc, Ctrl-C                    | Closes it                                     |
| Ctrl-T (the transcript)             | In detail, then closes                        |
| Ctrl-O                              | Expands every thinking, or collapses them all |

In detail the transcript shows every thinking's text and every tool call expanded, where the scrollback shows them as they were when written. Either way the thinking and tool calls still running are where they started, changing in place. Its selection, copying and search are the ones of [Reading the conversation](#reading) (drag, Ctrl-Space, F3).

The turn goes on while a pager is open, and what it writes meanwhile appears in the transcript at once and in the tail once you close it.

## Editing an earlier message [#edit]

On an empty composer, with no turn running and nothing open, Esc shows `esc again to edit a previous message`; any other key cancels it. A second Esc browses your messages with the latest highlighted: in place in Fullscreen, in the transcript in Scrollback, in the compact presentation either way. The footer reads `Browsing · ←/→ prompt · ↑/↓ scroll · ctrl+t details · ↵ edit · esc back`.

| Key           | Does                                           |
| ------------- | ---------------------------------------------- |
| ←/→ (`h`/`l`) | The earlier or the later message               |
| ↑/↓ (`k`/`j`) | Scrolls one line                               |
| Ctrl-T        | Shows or hides the details                     |
| Enter         | Edits the highlighted message                  |
| Esc           | Back to where browsing started, nothing edited |

In Fullscreen the conversation's other keys (Page Up/Page Down, Home/End, F3) still work, and any other key ends browsing; in Scrollback the transcript's keys work, and `q` closes it.

Enter edits in a copy of the session: it is forked before the message's turn and the interface switches to the fork, whose conversation ends before the message, with the message back in the composer to change and send. The original session is archived, whole: `hanafubuki-agent sessions list --archived` finds it ([Sessions](/docs/sessions#edit)). Files the Agent changed are not restored, which the first edit of a run says. The message's images come back with it, as `[Image #1]` and on, the copies the session keeps.

- A message sent while a turn ran (steering) did not start a turn of its own and cannot be edited by itself: edit the message that started the turn.
- While a turn runs, Esc interrupts it, as before; the edit is refused until no turn runs and no message waits.
- With no message yet, the second Esc says `No previous message to edit.` In Fullscreen, browsing reaches the messages loaded so far; scrolling up loads earlier ones. In Scrollback, those of a resumed session's latest 200 items.

## Thinking [#thinking]

Each stretch of the model's thinking (a reasoning item) is an entry of its own, in the conversation where it happened, in order with the answers and tool calls: a step that thinks, calls a tool, thinks again and answers shows four entries. While the model thinks it reads `• Thinking 3.4s`, counting up in tenths of a second; when the stretch ends it becomes `• Thought · 20.7s` in place (`1m 05s` past a minute). A stretch ends at the latest when the model starts its answer or a tool call, also when the Provider reports the thinking done only later (the Responses API may); what the Provider sends of it after that is not shown here, but is kept, and a resumed session shows it.

Each is collapsed to that line, with a `+ Show details` control once its text has arrived. A click on the control or on the line itself (in Fullscreen, in Scrollback while the entry is in the tail, and in the transcript), or F4 then Enter, shows the text below it as dim Markdown, streaming while the model still thinks, and `− Hide details` hides it again. Each entry expands on its own, and stays expanded when it completes. Ctrl-O expands every thinking in the conversation (in Scrollback, those in the tail, or in the transcript while it is open) at once, or collapses them all when all are expanded; a later thinking still starts collapsed.

A Provider that sends no text leaves only the line, with no control. If the turn ends before the thinking does (an error, an interrupt), the line is completed with the time so far. In Scrollback a thinking is written into the scrollback as it is shown when it leaves the tail, and cannot be changed afterwards; the transcript (Ctrl-T) still expands it, and a second Ctrl-T shows every thinking's text, as Ctrl-T's detailed conversation does in Fullscreen. A resumed session replays every stretch the same way, collapsed; a thinking whose text was cut at the Agent's bound says `• Thought · 20.7s (truncated)`.

The [status line](#layout) adds the time the whole turn has thought, `(Thinking 20.7s)`, and the rule before the answer says `thought for 20.7s`; both stop where the stretches stop, so neither runs on while the answer streams.

What you see depends on what the Provider sends: some send a summary of the thinking, some the raw thinking text, some nothing. See [Providers and models](/docs/providers-models#reasoning).

## Tool calls [#tools]

A tool call is one entry, collapsed at first, whatever its tool. Its header says what it did, its bullet is green, red when it failed, a spinner while it runs; below it, under `└`, are at most a few rows. Its control (`+ 12 lines` when the rest is lines of output, `+ Show details` otherwise) expands it in place, as in [Reading the conversation](#reading); the [transcript](#transcript)'s detailed view and `/raw` show every call expanded. A call that shows everything collapsed has no control.

| Tool                                      | Collapsed                                                                                                                                                                                                                                                          | Expanded                                                                                                                                                                              |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `exec_command`                            | `• Ran cargo test` (`• You ran ls` for a [`!` command](#composer)), the output's last 3 lines (or `(no output)`), and `exit 101 · 4.2s` when it failed or `still running · 4.2s` when it went on in the background; while it runs, the last 3 lines so far (below) | `$ cargo test`, the whole output as the tool returned it, then `✓ 4.2s` or `✗ exit 101 · 4.2s`, and where it ran; while it runs, the output so far                                    |
| `write_stdin`                             | `• Interacted with session 3 ← ls` (or `• Waited for session 3`) and the output's last lines                                                                                                                                                                       | the whole output                                                                                                                                                                      |
| `apply_patch`                             | `• Edited src/lib.rs (+12 -3)` (`Added`, `Deleted`), or `• Edited 3 files (+20 -5)` with a row per file; `Failed to edit` when it did not apply                                                                                                                    | the diff: each row behind its line number (an updated file's from where the patch landed, unless it did not apply) and its sign, tinted, `⋮` between chunks ([Rendering](#rendering)) |
| `read_file`                               | `• Read src/lib.rs (lines 1–120)`                                                                                                                                                                                                                                  | the text, behind its line numbers, highlighted by the file's language                                                                                                                 |
| `list_directory`                          | `• Listed src (24 entries)`                                                                                                                                                                                                                                        | the entries, directories first, files with their sizes                                                                                                                                |
| `search_text`                             | `• Searched "foo" in src (7 matches)`                                                                                                                                                                                                                              | `path:line: text` per match, the query in bold where it matched as written                                                                                                            |
| `web_search`, `fetch_web_page`            | `• Searched the web for QUERY`, `• Fetched URL`                                                                                                                                                                                                                    | the results' titles and addresses; the page's title and first 40 lines                                                                                                                |
| `move_path`, `delete_path`                | `• Moved a → b`, `• Deleted x`                                                                                                                                                                                                                                     | (nothing more)                                                                                                                                                                        |
| Any other (MCP, plugins, Skills, memory…) | `• Called TOOL: SUBJECT` (or `• Failed`) and the first 3 lines of what it returned: its text, JSON on one line; an image or audio clip as its type and size (`image/png · 33.2 KiB`), a link or resource by its address; or a structured result's fields           | all of it, JSON indented ([Rendering](#rendering))                                                                                                                                    |

Read, list and search calls in a row share one entry, as in Codex: `• Exploring` while one runs, then `• Explored`, with a row per call (`Read a.rs, b.rs` for reads in a row, `List src (24 entries)`, `Search "foo" in src (7 matches)`) and `· 1 failed` in the header when one failed. Expanded, each call shows as above. Any other entry between them (a thinking, a message, another tool) starts a new one; a single call shows as its own. A `compress` call is folded ([Hierarchical compression](#compression)).

What a call shows is read once it finished, so its header can change a moment after: until then it reads `• Called TOOL` (`• Ran COMMAND` for a command). From its start until then, a dim row under its header stands where its first rows will be (`(running…)` while a command runs, `…` otherwise), so they take its place rather than push what is above: a call that completes adds only the rest of its collapsed rows, its control and, for a command that failed, its exit. A resumed session shows its calls the same way, grouped as they were. A command's output is what the tool returned, after the Agent rendered the terminal's text ([Commands and terminals](/docs/tools#commands)), in the colours it was printed in ([Rendering](#rendering)).

A command's output streams into its entry while it runs. Its header reads `• Running cargo test · 3.4s`, with the time so far (left out when the header's last row has no room for its widest, `· 99h 59m 59s`, so the header never wraps anew as the time grows), and the rows below are the last 3 lines it has printed, as a terminal shows them: a line redrawn in place (a progress bar, a row a pseudo-terminal repaints) changes in place. Expanded, it shows `$ cargo test` and the lines so far. Past 400 lines it keeps the first 200 and the newest 200, with `… +N lines` between them; a line longer than 1 KiB is cut, and `…` stands for output that was skipped. The entry is drawn at the next frame, not at every piece of output. Once the command finished, the entry keeps these rows until what the tool returned replaces them; a call the turn's end overtakes (you interrupted, or the turn failed) ends as it stood, `• Ran COMMAND` with a red bullet and what it printed. Output a process prints after its call returned, when it goes on in the background, is not added: the entry shows what the call returned, and `/ps` shows the rest.

## Approvals [#approvals]

A tool call the [permission mode](/docs/permissions) asks about opens an approval with the kind of operation (such as `Would you like to run the following command?`), its summary and its risk level:

| Option                                                                                              | Key        |
| --------------------------------------------------------------------------------------------------- | ---------- |
| `Yes, proceed`: allows it once                                                                      | `y` or `1` |
| `Yes, and don't ask again this session`: allows the same for the rest of the session (when offered) | `a` or `2` |
| `No`: denies it                                                                                     | `n` or Esc |

A command the model asks to run [outside the sandbox](/docs/permissions#escalation) says so in its summary, with the model's question (`… outside the sandbox in DIR: COMMAND (reason: QUESTION)`); allowing it for the session allows only that command outside the sandbox again.

Up, Down and Enter pick an option too. Ctrl-C denies the open request and every one waiting behind it. Further requests wait their turn. The conversation records `✔ You approved …` or `✗ You did not approve …`.

An approval a subagent waits on is shown the same way in its parent, its summary starting `Subagent NAME:` ([Subagents](#subagents)).

## Questions [#questions]

The model can ask you one or more questions, each with a few options. The interface shows `Question 1/2`, the question and its options:

- Up/Down (`k`/`j`) select, Enter confirms and moves on, and on the last question submits.
- A number picks that option and moves on.
- Left goes back a question, Right or Tab forward.
- Esc or Ctrl-C interrupt the turn.

You answer by picking an option; there is no free text.

## Resuming a session [#resume]

```sh
hanafubuki-agent resume                    # the resume picker
hanafubuki-agent resume 12                 # session 12
hanafubuki-agent resume --last             # the latest session a turn ran in
hanafubuki-agent resume 12 "Carry on"      # resume, then send a message
```

The resume picker lists the sessions a turn ran in, the latest first: when each was last updated, the Git branch and the directory it was created in (when any session has them), and its title (the first message until the session is named). Child sessions are not listed. Type to search the titles; Up/Down and Page Up/Page Down move, Enter resumes, Esc goes back (at `resume`'s start, to the interface with no session), and Ctrl-C quits.

- **Archived sessions.** Tab switches between the sessions and the archived ones. Ctrl+A archives the selected session, or, in the archived list, restores it (Enter restores there too); it leaves the list. The session the interface shows is not archived from here: `/archive` does that.
- **From the interface.** `/resume` opens the picker. `/resume ID` resumes the session with that id, and `/resume TITLE` the one session with that title; when no session, or several, have it, the picker opens searching for it.

A resumed session shows its box and its latest 200 items: messages, the plans the model proposed, tool calls with their output, and context compactions. In Fullscreen the earlier items are read 200 at a time as you scroll up to them (`↑ Loading earlier messages…`); a tool call whose output was read before its call shows without its output. In Scrollback they are left out, with `Earlier messages are not shown.` Your next message continues the session.

With no session to resume, `resume --last` starts with no session, as `hanafubuki-agent` does. `hanafubuki-agent sessions list` shows the session ids; see [Sessions](/docs/sessions).

## Quitting [#quit]

Type `/quit` or `/exit`, or press Ctrl-C twice within one second (or Ctrl-D twice on an empty composer). Quitting restores the terminal (in Fullscreen, leaving the alternate screen, and the conversation with it) and shuts the Agent down, and prints nothing more.

The exit code is 0; 1 when the Agent could not start, the session to resume could not be opened or given the `-m` model, or the terminal could not be used; 2 without a terminal.

## Rendering [#rendering]

Answers, plans and thinking show their Markdown as Codex does:

- **Lists.** An unordered item's marker is `•`; an ordered one keeps its number. After an item that took more than one row (wrapped, several paragraphs, a nested list), a blank line comes before the next item of its list. In Fullscreen and in the [transcript](#transcript), once an answer or a plan has ended, such a list has a blank line between every two items, as in Codex.
- **Task lists.** `- [ ]` and `- [x]` show `☐` and `☑` in place of the bullet, or after the number of an ordered item; the item's further rows are indented under its text.
- **Tables.** A pipe table is laid out in columns: the header in bold over a heavy rule, a light rule between rows, each column aligned as its delimiter row says (`:---`, `:---:`, `---:`). A cell keeps its emphasis, code and links and wraps within its column; a wide character (CJK, an emoji) counts two columns. When the table is wider than the conversation, columns of long tokens (paths, URLs) give up width first, then columns of prose, then short values.
- **Tables too narrow to read.** When a short value would be split, prose would stand in a tall strip, or the columns do not fit at three each, every row is shown as a record instead: a `header  value` line per cell, the records apart by a rule; on a very narrow terminal each header has a line of its own and its value comes under it. A table with a header and no row keeps its pipe source then.
- **Text after a table.** A line without pipes right after a table, which the Markdown parser takes as one more row, is shown after the table as text.
- **Tables in a fence.** In an answer, a ` ```md ` or ` ```markdown ` fence that holds a table is shown as the Markdown it holds, not as code. Other fences stay code, and so does a Markdown fence without a table.
- **Links.** A web link shows its text in the link style, as a terminal hyperlink (OSC 8) to its address, which a click in the terminal opens. On a terminal known to open such links (below) the text is all that shows: `docs`. On any other, and under a multiplexer, the address follows it, linked too: `docs (https://example.com/docs)`; a link whose text shows nothing shows its address everywhere. A web address written bare in the text (`https://example.com/a`, not in code) takes the link style and is linked the same way. Only an `http` or `https` address with a host, at most 8 KiB, becomes a hyperlink, its control characters removed. A link to a local file shows its text and the file's path, relative to the session's working directory when the file is under it, its location as `:line:column`: `the parser (src/parse.rs:12:3)`; with no text, the path alone. It is not a hyperlink, nor is any other link (`mailto:` and the like), which shows its text and its destination. Thinking shows its links as text, each with its address.
- **Long addresses.** A web address is kept whole on a row when it fits there, moved to the next row rather than split. One wider than the conversation is cut at the edge of each row, as the terminal would wrap it, and each piece opens the whole address. In a table cell an address wraps within its column. The interface's selection copies, and its find bar searches, the text shown: where the address is hidden, `/raw` shows the Markdown with its addresses.
- **Math.** TeX math shows in Unicode notation, as in Codex. Inline between `$…$` or `\(…\)`: `$\alpha^2 + \beta_{10}$` shows `α² + β₁₀`, `$\sqrt{x}$` shows `√(x)`, `$\frac{a}{b}$` shows `((a)/(b))`. As a display between `$$…$$` or `\[…\]` standing on lines of their own, over several rows where it needs them: a fraction as its numerator over a bar over its denominator, a sum's or an integral's limits above and below it, `aligned` equations in columns, a `pmatrix` in tall parentheses, `\boxed` in a frame. Greek letters, operators, relations, arrows, set and logic symbols, `\mathbb`, `\mathcal`, accents, `\text`, `\left`/`\right` delimiters and the characters that have a Unicode superscript or subscript are converted; another script is written out (`x_{gpt}`). A formula is shown as its source, wrapped like text, when it uses a command the converter does not know (`\unknown`, `\sqrt[3]`, `matrix`), when a display is wider than the conversation less four columns, or when a display of several rows is inside a list or a quote. Math in code, in a link or in HTML stays as it is; so does a ` ```latex ` fence, which is code. A formula is never linked or styled as an address.
- **Dollar signs that stay text.** A single `$` starts a formula only when it is not escaped (`\$`) and not followed by a space, `(` or `{` (`$(cmd)`, `${HOME}`), and a closing `$` follows on the same line, within 4 KiB, not after a space and not followed by a letter or a digit (`$5 and $10`, `$HOME/$USER`, `$x=$y`); a number without an operator (`($5) or ($10)`) and an upper-case word (`$USD$`) are not formulas either. A CJK character counts as a letter: `公式 $x^2$ 很` is math, `公式$x^2$很` is not (`\(x^2\)` is math anywhere). `$$` and `\[` open a display only with nothing before them on their line, a list marker or a quote's `>` included (`echo $$` and `- $$x$$` stay text), and a display of several lines whose closer has text after it on its line is not one. These are Codex's rules, with their limits: a closing `$` followed by punctuation makes a formula of text such as `s/^a$/b$/` (shown `s/^a/b/`); a `$$` after text pairs with the next `$$` that is not at a line's start, within 4 KiB, and a formula between the two is shown as written; a line that starts with `$$` or `\[` and is never closed shows the rest of the answer as written; and `\(…\)` and `\[…\]` have no guard, so Markdown's escaped parentheses and brackets are math too: `f\(x\)` shows `fx`, `s/\(a\)\(b\)/\2\1/` shows `s/ab/\2\1/`, a line `\[note\]` shows `note`, and an empty `foo\(\)` keeps its backslashes, where Markdown alone shows the parentheses and brackets (with math off they keep their backslashes). In code (`` `…` ``) none of this happens.
- **Diagrams.** A closed ` ```mermaid ` fence is drawn as a text diagram with box-drawing characters, as in Codex, when it is one of the subsets Codex draws: a flowchart (`flowchart` or `graph`, top-down unless it says `LR`, `RL` or `BT`; rectangles `A[…]`, decisions `A{…}` shown with `◇`, stadiums `A([…])` with rounded corners, `<br>` in a node's label; solid, dashed and two-way edges with their labels; `&` groups, chains and loops); a sequence diagram (`participant` and `actor`, aliases, the arrows `->`, `->>`, `-->`, `-->>`, `-x` and `--x`, messages to oneself, `Note over` one or two participants, `loop`, `alt` with one `else`, `opt`, `critical` and `break`, nested); a flat state diagram (`stateDiagram-v2` or `stateDiagram`, `[*]` as start and end, labelled transitions, descriptions); a class diagram (members, inheritance, composition, aggregation, association, dependency and realization, cardinalities, labels); or an entity-relationship diagram (attributes with `PK`, `FK`, `UK` and a comment, the four cardinalities). The nodes stand one after another in the diagram's direction and every edge has a lane of its own, so lines never merge; a crossing is `╪`. Boxes take the syntax theme's type color and lines its comment color. A CJK character or an emoji in a label counts two columns. Nothing in a diagram is linked or styled as an address.
- **Diagrams that stay code.** A fence that cannot be drawn shows a dim line saying why, then its code as any code block shows it: another kind of diagram (`pie`, `gantt`, `gitGraph`, `mindmap`, …); syntax outside the subset (subgraphs, other node shapes, styles, `click`, directives such as `%%{init: …}%%`, HTML other than a node label's `<br>`, entities such as `&amp;`, combining or zero-width characters, identifiers that are not ASCII); or a diagram past a limit: a source over 16 KiB, more than 16 nodes, 24 edges (each `&` expanded) or 16 members in a node, more than 8 participants, 64 events or 4 nested fragments, a label line over 40 columns, or a drawing over 65,536 cells, whatever the width. A drawing wider than the conversation, less a list's or a quote's indent, shows the line `This Mermaid diagram doesn't fit the current terminal width.` and the code. A fence the answer never closes shows its code with no notice; an empty one shows nothing.

For example, this fence in an answer:

```text
flowchart TD
    A[Request] --> B{Valid?}
    B -->|yes| C[Reply]
    B -->|no| A
```

is drawn at 40 columns as:

```text
┌──────────┐
│ Request  │
│          ├────────┐
│          ├◄───────╪───┐
└──────────┘        │   │
                    │   │
                    │   │
┌──────────┐        │   │
│ ◇ Valid? │        │   │
│          ├◄───────┘   │
│          ├──yes─────┐ │
│          ├──no──────╪─┘
└──────────┘          │
                      │
                      │
┌──────────┐          │
│ Reply    │          │
│          ├◄─────────┘
└──────────┘
```

Each edge leaves its source at `├` and enters its target at `├◄`; its label is written where it leaves. The same diagram with `flowchart LR` is laid out left to right, 41 columns wide, so at 40 columns it shows the notice and the code instead.

While an answer or a plan streams, it shows as it arrives, as in Codex:

- Each line is rendered once its newline has come. Its rows are then committed, one per frame, or all of them at once when they pile up (eight rows waiting, or one waiting 120 ms); a row committed never changes.
- What a later line may still change stays after the committed rows and is drawn again as lines arrive: a table from its header on, until a block follows it (each row that arrives lays the table out again, and a row shows once its line is complete); a ` ```md ` fence, shown as code until it closes, then as the table it holds or still as code; a list item's marker alone on its line (its text may come on the marker's row); a line ending with a link to a local file, which a `: description` line joins. In Scrollback this part stays in the tail and is written into the scrollback only once committed.
- The line still arriving is shown as it grows (its last 8 KiB at most), outside a table or a fence; a link shows `[its text]` until its address is complete.
- A display formula shows as its source while it arrives, from its opening line on, and stays after the committed rows until its closer comes; then it is laid out. The line still arriving inside it shows as its source, wrapped, and so does a line that opens a display (`$$\frac{1}{2}$$`) until its newline. An answer that ends, or is interrupted, before the closer keeps the formula's source.
- A fenced code block is highlighted a line at a time as it arrives.
- A ` ```mermaid ` fence shows as code while it arrives, highlighted a line at a time, and stays after the committed rows; its closing fence turns it into its diagram (or its notice and code), which stays there until another block starts, so a resize meanwhile can still change it. An answer that ends, or is interrupted, inside the fence keeps its code.
- In Fullscreen and in the transcript a list streams without blank lines between its items; once the answer has ended it is spaced as above, so an answer whose list has an item of several rows gains rows then.
- When the answer ends, its rows give way to the answer laid out from its Markdown. When a committed row differs from it (a `===` line making the line above a heading, a link's definition arriving after its use, a resize), Scrollback writes the conversation again once more.

An answer and a plan keep their Markdown and are laid out for the width they are shown at: after a resize, a table goes from its columns to records or back, a display formula to its source or back, a diagram to its notice and code or back, and lists, prose and code wrap for the new width, in Fullscreen, in the transcript and in Scrollback's rewrite ([Reading the conversation](#reading)). While one streams, a resize lays out what it has not committed at the new width; the rows it committed keep the old width until it ends, when they give way to the answer laid out from its Markdown. A resumed session's answers and plans are laid out from their Markdown from the start. A selection or a search match keeps the rows it was made on, wrapped for the new width, until it ends.

A command's output keeps the colours and attributes its program printed, as in Codex, in its entry while it runs, once it finished and in a resumed session, for a command the model ran and a `!` command alike:

- **What is kept.** The foreground and background colours, bold, dim, italic, underline and reverse video of the program's SGR sequences (`ESC [ … m`). The 16 basic colours are your terminal's own, so they follow its theme; the 256-colour palette and 24-bit colour are passed on as they are. Blink, hidden text, strike-through, overline and underline colours are dropped, the text shown plain.
- **What is never kept.** Every other sequence is applied to the text or dropped as before (carriage returns, moves along a line and erases; cursor movement elsewhere, titles, hyperlinks, clipboard writes, screen switches and the rest), and only styles reach the screen: output cannot move the cursor, change the title, write the clipboard or leave a colour on past its own text.
- **Where it shows.** Collapsed, the last rows are dimmed in their colours; expanded and in the [transcript](#transcript), a wrapped row keeps them. A style goes on from line to line, as in a terminal, until the program resets it, and starts plain again after output that was skipped (the `…` row while it streams, `[… N bytes omitted …]` in the result). `/raw`, the clipboard, the find bar and the export see the text alone.
- **When there is any.** Commands run with `NO_COLOR=1` and `TERM=dumb` ([Environment](/docs/environment#commands)), so most programs print no colour; one that forces it (`ls --color=always`, `cargo --color=always`, `grep --color=always`) or writes its sequences regardless shows it. In a pseudo-terminal the colours are those of the screen's cells, read after the screen applied every sequence, so a repaint in Windows's ConPTY sequences keeps the colours it draws. The model never reads them: what it gets is the plain text.

Four settings turn these off, for what is shown from then on and for an answer or a plan laid out again after a resize (the [settings center](#config)'s Interface tab, or `config set`):

- `tui.rendering.tables = false` shows a table, and a ` ```md ` fence that holds one, as its source.
- `tui.rendering.lists = false` shows `-` and `[ ]`/`[x]` as written.
- `tui.rendering.math = false` shows each formula as written, its delimiters and TeX included. Formulas are still found by the rules above, so their backslashes, `*` and `_` are not read as Markdown: `\(x^{2}\)` keeps its backslashes, which Markdown alone would take away. A display still open while an answer streams is held as above.
- `tui.rendering.mermaid = false` shows a ` ```mermaid ` fence as the code block it is, with no notice, and lets it stream as any code block.

A tool's other output and a patch's diff are laid out as in Codex:

- **JSON.** A tool's text that is one JSON value (an MCP tool's result, a plugin's) shows on one line collapsed, a space after each `:` and `,`: `{"name": "ratatui", "versions": ["0.29", "0.30"]}`. Expanded and in the [transcript](#transcript) it is indented by two spaces, a value per line. Its keys keep their order, and its numbers and escapes their spelling. A text that is not one JSON value, and JSON over 1 MiB or nested deeper than 128 levels, shows as it came; so does every text in `/raw`.
- **Items.** A tool's output shows item by item: an image or an audio clip as its media type and size (`image/png · 33.2 KiB`), never its data; a link as `link: URI`; an embedded resource as `embedded resource: URI`, then its text, or its media type and size when it is binary. A line break or an escape sequence a server puts in such a field is not shown.
- **Diffs.** A patch's expanded diff has a row per line: its number, its sign, then the line, highlighted by the file's language a chunk at a time. An added file is numbered from 1; an updated file from where each chunk landed in it, a removed line by the file before the patch and the others by the file after; a patch that did not apply, or one recorded before the Agent kept these positions, shows its updates unnumbered. A long line wraps by display width (a wide character two columns, a tab four), its continuation past the number and the sign; a long path wraps under itself.
- **Diff colours.** An added or a removed row is tinted from edge to edge: dark green or dark red (`#213A2B`, `#4A221D`) in a terminal of 24-bit colour, palette colours 22 and 52 in one of 256 ([Terminal requirements](#terminal)). With 16 colours there is no tint: the sign and a line that is not highlighted are green or red. A syntax theme that gives `markup.inserted` and `markup.deleted` (or `diff.inserted` and `diff.deleted`) a background tints with it instead. A theme's colours are made readable on the tint, and a theme's 24-bit colours do not show in a diff on a terminal of 16 colours. Codex uses a light palette on a light background; the interface does not ask the terminal for its background, so the palette is the dark one, as Codex's is when the terminal does not answer.

## Syntax highlighting [#highlighting]

Fenced code in an answer (` ```rust `) is highlighted by its language: a name, an alias or a file extension. A block with no language, or in one the interface does not know, keeps its plain text. A patch's diff is highlighted by each file's extension, a chunk at a time, over its tints ([Rendering](#rendering)); `/diff`'s by each file's extension too, its `+` and `-` keeping their colors and a removed line dimmed. Code over 512 KiB or 10,000 lines, or with a line over 4 KiB, is not highlighted.

The grammars and the 32 themes are the ones [two-face](https://github.com/CosmicHorrorDev/two-face) bundles, curated from bat. `/theme` opens the [settings center](#config) at the theme's page, which lists them with the custom themes:

- Moving through the list makes the highlighted theme the one in use, shown on a sample diff: beside the list in a wide terminal, under it otherwise. Typing filters the list.
- Enter keeps the theme and saves it as `tui.theme`. Esc and Ctrl-C put back the theme in use when the list opened.
- A custom theme is a `.tmTheme` file in the `themes/` directory of the [data directory](/docs/data-directory#contents), named by its file name without `.tmTheme`. A file that cannot be read as a theme is not listed; a custom theme with a bundled theme's name is the bundled one.
- Without `tui.theme` the theme is `ansi`, which colors with the terminal's own palette and so reads on a light background as on a dark one. A `tui.theme` that names no theme, or a custom theme that cannot be read, is a [warning](#warnings), and the default is used.
- What the conversation already shows keeps the colors it was drawn with.

## The keymap [#keymap]

Each action in the table below has default keys, and `tui.keymap.CONTEXT.ACTION` changes them: one key or a list of them, `[]` to unbind the action. An action takes its context's entry, else `tui.keymap.global.ACTION` (when no global action has that name: `global.page_up` sets both `transcript.page_up` and `pager.page_up`), else its default keys.

```toml
[tui.keymap.global]
open_transcript = "ctrl-q"
leader = "ctrl-b"

[tui.keymap.chat]
toggle_thinking = ["ctrl-o", "f2"]
open_presets = "ctrl-b 1"

[tui.keymap.editor]
yank = []
```

- **Keys** are modifiers then a key, joined with `-`: `ctrl-t`, `alt-<`, `shift-enter`, `page-down`, `f3`, `space`, `minus`; an upper-case letter is `shift-` and the letter. A sign matches with or without Shift, as terminals differ; but with Ctrl or Alt, Shift on an unshifted one (`,`, `.`, `/` and the like, on a US keyboard) makes another key: `alt-shift-,` is Alt+`<`, not `alt-,`.
- **Chords** are two keys separated by a space (`ctrl-q o`): the first waits a second for the second. `leader K` is the leader key (`global.leader`, Ctrl-X by default) then `K`; the leader waits until the next key. A key that completes no chord, or Esc, drops both. A configured key that is the default leader's takes it: the leader is then unbound unless `global.leader` sets one.
- **Contexts** are where the keys are read: `global` everywhere, `chat` and `composer` while the composer has the keys, `editor` in every text field, `transcript` in the Fullscreen conversation beside the composer, `pager` in the transcript and `/diff`, `agents` in the [command center](#agents). Beside the composer, a key that types text (a letter without Ctrl or Alt) cannot be bound, and neither can a chord that starts with one; the actions read only on an empty composer (`composer.show_shortcuts`, `composer.previous_agent`, `composer.next_agent`) may take such a key, but no chord that starts with one.
- **Conflicts**: one key (or chord) cannot trigger two actions read together, nor start another action's chord, nor be Ctrl-C (or Ctrl-D but in the editor and the pagers), which the interface keeps. The pairs that share keys by default stay allowed: `chat.interrupt_turn` and `chat.edit_previous` (Esc), `composer.submit` and `editor.insert_newline` (Enter), the history and the editor's Up and Down, `global.open_transcript` and `pager.close_transcript`, `composer.previous_agent` and `editor.move_word_left` (Alt+Left), `composer.next_agent` and `editor.move_word_right` (Alt+Right).
- What cannot be used (an unknown context or action, a key that is not one, a conflict) leaves the action its default keys, with a [warning](#warnings).

`/keymap` opens the [settings center](#config) at the keymap's page, which lists the actions with their keys (type to search). Picking one offers to replace its keys or add one (a key, two keys, or the leader and a key), to remove one, to unbind it, and to put its defaults back. A new key is captured as it is pressed (Esc cancels); one that conflicts is refused with the reason, and another can be tried. A change is saved into `tui.keymap` and applies at once. `/keymap debug` lists every action's keys, each marked `default` or `configured`.

Popups, lists, forms, approvals and questions keep their own keys (arrows, Enter, Esc, Tab), and so do a selection, a search and select mode in the conversation, browsing the earlier messages, and the history search (Up, Down, Ctrl-S, Enter, Esc).

## Presets [#presets]

A preset is an input kept in a slot from 0 to 9 (`tui.presets."N"`), with an optional label: run, it goes through the slash commands as if typed and sent, so it is a message or a command such as `/status` or `/statusline git-branch --colors`. Its input cannot be empty, longer than 8,000 bytes, or start with `!`.

`/presets` (or Ctrl-X P) opens the [settings center](#config) at the presets' page, which lists the slots; a preset run closes the center first:

| Key     | Does                                                                                                                                         |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `0`–`9` | Runs that slot's preset                                                                                                                      |
| Enter   | Runs the selected one                                                                                                                        |
| `n`     | A new preset: its slot (the first free one), input and label                                                                                 |
| `s`     | A new preset from the current settings: the session's `/permissions …`, the terminal title's `/title …` or the status line's `/statusline …` |
| `e`     | Edits the selected one                                                                                                                       |
| `d`     | Deletes the selected one, after `y`                                                                                                          |

`/model` takes no model in this interface, so the model cannot be a preset. A preset that a profile, the project's file or `-c` sets wins over the user's file: saving into its slot says so.

## Settings [#config]

`/config` opens the settings center over the whole screen (the alternate screen in Scrollback), after Codex's `/config`: every setting the Agent has, read from its [settings catalog](/docs/architecture#settings-catalog), in tabs (General, Model, Tools, Memory, Context, Network, Interface, Plugins, Advanced; a tab shows how many of its values have an issue). Each row is label · value · description: `[x] On` or `[ ] Off`, a choice's label, a number, a text (`(empty)` when it is empty), a list's items (`(none)`), `••••` for a secret that is set, `(unset)`, and a dim `· profile NAME`, `· project` or `· -c` when a layer above your `config.toml` sets it. A value a layer could not use shows why in place of its description. Under the title, `Changes save automatically`, or what the last change did: `Saved`, `Saved · the project layer overrides it` (or `the profile NAME layer`, `the -c layer`), `Saved · applies at next launch`, `Saved · applies from the next session`, `Could not save: …`. While a change is written it says `Saving…`, and while an action runs, the action (`List models…`, `Add a Provider…`). The bottom line names what the selected row's keys do. Under 45 columns of description, the selected row's description moves below the list.

- **Left** and **Right** switch tabs; Up, Down, Page Up, Page Down, Home and End move; Esc goes back, and closes the center from the tabs.
- **`/`** searches every tab: setting, collection, record and page labels, keys, values, keywords and summaries. A result shows its tab and section as its description. Enter leaves the query for the results, and Esc clears it.
- **A boolean** is saved at once with Enter or Space. **A choice** opens its values, the current one marked `(current)` and a value that cannot be chosen dimmed with why; choosing one saves it. **A choice or a text** (the model policy's reasoning effort) opens its values, then Default (unset) and Custom, which edits it in its row as a text is ([Reasoning effort](#effort)). **A text, a number or a path** is edited in its row: Enter checks it as the write does and saves it, and a refusal stays in the editor with the reason (Esc cancels). **A list of texts** opens as a list: Enter edits an item or adds one, `d` removes one, and each change is saved. The settings that are saved together (the web search provider and its URL) open as a small form with a Save.
- **`r`** resets the selected setting: it is removed from your `config.toml`, and the layer below (or the default) applies again.
- **A collection** (Providers, model overrides, the model policy, MCP servers, MCP secrets, the plugins' MCP servers, plugins, installed plugins, marketplaces, hooks, roles; standalone, profiles and projects) opens its records, each with its state and summary, and what could not be read of it above them. Enter opens a record as a form of its fields, each saved as it is changed; a field the record refused stays marked `unsaved` and goes with the next change (an MCP server's transport, then its URL). `r` on a field of a record unsets it (a profile's key, a model's window, a plugin's server back to the plugin's tools). The form's other rows are the record's actions (Make default, List models, Connect, Update, Trust, Delete…); some, such as Delete and Trust, ask first. `a` adds a record (a form saved by its Add, its fields starting from what the add writes; the MCP servers, model overrides, profiles, projects and roles are named in it, an installed plugin by `PLUGIN@MARKETPLACE` or its directory), `d` deletes the selected one after asking. A secret is never shown: `••••` says it is set, and typing one replaces it. A record written elsewhere (a role of a role file, a profile or a plugin, a built-in role) is shown with where; a hook's definition is its summary, written in its file. A write over `providers.toml` or `mcp.toml` that another change overtook is refused: the records are read again and your change stays to be saved again. The model policy, a collection of one record, opens as its form.
- **Pages**: the syntax theme, the status line and the terminal title rows open the theme picker and the two setups, and the Keymap and Presets rows (Interface), Plugin browser (Plugins), Hook review (Tools) and Memory store (Memory) open the keymap, the presets, the plugin browser, the hooks browser and the memory's status, contribution and reset. A Provider's **Choose the model** and an MCP server's **Log in** are pages of their record. Esc returns to the row that opened them. What a page saves (a key bound, a preset, a theme) is said under the title too. These pages are only in the center: the commands that had them open the center at them.
- **The pointer**: the wheel moves the selection, a click on a tab shows it, a click on a row selects it, and a click on the selected row does what Enter does.

`/config TARGET` opens the center at a tab (`memory`), a section (`web`, `compaction`, `tui`, `pluginOptions.subagents`), a collection (`providers`, `providerModels`, `modelPolicy`, `mcp`, `mcpSecrets`, `pluginMcp`, `packages`, `roles`) or a page (`theme`, `statusline`, `title`, `keymap`, `presets`, `plugin-browser`, `hook-review`, `memory-store`). The commands are shortcuts to it: `/providers` is `/config providers` (`policy`: `modelPolicy`), `/mcp` is `/config mcp`, `/plugins` `plugin-browser`, `/hooks` `hook-review`, `/memories` `memory`, `/tui` `tui`, and `/theme`, `/statusline`, `/title`, `/keymap` and `/presets` their own page. Every write is made off the interface's loop, one at a time; the center never waits for it. The layers are no longer a page: each row names the layer that sets it, profiles and projects are collections, and [`/warnings`](#warnings) keeps what the layers could not use. The session's role is [`/role`](#role)'s. A target that names none of them says there is no such settings page. `config set` is the command-line equivalent for one key.

## Warnings [#warnings]

What the interface or the Agent could not use as configured is kept for the run, and `/warnings` lists it, newest first, each once, counted by source:

- **configuration**: what reading `config.toml`, `providers.toml` and `mcp.toml` had to repair ([Configuration recovery](/docs/recovery)), and what a layer of `config.toml` holds that the settings cannot use: an unknown key, or a value the layer below replaces;
- **roles**: what reading the [roles](/docs/roles#issues) left out, a role defined twice in one source, and each role that cannot be used, with why;
- **plugins**: a plugin that failed, or that is left out of turns;
- **installed plugins**: what an [installed plugin](#plugins) could not use: a manifest field, a component, what its [roles](/docs/roles#plugins) leave out, an MCP server that gives way to another of its name; a plugin whose code failed (its fourth failure within 10 minutes, or a start that failed) until it is retried, and what its code left out;
- **MCP**: a server's latest error or warning, and what reading `mcp.toml` repaired;
- **hooks**: the hooks' configuration problems;
- **panics**: the internal errors the Agent caught;
- **compaction**: a compaction a turn ran that failed ([above](#reading));
- **interface**: a command turned off after an internal error, a theme or an item of `[tui]` it does not know, a keymap entry it could not use.

When there are any at launch, one line says how many (`2 warnings: /warnings`). In the list, `c` copies the selected warning and `d` dismisses it for the rest of the run. With none, `/warnings` says `No warnings.`

## Updates [#updates]

When the interface starts (`hanafubuki-agent` and `hanafubuki-agent resume`; never `exec` or the other commands, and never without a terminal), the command line asks GitHub in the background whether a newer release exists, at most once every 20 hours; the interface does not wait for the answer. A newer release shows on the right of the [footer](#layout)'s row for the rest of the run:

```text
  gpt-5.1 high · ~/src/project · Fix the footer          Update available: 0.3.0 · hanafubuki-agent update
```

- On a narrower row it is shortened to `Update available: 0.3.0`, and left out when even that does not fit beside the row's own content: the status line and the hints are never cut for it, and it adds no row. The shortcuts (`?`), the history search, the external editor's line and the command and file lists take the row without it.
- A release an earlier launch found shows from the first frame; one this launch's check finds shows as soon as the answer comes, without moving the composer. It is shown in a side conversation too.
- The command after it depends on how this copy was installed: `hanafubuki-agent update` for a released binary, `cargo install --locked hanafubuki-agent-cli` for one `cargo install` put in place, and `hanafubuki-agent update --check` otherwise, which says what to do ([update](/docs/cli-reference#update)).
- Only a stable release counts, and only one newer than this version. A check that fails (no network, GitHub's rate limit, an answer it does not read) shows nothing and is made again at the next launch. A build from a checkout (`target/debug`, `target/release`, or `cargo install --path`) never checks.
- The answer is kept in [`update-check.json`](/docs/data-directory#contents).

### The prompt at launch [#update-prompt]

When the release an earlier check found is newer than this version, the next launch asks first, before the Agent starts: nothing of it runs yet, so no lock is taken and no plugin holds the executable an update replaces. The screen is Codex's:

```text

  Update available · 0.2.0 → 0.3.0
  Release notes: https://github.com/licyk/hanafubuki-agent/releases/tag/v0.3.0

› 1. Update now (downloads 0.3.0 and replaces this executable)
  2. Skip
  3. Skip until next version

  enter continue · esc skip
```

- **Update now** runs [`hanafubuki-agent update`](/docs/cli-reference#update) in the terminal: the screen is cleared, the latest release is looked up again (it may be newer than the one shown, and `GITHUB_TOKEN` is sent to that lookup as `update` sends it), its lines are printed, and the program ends; start it again to run the new version. When the update fails, the error says what was kept, the executable is as it was, the program ends with exit code 1, and the next launch asks again. For a copy `cargo install` put in place, on Linux and macOS, the option reads ``Update now (runs `cargo install --locked hanafubuki-agent-cli`)``, with `--root` when it was installed elsewhere, and runs cargo.
- **Skip** starts the interface; the next launch asks again.
- **Skip until next version** starts the interface and does not ask again until a newer release is found; the version is kept in `update-check.json` as `dismissedVersion`. The footer's notice still shows it.
- Up or `k` and Down or `j` move the highlight, wrapping around; Enter chooses it; `1`, `2` and `3` choose at once; Esc, Ctrl+C and Ctrl+D are Skip. What was typed before the screen appeared is dropped, so an Enter pressed while the program started never chooses Update now.
- It is shown on `hanafubuki-agent` and on `hanafubuki-agent resume`, but not when a prompt was given on the command line (`hanafubuki-agent "fix the tests"`, `resume ID PROMPT`), not when the check is off, never in `exec` or without a terminal, and not for a build from a checkout. Nor is it shown when this copy cannot be updated from here (a directory you cannot write, a platform without a released binary, a cargo installation on Windows): the notice names the step instead.
- It takes the whole screen in both presentations and is cleared once a choice is made, before the interface starts; nothing of it is left in the scrollback. A narrow or short window wraps it and keeps the highlighted option and the keys' line in view, down to about 20 columns and 4 rows; the blank rows, then the heading and the release notes give way first.
- Two windows started at once may both ask. When both choose Update now, the second finds the executable updated and says so (`… is already 0.3.0 (another process updated it).`).
- On Windows the launch also removes the executables earlier updates set aside (`hanafubuki-agent.exe.NUMBER.outdated`) that no program runs any more, whether the check is on or not.

What the check sends: one HTTPS request, `GET https://api.github.com/repos/licyk/hanafubuki-agent/releases/latest`, with `Accept: application/vnd.github+json` and `User-Agent: hanafubuki-agent/VERSION` (this copy's version), through [`network.proxy`](/docs/network-logging#proxy-scope). No token, cookie or identifier is sent (not even `GITHUB_TOKEN`), and nothing of your configuration, sessions or projects; GitHub sees the request's address and the version, as it would a download. A failure is logged at `debug` as its kind alone.

Turn it off with `tui.checkForUpdates = false` ([Configuration reference](/docs/config-reference#tui)) or by setting `HANAFUBUKI_AGENT_NO_UPDATE_CHECK` to any non-empty value ([Environment](/docs/environment#read)): then nothing is sent and neither the notice nor the prompt is shown, not even for a release an earlier check found. Either applies at the next launch.

## Terminal requirements [#terminal]

- The terminal must answer the cursor-position query, or the interface cannot start.
- Only the basic ANSI colours, bold, dim and italic are used, and OSC 8 hyperlinks for web links, each closed before the cursor moves on; a terminal that does not know OSC 8 shows the text without them. A command's output also shows the colours and attributes it was printed in ([Rendering](#rendering)): 256-colour and 24-bit colour, underline and reverse video among them, which a terminal without them shows as it can.
- A diff's tints ([Rendering](#rendering)) follow the terminal's colour depth, read from the environment as Codex reads it: 24-bit with `COLORTERM=truecolor` or `24bit`, a `TERM` ending in `direct` or `truecolor`, or iTerm2; 256 colours with a `TERM` ending in `256color` (or `256`) or Apple Terminal; 16 colours otherwise, and when stdout is not a terminal, `TERM=dumb` or `NO_COLOR` is set. `FORCE_COLOR` (`1` to `3`) or `CLICOLOR_FORCE` sets it. Windows Terminal (`WT_SESSION`) counts as 24-bit unless `FORCE_COLOR` is set.
- Whether a web link shows its text alone depends on the terminal, told by its environment at launch (`TERM_PROGRAM`, `WT_SESSION`, `VTE_VERSION`, `TERM` and the other variables Codex reads, in its order), with no setting. Ghostty, iTerm2, WezTerm, Rex, kitty, Visual Studio Code's terminal, Alacritty, Windows Terminal, Konsole, GNOME Terminal and the other VTE terminals show the text alone. Terminal.app, Warp, the Windows console, a terminal not recognised, `TERM=dumb`, tmux, Zellij and GNU screen (also when `TERM` starts with `screen` or `tmux`) keep the address after the text, as does output that is not a terminal.
- A click opens a link the way the terminal opens one, often with Ctrl or Cmd held. Fullscreen captures the mouse, so the terminal sees the click only with its bypass held, usually Shift, as for its own selection; a click the interface takes does what it does there (a selection, a disclosure control) and opens nothing. The interface opens no link itself.
- Fullscreen uses the alternate screen and the mouse (SGR reporting).
- In Scrollback, the pagers and the resume picker use the alternate screen, where the mouse wheel acts as the arrow keys; the transcript captures the mouse for its selection and its controls. Outside them, Scrollback captures clicks and the wheel (SGR reporting; on Windows the console's mouse input, which turns Quick Edit off while held) only while the tail shows a control, until the first turn of the wheel (`tui.scrollbackMouse`).
