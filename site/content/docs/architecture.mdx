## 目标 [#goals]

Agent 是一个**内核**（`hanafubuki-agent-kernel`），拥有会话、轮次、历史和每个步骤的快照；能力由 [kardia](https://github.com/licyk/kardia) 上的**插件**提供。内核只通过 `hanafubuki-agent-contracts` 中的注册表接触插件。设计服务于三个目标：

- **故障隔离。** 故障限制在它的所有者之内：工具调用失败是模型可见的错误；插件故障停止并重启那个插件；MCP 服务器故障让那台服务器进入 `Failed` 再重新连接。只有内核故障才会重建整个 Agent，而 Agent 失败从不让宿主应用停止。
- **可扩展。** 新能力是一个插件加一行清单；内核、契约和前端都不用改。
- **固定模型看到的内容。** golden 测试记录每个模型可见的面；模型能看到的变化要有意地重新生成它们。

## crate 与分层 [#crates-and-layers]

依赖只向下指。`cargo xtask check-dependencies` 按层表（`xtask/src/dependencies.rs` 的 `LAYERS`）检查每个成员只依赖它那一行允许的成员。

| 层         | crate                                                                                                                                                    | 作用                                                                                                                                       |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 中性机制   | `foundation`、`tool-contracts`、`process`、`runtime`、`host`                                                                                             | 路径、取消、阻塞边界、panic 隔离；工具规格类型；进程所有权；被隔离的 Tokio 运行时；通用模块宿主（注册表、租约、故障、重启策略）            |
| 领域       | `approval`、`skills`、`web-search`、`model-api`、`workspace-fs`、`execution`、`mcp`、`memory`、`worktree`、`hooks`、`sandbox`、`compression`、`packages` | 各自独立、可单独测试的能力                                                                                                                 |
| 插件 API   | `contracts`                                                                                                                                              | 注册表与扩展点契约；重新导出 `host` 的注册与故障机制，插件只依赖它                                                                         |
| 内核与历史 | `kernel`、`history`                                                                                                                                      | 会话、轮次循环、工具规划与流水线、请求组装、世界状态、压缩与分层压缩、审批流程、恢复；JSONL 历史与 SQLite 索引                             |
| 插件       | `plugin-web`、`plugin-workspace-fs`、`plugin-execution`、`plugin-mcp`、`plugin-worktree`、`plugin-hooks`、`plugin-packages`                              | 每个把一个领域 crate 绑定到扩展点，或作为服务提供给门面的调用；`plugin-packages` 是访客宿主，在进程外或以 WebAssembly 运行已安装插件的代码 |
| 配置       | `config`                                                                                                                                                 | Agent 自己的配置（`AgentConfig`）：三个 TOML 文件，独立模式下分层                                                                          |
| 门面       | `hanafubuki-agent`（`crates/agent`）                                                                                                                     | 组合：插件宿主与清单、Agent 自己的插件、槽位、服务 API、宿主接口、独立运行时、数据目录锁、日志                                             |
| 界面       | `tui`、`cli`                                                                                                                                             | 终端界面（只依赖门面）和 `hanafubuki-agent` 二进制（依赖门面与终端界面）                                                                   |

（表中省略了 `hanafubuki-agent-` 前缀。）除了层表，检查还执行与表无关的规则：不依赖任何 Hanafubuki crate（任何来源）；内核不依赖任何插件；插件依赖插件 API，不依赖内核、门面或其他插件；每个插件 crate 都是门面的依赖（门面挂载它）；只有门面依赖配置 crate；`host` 只依赖 `foundation`；kardia 只出现在 `host`、插件 API、内核、插件和门面中，它的加载器和访客桥（`kardia-loader`、`kardia-hmr`）只出现在访客宿主（`plugin-packages`）中，而且从不使用 `kardia` 门面 crate（它带有 WASM/dylib 热重载）。

三条边界承载了大部分设计：

- **内核和插件只在契约中相遇。** 内核不依赖插件，插件不依赖内核、组合或其他插件。内核不注入任何插件可以替换的东西，所以替换插件从不重启内核，也不丢失会话。
- **模型 API 只是线路。** 它把 `ModelInputItem::ContextFragment { role, kind, content }` 原样发送，`kind` 只是标签。段的包装文字属于拥有它的插件；`check-model-api-context` 检查模型 API 的源码不出现任何上下文段类型。
- **Agent 不知道宿主的领域。** 宿主的东西（在 Hanafubuki 里是实例、任务中心、界面上下文、它那部分指令）通过宿主接口到达 Agent。

## 插件宿主 [#the-plugin-host]

```text
宿主（例如 Hanafubuki 的模块宿主）
└── AgentSlot                 每次启动的运行时、内核故障重启、崩溃循环停止
    └── AgentHost = ModuleHost<AgentPlugins>
        ├── Core:       agent-host-services（BlockingService）
        │               agent-kernel（发布 AgentKernelRegistries）
        ├── Capability: web、workspace-fs、view-image、execution、mcp、memory、skills、titles、
        │               recap、goal、subagents、worktree、hooks
        ├── 宿主行:     Hanafubuki 的 tasks、instances（Capability）、ui-context（Context）
        └── Context:    workspace-context、permission-mode
```

- **`AgentSlot`** 保存 Agent 的状态（`Disabled`、`Starting`、`Running`、`Faulted`、`Stopping`、`Failed`、`Stopped`）并监督它：每次启动构建自己的被隔离运行时，构造并恢复服务，启动插件，然后在后台连接 MCP 服务器。持有者每次调用时重新解析槽位，所以没有旧的 Agent 能被继续访问。
- **`AgentHost`** 是通用 `ModuleHost` 的 Agent 配置：两个核心行，然后是清单（`host/manifest.rs`）中每个启用的行，宿主的行在其中；每行在前一行就绪或超时（`PLUGIN_START_TIMEOUT`，20 秒）后挂载。配置从 Agent 的设置和宿主的代理派生，启用状态来自 `disabledPlugins`。
- **注册表在运行时启动前由内核创建**，`agent-kernel` 插件发布它们；插件注入并注册条目。共十个：工具、工具源、上下文贡献者、上下文渲染器、轮次准入、提示贡献者、审批规则、继续钩子、工具生命周期钩子、观察者。内核在固定的时刻读取每个注册表的快照（每个采样步骤、每个请求、轮次准入、提交之后）。
- **注册是调用者的副作用。** 条目属于注册它的插件并随它离开：停止中的插件先把条目从新快照中隐藏，等待租用中的调用（`DRAIN_GRACE`），再取消它们。无法接受的注册（重复的 ID、保留或冲突的工具名、同一类型的第二个贡献者或渲染器）让注册的插件启动失败，不影响任何轮次。

### 故障 [#faults]

三类所有者，三种结果：

| 故障                       | 由谁捕获                                                                                                       | 结果                                                                                                                                                 |
| -------------------------- | -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 插件代码 panic             | 内核调用插件时的守卫（`RegistryEntry::guard`、`PluginFaults::guard`）；kardia 守卫 `apply`、effect 与 disposer | 那次调用自己的错误路径；插件的 `PluginFault`；宿主停止插件，按 `RestartPolicy` 重新挂载（2 秒、10 秒、30 秒，10 分钟内三次，之后 `failed` 直到重试） |
| 功能调用 panic             | 门面功能辅助函数（`AgentApplicationService::feature`）中的 `PluginFaults::guard_async`                         | 该调用返回 `FeatureUnavailable`；提供该功能的行的 `PluginFault`，宿主像上面一样停止并重新挂载它；其他功能和 Agent 继续运行                           |
| MCP 服务器的工具调用 panic | `McpTool::invoke` 中的 `catch_panic_async`                                                                     | 那次调用的“internal error”；那台服务器 `Failed` 并重连；`mcp` 插件和其他服务器继续运行                                                               |
| 内核代码 panic             | 轮次任务、命令守卫、Agent 的工作线程组、宿主任务（`spawn_kernel_task`）                                        | 报告给实例的 `AgentKernelFaultSink`；槽位把 Agent 标为 `Faulted`，停止它，2 秒、10 秒、30 秒后启动新实例，从磁盘重建会话                             |

**功能插件失败只损失它的功能。** 门面作为调用提供的功能（概要、标题建议、工作树、钩子的列表与信任）由它的插件行提供的服务承担，每次调用时解析；该行关闭、启动中、失败或重启时，调用返回带原因的 `FeatureUnavailable`，其他一切不变（[宿主、配置与状态](/docs/plugin-rules#host-configuration-and-status)）。

**为什么内核故障要重建整个 Agent：** 锁不会中毒（全部使用 `parking_lot`），所以 panic 后什么都不会回滚，内存中的会话状态可能只改了一半；磁盘上的历史才是一致的副本。

这一切依赖展开。进程的 panic hook 只允许已知会被捕获的 panic 展开：Agent 的线程运行在被隔离的运行时（`ContainedRuntime`，线程名 `agent-rt`）和被隔离的工作线程组上，守卫也做标记。这些标记在 Agent 自己的 foundation 里，所以宿主的 hook 必须询问 `hanafubuki_agent::panic::is_panic_contained`（[panic hook 桥](/docs/embedding#the-panic-hook-bridge)）。kardia-hmr 的访客线程自己捕获 panic，并在 kardia-hmr 中标记自己；访客宿主把这个检查注册到 foundation，所以同一个函数也为它们回答。

### 启动与关闭 [#start-and-shutdown]

启动领取一个代次，构建运行时和进程所有者组，回收上一次运行留下的进程组（`process-groups.json`），在运行时的阻塞池上构造服务（构造时启动[模型发现](#model-metadata)，在后台列出默认 Provider 的模型）并运行恢复，启动插件，安排 MCP 连接（同时最多四个，各有自己的超时），然后把服务装为 `Running`。崩溃循环标记（`start-marker.json`）在三次未完成的启动后停止自动启动。关闭在 20 秒预算内按固定阶段进行：关闭槽位、停止轮次、MCP、插件（一次性释放 kardia 根）、记忆、历史与执行、进程组、运行时。插件不拥有 MCP、记忆、历史或执行的生命周期，所以它们拆除的顺序无关紧要。

## 会话与轮次 [#sessions-and-turns]

- **会话**有配置（Provider、协议、模型、指令、模式、推理强度、上下文窗口、压缩设置）、模式（`Default` 或 `Plan`）、生命周期（`Available`、`Archived`）、标题、记忆贡献模式和[角色](/docs/roles#sessions)。会话可以在某个轮次之前或在头部分叉。配置在一个地方规范化（`normalize_session_config`）：创建、每次更新和恢复时。
- **能力范围。** 会话创建时（`create_session(mode, role)`，没有角色时为 `default`）或在轮次之间切换到（`set_session_role`）的角色给它一个范围（`AgentCapabilityScope`）和该角色的指令，保存在它的配置中：之后编辑或删除角色文件不会改变已有它的会话，恢复也不读取角色文件。范围只收窄，内核在本来就取快照的地方应用它：工具计划、工具来源、上下文与轮次准入贡献者、提示贡献者、继续钩子，以及每个轮次冻结的模式；审批规则、工具生命周期钩子、观察者和渲染器始终适用（[能力范围](/docs/plugin-rules#capability-scope)）。子会话的范围是父会话的范围再被它自己的收窄；分叉保留源会话的范围。
- **谱系。** 会话在创建时记录它所在的工作区（主根目录及其 Git 分支）；如果它是子会话，还记录它的父会话和来源（`Side`、`Subagent`、`Review`）。分叉和子会话沿用来源的工作区。`create_child_session` 用父会话的模型和配置创建子会话（它的范围是父会话的范围再按请求的范围收窄，从不更宽；它的角色指令是赋予它的角色的指令，否则是父会话的），可以是空的，也可以从父会话最近的回合边界开始（它的头部，或正在运行的轮次之前的状态），并在创建时一并提交给它的上下文条目（继续上下文）。
- **临时会话**和其他会话在同一个会话表里，运行轮次的方式也完全一样，区别只在历史存储。内核的存储是 `SessionStores`：它按会话 ID 把每个会话的提交和读取分到持久存储，或分到内存中的 `EphemeralAgentHistoryStore`。所有 ID 都由持久存储分配，两者从不共用；会话列表和恢复只读持久存储，所以临时会话从不被列出或恢复，`close_ephemeral_session`（或进程结束）会丢弃它。它的记录只包含它自己提交的内容，而它的模型历史从继承来的内容开始；继承来的图片通过它们所属的持久会话读取。在每条提交路径上加标志会改动每一条路径；改为路由存储则一条也不用改。
- **轮次**作为托管的 Tokio 任务运行，经过 `Sampling`、`RunningTools`、`WaitingForUserInput`，以 `Completed`、`Cancelled`、`Failed` 或 `Interrupted` 结束。循环的每次迭代可能自动压缩，用冻结的工具计划对模型采样，运行工具（每个都在适用于它的工具生命周期钩子之间），消费 steering 输入，并询问继续钩子。轮次自身工作中的 panic 让轮次以 `Failed`（`InternalFailure`）结束，会话接受下一个轮次。
- **会话驱动器。** `AgentSessionDriver` 是应用驱动子会话的窄端口：创建子会话、为它命名、为它选择模型（门面的 `set_session_model` 是同一段代码）、列出父会话的子会话、把父会话的权限模式交给子会话、运行一个轮次并等待结果、引导或中断这个轮次、读取最后的回答、关闭（停止它的后台终端，临时会话则丢弃）。外观层接受的每个轮次也由它准备（会话的 Provider、权限模式、世界状态和轮次扩展），所以它运行的轮次和用户的轮次准备得一样。旁路对话和 `subagents` 插件使用它；评审插件以后也会使用它。
- **子代理。** `subagents` 插件的工具把子代理做成持久的子会话（来源 `Subagent`，标题是任务名），在 Agent 运行时上由它自己的任务用 `run_turn` 运行它的轮次，所以父会话的工具调用立即返回，`wait_agent` 只等待该任务在轮次结束时发出的通知：父会话的轮次从不占着子会话的轮次需要的东西，两者在运行时上并排运行。插件跟踪的内容（运行中的轮次、父会话还没等到的已结束轮次、留给空闲子代理下一个轮次的消息）保存在内存中，在同一个 Agent 实例内插件重启后仍然保留；子代理有哪些则从内核读取（父会话的子会话），所以之前运行留下的子代理仍会被列出、能收到消息。中断使用内核的确认取消，只有在该子代理之后没有开始新的轮次时才记录轮次的结果。子代理的角色（`spawn_agent` 的 `agent_type`）通过 `AgentRoleCatalogReader` 读取，这是应用基于它的角色目录构造的第二个窄端口，插件每次调用时读取它，所以派生看到的是当时的角色，插件自己不保留目录：子会话在一次提交中带着角色的范围和指令创建（由内核收窄范围），再通过模型选择得到角色的模型和推理强度，角色没有设置推理强度时保留父会话的。指引在每一步列出可派生的角色，且只在该步骤的计划提供 `spawn_agent` 时出现（内核的 `PromptStep.tools`），所以略去这个工具的角色也略去指引；`spawn_agent` 的描述符在注册时固定，不列出任何角色而是指向指引，所以从不过时。
- **持久化先于可见。** 每次修改先持久提交到历史，才对外可见；提交失败恢复内存状态。提交在会话单元（cell）的锁下暂存，当追加被确认时结算：发布持久化的修订号或回滚，然后才发出事件。结算在历史写入线程上的确认中运行，而不是在等待的 future 里，所以 future 被丢弃时它照样发生。
- **会话之间从不互相等待。** `SessionTable` 只在查找、插入或删除时持有它的锁；每个单元有自己的锁，只在内存中工作时持有，从不跨越 await、历史追加或其他 I/O，也从不同时持有另一个单元的锁。
- **取消**先协作，再中止任务，并在 5 秒内确认。被重启打断的轮次在恢复时变为 `Interrupted`。恢复拒绝的会话被**隔离**而不是致命：不改写也不删除它的任何文件，其他会话照常打开。
- **独立运行时工作区可以移动。** `AgentRuntime::set_working_directory` 不新建实例就改变独立模式的工作区（它的根目录在一把锁后面）：文件工具的 `WorkspaceFsPolicy` 按新的根目录重建，没有 `workdir` 的命令在新的第一个根目录中运行，所以活着的会话保持活着，每个会话在下一个轮次的 `workspace_roots` 段中看到新的根目录，不需要别的提示。有轮次、压缩或后台终端在运行时它被拒绝，因为它们都是在旧工作区中启动和批准的。配置的项目层仍是启动时读取的那一个。嵌入的宿主拥有自己的 `WorkspaceRootsPort`，所以这个调用只用于独立模式。工作树（`hanafubuki-agent-worktree`，由 `worktree` 行提供）是数据目录下的分离检出，使用者用这种方式移入其中。
- **限制**（`AgentHardLimits`）：一个轮次最多采样 32 次，超过则以 `budget_exceeded` 失败（之前的输出都已提交）；30 分钟的期限像用户取消一样取消轮次，以 `deadline_exceeded` 失败。两者都不让模型看到。内核对插件的调用若没有自己的上限（上下文、轮次准入、工具源或提示 `prepare` 的贡献，工具的 `permission`），就在 `plugin_call_deadline`（10 秒）内运行，所以挂起的内置、宿主或客体插件只损失它的贡献，从不拖住轮次（[插件调用的上限](/docs/plugin-rules#bounds-on-plugin-calls)）。

## 工具 [#tools]

### 每个步骤的计划 [#a-plan-per-step]

每个采样步骤构建一个不可变的 `AgentToolPlan`：内核的核心工具（`new_context`、`update_plan`、`request_user_input`，会话的压缩策略为 `hierarchical` 时还有五个压缩工具），注册的工具（每个处理器对这一步的 `availability`），每个工具源为这一步提供的工具，以及有工具被延迟时的 `tool_search`。随后会话的能力范围排除它不允许的每个插件工具，它关闭的插件的工具源不会被询问；被排除的工具与未知工具一样不存在，也不算遗漏（[能力范围](/docs/plugin-rules#capability-scope)）。内核自己的工具和 `tool_search` 从不被排除。计划同时冻结该步骤的审批规则快照和工具源的计划租约；调用针对宣告它的那个计划运行，租约让工具规划时依赖的东西（例如一个 MCP 连接）存活到步骤结束。计划模式只在范围保留的工具中保留 `ReadOnly` 工具、`request_user_input` 和压缩工具。

### 线路上的名字 [#names-on-the-wire]

工具在 Agent 内部的身份是 `ToolName`（命名空间段和本地名），注册表按扁平形式 `namespace__name` 索引它，这个字符串从不被反向解析。线路名按请求选择（`ProviderToolTable`）：Responses 接受命名空间，带命名空间的函数保留命名空间和本地名；其他协议使用扁平名。每个名字被适配到协议的上限（Responses 与 Anthropic Messages 为 128 字节，Chat Completions 为 64 字节）；后来者发生冲突或过长时被截断，并加上 `_` 和它 `(provider id, tool id)` 哈希的 12 位十六进制，每一步都相同。返回的调用按 `(namespace, name)` 查找解析，历史记录两者。

schema 遵循同样的按协议规则：支持 `strict_json_schema` 的协议（Responses）收到完整 schema，其他协议收到所有 OpenAI 兼容端点都接受的关键字（`portable_model_schema`）。从不发送 `strict`，内核无论如何都按完整 schema 校验参数。

**注册拒绝，规划改名。** 注册时就能拒绝的都拒绝（保留名、已注册的扁平名、过长的名字），所以只有来自外部目录的工具源工具会在规划时冲突，它们被确定性地改名，而不是让步骤失败：拒绝一个冲突的注册只让一个插件失败一次，而让步骤失败会让每个轮次都失败，直到插件被关闭。

### 暴露与延迟工具 [#exposure-and-deferred-tools]

`ToolExposure` 是 `Direct`、`Deferred`、`DirectModelOnly` 或 `Hidden`。直接目录超出预算时，只有工具源的直接工具会被延迟，并在各提供者之间公平分配。延迟的工具通过 `tool_search`（对名称、说明和 schema 的 BM25 索引）找到；搜索提交它的输出，然后提交一个 `ConversationItem::ToolSelection`。规划器接受上次压缩以来模型上下文中的选择，所以选择跨轮次有效，直到下次压缩。

### 调用流水线 [#the-call-pipeline]

内核拥有流水线，插件不能改变它的顺序：

<Steps>
  <Step>**流式接收并提交。** 响应流到结束，每个工具调用在运行之前提交到历史。</Step>
  <Step>
    **处置。**
    未知、隐藏或未被接受的名字，或无法解析、过大的参数，变成模型可见的错误输出，轮次继续。
  </Step>
  <Step>
    **参数**按工具的输入 schema 规范化（整数形式的浮点数和数字字符串变为数字，去掉不可为空的可选
    `null`，在 `additionalProperties: false` 下去掉未声明的键），再由处理器容错解码。
  </Step>
  <Step>
    **门。** 调用取得步骤的门：一个在途许可，然后对 `ConcurrentRead`
    工具取得读访问，否则取得独占访问，先到先得。在门下运行模式策略、工具源工具的 schema
    检查和处理器的
    `permission`（在插件调用期限内，超过即为工具错误），所以分类能看到同一步骤之前的调用做了什么。
  </Step>
  <Step>
    **审批路由。** 任何规则 `Deny` 就拒绝；否则任何 `RequireUser`
    就询问用户；否则会话对该工具的许可授权；否则由轮次的权限模式决定（`Manual` 询问，`AutoReview`
    询问审查模型，`FullAccess`
    允许）。等待中的决定释放门，批准后再取回，所以同一步骤的其他调用可以继续。
  </Step>
  <Step>
    **调用**在条目租约和子取消令牌下进行，受 `ToolDescriptor::timeout` 或轮次的工具空闲超时（10
    分钟）限制。`invoke` 重新检查审批与它要运行的调用一致。
  </Step>
  <Step>
    **按调用顺序提交，每个尽早提交。**
    一个输出在之前每个调用的输出都提交后提交。以错误结束的调用（包括取消）不提交；其他调用照常完成并提交，因为它们的效果已经发生。取消时只有未完成的调用得到合成的“已中断”输出。
  </Step>
</Steps>

**没有流式分派。** 调用在响应流完、其条目提交之后才开始。像 Codex 那样每个条目完成就开始调用能缩短某些步骤；提交与取消的规则写成了以后可以加上它而不必改变，但目前没有需要。

### 审批 [#approval]

`AgentPermissionMode` 是 `Manual`（默认）、`AutoReview` 或 `FullAccess`，每个轮次冻结：会话被设置了自己的模式时（`set_session_permission_mode`，与会话的许可一样只在运行时状态中）取它，否则取设置。每个工具调用由处理器的 `permission` 分类为一个 `ApprovalAction`（类型、风险等级、规范化摘要）。规则只能收紧。用户可以对 `Manual` 模式的提示回答 `AllowForSession`：之后同一工具（按 `(provider id, tool id, generation)`）在会话剩余时间内不再询问，只保存在运行时状态中，所以重启、分叉和改变了的工具都会重新询问（对 MCP 工具来说是服务器的配置、凭据或目录条目改变了；未改变的服务器重新连接后，许可仍然有效）。审批产生一次性的 `AuthorizedAction`；修改型工具在 `invoke` 中重新计算动作并要求它们完全一致。审批决定由谁允许一个命令，[沙箱](/docs/permissions#sandbox)决定它能触及什么。请求离开沙箱的动作带有 `sandbox_escalation`（它在规范化摘要中，所以沙箱内命令的批准不能让它在沙箱外运行）：`FullAccess` 拒绝它，与 Codex 的 `never` 一样；它的 `AllowForSession` 只允许同一个动作再次运行（按工具和动作的详情区分），与工具的许可分开。用户事后批准的 `AutoReview` 拒绝（`approve_denied_action`，会话最近十个被拒绝的 `PermissionReview` 条目之一，在轮次之间）成为内核的 `ContinuationContext` 说明，provider 为 `kernel`，hook 为 `approved-denied-action`：模型把它读作可信的上下文，审查证据把它作为 `user approval` 条目与用户的消息一起保留。它本身不授权任何东西，所以重试仍会再次审查；历史格式不变。

## 上下文 [#context]

### 段、槽位与渲染器 [#sections-slots-and-renderers]

模型可见、既不是历史也不是工具的所有内容都是某个 `ContextSectionKind`（一个开放的标识符，按蛇形命名持久化）的**上下文段**：

- **世界状态段**在轮次准入时由 `ContextContributor` 产生，按类型与内容的 SHA-256 定版本，只把变化作为 `WorldStateUpdate` 提交。内核每个步骤自己写 `tool_catalog_omissions`，steering 在轮次中替换它携带的宿主上下文。
- **提示片段**每个请求由 `PromptContributor` 产生：先 `prepare`（异步，每步一次，可以 I/O），再 `contribute`（纯函数）。`skills` 插件渲染 Skill 目录（`skill_catalog`），`memory` 插件渲染记忆摘要（`agent_memory`）。

段通过它类型的 `ContextRenderer` 展示给模型：一个槽位、槽位内的顺序、一个角色、前言、后记和是否带版本。**渲染器是数据**，渲染不运行插件代码，所以它不需要守卫、租约或超时，请求也不会因它失败。每一串相邻的段按槽位（`Instructions`、`WorldState`、`Capabilities`、`Memory`）排序，再按渲染器的 `order`，再按类型名；稳定的槽位在前，每步都可能变化的记忆摘要在最后，以保持缓存的前缀尽量长。顺序是显式的，按所有者分段（内核 0，Agent 的能力插件从 100 起，宿主的 500–599，Agent 的上下文插件从 700 起，已安装插件 900；[上下文渲染器](/docs/plugin-rules#context-renderers)），而不是注册顺序，所以插件重新启动不会改变请求的顺序、让提供方缓存的前缀失效，清单的顺序也不会被模型看到。

**变化检测：** 每种类型只显示最新版本，放在它最后变化的位置；更早的版本不再出现在请求中。所以没有“替换先前提供的内容”的通知，也没有段变化事件：持久化的 `WorldStateUpdate` 就是变化记录。

### AGENTS.md [#agentsmd]

`workspace-context` 插件的 `workspace_instructions` 段在每次轮次准入时读取：先读用户自己的文件（数据目录下的 `AGENTS.override.md`，否则 `AGENTS.md`），再读每个工作区根目录从根一直到宿主选中的目录中的文件，所有文件共用 32 KiB 预算，每组公平分配（每组最多 16 KiB）。因为每个轮次都重新读取并按摘要比较，会话中途的编辑会到达下一个轮次。

### 上下文窗口与 token 估算 [#the-context-window-and-the-token-estimate]

会话的 `context_window_tokens` 在创建会话或选择模型时解析，每个轮次开始时再解析一次：配置的窗口，否则[模型元数据](#model-metadata)对该模型所知的窗口（从拒绝中学到的窗口，仅在它更小时；Provider 的模型列表报告的窗口；否则一张已知模型系列的小表）；都没有就不做自动压缩。整个 Agent 只有一种 token 估算（`hanafubuki_agent_contracts::tokens`，字节数 / 4）。计数之所以一致，是因为它们数的是同一个请求：准入检查、步骤的请求和自动压缩对下一个请求的检查都用 `step_model_request` 构建请求，用 `estimate_model_request_tokens` 计数，工具和记忆都包括在内。

### 模型元数据 [#model-metadata]

Agent 对它访问的每个模型所知道的内容，是内核的 `ModelMetadataRegistry`，每个 Agent 一个，按路由（`ModelRouteKey`：协议、规范化的 base URL 和模型 ID，所以提供同一模型 ID 的两个 Provider 互不混淆）存放。每项事实（上下文窗口、最大输出、推理及其强度、图片输入）都可以未知，并带有来源和观察到的时间（`ModelMetadata`）。注册表为每个路由保存三种来源，逐项事实分别解析，顺序如下：

1. **配置**：设置中的值，由调用方传入（注册表不读配置）。
2. **学到的**，来自 Provider 的拒绝，且只朝安全的方向：学到的窗口只在小于其他来源给出的窗口时采用，学到的“不支持”优先于报告的“支持”。学到的事实保留 7 天。
3. **报告的**，来自该路由自己的模型列表（`list_provider_models`，每个条目整条记录）。
4. **目录**，第三方模型目录，只补充其他来源都没说的事实（目前没有写入它的地方）。
5. **内置**：窗口表。

目前据此行事的有：窗口，在创建会话、选择模型和每个轮次开始时（见下文）；从“请求过长”的拒绝中学到的窗口（见下文）；最大输出，用于阈值压缩为回复留出的空间（[压缩](#compaction)），以及 Anthropic 带思考时的 `max_tokens`；图片输入和推理（都见下文）。内核从不访问数据目录：它的所有者注入一个 `ModelMetadataStore`，注册表启动时加载一次，每次变化后把快照交给它。facade 的存储是 `model-metadata.json`（[数据目录](/docs/data-directory#contents)）；内核的其他构造方式只在本次运行中保留这些事实。列表的合并、过期和文件格式见[内部细节](/docs/internals#model-metadata)。

**模型发现。** facade 自己列出各 Provider 的模型，所以在任何人打开模型列表之前，列表报告的事实就已知道（`model_discovery.rs`）。Agent 的 worker 组里有一个 worker，带自己的运行时，从通道接收请求，一次列出一个 Provider，经由内核的 `list_provider_models`：用该 Provider 的端点、令牌和请求头，与它的请求相同，列表也像其他列表一样被记录。构建服务时请求一次（默认 Provider）；此后每当会话绑定到某个 Provider 时都请求：在它上面创建会话，选用它的模型（`/model`、角色的模型），或为一个轮次激活会话，这也覆盖了在另一个 Provider 上恢复的会话。请求只是往通道发送一条消息，所以从不延迟会话的创建、模型选择或轮次。一个端点只有在它最近一次记录的列表已满一天，并且在本次运行中距它上次列出已满一天、或距上次失败的列出已满 15 分钟时，才会再次列出。这一天从模型元数据保存的列出时间（`listedAtMs`）算起，所以新的运行（包括每次 `exec`）不会再列一次，用户自己请求的列表也计算在内；失败只在本次运行中记住。失败以 warn 级别记录 Provider 的 id，从不记录它的回答（那是它的内容，可能回显凭据），也从不让轮次失败。关闭时 worker 组会取消进行中的列出；被取消的列出不记录任何东西。`modelMetadata.discovery = "off"`（[配置参考](/docs/config-reference#model-metadata)）让所有请求都不被执行；用户自己请求的列表（模型列表、Provider 的测试、`doctor --online`）仍会记录。facade 的测试构造方式无论设置如何都不运行模型发现，测试用 Provider（`test_support::configure_test_provider`）也会关掉它，所以脚本化的模型服务器只看到测试自己的请求。

**延后解析。** 会话以创建时已知的信息创建，从不等待列表。每个轮次被接纳时，内核在会话的锁内、在接纳该轮次的同一次提交中，再次解析会话的路由（`service/context_window.rs`）：值或来源不同的窗口会替换 `context_window_tokens`，会话记录的用量也在同一次提交中改用这个窗口计量，所以恢复时“用量与窗口一致”的检查仍然成立。会话记住窗口的来源（`AgentSessionConfig.context_window_source`，未知时省略，所以之前写入的会话保持不变）。配置的窗口从不被替换；没有来源的窗口（在记录来源之前写入的会话）视为配置的；没有窗口的会话采用已知的窗口。路由完全解析不出窗口时（报告它的列表已过期，也没有其他来源知道这个模型），会话保留已有的窗口：轮次开始时从不丢弃已知的窗口。尚未绑定到 Provider 的会话没有路由，不会被解析，所以内置表不会单独替换 Provider 报告的窗口。

**学到的窗口。** Provider 以超出窗口为由拒绝某一步的请求时（`ProviderContextWindowExceeded`，在 `hanafubuki-agent-model-api` 中分类：[内部细节](/docs/internals#context-refusals)），路由会学到一个窗口，这发生在 `run_sampling_request` 中、轮次循环压缩并重试之前：拒绝中写明的窗口（`context_limit_in`），否则被拒请求自己的估算（`estimate_model_request_tokens`），作为上界；两者都只在 1024 到 20,000,000 token 之间才采用（`PLAUSIBLE_CONTEXT_WINDOW`）。路由在学到的窗口有效期内（7 天）保留其中最小的一个，解析时只在它小于其他来源给出的窗口时采用。被拒的会话立即采用它：在会话的锁内单独提交一次，与延后解析走同一个改写（`refresh_context_window`，所以配置的窗口不变，用量随窗口一起改），并在它采用的是学到的窗口时记录 `ModelContextWindowLearned { tokens, previous }`；于是拒绝之后的压缩、重试以及之后的每一步都按它压缩。此后该路由上的每个会话都从它开始，本次运行和下次运行都一样（`model-metadata.json`）。无论自动压缩是否开启都会学习；只从轮次的请求中学习（压缩自己的请求过长时照旧被裁剪，不学习），轮次被取消后也不再学习。

**图片输入。** 会话是否向模型发送图片（`effective_input_capabilities`，从不持久化），由用户的策略和路由的图片输入事实共同决定（`service/image_capability.rs`）。`imageInput = "disabled"` 优先，它作为配置的“不支持”传给注册表（按模型的设置将来也只在这一处读取）。否则，“不支持”（列表报告的，或从拒绝中学到的；学到的“不支持”优先于报告的“支持”）会关闭图片；“支持”或没有事实时图片照旧开启；目录的“不支持”被忽略，因为目录只做补充。会话在创建、选择模型或恢复时采用它（所以压缩在任何轮次之前读到的也是它），并在接纳轮次、接受插话、准备每个采样步骤、运行每个工具调用以及每次快照之前，在会话的锁内再取一次；传输层给不出路由的会话保留已有的值。图片关闭时，该步骤的工具计划不含 `view_image`（`ToolPlanContext.image_input`），请求构建时其中的图片被替换为占位文字（`sanitize_images_for_unsupported_input`），所以不会先有请求被拒绝；带图片的轮次开始或插话会被拒绝（`InvalidInput`）。轮次进行中变化的事实从下一步起生效，此前已计划的 `view_image` 调用在运行时被拒绝（`ToolCallContext.image_input`）。拒绝后的回退不变：用占位文字重试一次（`ModelRetryScheduled { stage: ImageInputFallback }`），之后路由学到“不支持”，保留 7 天，存入 `model-metadata.json`。未加载会话的快照没有传输层，只反映策略本身。

**推理。** 请求携带的推理强度按请求解析，从不保存（`service/reasoning.rs`）：会话配置的推理强度，按路由解析出的推理事实收窄（`hanafubuki-agent-model-api` 的 `request_reasoning_effort`）。一无所知，或模型会推理但列表没有列出档位时：按配置发送。列出了档位时：配置的在列表中则用它，否则它的别名在列表中则用别名，否则用 `minimal < low < medium < high < xhigh < max` 上最近的档位（距离相同时取较低者），否则不发送。不接受推理参数的模型（列表报告的，或从拒绝中学到的，学到的优先于报告的“支持”）：不发送。没有配置推理强度：不发送。步骤的请求（`begin_sampling`）和压缩自己的请求都采用它，并带上路由的最大输出，Anthropic 据此确定思考的大小；推理强度被收窄或去掉时，每个会话以 warn 级别记录一次日志（用日志而不是事件：活动跟踪器的事件分派是穷举的，且已到大小上限）。传输层给不出路由时，一无所知。Provider 拒绝该参数时（`UnsupportedReasoning`，[内部细节](/docs/internals#reasoning-refusals)），去掉它重试一次（`ModelRetryScheduled { stage: ReasoningFallback }`），与图片回退可以叠加，路由学到“不推理”，保留 7 天，存入 `model-metadata.json`。`normalize_session_config` 不再在任何协议上去掉推理强度：每种协议都会发送它（[模型 API](#the-model-api)）。

### 压缩 [#compaction]

压缩用本地摘要或 Responses 的压缩替换历史，由会话的压缩能力选择。它在会话记录的克隆上暂存，并作为 `Compacted { checkpoint }` 边界安装，所以失败只丢弃克隆，历史不变。本地摘要的请求声明轮次的工具，工具选择为 `none`（回答里的工具调用是错误），就像重放的请求保留工具、只禁止调用它们一样：它与轮次有相同的指令和工具缓存前缀，而且在每种协议上，历史中的工具调用和结果都与产生它们的工具一起发送。它保留用户消息（最新的优先，在预算内）和摘要，从不摘要上下文段：下一个请求从注册表重新渲染每个段，所以轮次中途被压缩的窗口仍带有 Skill 目录和记忆。触发条件：轮次前和轮次中达到阈值、手动、Provider 报告上下文窗口错误之后。阈值（`AgentContextTokenStatus::calculate`）是窗口的 `autoCompactThresholdPercent`（默认 80%），当剩下的部分容不下一次回复时更低，源自 Hoshimi：`min(window × percent / 100, window − headroom)`，其中 headroom 是路由的最大输出（未知时为 32,768），但不超过 `max(4096, window / 10)`，也不超过 `window / 2`。最大输出在检查阈值的地方从模型元数据解析（会话不保存它），所以在默认的 80% 下，20,480 及以上的窗口按百分比压缩，更小的窗口更早（10,000 的窗口在 5,904）。同一个限值也界定后台压缩的区间和安装压缩后的下一个请求。错误触发有上限：每步一次压缩加重试，成功响应之前第二次出错则轮次失败（`context_window_exceeded`）。每次出错都会先让路由学到一个窗口（[学到的窗口](#model-metadata)）。

会话还有压缩策略（`AgentSessionConfig.compaction_strategy`）：`standard` 即上面的压缩；`background` 在会话工作时对快照运行它，稍后安装结果；`hierarchical` 由模型自己把历史折叠成摘要，在请求时投影（源自 [billion-context](https://github.com/ranxianglei/billion-context)）。每种策略都以这种压缩为底线（手动、模型的 `new_context`、上下文错误后的重试）。facade 在每次模型操作前从 `[compaction]` 读取策略，并在会话空闲时应用（`set_session_compaction_strategy`）；临时会话（`/side`）总是 `standard`；`background.childSessions` 关闭时，子会话（子代理的、评审的）以 `standard` 代替 `background`。同一次激活还把修改后的 `remoteCompaction` 写入会话的压缩能力，压缩会用它核对传输。

**后台压缩**（`background`，来自 Codex 的 `async_compaction`）运行会话自己的实现，三种中的任一种，适用任何 Provider。轮次在第一个请求之前和每个请求之后启动它，条件是：上下文达到或超过窗口的 `[compaction.background] thresholdPercent`（facade 把它放进轮次扩展）且低于前台阈值，之前已有完成的轮次，轮次没有被取消、没有预算压力，并且自动压缩开着。它只压缩已完成的轮次，即当前轮次 `TurnStart` 之前的历史，所以它之后的部分总是从一个轮次开始，安装后的历史保持完整的轮次结构。它运行在会话拥有的任务上，而不是作为会话的操作：轮次、steering、`/model` 和其他所有更改照常进行，中断轮次只停止这个轮次的启动。它的槽位不持久化，所以重启丢弃它，不留下恢复义务。

结果在下一个检查点安装：步骤的自动压缩检查之前，或 `/compact` 之前。需要压缩时（阈值、Provider 的上下文错误、`/compact`），如果有一个仍在运行，就等待它而不发送自己的请求，直到轮次被中断；结果失败、不适用或过期时在线压缩，安装后的结果仍让下一个请求超过阈值时再在线压缩一次。模型请求的新上下文总是在线压缩。安装是变基（`InstallMode::Rebase`）：窗口必须仍是它压缩的那个，历史必须仍以它读取的历史开头，之后添加的历史保留在替换之后。它的用量属于会话，在它结束时记录，无论是否安装，任何轮次的预算都不计入它。关闭、归档和删除会取消它并等待它的任务；策略或压缩能力的更改会取消它。

**分层压缩**（`hierarchical`）是 billion-context 的算法，移植为纯 crate `compression`，由内核驱动（`service/compression/`）。它从不改写历史：每个请求都从窗口历史的投影构建，投影中模型折叠的块代替它们覆盖的消息。用户、助手和工具输出的文本带有引用标签（`<acp tokens="…" type="…">m00001</acp>`），模型用它们指明要折叠的范围；工具调用的参数从不带标签。仍然有效的 `compress` 调用留在请求中，作为它的摘要的载体；载体已不在的块，在它的位置显示为 `[Compressed conversation section]` 摘要。压缩过的前缀和压缩摘要从不折叠。策略为 `hierarchical` 时，请求还带有：指令之后的算法静态提示，作为最后一条用户输入的提醒或状态行（从不持久化），以及五个内核核心工具：改变状态的 `compress` 和 `decompress`，只读取状态的 `search_context`、`acp_status` 和 `acp_cache`。`decompress` 从存储的历史返回一个块、它的一个范围或一条消息的图片（重新附在输出上），或通过历史存储把块写到会话的导出文件；`search_context` 搜索摘要和被折叠的原文。可选功能默认关闭，它们加入：`absorb`（模型用工具 `absorb` 提炼一个大的工具结果，此后它离开请求）、`crush`（在 `absorb` 要求之前，确定性地折叠 JSON、代码和日志）、内容存储（大的工具结果在到达时被替换为占位符，原文由 `acp_retrieve` 返回，保存在会话自己的一个文件中，位于其附件旁边，不在记录里）和 `rules`（模型用 `acp_rule` 记录的提醒，显示在指令中）。状态（引用、块、提醒的基线）增量持久化：每个改变了它的运行时检查点带一条链的一个链节，即快照或自上一个链节以来的差分，差分超过上次快照时写新的快照（`PersistedAgentRuntimeState.compression_update`）；`compress` 或 `decompress` 在写入其输出的那次提交的锁下再应用一次，所以折叠和它的回执落在同一次提交中。分叉或子会话保留它持有其消息的那些块及其引用；缺失或无法读取的状态从窗口中的 `compress` 调用重建。

窗口由模型负责，所以阈值压缩（轮次前和轮次中）关闭。标准压缩仍是底线：Provider 的上下文窗口错误、`/compact`、`new_context`，以及最终出口（上下文连续三个请求超过紧急阈值，且已没有可折叠或可截短的内容）各运行一次。它压缩的是投影后的视图，摘要作为文本；安装后，被覆盖的条目已离开窗口，块随之失效。切换到 `hierarchical` 时从空状态开始，在当前窗口上生成引用。切换离开时，有效的块继续投影，标签和载体都保留，所以请求只在指令和工具上变化；不再有提示、提醒或工具产生新块，下一次标准压缩结束它们。对该 crate 的每次调用都在 `catch_panic` 下运行：投影中的 panic 让这个请求带完整历史发送，轮次剩下的部分按 `standard` 运行（下一轮次再尝试）；`compress` 或 `decompress` 中的 panic 是这次调用的错误。

宿主在调用输出的那次提交中看到每次折叠的 `ContextCompressed` 事件（生成的块数、它们替换的 token 数、层级），投影的 panic 则是 `ContextCompressionFailed`。会话的快照带有活动块数和压缩的 token 数（`compression`），facade 的 `compression_status` 读取算法的状态面板和缓存报告，不改变会话。终端界面以折叠的形式显示 `compress` 调用（它的范围和回执的第一行），并提供 `/compression` 和状态栏的 `compression` 项。

## 思考 [#thinking]

模型流式输出的思考作为类型化事件传给使用者，并作为对话条目保存，其文本**从不**作为模型输入回放；Anthropic 签名的思考块按其协议的要求在本轮内回传（见下文）。

- **模型 API。** 思考是 `ModelEvent::ReasoningDelta { item_id, kind, index, delta }`（`kind` 为 `Summary` 或 `Raw`），位于推理条目的开始与完成之间。Responses：`reasoning_summary_text.delta` 与 `reasoning_text.delta`，请求在设置了推理强度时发送 `reasoning: {effort, summary: "auto"}`（否则 OpenAI 不发送摘要）。Chat Completions：`delta.reasoning_content` 或 `delta.reasoning`，每段连续的思考一个条目。Anthropic Messages：`thinking` 块与 `thinking_delta`，以 `display: "summarized"` 的自适应思考（Claude 4.6 及以后）或思考预算请求（[Provider 与模型](/docs/providers-models#reasoning)）。
- **内核。** 每个推理条目得到内核自己的 ID（`AgentReasoningId`，提供者的 ID 从不离开流），依次发布 `ReasoningStarted { reasoning_id, sampling_step }`、`ReasoningDelta { reasoning_id, delta }`（Markdown）和 `ReasoningCompleted { reasoning_id, duration_millis }`。保留的文本是条目的摘要（有的话），否则是原始文本。
- **单独的上限。** 思考不计入 `maximum_model_output_bytes`：每个条目在 `maximum_reasoning_text_bytes`（256 KiB）处按字符边界截断，其余的既不显示也不保存。否则一个有 30 KB 思考的轮次会开始失败。
- **历史。** 步骤把每个条目作为 `ConversationItem::Reasoning { text, duration_millis, sampling_step, truncated, replay }` 与其他条目一起按模型产生的顺序提交。它的文本只用于展示：`as_model_input` 跳过它，token 估算不计它，压缩丢弃它，权限审查和记忆从不读取它。提前停止的响应用已经流出的内容完成打开的条目。
- **回传 Anthropic 的思考块。** 手动思考（带预算的 `type: "enabled"`）会拒绝这样的工具结果：它回应的助手消息不以思考块开头；也会拒绝任何被改动的思考块。所以解码器把每个 `thinking` 块连同 `signature`（`signature_delta`）完整保存，`redacted_thinking` 块保存其 `data`，作为条目的 `replay`（`ModelReasoningReplay`，每块最多 1 MiB，`Debug` 不显示内容）。它从不序列化：不进历史、不进快照、不进事件。步骤的请求把本轮（最后一个 `TurnStart` 之后）的思考块作为 `ModelInputItem::Reasoning` 放在它们之前的助手条目前面，Anthropic 编码器只在手动思考时发送它们；Responses 和 Chat Completions 略去它们。手动思考的请求若要接续的工具调用所在消息没有可回传的思考块（重启后恢复的轮次、轮次中途的压缩、没有思考的第一步），就不带思考发送，Anthropic 接受这样的请求。自适应思考不回传任何思考块：Anthropic 允许全部省略，而它 5.1 及以后的模型在系统提示、工具或思考块之前的任何消息变化后会拒绝该块，Agent 的请求在步骤之间恰恰会变化（任务计划跟在历史之后；世界状态段移到最后变化的位置；`tool_search` 会添加工具）。

## 存储 [#storage]

数据目录（嵌入时由宿主指定，Hanafubuki 是 `<app_data>/data/agent`）的内容见[数据目录](/docs/data-directory)。

- **历史**（`hanafubuki-agent-history`，格式版本 5）：每个会话一份 JSONL rollout，它是权威的；SQLite 索引是投影，需要时重建。新条目和字段都是增量添加的（`ToolSelection`、`Reasoning`、`ToolCall` 上可选的命名空间；运行时状态的 `parentSessionId`、`origin`、`cwd` 和 `branch`，旧记录中没有，读作空），移除的字段是被忽略的未知键。打开时无法接受的东西只损失它自己的会话：另一种格式的 rollout 移入 `.recovery`，无法投影的留在原处并在每次启动时重试修复，会话被隔离；其他会话和 Agent 照常打开。写入经过每个会话一个的写入线程，追加和它的投影写好后才确认。
- **记忆**（`hanafubuki-agent-memory`，移植自 Codex）分两阶段从会话历史中派生：阶段一用一个小模型提取每个空闲会话，阶段二由整合子 Agent 处理提取结果，发布 `MEMORY.md` 和 `memory_summary.md`。先判断资格再应用上限，两个阶段都有退避（30 秒翻倍到一天），发布先提交数据库再重命名文件。
- **Skill**（`hanafubuki-agent-skills`）：仓库 Skill 来自每个工作区根目录及其祖先直到 Git 根目录中的 `.agents/skills`，每次读取目录时重新计算；然后是用户根目录和内置的 System Skills。Skill 的正文作为 `ConversationItem::SkillContext` 每个轮次每个 Skill 只交付一次。Skill 从不注册或限制工具。
- **配置**（`hanafubuki-agent-config`）：三个 TOML 文件，各自一个修订域和一把锁（`config.toml`、`providers.toml`、`mcp.toml`，后两者只有所有者可读）。读取逐字段解码，无效值取默认值，未知键保留，需要修复的文件先复制到 `.recovery/`；写入用 `toml_edit` 编辑磁盘上的文档（注释、布局和未知键得以保留），再原子重命名。独立模式下设置是分层的（profile、受信任的项目文件、`-c`），但只有用户的文件会被修复或写入。终端界面的配置中心是这些设置的视图：它的类型化表单通过相同的补丁和原子写入器保存，自己不做任何配置解析。详见[配置](/docs/configuration)。
- **数据目录锁**：`<data_dir>/.lock`，因为历史索引、记忆存储和进程组台账都假定只有一个写进程。
- **持久化格式是不稳定的。** 规则是读取方容错解码，隔离它不能使用的东西，从不删除用户数据。

## 已安装的插件 [#installed-plugins]

已安装的插件是一个**包**：一个带清单的目录，从目录或市场安装，名字是 `<插件>@<市场>`。它不是插件宿主的一行。包存储（`hanafubuki-agent-packages`，移植自 Codex 的插件存储）把它们放在数据目录的 `plugins/` 中（[数据目录](/docs/data-directory#contents)）；配置中的 `[plugins]` 和 `[marketplaces]` 决定哪些启用（[插件](/docs/config-reference#plugins)）。

- **五种清单格式**，按以下顺序探测：本项目的 `.hanafubuki-plugin/plugin.json`、Agent Plugins 1.0.0 的根 `plugin.json`（按 `$schema` 识别），然后是 Codex 的 `.codex-plugin`、Claude Code 的 `.claude-plugin` 和 Cursor 的 `.cursor-plugin` 中的 `plugin.json`。清单或其目录是符号链接或不是普通文件时，探测停止，这样无害的清单无法遮住另一个清单。我们的格式是 Codex 的清单加上供代码使用的 `runtime`、`contributes`、`permissions` 和 `configSchema`；存储保留它们，留给将来运行代码的部分。
- **按外部来源读取。** 无法使用的清单字段或组件路径会被略去并记录一个问题；只有不是 JSON 对象的清单，或无法读取的 Agent Plugins 名字或 `$schema`，才会失败。路径必须以 `./` 开头并留在包内。Codex 遇到某些类型错误的字段会让整个清单失败；这里只略去该字段。
- **市场**是 `.agents/plugins/marketplace.json`、`.agents/plugins/api_marketplace.json`、`.claude-plugin/marketplace.json` 或 `.cursor-plugin/marketplace.json`，支持本地、`url` 和 `git-subdir` 来源（不支持 npm）。无法使用的条目会被跳过；只有无法读取的文件才让它的市场失败。市场可以从目录添加（留在原处），也可以从 git 仓库添加（克隆到 `plugins/marketplaces/`）；升级时取得远端的修订并替换检出。存储返回 `[marketplaces]` 记录，由调用方写入配置。
- **安装先暂存再替换。** 包被复制到暂存区（不含符号链接和 `.git`）；没有清单时，把市场条目的字段写成它的清单；暂存的清单逐字节与来源核对；带描述的 `commands/*.md` 变成 Skill；然后把副本重命名为 `plugins/cache/<市场>/<插件>/<版本>/`，同一版本的旧副本保留到替换成功，更旧的版本被清理。使用中的版本：有 `local` 时用 `local`，否则用最高版本。包的数据目录在卸载后保留，除非清除。
- **链接只是一条记录。** `plugins link` 按引用记录一个目录：它的条目在 `linked.json` 中，与缓存的 `install.json` 分开，所以旧版本重写 `install.json` 不会丢掉它；不复制任何东西，不计算内容哈希，也不向目录写入任何东西（它的命令不会变成 Skill）。存储在缓存中的包之后列出它，按目录当前的样子读取；同一 ID 的链接与安装互相拒绝，卸载删除记录并保留目录，`update_package` 拒绝它。
- **`git` 通过 Agent 的 `ExecutorManager` 运行**，和工作树一样隔离：不继承仓库选择变量，不运行钩子，不提示，并有超时。

包是内容而不是代码：它贡献的东西流入各领域自己的来源，而这些来源本身已经是内置行。门面（`crates/agent/src/packages`，仿照 Codex 的 `load_plugin`）按键的顺序读取设置启用的已安装包，把每个包变成：

- **Skill 根目录**：清单的 `skills`（否则是 `skills/`），以及（Agent Plugins 除外）由它的命令转换成的 Skill。它们的 ID 是 `plugin:<plugin>@<marketplace>:<路径>`，名称是 `<清单名称>:<名称>`，与 Codex 的命名相同（[Skill 从哪里来](/docs/skills#sources)）。Agent Plugins 包的 Skill 是其根目录的直接子目录。
- **包拥有的 MCP 服务器**（[插件的服务器](/docs/mcp#plugin-servers)）：`.mcp.json`（或清单的 `mcpServers`）或 Agent Plugins 的 `mcp.json`，从不写入 `mcp.toml`，由 `[plugins."p@m".mcpServers]` 限制，与用户的服务器在同一套监管下运行。同名时用户的服务器优先，其次是键的顺序中第一个包；让出的服务器记为该包的问题。
- **钩子来源**，排在用户和项目之后（`HookSource::Plugin`），凭定义和包的内容哈希被信任，每次运行前再次检查（[插件的钩子](/docs/configuration#hooks-plugins)）。与 Codex 相同，Agent Plugins 包的钩子从不运行。
- **角色**（`packages/roles.rs`）：清单的 `agents`（没有时是 `agents/`）。本项目格式的包中是角色文件，由配置的角色读取器读取；Claude Code 包中是代理文件，由 packages crate 读取（`read_claude_agents`：frontmatter 逐键读取，Claude 工具名按固定对照表映射，一个不含任何我们工具的 `tools` 不允许任何工具，`disallowedTools` 作为禁止列表，`permissionMode` 作为权限模式上限，`plan` 还禁止计划模式去掉的写入类工具）；Codex、Cursor 或 Agent Plugins 包没有角色。每个角色以 `<插件>:<角色>` 命名，插件部分取自 id 中的插件名；同一插件名的两个包中，id 在前的保留它，另一个包的角色记为它的问题。角色目录把它们排在内置角色之上、用户的角色之下，和所有角色一样经过合并和收窄（[插件的角色](/docs/roles#plugins)）；读取时略去的内容是该包的问题。

读不了的包，或包中读不了的组件，记为该包的问题；其他包照常加载。这一组包在构建 Agent 时加载（MCP 服务器随启动连接），并由 `reload_packages` 重新加载：门面在每次写入设置和 `mcp.toml` 之后运行它，每个生命周期调用也在变更后运行它；它替换 Skill 根目录和钩子来源，只连接或断开有变化的 MCP 服务器，并带着包的角色重建角色目录，无需重启。`packages()` 列出每个已安装的包及其版本、格式、启用状态、内容和问题（`AgentPackageStatus`）。

模型通过 `plugins` 行得知启用的包：当某个包向本轮的 Skill 目录贡献 Skill 或贡献 MCP 服务器时，Capabilities 槽位带有一个"可用插件"段落（Codex 的 `PluginCapabilitySummary`：显示名称、单行且至多 1,024 个字符的描述、Skill 前缀、MCP 服务器名称）；没有这样的包就没有该段落，所以没有包的 Agent 的请求不变。该行拥有这份摘要并挂载访客宿主（[代码插件](#code-plugins)），所以关闭它会隐藏摘要并停止所有访客，而内容仍经由 `skills`、`mcp` 和 `hooks` 行流入。安全模式下这些包会被列出，但都不加载。

生命周期由门面负责（参照 Codex 的插件管理器），并且只通过 Agent 打开的那一个包存储进行，因为再打开一个会清扫它的暂存区：

- **安装**（`install_package`，来自已添加的市场或一个目录；没有指定市场时归入 `local`）通过存储安装，写入 `[plugins."<id>"] enabled = true`（合并进用户的文件，所以条目中的 `mcpServers` 保留），重新加载，并返回这个包和它需要的东西：需要信任的钩子（对代码包还有需要授予的权限；内容包没有）。
- **卸载**删除包及其 `[plugins]` 条目；除非清除，它的数据目录会保留。**启用**和**停用**写入 `enabled`；所属市场被关闭的包不能启用。**更新**从它的市场（按市场当前的内容）或它的目录重新安装。**重试**重新加载，并以空的重启窗口再次启动失败的访客。
- **市场**（`marketplaces`、`add_marketplace`、`upgrade_marketplace`、`remove_marketplace`）只包括用户添加的那些（`[marketplaces]`）：不会从主目录或仓库中发现市场。每个调用写入它的记录并重新加载。
- **`package_changed`**：对包的每个生命周期调用都会在重新加载之后告诉插件事件接收器（`AgentPluginEventSink::package_changed`）发生了什么：`installed`、`removed`、`enabled`、`disabled`、`updated`，或 `failed` 以及原因。它不在 `exec --json` 的事件流中，那里的事件属于会话；`exec` 回合期间没有任何东西改变这些包。

`plugins` 命令和 `/plugins`（[终端界面](/docs/terminal-interface#plugins)）是这些调用的界面；`mcp list` 和 `/mcp` 显示包的服务器并标明所属包，`/warnings` 显示包的问题和失败的访客。使用方法见[插件](/docs/plugins)。

### 代码插件：访客宿主 [#code-plugins]

本项目格式的包还可以带代码：清单的 `runtime` 指明一个讲 Kardia 访客协议（`kardia-guest/2`，或版本 1）的程序，它**在进程外**运行，所以它的崩溃、中止或挂起都到不了 Agent 的进程；或者指明一个讲访客 ABI 的 **WebAssembly 模块**，它在 Agent 的进程内、在 wasmtime 中运行，受燃料、时间和内存的限制。访客宿主（`hanafubuki-agent-plugin-packages`）运行这两种访客，由 `plugins` 行挂载为其子 fiber（`plugin-guests`）。

- **一棵 kardia-loader 子树。** 访客宿主是一个 kardia-loader，它的树中每个代码包一个条目：条目的 id 就是包的 id，它的插件以启动所依赖的一切命名（版本、记录的内容哈希、命令、请求与授予的权限，以及已链接包的目录改动次数），任何一项变化都会重新启动它：新名字就是升级路径，kardia-loader 对此的处理是释放条目的 fiber 并启动新的插件。每次重新加载之后，门面把代码包（无论启用与否）交给访客宿主，访客宿主用一次组更新把它们应用到树上：安装时创建条目，包关闭时禁用条目，卸载时移除条目。树的 `TreeBackend` 把加载器自己做出的变更（自行释放的插件被写回为关闭）通过门面提供的设置端口写入 `[plugins]`，交给门面的阻塞写入者排队，并且只在值不同时写入；组更新是设置的镜像，不写回任何东西。
- **每个包版本一个解析器条目。** 条目的名字解析为一个缓存的 kardia-hmr `ProcessGuest`，它的元数据来自清单（`name`，以及每个访客都在自己的领域中提供的服务 `plugin`），所以解析不会启动任何东西；访客启动时必须声明相同的元数据，否则启动失败。模块的条目在第一次解析时解析为一个 kardia-hmr `WasmGuest`：在阻塞线程池上，模块在它的限制所对应的引擎上编译（限制相同的访客共享一个引擎及其 epoch 线程），元数据同样来自清单，所以生成它不实例化任何东西；每个实例启动时都声明相同的元数据，否则启动失败；之后这个插件就属于这个名字。它的插件名为 `guest:<插件>@<市场>`，使访客在注册表和日志中区别于内置行。
- **进程属于 Agent。** 程序访客的启动器先预留所有者，再通过实例的 `ExecutorManager` 以预留的管道执行器启动进程，并把管道交给访客桥；访客桥只通过收据结束进程，确认进程结束后才释放执行器。进程属于实例的所有者组，记录在 `process-groups.json` 中，在实例停止时被清扫，在下次启动时被回收（[进程](/docs/internals#plugin-guests)）。
- **启动需要什么。** 对程序，清单请求的权限必须已授予（`install.json` 保存授权，已链接的包则是 `linked.json`，由 `grant_package_permissions` 记录）；包的内容哈希必须仍是安装时记录的那个（每次启动进程时检查，模块则在编译前检查一次）。等待授权的访客处于 `blocked`；内容变化的包启动失败。已链接的包没有要保持的哈希：它按目录当前的样子启动，授权和沙箱配置与已安装的包相同。
- **已链接的包跟随它的目录。** 访客宿主运行期间，它在实例的受控 worker 组的一个线程上监视每个启用的已链接包（有代码或没有）的目录。某个目录改动并随后安静 500 毫秒，该包的修订号加一，访客宿主发出信号；`plugins` 行随即在后台运行门面对包的重新加载，也就是 `reload_packages` 运行的那一个，所以这个包的 Skill、MCP 服务器、钩子和角色被重新读取，它的访客以新的名字重新启动（[插件访客](/docs/internals#plugin-guests)）。
- **模块什么也访问不到。** 它能导入的只有访客 ABI 的宿主函数（`view` 和 `invoke` 与程序一样受限），所以它没有文件、网络、时钟或环境变量：清单的 `permissions` 被忽略并记为问题，它不需要授权（`AgentPackageGuest::ungranted` 为 `None`）也不需要沙箱，在所有平台上都能启动。它的限制（`runtime.limits`）约束每个导出：燃料、通过 epoch 中断实现的时间（默认为它最长的调用可能用的时间，每次调用自己的期限也同样生效）以及线性内存（默认 256 MiB）。
- **插件配置。** 进程以空环境启动，只带被授予的 `env` 变量、`PLUGIN_ROOT` 和 `PLUGIN_DATA`（在 Windows 上还有 `SystemRoot`），工作目录是它的数据目录，并受沙箱的插件配置（`SandboxPolicy::Plugin`）约束：它读取平台的系统目录和它的包，只写它的数据目录，按授权访问工作区（`none`、`read` 或 `write`），只有被授权时才能使用网络。Linux（Landlock）和 macOS（Seatbelt）强制限制读取；Windows 的受限令牌不能拒绝读取，所以在那里访客能读它的用户能读的一切，`workspace: "none"` 不被强制。访客使用平台的沙箱，无论 `[windows] sandbox` 怎样设置（该设置管的是模型的命令）；没有沙箱的地方（没有调用 `helper_dispatch` 的程序、没有 Landlock 的 Linux 内核），访客不会启动。
- **它的状态**属于访客宿主：`starting`、`running`、`restarting`、`failed`、`stopped` 或 `blocked`，附带原因、最后一次退出报告（自行退出、被杀死或被释放，原因与状态）以及 stderr 的最后 16 KiB。`packages()` 连同请求与授予的权限一起显示它（`AgentPackageStatus.guest`）。
- **重启。** 运行之后失败的访客（进程退出或被杀死、调用超过期限、违反协议或发送超过 4 MiB 的帧；模块触发陷阱、用尽燃料或时间，或要把内存增长到超过限制，`GuestHost::call` 从调用的错误中识别这些情况）使它的 fiber 失败，即 Kardia 的 `Failed`；访客宿主随后按重启策略（2 秒、10 秒、30 秒之后，10 分钟内三次）通过更新失败的 fiber 来重启它，这不写任何配置。窗口内的第四次故障使它保持 `failed`，直到 `retry_package`。启动失败不会被重启。因故障停止不等于关闭：这些都不会写入 `[plugins]`。

- **通过代理贡献。** 访客贡献的是它的清单声明的东西（`contributes`），从不是访客自己说的：它的 fiber 变为活动时，访客宿主把代理注册为该 fiber 的副作用（一个工具源、每个上下文段 kind 一个上下文贡献者和渲染器、一个提示渲染器、一个工具生命周期钩子和一个继续钩子、一个观察者），所以它们随每次失败、停止或重启撤销，并随下一次启动回来。每个代理在比内核自身更短的期限内调用访客 `plugin` 服务的一个方法，所以挂起的访客会被终止并重启，而内核仍能及时走该调用的错误路径：一个工具错误、一个被略去的段或片段、一个没有发言权的钩子、一个被丢弃的事件。由于一个步骤准备好的值按类型区分，提示片段统一经过访客宿主的一个贡献者。审批规则和轮次准入不对访客开放。规则与协议见[插件规则](/docs/plugin-rules#code-plugins-rules)。
- **访客能访问什么，以及它的设置。** 在每个访客的 loader 条目旁边，一个宿主服务条目（`<id>#host`）在两者按标签共享的 realm 中提供 `workspace` 和 `settings`，访客的条目声明了它们；受检访问找不到访客能 `view` 或 `invoke` 的其他东西，kardia-hmr 拒绝访客提供 `plugin` 以外的任何服务（这个拒绝是访客自己的错误）。它的设置 `[plugins."<id>"].settings` 是两个条目的配置，所以 `set_package_settings`（按清单的 `configSchema` 校验）会以新设置重启它。
- **编写代码插件。** `plugins new` 生成一个代码插件，`plugins validate` 像访客宿主运行它那样检查它（加 `--run` 时在临时主目录中启动它），`plugins dev` 在每次改动后重新安装它，`plugins link` 链接它的目录，运行中的 Agent 跟随这个目录；包、清单、SDK 和线路格式见[编写插件](/docs/writing-plugins)。

## MCP [#mcp]

`McpManager`（`hanafubuki-agent-mcp`）拥有连接（stdio 与 Streamable HTTP 传输、OAuth、工具目录、存活检测、重连、租约）；`mcp` 插件只是它之上的工具源加三个资源工具。每个步骤，工具源绑定已连接服务器的目录（作为计划租约），为每个目录条目提供一个工具。

- **目录逐个工具构建**，一个坏工具只损失它自己；名字按字符清理为 `[A-Za-z0-9_-]`。
- **注解是提示，不是授权。** `readOnlyHint` 且不带 `destructiveHint: true` 的工具是 `ConcurrentRead`、`ReadOnly`（计划模式可用）；其余都是 `Exclusive`、`Mutating`。审批只读服务器或工具的策略和破坏性提示，缺失的提示视为破坏性的。
- **存活与重连。** 服务器一侧结束连接时，服务器变为 `Failed` 并附原因，它的条目退役（工具离开下一个计划），管理器按重启策略用打开时的配置和密钥重新连接它。
- **连接就是目录修订。** 步骤保留它规划时的连接；过期的调用只能是因为连接已关闭，这时返回 `McpError::CatalogChanged`，不请求审批，模型重新搜索或重试。用计数器会让被用户刷新退役、但仍在运行的连接上的调用失败，破坏“步骤保留它的连接”的保证。
- **每台服务器一个故障所有者，而不是每台服务器一个子 fiber。** 命名的子 fiber 会以宿主故障处理器不认识的名字出故障，只被记录而不被停止，于是每次调用都再 panic 一次；未命名的子 fiber 以 `mcp` 的名义出故障，停止整个插件。在调用处捕获就能隔离到服务器，而所有服务器本来就共享一个进程。

## 模型 API [#the-model-api]

`hanafubuki-agent-model-api` 实现三种协议：Responses、Chat Completions 和 Anthropic Messages，包括编码、流式解码、工具降级和模型列表。它用 `ModelRouteKey`（其中端点为 `ModelEndpointKey`）命名 Agent 访问的模型，端点取规范化 base URL 的 SHA-256 而不是 URL 本身，因为键会写入日志和磁盘，而 base URL 的查询串里可能带有凭据。它不知道任何插件和任何上下文段类型，也不依赖插件 API。Provider 的流是外部输入，容错解码：空的工具参数是 `{}`；无法解析的是 `{}` 加 `argument_error`；缺失的用量计数是 0；没有结束原因的流以未知的 `end_turn` 结束；Responses 的 `response.incomplete` 保留已完成的条目和已流出的文本，只有什么都没产生时才失败。每种协议都发送推理强度，各用自己的字段（`responses/encode.rs`、`chat_completions/reasoning.rs`、`anthropic_messages/thinking.rs`；对照表见 [Provider 与模型](/docs/providers-models#reasoning)）；Anthropic 用自适应思考还是预算，按模型 ID 判断，因为两类模型互相拒绝对方的形式。线路正文只按[内容日志规则](/docs/contributing#content-logging)在 `trace` 级别、截断后记录。

## 终端界面与命令行 [#the-terminal-interface-and-the-command-line]

- **`hanafubuki-agent-cli`** 是 `hanafubuki-agent` 二进制，位于门面之上，不依赖工作区的其他东西。每个命令从全局标志组合运行时，安装 panic hook 和日志文件；读写配置的命令（`config`、`providers list`、`mcp list`、`roles`、离线的 `doctor`）从不启动 Agent，所以它们可以在 Agent 运行时使用；`roles` 和 `doctor` 用包存储的只读列举（`PackageStore::read_installed`：不清理暂存区、不隔离、不写入、不取锁）读取已安装插件的角色。`exec` 自带 sink：轮次的 `AgentEventSink` 和槽位的状态 sink 送入命令线程读取的同一个通道，所以它打印的事件就是门面自己的（`--json` 原样序列化 `AgentEvent`）。见[命令行参考](/docs/cli-reference)。
- **`hanafubuki-agent-tui`** 是移植到门面之上的 Codex 终端界面（`rust-v0.93.0`），使用上游的 ratatui 0.30 与 crossterm 0.29（Codex 用 git 分支给它们打补丁，crates.io 不接受）。终端底部是内联视口，转录写入终端自己的回滚区。一个适配器（`agent_bridge`）把轮次的 `AgentEvent` 映射为聊天组件显示的内容，把界面的请求映射到门面；一个循环、一个通道：读终端的线程和 Agent 的 sink 都送到同一个通道，会等待的门面调用作为 Agent 运行时的任务运行并在通道上回报，所以循环从不阻塞在 Agent 上。见[终端界面](/docs/terminal-interface)。

### 终端界面的移植改动 [#what-the-port-of-the-terminal-interface-changed]

`crates/tui` 中派生自 Codex 的文件都带有说明这一点的标记行（[许可证](/docs/contributing#licence)）。移植对 Codex 的终端界面做了这些改动：

- **上游的 ratatui 与 crossterm。** Codex 用 git 分支给 ratatui 和 crossterm 打补丁，crates.io 不接受；移植使用上游的 ratatui 0.30（它的 `scrolling-regions` 特性让视口增长），通过 ratatui 的重新导出使用 crossterm 0.29，并去掉了终端调色板查询，改用 Codex 在没有它时回退到的固定主题。
- **在门面之上。** `agent_bridge` 代替 Codex 的 `ConversationManager` 与 `CodexConversation`。工具事件既不带参数也不带输出，所以已完成调用的输出（`apply_patch` 的补丁由 Agent 自己的解析器 `preview_patch` 读取）来自轮次已提交的历史（`read_turn_page`）；diff 没有行号，因为那种读取没有行号。斜杠命令映射到门面的调用；`/diff` 在第一个工作区根目录运行 `git diff`，这是界面自己的短生命进程，不是 Agent 的工具调用，所以不在 Agent 的进程所有权之内。
- **`@` 文件提及**来自 Codex 的 `file-search` crate，作为界面的 `file_search` 模块而不是单独的 crate 移植，因为只有界面使用它。crates.io 上的 `nucleo` 0.5 没有 Codex 固定的 git 版本读取的匹配分数访问器，所以匹配不带分数（没有地方显示它们）；匹配器在带期限的 std 通道上等待，而 Codex 在 `crossbeam` 通道上 select；锁是 `parking_lot` 的。
- **终端的恢复。** 每次返回（一个 drop guard）和结束进程的 panic 都会恢复终端：界面的 hook 先恢复终端，再运行 Agent 的 hook。被隔离的 panic 让界面继续运行。
- **斜杠命令是隔离的模块。** Codex 中平铺的 `SlashCommand` match 变成一张表（`commands`）：每个命令的规格（名字、别名、说明、是否接受行内参数、回合中能否运行、是否需要会话）和它的分派，命令列表、`/名字 参数` 的查找和分派都来自这张表。每次分派，以及命令推入的每个视图（按键处理和绘制），都在 `hanafubuki_agent::panic::catch_panic` 中运行：panic 的命令失去它的视图，在本次运行的剩余时间内关闭，对话中显示一条错误，会话、输入框和其他命令照常工作。聊天本身（输入框、转录、流式输出）不是模块，那里的 panic 仍会结束进程。
- **配置中心。** `/config` 打开可全屏搜索的列表，列出每个配置域及其当前生效值。每个域以整份类型化表单编辑，通过 `AgentSettingsPatch`、独立设置写入器或 `AgentTuiPreferencesPatch` 保存，或者打开拥有它的编辑界面；分层页面列出读取的文件和警告，写入被配置档、项目文件或 `-c` 覆盖时会说明。Providers 和 MCP 保留按修订号保护的编辑界面，并说明它们是不分层的、仅所有者可读的文件。
- **Agent 工作时发送的消息。** Codex 的输入队列（Enter 引导回合、Tab 排队、Esc 中断并发送等待中的补充消息、Shift+Left 编辑最后一条排队的消息）放在聊天中，每个对话一个，建立在内核的 steering 之上：聊天一次只发送一条补充消息，让回合按顺序接收；每条消息的文本一直保留，直到回合的 `SteeringConsumed` 覆盖它被接受时的序号；回合结束后，要等每条补充消息都得到答复才处理队列，因为内核会丢弃被取消或失败的回合还没读到的内容，并拒收晚到的补充消息。用 Tab 输入的命令立即执行而不排队，Shift+Left 把消息放在草稿之前，而不是覆盖草稿。
- **需要时才有会话。** Codex 启动时就开始一个线程；这里的桥在第一条消息或需要会话的命令创建会话之前不持有会话（期间提出的请求等它创建好），`/new` 回到没有会话的状态。创建失败（没有默认 Provider）是对话中的一条错误，而不是退出。
- **语法高亮和状态显示。** `render/highlight` 保留 Codex 的 syntect 和 two-face 组合（Oniguruma 语法、32 个内置主题、自定义 `.tmTheme` 文件），但没有 Codex 自己的以模型命名的主题；由于不查询终端调色板，默认主题是 two-face 的 `ansi`，它用终端的调色板着色，取代 Codex 根据查询到的背景在 Catppuccin Mocha 和 Latte 之间的选择。主题选择器在列表旁边或下方的示例差异上预览。状态栏和标题去掉了 Codex 的账号、速率限制、费用和版本项目，增加了权限模式和目标；会话的值在事件改变它们时从门面的会话快照读取，Git 分支从 `.git/HEAD` 读取，而不是启动 `git` 进程。Codex 不恢复它最后设置的终端标题；这里把标题压入终端的标题栈，退出时弹出。
- **没有移植的：** 转录分页器中的实时尾部与回溯、自定义提示、编辑框中的 Skill 与应用提及和图片附件、状态卡中的账号与速率限制、状态栏和标题设置界面中的搜索框，以及 Codex 对流式代码的增量高亮（流式回答在每完成一行时整体重新渲染，代码也随之重新高亮）。

## 设计选择 [#design-choices]

以下是读者可能想撤销、但有理由的选择：

- **没有流式分派**（见上文）。
- **每台 MCP 服务器一个故障所有者**，**连接就是目录修订**（见 [MCP](#mcp)）。
- **Skill 正文作为 `SkillContext`，而不是工具输出。** 压缩两者都不保留，所以不由它决定；`$mention` 路径没有工具输出，而 `SkillContext` 是每轮一次检查读取的类型化记录，所以无论 Skill 怎样被选中，正文只有一种形式。
- **MCP 工具总是 `PollutesContribution`**，只读的也是：只读工具的输出仍是外部内容，与网页抓取一样。
- **插件宿主关闭 `module_faults`、开启自动重启。** 那个标志是关于应用的模块故障 sink 的，插件故障从不使用它，而是通过 `PluginFaults` 到达 Agent 的宿主。
- **渲染器是数据**，**注册拒绝、规划改名**（见上文）。
- **轮次限制对模型不可见。** 历史中没有失败轮次原因的条目；用户读轮次的错误消息，没有什么需要模型看到它。
- **沙箱改写 argv；进程 crate 不知道它。** `sandbox` 把一个命令变成辅助进程的命令行：辅助进程就是 Agent 自己的程序文件，由第一个参数选中（`--hanafubuki-agent-sandbox`，和 Codex 选择它的其他辅助进程一样），它先限制自身，再原地执行那个命令。`ExecutorManager` 像对待其他进程一样启动、拥有和回收这个进程，管道和 PTY 模式都一样，所以 `process`（Hanafubuki 那份的孪生）没有改动；Codex 按 argv[0] 选择的方式需要它能设置 `arg0`。它所在的位置：回合冻结会话的沙箱设置（`SandboxSettings`，门面准备回合时加入的扩展），`plugin-execution` 把它和命令一起交给 `execution`，`execution` 在自己的工作区根目录上解析它，并在启动前包装已获批准的命令。在 Linux 上，辅助进程使用 Codex 的 Landlock 流程，而不是它默认的 bubblewrap：不需要许多发行版都会限制的用户命名空间，不需要从 C 构建的随附 `bwrap`，而 Codex 放弃 Landlock 的理由（它的 app-server 的 Unix 套接字、拒绝访问的例外路径）在这里都不适用。在 macOS 上没有辅助进程：命令行是 `/usr/bin/sandbox-exec` 加上 Codex 的 Seatbelt 策略，可写根目录和只读的例外路径（`.git`，Landlock 做不到）作为参数（`-D`）传入，而不是拼进策略的文本。机器无法执行的模式会让命令失败，绝不会不受限地运行它（[权限](/docs/permissions#sandbox-unavailable)）。
- **`hierarchical` 是内置策略，不是插件。** 做成插件需要一个内核每次请求都调用的新注册表，于是每个请求都依赖插件可以替换的代码（[组合规则 1](/docs/plugin-rules#composition-rules)），而且契约无法引用模型 API 的类型。所以算法是一个纯 crate（没有 I/O、没有异步，生产代码不 panic，与插件一样受检查），内核在 `catch_panic` 下调用它：那里的失败只损失一个请求的投影或一次工具调用，不会损失会话，这正是插件的隔离本来能给的。
- **没有做的：** 代码模式（用 JS 调用所有工具）、跨会话的 MCP 连接池、无论目录大小都延迟所有 MCP 工具、MCP 的 prompts/subscriptions/sampling/roots、Skill 注册的工具或 `allowed-tools` 的执行、从 Agent 单独安装一个 Skill（Skill 随携带它的[插件](/docs/plugins)一起安装，或者手动复制到某个 Skill 根目录），以及进程外的 Agent。

与 Codex（`codex-rs`）相比，Agent 的机制都对照过它：

| 方面      | Codex                                                     | hanafubuki-agent                                                                                        |
| --------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 工具快照  | 每步一个工具路由器                                        | 每步一个工具计划，带计划租约                                                                            |
| 名字      | `{namespace, name}`，只做查找                             | 相同；每个请求一张线路名表，按协议适配                                                                  |
| 延迟工具  | `tool_search`；选择保存在历史中                           | 相同，通过 `ToolSelection` 条目直到压缩                                                                 |
| Schema    | 精简的关键字集合，从不 strict                             | 协议接受时发送完整 schema，否则可移植的，从不 strict                                                    |
| 审批      | 执行之前                                                  | 决定等待时在门外；`AllowForSession`                                                                     |
| 工具超时  | 注册表层面没有                                            | 按描述符，否则轮次的空闲超时                                                                            |
| MCP 存活  | 只对一个内置服务器重连                                    | 每台服务器：`Failed`，然后有界重连                                                                      |
| AGENTS.md | 每步读取；错过项目内的就地编辑                            | 每个轮次读取并按摘要比较；用户与项目文件                                                                |
| 上下文段  | 类型化的世界状态                                          | 类型化的段，渲染器与槽位属于插件                                                                        |
| 压缩      | 本地、remote 与 remote v2，在线或异步；重新渲染初始上下文 | 本地摘要、Responses compact 与 v2，在线或在后台（`background`，变基安装）；重新渲染每个段；有上限的重试 |
| 记忆      | 两个阶段、租约、引用                                      | 相同的设计，加上先判断资格再限量和两阶段退避                                                            |
| 沙箱      | bubblewrap 和 seccomp、Seatbelt、受限令牌；审批后可提升   | Linux 上为 Landlock 和 seccomp，macOS 上为 Seatbelt；没有提升                                           |

## 已知的限制 [#known-limits]

- 文件工具的策略根目录在构建 Agent 时固定；只有 Skill 根目录和上下文段按每次读取跟随工作区。
- 会话的窗口只在轮次开始时重新解析：轮次运行期间得知的窗口在会话的下一个轮次才采用，模型元数据完全不再知道的窗口会一直保留，直到再次选择会话的模型。
- MCP 重连复用打开连接时的密钥，所以过期的 OAuth 令牌会让重连失败，直到用户手动连接。
- Skill 监视器只监视启动时存在的根目录；之后出现的根目录（包括之后启用的包的根目录）依靠读取时的标记。
- 手动编辑 `[plugins]` 在下次启动或重新加载时生效；Agent 只在它自己写入设置之后重新加载包。
- 在 Windows 上，程序访客的沙箱不限制读取。
- WebAssembly 访客的实例失败只能由调用者等到结果的调用识别：在调用者已放弃的调用（被取消的轮次）中停止的访客，由它的下一次调用使其失败，而那次调用本身也会失败。每组在用的限制保留一个引擎，以及一个每 10 毫秒推进一次其 epoch 的线程。
- 内置的上下文窗口只覆盖公开了上限的模型系列（GPT、o 系列、Claude、Gemini 2.5）；其他模型需要 Provider 的列表或设置才能自动压缩。
- 命令沙箱只存在于 Linux 和 macOS；Windows（受限令牌及其提权设置）还没有，所以在那里未设置的 `sandboxMode` 即完全访问。macOS 的沙箱只由它在 macOS 上运行的测试检查。
- 在 Linux 之外未验证：`notify` 监视器的 macOS 与 Windows 后端、Skill 目录中显示的 Windows 路径、Windows 上 MCP stdio 的退出原因和已退出子进程的释放，以及 Windows 上记忆制品的安装重命名。
