hanafubuki-agent runs in two ways, and both are the same composition:

- **Standalone**: the `hanafubuki-agent` command line and terminal interface. The facade crate's `AgentRuntime::standalone` supplies a default for every host port (the working directory as the workspace, the operating system's keyring, the proxy from the configuration file).
- **Embedded**: a host application (such as [Hanafubuki](https://github.com/licyk/Hanafubuki)) composes the Agent itself and supplies plugins, workspace, context, instructions, network settings and a secret store through the **host interface**. The Agent knows none of the host's domains and depends on none of its crates; dependencies point one way: the host depends on the Agent.

This page covers embedding. Writing a host plugin is [Host plugins](/docs/host-plugins); how the parts work together is [Architecture](/docs/architecture).

## Adding the crates [#adding-the-crates]

```toml
[dependencies]
hanafubuki-agent = "0.2"
hanafubuki-agent-contracts = "0.2"
hanafubuki-agent-runtime = "0.2"
# The tools of a host plugin also need:
hanafubuki-agent-approval = "0.2"
hanafubuki-agent-tool-contracts = "0.2"
kardia-core = "0.2.0"
```

| Crate                             | What it is for                                                                                                              |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `hanafubuki-agent`                | The facade: the composition, the slot, the service API, the host interface, the configuration (it re-exports `AgentConfig`) |
| `hanafubuki-agent-contracts`      | The plugin API: registries, the tool and context contracts, `TurnExtensions` (which `WorkspaceRootsPort` needs)             |
| `hanafubuki-agent-runtime`        | `ContainedRuntime`: each Agent instance's runtime, named in `AgentConstructor`'s signature                                  |
| `hanafubuki-agent-approval`       | The approval types a host plugin's tools use (`ApprovalAction`, `PermissionRequirement`, `AuthorizedAction`)                |
| `hanafubuki-agent-tool-contracts` | Tool names and tool-spec types (`ToolName`, `ToolExposure`, `ToolExecutionClass`)                                           |

Plugins are kardia `PluginDef`s, hence `kardia-core`. A host should not depend on the kernel (`hanafubuki-agent-kernel`), the model API or any other internal crate; the facade re-exports what a host needs.

<Callout title="Versions">
  Before 1.0 a minor release may break (Cargo's rule for `0.x`), so depend on a minor requirement
  such as `"0.1"` and move with each minor release by hand. Until the first release is on crates.io,
  a host pins a git revision instead (as Hanafubuki does today).
</Callout>

## Composition [#composition]

Embedded, the host assembles the parts the standalone mode uses too:

| Part                      | What it does                                                                                                                        |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `AgentSlot`               | The Agent's state machine and supervisor: start, automatic restarts after a kernel fault, the crash-loop stop, on and off, status   |
| `AgentStartMarker`        | The crash-loop marker (`start-marker.json`), which also holds the data directory's lock                                             |
| `DesktopAgent`            | The slot, the marker and the environment of the Agent's child processes; `start` and `shutdown`                                     |
| `AgentLaunch`             | The closure that builds every Agent instance (`AgentConstructor`) and the path of the process-group ledger                          |
| `AgentServiceInputs`      | What the closure hands `AgentApplicationService::open`: configuration, storage, Skill roots, blocking pool, event sinks, host ports |
| `AgentApplicationService` | The running Agent's service API: sessions, turns, settings, Providers, MCP, Skills, memory, plugin status                           |

The construct closure runs on every start: the first, a user's restart, an automatic restart after a kernel fault, turning the Agent back on. So the host ports are **built again for every instance** inside the closure: each instance mounts the plugin rows it is given once.

A complete minimal example:

```rust
use std::collections::{BTreeMap, HashMap};
use std::path::PathBuf;
use std::sync::Arc;
use std::time::{Duration, Instant};

use hanafubuki_agent::{
    agent_workspace_roots_from, AgentApplicationService, AgentConfig, AgentConstructor, AgentEvent,
    AgentEventKind, AgentEventSink, AgentHostInstructions, AgentHostPorts, AgentInstanceInputs,
    AgentLaunch, AgentPluginDescriptor, AgentPluginGroup, AgentPluginRow, AgentProxy,
    AgentServiceInputs,
    AgentSessionMode, AgentSlot, AgentStartMarker, AgentStatusEventSink, AgentStoragePaths,
    AgentTurnRequest, AgentWorkspaceRoots, DesktopAgent, NetworkSettingsPort, NoHostContext,
    NoopAgentPluginEventSink, NoopMcpEventSink, SecretFuture, SecretKey, SecretStore, SkillRoots,
    WorkspaceRootsPort, AGENT_SHUTDOWN_BUDGET,
};
use hanafubuki_agent_contracts::TurnExtensions;
use hanafubuki_agent_runtime::ContainedRuntime;
use parking_lot::Mutex;

fn main() -> Result<(), String> {
    // 0. First, before any thread: the sandbox helper (see below).
    hanafubuki_agent::sandbox::helper_dispatch();
    let config_dir = PathBuf::from("/var/lib/my-app/config/agent");
    let storage = AgentStoragePaths::under(PathBuf::from("/var/lib/my-app/data/agent"));
    let project = PathBuf::from("/srv/project");

    // 1. The slot and its crash-loop marker, then the Agent beside the host.
    let marker = AgentStartMarker::new(storage.start_marker_file.clone())
        .with_crash_record(storage.crash_record_file.clone());
    let slot = AgentSlot::new(marker.disabled_reason(true), Arc::new(LogStatus));
    let agent = DesktopAgent::new(slot, marker, HashMap::new())?;

    // 2. What builds every Agent instance: the first start and each restart.
    let process_groups_file = storage.process_groups_file.clone();
    let construct: AgentConstructor = Arc::new(
        move |runtime: &ContainedRuntime, instance: AgentInstanceInputs| {
            let blocking = runtime.blocking_port();
            AgentApplicationService::open(AgentServiceInputs {
                config: AgentConfig::new(&config_dir),
                storage_paths: storage.clone(),
                skill_roots: SkillRoots {
                    system: storage.skills_root.join("system"),
                    user: storage.skills_root.join("packages"),
                    install_bundled_system_skills: true,
                    state_file: storage.skill_state_file.clone(),
                },
                blocking,
                mcp_event_sink: Arc::new(NoopMcpEventSink),
                plugin_event_sink: Arc::new(NoopAgentPluginEventSink),
                host: AgentHostPorts {
                    plugins: vec![(
                        AgentPluginRow::unconfigured(
                            AgentPluginGroup::Capability,
                            app_info_plugin(),
                        ),
                        AgentPluginDescriptor::new("app-info", "What My App is"),
                    )],
                    workspace: Arc::new(ProjectRoots(project.clone())),
                    steering_context: Arc::new(NoHostContext),
                    instructions: AgentHostInstructions {
                        identity: "You are My App's coding agent.".to_string(),
                        application: "My App".to_string(),
                        ..AgentHostInstructions::default()
                    },
                    network: Arc::new(SystemProxy),
                    secrets: Arc::new(MemorySecrets::default()),
                },
                instance,
            })
        },
    );

    // 3. Start, and wait for the running Agent.
    agent.start(AgentLaunch {
        construct,
        process_groups_file,
    });
    let handle = agent
        .slot()
        .wait_until_started(Instant::now() + Duration::from_secs(120))
        .map_err(|unavailable| unavailable.to_string())?;

    // 4. Every call into the Agent runs on its own runtime.
    let turn = handle
        .runtime()
        .block_on({
            let handle = handle.clone();
            async move {
                let session = handle.create_session(AgentSessionMode::Default, None).await?;
                let request = AgentTurnRequest {
                    text: "Summarize the README.".to_string(),
                    images: Vec::new(),
                    skills: Vec::new(),
                    host: TurnExtensions::default(),
                };
                handle
                    .submit_turn_with_sink(session.id, request, Arc::new(PrintEvents))
                    .await
            }
        })
        .map_err(|failure| failure.to_string())??;
    println!("turn {:?} accepted", turn.turn_id);

    // 5. Shut down within the budget, outside any async context.
    for diagnostic in agent.shutdown(AGENT_SHUTDOWN_BUDGET) {
        eprintln!("{} did not stop: {}", diagnostic.worker, diagnostic.message);
    }
    Ok(())
}
```

`ProjectRoots`, `SystemProxy` and `MemorySecrets` (under [The host interface](#the-host-interface)) and `LogStatus` and `PrintEvents` (under [Events and history](#events-and-history)) are the host's own small types, in the same file as the code above and using its `use` lines; `app_info_plugin` is the example plugin of [Host plugins](/docs/host-plugins).

Points to note:

- `AgentSlot::new` takes an `Option<AgentDisabledReason>` first: `None` means the Agent will start. `AgentStartMarker::disabled_reason(module_enabled)` gives the reason to stay off when the host turned the Agent off, or when the last starts never finished (a crash loop, `CRASH_LOOP_STARTS` being 3).
- `DesktopAgent::new`'s third argument is the environment the Agent's child processes inherit in place of this process's (`HashMap<String, Option<String>>`, `None` removing a variable). When the host's proxy changes, `DesktopAgent::replace_child_environment` replaces the overlay applied last.
- `start` returns at once: the start runs on the Agent instance's own runtime (construction and recovery on its blocking pool, the plugins as its tasks, the MCP servers connecting in the background). A failure leaves the slot `Failed` and never reaches the host.
- `wait_until_started` returns the running `AgentHandle`, or why the Agent does not run (`AgentUnavailable`, whose `Display` is "the Agent is unavailable: …").
- `AgentHandle` dereferences to `AgentApplicationService`. Its async methods run on `handle.runtime()` (`ContainedRuntime::block_on`, or `spawn` on its handle): kardia and the Agent's tasks run only there, and only there is a panic contained.

### The same composition, standalone [#the-same-composition-standalone]

Without a host, `AgentRuntime::standalone` composes the same slot, marker, `DesktopAgent` and `AgentLaunch`, with a default for every port. The command line uses it like this:

```rust
use std::time::Duration;

use hanafubuki_agent::{
    logging, panic, AgentDirs, AgentRuntime, AgentRuntimeHost, AgentRuntimeOptions,
    AgentStartOptions, ConfigOverrides, AGENT_SHUTDOWN_BUDGET,
};

fn main() -> Result<(), String> {
    // First, before any thread starts (see "The sandbox helper").
    hanafubuki_agent::sandbox::helper_dispatch();
    let runtime = AgentRuntime::standalone(
        AgentRuntimeOptions {
            dirs: AgentDirs::standalone()?,
            bundled_skills: None,
            cwd: std::env::current_dir().map_err(|error| error.to_string())?,
            add_dirs: Vec::new(),
            profile: None,
            overrides: ConfigOverrides::default(),
            start: AgentStartOptions::default(),
        },
        AgentRuntimeHost::default(),
    )?;
    panic::configure_crash_record(runtime.storage_paths().crash_record_file.clone());
    panic::install_panic_hook(logging::logging_blocked);

    runtime.start();
    let agent = runtime
        .wait_until_started(Duration::from_secs(120))
        .map_err(|unavailable| unavailable.to_string())?;
    // … call the agent's methods on agent.runtime(), as embedded …
    drop(agent);
    runtime.shutdown(AGENT_SHUTDOWN_BUDGET);
    Ok(())
}
```

`AgentRuntimeOptions` holds the directories (`AgentDirs`, which follows `HANAFUBUKI_AGENT_HOME`), an optional System Skills directory, the working directory and `--add-dir`s, the configuration profile, the `-c` overrides and the first start's options. `AgentRuntime::standalone` reads the layered configuration once right away, so a bad profile fails there. A standalone first start always runs: a command line that starts the Agent asks for it, so an earlier run's unfinished starts do not keep it off (the crash marker still counts them).

`AgentRuntime::set_working_directory(path)` makes `path` (relative to the current working directory, or absolute) the working directory while the Agent runs, and returns the new roots: it, its Git root, then the `--add-dir`s. The running Agent's filesystem tools and commands move to them at once and its sessions stay live, each seeing the new roots in its next turn's context. It is refused, with nothing changed, while a turn, a compaction or a background terminal runs, and the error says which. The configuration's project layer stays the one read at start. It is standalone only: an embedded host supplies the workspace through its own `WorkspaceRootsPort`.

`AgentRuntimeHost` is what a standalone consumer replaces:

| Field           | Default                              | Notes                                                                        |
| --------------- | ------------------------------------ | ---------------------------------------------------------------------------- |
| `secrets`       | `None`: the OS keyring (`keyring` 4) | service `org.licyk.hanafubuki-agent.secrets`                                 |
| `status`        | `NoopAgentStatusEventSink`           | `status_changed()` on every change of the slot, with no payload              |
| `plugin_events` | `NoopAgentPluginEventSink`           | hints that the plugin status changed, and each change to an installed plugin |
| `mcp_events`    | `NoopMcpEventSink`                   | MCP status and catalog changes                                               |

Turn and session events do not go through it: they go to the `AgentEventSink` each call is given (see [Events and history](#events-and-history)).

## The host interface [#the-host-interface]

A host adds to the Agent only through `AgentHostPorts`. The interface takes plain values (`PathBuf`, strings, maps) or the Agent's own types: the Agent carries its own copies of the foundation, process and module-host crates, whose types are distinct from a host's of the same name, so the host adapts at the edge.

| Field              | Type                                           | What it supplies                                                                                         | Standalone default                                    |
| ------------------ | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `plugins`          | `Vec<(AgentPluginRow, AgentPluginDescriptor)>` | the host's plugin rows, each with its descriptor                                                         | none                                                  |
| `workspace`        | `Arc<dyn WorkspaceRootsPort>`                  | the workspace roots, the protected roots, the directory instruction discovery selects, file-search roots | the working directory, its Git root, the `--add-dir`s |
| `steering_context` | `Arc<dyn HostContextPort>`                     | the host context a steering message carries                                                              | `NoHostContext`                                       |
| `instructions`     | `AgentHostInstructions`                        | identity, application name, and what the host adds to the base instructions                              | `AgentHostInstructions::default()`                    |
| `network`          | `Arc<dyn NetworkSettingsPort>`                 | the proxy the web tools, MCP, OAuth, the model Providers and models.dev use                              | the configuration's `[network] proxy`                 |
| `secrets`          | `Arc<dyn SecretStore>`                         | where MCP OAuth tokens are kept                                                                          | the OS keyring                                        |

### Plugin rows [#plugin-rows]

`AgentPluginRow::unconfigured(group, plugin)`, with `group` either `AgentPluginGroup::Capability` (tools, tool sources and their rules) or `AgentPluginGroup::Context` (world-state sections). A host's rows mount after the Agent's own capability plugins and before its context plugins, so the host's world-state sections come before the workspace roots, environment and permission mode. Host plugins follow the same rules as the Agent's own: `disabledPlugins` turns them off and safe mode leaves them unmounted. How to write one is [Host plugins](/docs/host-plugins).

Each row comes with its `AgentPluginDescriptor`: `AgentPluginDescriptor::new(name, summary)`, with `name` its `PluginDef`'s name and `summary` one line of what it gives the model or the user, which `plugin_status` and `/plugins` show. A row without one, or a name the Agent or another row already describes, keeps the Agent from being built. A row with options adds `.with_options(schema)` (a `PluginOptionSchema`, each option with a default), is `AgentPluginRow::from_settings(group, plugin, |settings| settings.options_value("NAME"))`, and decodes its configuration with `PluginDef::typed`; the options are then `[pluginOptions.NAME]` of the Agent's configuration, checked against the schema, edited with `set_plugin_options` ([Plugin options](/docs/config-reference#plugin-options)).

### `WorkspaceRootsPort` [#workspacerootsport]

```rust
/// One project directory as the whole workspace.
struct ProjectRoots(PathBuf);

impl WorkspaceRootsPort for ProjectRoots {
    fn roots(&self) -> Result<AgentWorkspaceRoots, String> {
        agent_workspace_roots_from([self.0.clone()]).ok_or_else(|| "no workspace".to_string())
    }

    fn protected_roots(&self) -> Vec<PathBuf> {
        Vec::new()
    }

    fn selected(&self, _host: &TurnExtensions) -> Option<PathBuf> {
        None
    }

    fn search_roots(&self, _host: &TurnExtensions) -> Result<Vec<(String, PathBuf)>, String> {
        Ok(vec![("project".to_string(), self.0.clone())])
    }
}
```

- `roots()` is read again for every turn and every Skill catalog read; the first root is the base of relative requests. The filesystem tools' policy and the directory a command without a `workdir` runs in are taken from it when an Agent instance is built, so new roots reach the tools with the next instance (a restart). `agent_workspace_roots_from` removes duplicates (by path identity) and roots nested in an earlier one.
- `protected_roots()`: directories the filesystem tools refuse, reads included, even under a workspace root; a request there fails with `ProtectedPath` before any approval (Hanafubuki: the application's data and log directories, where its credentials are). The standalone Agent names none.
- `selected(host)`: the directory the turn's host input selects; `AGENTS.md` files are read from each root down to it (Hanafubuki: the instance the user is looking at).
- `search_roots(host)`: the directories `@` file search walks, each with its label.
- Every method may block; the Agent calls them on its blocking pool.

### `HostContextPort` [#hostcontextport]

The host context a steering message (a message added to a running turn) carries: `steering_context(host)` returns an `Option<AgentHostContext>` (a `ContextSectionKind` and its content, at most `MAXIMUM_HOST_CONTEXT_BYTES`, 4 KiB). The kernel writes it to the world state as a section of that kind when it changed; the host's plugin registers the kind's renderer. Use `NoHostContext` when there is none.

### `AgentHostInstructions` [#agenthostinstructions]

| Field         | What it is                                                                        | Default (standalone)                     |
| ------------- | --------------------------------------------------------------------------------- | ---------------------------------------- |
| `identity`    | the sentence that opens the base instructions (`{identity}` in `prompts/base.md`) | `You are a coding and operations agent.` |
| `application` | the application name the environment section reports                              | `hanafubuki-agent`                       |
| `sections`    | Markdown after the tool guidance: how the host's tools and context are used       | empty                                    |
| `ownership`   | the paragraph that closes "Approval and ownership": what the host owns            | empty                                    |

The blocks are joined one blank line apart. The text is model-visible, so a host pins it with goldens of its own (Hanafubuki's are in `hanafubuki-agent-integration`).

### `NetworkSettingsPort` and `SecretStore` [#networksettingsport-and-secretstore]

```rust
struct SystemProxy;

impl NetworkSettingsPort for SystemProxy {
    fn proxy(&self) -> Result<AgentProxy, String> {
        Ok(AgentProxy::System)
    }
}

/// Keeps MCP OAuth tokens in memory; a real host uses the platform's store.
#[derive(Default)]
struct MemorySecrets(Mutex<BTreeMap<SecretKey, Vec<u8>>>);

impl SecretStore for MemorySecrets {
    fn get<'a>(&'a self, key: &'a SecretKey) -> SecretFuture<'a, Option<Vec<u8>>> {
        Box::pin(async move { Ok(self.0.lock().get(key).cloned()) })
    }

    fn set<'a>(&'a self, key: &'a SecretKey, value: Vec<u8>) -> SecretFuture<'a, ()> {
        Box::pin(async move {
            self.0.lock().insert(key.clone(), value);
            Ok(())
        })
    }

    fn delete<'a>(&'a self, key: &'a SecretKey) -> SecretFuture<'a, ()> {
        Box::pin(async move {
            self.0.lock().remove(key);
            Ok(())
        })
    }
}
```

- `NetworkSettingsPort::proxy()` is read when the Agent starts and again whenever the host calls `AgentSlot::apply_saved_settings`; it answers from memory and must not block. The model Providers take a change at each session's next turn. `AgentProxy` is `System`, `Disabled` or `Explicit(url)`.
- `SecretStore` calls may block (a keyring), so a host runs them on the Agent's blocking pool (`ContainedRuntime::blocking_port` with `run_blocking_operation`), as Hanafubuki's `KeyringSecretStore` does.
- Locks are `parking_lot`'s: an Agent panic unwinds on a contained thread, which would poison a std lock.

### Host input [#host-input]

`AgentTurnRequest`, `AgentSteeringRequest` and `AgentFileSearch` each have a `host: TurnExtensions` field: what the host submits beside a message or a search, keyed by type. The Agent passes it on unread, to the context contributors (`ContextRequest::turn`), to `HostContextPort` and to `WorkspaceRootsPort`. The host's plugins and ports read the types they put in.

## The sandbox helper [#sandbox-helper]

On Linux and Windows a sandboxed command ([The sandbox](/docs/permissions#sandbox)) runs as the program that embeds the Agent, started again with `--hanafubuki-agent-sandbox` as its first argument: on Linux that run confines itself and then becomes the command; on Windows it starts the command with a restricted token, in a job that ends with it, and exits with the command's status. So the program's `main` calls `hanafubuki_agent::sandbox::helper_dispatch()` first, before it starts any thread:

```rust
fn main() {
    hanafubuki_agent::sandbox::helper_dispatch();
    // … the program, as before …
}
```

- Started as the helper, the call never returns. Otherwise it records that this program (`std::env::current_exe()`) can serve as the helper, and returns at once.
- Without the call the Agent has no sandbox: `AgentApplicationService::sandbox_status()` (and `sandbox::Sandbox::detect().status()`) is `Unavailable`, and every command whose sandbox mode is not full access fails, unrun. On Linux the default `sandboxMode` is workspace-write, so a host that does not call it must configure `sandboxMode = "full-access"` to run commands.
- The `ExecutorManager` spawns the helper like any command; the host's process code is not involved.
- On macOS no helper is needed: a sandboxed command runs under `/usr/bin/sandbox-exec`, so the call only returns there.
- On Windows the sandbox is off until `windows.sandbox` (`AgentSettings::windows`) is `"unelevated"`; a turn takes it with its sandbox mode (`SandboxSettings::windows_sandbox`), and `Sandbox::with_windows_sandbox` applies it.

## The panic-hook bridge [#the-panic-hook-bridge]

The Agent's fault isolation rests on unwinding: a panic in plugin or kernel code unwinds, on a thread marked contained, to its catch, and becomes a tool error, a plugin fault or a kernel restart. So:

- A host must **not** build with `panic = "abort"`.
- A host that installs its own panic hook, and has it abort on a panic it does not see as contained, must also ask the Agent: the Agent marks its threads and guards in **its own** foundation, which the host's hook cannot see.

```rust
// Where the host's hook decides whether a panic is contained:
let contained = host_says_contained() || hanafubuki_agent::panic::is_panic_contained();
```

A WebAssembly plugin guest runs in the host's process inside wasmtime, which installs its own handlers for the signals a guest's trap raises (on Unix `SIGSEGV`, `SIGBUS`, `SIGILL` and `SIGFPE`) when the first WebAssembly guest is loaded, and hands a signal that is not a guest's to the handler installed before it. A host that installs handlers of its own for those signals installs them before, or chains to the one it replaces.

On macOS the Agent has wasmtime handle traps by those signals, not through a Mach exception port: before it makes its first WebAssembly engine, the guest host calls kardia-hmr's `set_macos_mach_ports(false)`. Signals are the path the Agent's checks run on Linux, and a host already chains them (above); Mach ports would add a second process-wide mechanism, and are the suspect of an intermittent hang of the first WebAssembly check on macOS CI, in a process that had started guest processes. The setting is process-wide and fixed by the first engine: a host that makes wasmtime engines of its own makes them with `Config::macos_use_mach_ports(false)` too (wasmtime panics when a later engine asks for the other setting); if a host's engine with Mach ports came first, the Agent's guests keep them, and the guest host logs a warning.

kardia-hmr's own threads (a process guest's `guest-stdin`, `guest-stdout` and `guest-stderr`, the WebAssembly `wasm-epoch` thread) catch their panics, which kill the guest they serve. The guest host registers kardia-hmr's check with the Agent's foundation (`register_containment_check`), so `hanafubuki_agent::panic::is_panic_contained` above is true on those threads too: a host's hook needs no third check.

Without the bridge every Agent panic aborts the host application. Hanafubuki's `platform::panic_hook` installs its hook with this second check and tests both outcomes in a child process (with the bridge the panic unwinds, without it the process aborts); that test is the host's.

Before a fatal panic aborts the process, the host's hook should write the crash record at `AgentStoragePaths::crash_record_file` (`<data>/crash-record.json`): the Agent's crash-loop marker reads it to tell that an unfinished start ended in the host's own fatal panic. A host with no hook of its own can install the Agent foundation's, as the standalone binary does: `panic::configure_crash_record(...)`, then `panic::install_panic_hook(logging::logging_blocked)`.

A frontend that calls into its own code from a thread the Agent did not start (the terminal interface's main thread) can contain a region there with `panic::catch_panic` or `panic::catch_panic_async`: they mark the region contained in the Agent's foundation and return the panic's message as an error. The terminal interface runs each command module under them.

## The data directory's lock [#the-data-directorys-lock]

`<data_dir>/.lock` is an advisory lock (`flock` on Unix, `LockFileEx` on Windows) held from the Agent's first start until its shutdown, embedded and standalone alike. The history's SQLite index, the memory store and the process-group ledger assume one writer process; two processes on one data directory would corrupt the history and kill each other's processes.

- A host does nothing for it: the start marker holds it.
- While another process holds it, the start fails at construction with an error naming the directory; the host application runs on without its Agent.
- Turning a host's Agent off (`AgentSlot::turn_off`) keeps the lock until the application quits, so a standalone Agent on that data directory is refused meanwhile.

## Start, on and off, shutdown [#start-on-and-off-shutdown]

The slot's state (`AgentStatus::availability`) is `Disabled` (`setting` or `crashLoop`), `Starting`, `Running`, `Faulted`, `Stopping`, `Failed { stage, reason }` (`construct`, `recover`, `start`) or `Stopped`. `AgentStatusEventSink::status_changed()` carries no payload: read `AgentSlot::status()` again. The status also has the `generation` (which instance of this run), `safe_mode`, `degraded` (a plugin failed, its teardown is stuck, or it runs with a warning) and the quarantined sessions.

| Call                                      | What it does                                                                                                                         |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `DesktopAgent::start(launch)`             | hands over the launch and starts the first instance; returns at once                                                                 |
| `AgentSlot::wait_until_started(deadline)` | waits for the start to settle; the `AgentHandle`, or why there is none                                                               |
| `AgentSlot::agent()`                      | the running Agent, or why there is none; holders resolve it **per call** rather than keep a handle                                   |
| `AgentSlot::restart(options)`             | the user's restart, optionally in safe mode (`AgentStartOptions { safe_mode, rebuild_history_index }`); resets the crash-loop marker |
| `AgentSlot::enable()` / `disable()`       | turns the Agent on / off; `turn_off(deadline)` turns it off and waits until the deadline                                             |
| `AgentSlot::apply_saved_settings()`       | after the host saved its settings (the proxy): reconfigures the plugins on the Agent's runtime; returns at once                      |
| `AgentSlot::list_run_projections()`       | the Agent's runs (`AgentRunProjection`) for a host's activity view                                                                   |
| `DesktopAgent::shutdown(budget)`          | shuts down within the budget; blocks the caller, which must not be in an async context                                               |

A panic in kernel code (a turn's task, the Agent's worker groups, the host's tasks) makes the slot mark the Agent `Faulted`, stop it, and start a new instance after 2 s, 10 s and 30 s (at most three in a 10-minute window, `AgentRestartPolicy`), rebuilding the sessions from disk. Calls in flight on the old instance fail; a held `AgentHandle` whose `generation()` differs from `status().generation` belongs to an instance that is gone.

`AGENT_SHUTDOWN_BUDGET` is 20 s, spent in fixed stages, each with its own deadline:

<Steps>
  <Step>
    Stop the Skill watcher (2 s); close the slot, cancelling a start under way and waiting up to 8 s
    for it.
  </Step>
  <Step>
    Stop accepting turns, and cancel turns and compactions, background compactions included, and
    wait for them (5 s): a background compaction that finished records its usage first.
  </Step>
  <Step>
    MCP: cancel the background connects, close every connection and confirm its process gone (4 s).
  </Step>
  <Step>Stop the plugins: one disposal of the kardia root (5 s).</Step>
  <Step>
    Stop the memory workers, close the history, stop the service workers (a model listing under way
    is cancelled) and executions (3 s).
  </Step>
  <Step>
    Sweep the instance's process owner group: terminate what the Agent started and left running (1
    s).
  </Step>
  <Step>Stop the instance's runtime, with a 2 s bound for its blocking pool.</Step>
</Steps>

The processes the Agent starts are the Agent's: it has its own `ExecutorManager`, a process-ownership domain apart from the host's. The host neither needs to nor can terminate them for it.

## Configuration in a host [#configuration-in-a-host]

The host names a configuration directory for the Agent and opens it with `AgentConfig::new(dir)` (Hanafubuki's is `<app_data>/config/agent/`). It holds three TOML files, each its own revision domain with its own lock:

| File             | Contents                                                                                                     |
| ---------------- | ------------------------------------------------------------------------------------------------------------ |
| `config.toml`    | permission mode, sandbox, memory, `disabledPlugins`, web search and fetch, `[compaction]`, `[modelMetadata]` |
| `providers.toml` | the Provider registry and its revision, tokens verbatim (owner-only)                                         |
| `mcp.toml`       | the MCP servers and credential values and their revision (owner-only)                                        |

Unlike the standalone configuration, an embedded one has **no layers** (no profile, project file or `-c`) and ignores `[network]` and `logLevel` (reported as unknown keys): the host supplies the proxy and the logger. The host reads and writes the settings through the service API (`settings_view`, `write_settings`, the Provider and MCP methods), and a write applies the settings to the plugins. Among them:

| Call                                                           | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `test_provider_draft(draft)`                                   | the model catalog of a Provider not saved, read as `list_provider_models` reads a saved one's, or the Provider's error; writes no settings (the listing is recorded in the [model metadata](/docs/architecture#model-metadata) as any listing is)                                                                                                                                                                                                       |
| `model_metadata(provider_id, model)`                           | what is known of `model` on that Provider (`ModelMetadata`: its window, largest output, reasoning and its levels, image input), each fact with its source (`Sourced`, `ModelMetadataSource`): the model's own settings in `providers.toml` (not the policy's window), what its refusals taught, what its catalog reported, what models.dev says when it is on (`Catalog`), the built-in window ([Per-model settings](/docs/providers-models#per-model)) |
| `session_model_metadata(session_id)`                           | the same for a session's model, with the window the session has and its source, as `/status` shows them                                                                                                                                                                                                                                                                                                                                                 |
| `forget_learned_model_facts(provider_id, model)`               | forgets what that Provider's refusals taught of `model` (`None`: of each of its models), kept in `model-metadata.json`; returns how many models had something. A session takes it at its next turn ([Forgetting what was learned](/docs/providers-models#forget))                                                                                                                                                                                       |
| `mcp_set_credential(key, value)`, `mcp_remove_credential(key)` | change one MCP credential and keep the rest; a removal an enabled server depends on is refused. `McpCredentialKey::for_server_secret(server, name)` is the key a form stores a secret variable or header under: `SERVER-NAME`, any other character `_`                                                                                                                                                                                                  |
| `mcp_oauth_login(server, open_url, cancelled)`                 | an MCP server's OAuth login: listens on `127.0.0.1` at a free port, hands `open_url` the authorization URL to show or open, waits up to 5 minutes for the browser's redirect to `/callback`, or until the `cancelled` future completes, and cancels the flow if none comes                                                                                                                                                                              |

Each model operation (a turn, a compaction, a plan's implementation) first activates its session as the settings now describe it: `[compaction]`'s `strategy` reaches the session through the kernel's `set_session_compaction_strategy`, and the model policy's `remoteCompaction` reaches the session's configuration with the Provider's transport, and so does what is configured for the session's model (`AgentSessionConfig.configured_facts`, an `AgentConfiguredModelFacts`: the model's own settings in `providers.toml`, its window else the policy's), which `activate_model_session` takes and the next turn applies. Both change only while the session is idle and are persisted, but neither moves the session's revision, so a revision the caller read before the call is still current. A turn's extensions carry `[compaction.background]`'s `thresholdPercent` (`AgentBackgroundCompactionThreshold`), read at its admission; a host that admits turns through the kernel itself puts it there, or the turn starts no background compaction. While one runs or its result waits to be installed, the session's runtime snapshot says so (`backgroundCompaction`: `running` or `ready`); it is not an operation of the session and refuses nothing. Archiving or deleting a session cancels it and waits up to 5 s for it, and changing the strategy or `remoteCompaction` cancels it.

Reads are tolerant: an invalid value takes its default, unknown keys are logged and stay in the file, and a file that needed repair is copied into `.recovery/` before the repaired values are written; when the original cannot be kept, the repaired values are used from memory and the file refuses writes until a restart. Each repair is an `AgentConfigRecovery` (file, problem, whether read-only, time); `AgentConfig::recoveries()` returns those since the configuration was opened (the last 20 a file), and a host should show them to the user. The keys, defaults and repair rules are in [Configuration](/docs/configuration) and [Configuration reference](/docs/config-reference).

The configuration directory may also hold [roles](/docs/roles): its `agents/` and the `[agents]` entries of its `config.toml`, the one configured source of an embedded Agent's roles, beside the built-in ones and the [installed plugins'](/docs/roles#plugins) while they are on. `roles()` returns the `AgentRoleCatalog` as the service last read it (when it was built, and again at every `reload_packages`): its usable roles (`AgentResolvedRole`, with its chain, its merged fields, its `AgentCapabilityScope` and each field's provenance), its unusable ones with why, and its issues, which a host should show beside its configuration's. `AgentRoleCatalog::load(&config, plugins_root, safe_mode)` reads them without a service: the configuration's, and those of the installed plugins under `plugins_root` (`AgentStoragePaths::plugins_root`) that the settings leave on (none in safe mode), read without opening the package store, so it is safe beside a running Agent; what reading a plugin's roles left out is among its issues, naming the plugin. A session takes a role when it is created or switched ([Sessions and roles](#sessions)).

The Agent lists its Providers' models by itself ([model discovery](/docs/architecture#model-metadata)): the default Provider's when the service is built, and a Provider's whenever a session is created on it, given one of its models or activated for a turn, at most once a day per Provider (every 15 minutes after a failure), through the Provider's own endpoint, token and headers. So a host's Agent makes a `GET {baseUrl}/models` of its own at start and on these occasions; it never delays a call, and a failure is logged, never returned. What it learns is a session's context window at its next turn, and the session's configuration keeps where its window came from (`AgentSessionConfig.context_window_source`, `None` when unknown and left out of the record then; a host that builds the configuration itself passes `None`, and the kernel sets it). A host turns discovery off with `modelMetadata.discovery = "off"` in the Agent's `config.toml`, by hand, with `AgentConfig::set_user_value("modelMetadata.discovery", "off")`, or with the settings patch's `modelMetadata` (`AgentSettingsPatch::model_metadata`). The Provider's model list the host asks for (`list_provider_models`, `test_provider_draft`) is read and recorded either way.

A host's Agent never asks [models.dev](/docs/providers-models#models-dev) unless its configuration turns it on (`modelMetadata.modelsDev = true`, the patch's `AgentModelMetadataSettings.models_dev`, which a patch's `modelMetadata` now carries beside `discovery`): on, the same worker downloads `https://models.dev/api.json` from the host's machine, a request to a third party, at most once a day. The kernel's `AgentService::model_metadata` and `model_context_window` take the Provider's id, whose name picks its own entries there; `record_models_dev_catalog`, `forget_models_dev_catalog` and `models_dev_fetched_at` are the copy's.

Moving settings from an older format is the host's business: while `config.toml` does not exist (`AgentConfig::exists`), Hanafubuki's construct closure runs `import_legacy_agent_settings`, which writes the whole configuration once with `AgentConfig::create` (`config.toml` last, so an import that stopped part-way runs again) and leaves the old files untouched.

## Events and history [#events-and-history]

```rust
struct LogStatus;

impl AgentStatusEventSink for LogStatus {
    fn status_changed(&self) {
        eprintln!("the Agent's status changed");
    }
}

struct PrintEvents;

impl AgentEventSink for PrintEvents {
    fn emit(&self, event: AgentEvent) {
        if let AgentEventKind::TurnCompleted { .. } = event.kind {
            println!("turn completed");
        }
    }
}
```

- **Turn events** go to the `AgentEventSink` each call is given: `submit_turn_with_sink`, `steer_turn_with_sink`, `submit_plan_implementation_with_sink`, `compact_session_with_sink`. `emit` is called on the Agent's threads and does bounded work only (sending to a channel, say); it must not block. The event kinds (`AgentEventKind`) are those `exec --json` prints: [JSON events](/docs/json-events).
- **Approvals and questions**: answer `ApprovalRequested` with `resolve_approval` and `UserInputRequested` with `resolve_user_input`; `cancel_turn` cancels a turn.
- **The event journal**: each session keeps a bounded journal of its events; `events_since(session, after)` returns the `AgentEventBatch` after a sequence number, for catching up after a disconnect, and `snapshot(session)` the session's current runtime state.
- **History**: `list_sessions_page` (paged, searchable), `open_session` (a session with its latest transcript), `read_transcript_page` and `read_turn_page` read the committed `ConversationItem`s. A list holds the sessions without a parent unless its request's `parent` is `AgentSessionParentFilter::ChildrenOf(session)`; a request without the field lists those. An `AgentSessionSummary` carries the session's `parent_session_id` and `origin` (`AgentSessionOrigin`: `Side`, `Subagent`, `Review`), and the `cwd` and `branch` it was created in, each `None` when unknown or for a session from before these fields; a runtime snapshot carries `parent_session_id`, `origin` and `ephemeral`. Thinking is `ConversationItem::Reasoning { text, duration_millis, sampling_step, truncated, replay }`: its `text` is for presentation only and never replayed as model input; `replay` is the block the Provider asks to have sent back (`ModelReasoningReplay`): the typed item carries it, Chat Completions' `reasoning_content` on a loaded session too, and only a transcript page's serialization leaves it out ([Thinking](/docs/architecture#thinking)).
- **Export**: `export_session_markdown(session)` returns the session's whole conversation as Markdown, read from every page of its history: a `## User`, `## Assistant` or `## Plan` section per message and plan, a `## Activity` section per tool call (its name and arguments, and the first lines of its output), without the thinking ([Sessions](/docs/sessions#export)). A session with nothing to show is `InvalidInput`. It commits nothing; it reads the history, so call it off the async runtime, as `rename_session`.
- **Run projections**: `AgentSlot::list_run_projections` and `get_run_projection` (activity id, turn number, phase, times, error); Hanafubuki maps them to its Task Center.

| Call                                         | What it does                                                                                                                                                                                                                                                                                                                                                             |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `create_session(mode, role)` (async)         | a new session in `mode` with the role `role` of `roles()` (`None` is `default`): the role's merged instructions after the base instructions, its model and reasoning effort over the Provider's, and its narrowing as the session's `AgentCapabilityScope`. A role no source defines, or an unusable one, is refused (an invalid-input error naming the usable roles)    |

The snapshot (`AgentSessionRuntimeSnapshot`) carries the session's `role` and a summary of its scope (`AgentCapabilityScopeSummary`: how many allow lists and patterns, how many deny patterns, the plugins off, the cap); both are `None`, and absent from the serialized snapshot, for `default`. ## Permissions [#permissions]

A turn's permission mode is fixed when it starts: the mode it is started in, else the session's own mode when it has one, else the configured `permissionMode`, tightened to the `permissionModeCap` of the session's role. `submit_turn_with_sink` and `submit_plan_implementation_with_sink` give no mode of their own; `start_turn` gives its input's (`AgentTurnInput { text, images, skills, permission_mode }`, an `Option<AgentPermissionMode>`), which an input made from text (`AgentTurnInput::from`) leaves `None`. What the modes and the approvals do is in [Permissions and approvals](/docs/permissions).

| Call                                            | What it does                                                                                                                                                                                                                                                                                                                                                                                   |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `set_session_permission_mode(session_id, mode)` | the session's mode, in place of `permissionMode`, until the session ends; kept in memory only, never persisted nor forked. A running turn keeps its mode; the next turn takes this one                                                                                                                                                                                                         |
| `session_permission_mode(session_id)`           | the mode the session was given, or `None` while `permissionMode` applies                                                                                                                                                                                                                                                                                                                       |
| `set_session_sandbox_mode(session_id, mode)`    | the session's `AgentSandboxMode` (`ReadOnly`, `WorkspaceWrite`, `FullAccess`), in place of `sandboxMode`, until the session ends; kept in memory only, never persisted nor forked; a sub-agent takes its parent's. A running turn keeps its sandbox; the next turn takes this one. Independent of the permission mode                                                                          |
| `session_sandbox_mode(session_id)`              | the sandbox mode the session was given, or `None` while `sandboxMode` (or the platform's default) applies                                                                                                                                                                                                                                                                                      |
| `sandbox_status()`                              | `SandboxStatus::Available { backend }` (Linux: `"Landlock (ABI n) and seccomp"`; macOS: `"Seatbelt (/usr/bin/sandbox-exec)"`) or `Unavailable { reason }`, with the configured `[windows] sandbox` applied: whether a command that asks for a sandbox can run ([The sandbox helper](#sandbox-helper))                                                                                          |
| `approve_denied_action(session_id, review_id)`  | the user's approval of the operation the automatic review `review_id` (of a `PermissionReviewCompleted { status: Denied }`) denied, one of the session's ten latest denials: commits a context note the model and the next review read, and emits `HistoryCommitted`, with no turn id, to the sink of the session's latest turn. `approve_denied_action` returns `ApprovalNotFound` for a review that is not one of those denials, and `TurnAlreadyRunning` or `CompactionAlreadyRunning` while one runs. The calls but `sandbox_status`, which reads only the settings, may load the session's history or wait for its staged commit, so call them off the async runtime, as `rename_session` and `set_session_mode`.

## Child sessions [#child-sessions]

A child session records its parent and why it was made; what children are, and what a side conversation is, is in [Sessions](/docs/sessions#children).

| Call                                    | What it does                                                                                                                                                                                                                                                        |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `open_side_conversation(parent)`        | the parent's side conversation, as an `AgentSessionRuntimeSnapshot`: an ephemeral fork of its history at its last turn boundary, with the side policy the model reads first. Opening it again returns the open one. `InvalidInput` while the parent has had no turn |
| `close_side_conversation(side)` (async) | interrupts the side conversation's running turn, stops its background terminals and drops it; `InvalidInput` for a session that is not a side conversation                                                                                                          |

| `delete_session_confirmed`              | also deletes the session's persisted descendants, archived or not, in the same deletion, and closes its live ephemeral children; one that cannot be let go refuses the whole deletion                                                                               |

Turns run on a side conversation through `submit_turn_with_sink`, with their own `AgentEventSink`, as on any session. An ephemeral session is never listed, archived (`InvalidInput`) or recovered; it is gone when closed, when its parent is archived or deleted, or when the Agent stops. `open_side_conversation` blocks, like `rename_session`: call it off the async runtime.

## Editing an earlier message [#edit-from-turn]

`edit_from_turn(session_id, turn_id)` edits the message that started `turn_id` the way the terminal interface's Esc does ([Sessions](/docs/sessions#edit)). It forks the session before the turn (as `fork_session_before_turn`, at the session's current generation and revision), archives the original (as `archive_session`, so with its persisted descendants), and returns `AgentEditFromTurn { session, restored_prompt, restored_images }`: the fork's runtime snapshot and the message's text and image attachments, for the composer.

- `turn_id` is the `turn_id` of a `ConversationItem::TurnStart`, read with `read_transcript_page`; the `UserMessage` after it is the message restored. A turn without one (none started by a message) is refused.
- It returns `Err` with the reason for an archived session, while a turn runs in the session, for a child or ephemeral session, and for a turn the session does not hold.
- When the fork was made but the original could not be archived (a background terminal that would not stop, say), the error says so and names the fork; both sessions remain.
- Files are not restored. It blocks, like `rename_session`: call it off the async runtime.

A standalone consumer moves into a worktree with `AgentRuntime::set_working_directory`. A hook call naming a key no hook has, or a state file that cannot be written, is `InvalidInput`. In a host, the hooks are read from its configuration directory alone; their trust and enablement are in the data directory's `hooks-state.json`.

A review is a durable child session (origin `Review`), listed among its parent's children as soon as `start_review` creates it, which is how an interface finds the session to show or to `cancel_review` while the call waits. `start_review` is refused (`InvalidInput`) for a session that has had no turn, a blank custom request, or a base branch outside a Git repository; a review that is interrupted or fails tells the parent so and returns the error. The parent's note is a `ContinuationContext` of provider `agent` and hook `review-exit`; if the parent runs a turn or a compaction when the review ends, the call waits for it to end. `AgentReviewTarget` is a tagged object (`{"type": "baseBranch", "branch": "main"}`) that rejects unknown fields.

A sub-agent is a durable child session (origin `Subagent`), so its turns, events and history are read like any session's: a status feed reads the sub-agents from `subagents(parent)` and each one's events with `events_since`; no parent-side event is added. Its turns run with no `AgentEventSink` of the caller's: the events land in its journal. A turn the user starts on a sub-agent goes through `submit_turn_with_sink` as on any session.

## Installed plugins [#installed-plugins]

The [installed plugins](/docs/architecture#installed-plugins) are in the data directory's `plugins/`, and `[plugins]` in the Agent's settings says which are on. The service reads them when it is built and again on each reload:

- `reload_packages()` loads the installed packages again as the settings leave them on and brings the Agent up to date without a restart: the Skill catalog reads the enabled packages' Skills, the next turn's hooks include theirs, and their MCP servers run (one added or changed has connected, or failed, when it returns; one that is gone is disconnected). The service calls it in the background after `write_settings`, `set_plugin_enabled`, `mcp_write_server` and `mcp_delete_server`, and the `plugins` row once a linked package's directory changed; a host that writes `[plugins]` or changes the store by other means calls it itself.
- `packages()` returns `Vec<AgentPackageStatus { id, version, format, display_name, description, source, enabled, content, hooks_to_trust, guest, issues }>`: every installed package, on or off; `source` is where it was installed from (`PackageSource`, `None` without an install record); `content` (`AgentPackageContent { skills, mcp_servers, hooks, roles }`) is what it contributes while on (Skill ids, the names of its MCP servers that run, hook keys, the names of its roles, `<plugin>:<role>`); `hooks_to_trust` the keys of its hooks that wait to be trusted (`trust_hooks`); `guest` its code's, for a package in this project's format with a runtime (`AgentPackageGuest { runtime, permissions, granted_permissions, status, settings, config_schema }`, `runtime` a `RuntimeKind` (`Process` or `Wasm`), `status` a `GuestStatus { state, error, last_exit, stderr_tail, restarts, process_id, issues }`; `ungranted()` is what it asks for and was not granted, never anything for a WebAssembly module); and `issues` what could not be read or used. `package(id)` is one of them, `None` when it is not installed. In safe mode the packages are listed and none is loaded.
- `grant_package_permissions(id, permissions)` records that the user granted a package's code `permissions` (`PackagePermissions { network, workspace, env }`, those its consent showed) and reloads the packages; a program guest starts only once what its manifest asks for is granted, and a WebAssembly guest asks for nothing. `retry_package(id)` starts a guest that failed again, with an empty restart window ([Code plugins](/docs/architecture#code-plugins)).
- `set_package_settings(id, settings)` replaces the settings of a package's code (`[plugins."<id>"].settings`, a JSON object; `null` removes them), checked against its manifest's `configSchema`, and reloads the packages: its guest starts again configured with them, and views them as its `settings`. `AgentPackageGuest` shows `settings`, `config_schema` and, in `status.issues`, what of its declared contributions was left out ([Code plugins](/docs/plugin-rules#code-plugins-rules)).
- `validate_package(dir)`, a free function, checks a plugin's directory before it is installed, as `plugins validate` does ([Check it](/docs/writing-plugins#validate)): its manifest as an install reads it, the paths it declares, and its code as the guest host would run it, without starting anything. It returns `AgentPackageValidation { name, version, format, manifest, code, issues }`, or an error for a directory with no manifest an install accepts.
- A guest runs under the platform's sandbox, which on Linux and Windows is the program itself started again as the [sandbox helper](#sandbox-helper): a program that does not call `helper_dispatch()` runs no guest.

The lifecycle calls change the installed plugins through the store the service opened, write the settings, reload, and return when the result is in effect. Each takes or names a package by its id, `<plugin>@<marketplace>`; their errors are `String`s.

Each lifecycle call on a package tells the plugin event sink, after its reload: `AgentPluginEventSink::package_changed(&AgentPackageChange { id, kind, error })`, with `kind` `Installed`, `Removed`, `Enabled`, `Disabled`, `Updated`, or `Failed` (the call failed, `error` says why; the package is as it was). The method has an empty default, so a sink that only refreshes on `plugins_changed` needs no change. `retry_plugin(name)` starts a failed built-in or host row again; `--safe-mode` (`AgentStartOptions::safe_mode`) is how the command line reaches safe mode.

- A plugin's hook is listed by `hooks_list()` with `source` `{"plugin": {"id", "root", "data"}}` (`HookSource::Plugin`); the user's and the project's stay `"user"` and `"project"`.
- `mcp_snapshot()` lists the plugins' servers as `plugin_servers` (`McpPluginServerSnapshot { plugin, server, status }`); `settings` stays `mcp.toml`'s.
- `plugin_status()` has the `plugins` row, which tells the model of the enabled packages.

## Logging [#logging]

The facade installs no logger: the host keeps its own `log` implementation, and the Agent's records go there. The standalone binary uses `logging::install_file_logger` (`hanafubuki-agent.log`, rotated past 8 MiB into `.1`…`.3`). The Agent's own records follow its content-logging rule: model content, reasoning, tool arguments and tool results appear only at `trace`, truncated to a bound, and headers and credentials never. So the host's log level is how a user selects `trace` (Hanafubuki's `log_level` setting).

## Testing [#testing]

- Turn on the `test-support` feature of `hanafubuki-agent` in `[dev-dependencies]` for `hanafubuki_agent::test_support`: `mount` (mounts a plugin in a context that provides the registries and `PluginFaults`), `test_host`, the scripted model and MCP servers. The scripted model server answers `GET …/models` from listings of its own when it is given some (`FakeServer::with_listings`, `FakeListing`), else with its next response, as any request. The test Agent (`new_with_host`) discovers no models by itself, and `configure_test_provider` writes `modelMetadata.discovery = "off"`, so even an Agent a test builds as a host builds its own (`AgentApplicationService::open`) sends the scripted server only the requests the test makes.
- A host keeps goldens of its own that pin what the model receives with its plugins and instructions; a model-visible change on the Agent's side changes them too, and they are regenerated on purpose.
- A host tests the panic-hook bridge, in a child process.
