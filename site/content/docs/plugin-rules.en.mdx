The Agent is composed of plugins on [kardia](https://github.com/licyk/kardia), the Rust implementation of Cordis. This page holds the **rules** of that composition: read the sections a change touches before changing any tool, context section, approval rule, continuation hook, tool lifecycle hook or observer, the plugin host, its manifest or the plugin configuration, the crate boundaries or the host interface, or the goldens; update this page when the design changes. The repository-wide rules (locks, paths, decoding strictness, content logging, layout) are in [Contributing](/docs/contributing) and [AGENTS.md](https://github.com/licyk/hanafubuki-agent/blob/main/AGENTS.md); how the parts fit together, and why, is [Architecture](/docs/architecture).

## Composition rules [#composition-rules]

1. **The kernel depends on nothing a plugin can replace.** kardia restarts a plugin when an injected service is replaced, and a kernel restart would drop every live session. The kernel plugin injects nothing; it publishes registries created before the runtime starts, and the kernel reads them as snapshots per turn or per sampling step.
2. **Registrations are effects of the caller.** Contribute through `hanafubuki_agent_contracts::Register` on an injected registry service. The entry belongs to the calling plugin (`Svc::caller`) and is removed when that plugin stops; a plugin never keeps a handle to undo it. A refused registration (`RegistrationError`, a duplicate id for one) fails the plugin.
3. **Running calls keep their entry's plugin alive, bounded.** A call takes an `EntryLease` from a snapshot entry and observes its cancellation. A tool a source planned leases its source's entry, and so does the source while it contributes. A stopping plugin first hides its entries from new snapshots, waits `DRAIN_GRACE` for leased calls, cancels them, waits `RETIRE_CANCEL_BOUND`, then continues its teardown.
4. **The kernel reaches plugins only through the contracts' registries.** A hook that changes an outcome is a kernel-owned registry with a documented ordering and combination (deny-only, tighten-only, first match, ordered by priority and id), never a kardia event: the kernel holds no kardia context. The result never depends on registration order, because plugins start concurrently. A new extension point is added with its first real user.
5. **No long async effect bodies.** kardia never cancels `apply` or an async effect, so a loop there keeps its plugin and every ancestor from stopping; the host only bounds the damage (the row fails after `PLUGIN_START_TIMEOUT`, and the fiber stays stuck until its Agent instance's runtime stops). `apply` validates config, registers and spawns; long-lived work runs through `spawn_scoped_worker` (the plugin injects `PluginFaults::NAME`, which the kernel plugin provides), or in a worker group the plugin stops from a `ctx.defer` disposer (the `execution` plugin's activity monitors).
6. **Unchecked root access stays in the host.** Only the module host that owns the kardia root (`hanafubuki-agent-host`, configured by the facade's `AgentHost`) and the facade read plugin state from it. Plugins declare what they use (`PluginDef::inject`); domains never see a kardia context.
7. **Plugins return errors, never panic.** Production plugin sources contain no `.unwrap()` or `.expect(`; a failing `apply` leaves the plugin `Failed`, which the host reports and a configuration update or `retry_plugin` restarts. A panic is a bug, but it stays in its plugin (which the host restarts after a backoff): kardia catches it in `apply`, effect bodies, disposers and event listeners, and the kernel guards every call it makes into plugin code. That holds in release builds too: they unwind, and the panic hook lets a panic on an Agent thread unwind to its catch. Locks are `parking_lot`, never std.
8. **Every kardia mutation runs on the Agent runtime.** kardia spawns on the ambient runtime and panics without one; host methods that mount or update plugins are async, and their callers send them to the Agent runtime.

## Where Agent code runs [#where-agent-code-runs]

Everything the Agent runs is on a thread where a panic is contained: the panic hook lets it unwind to its catch there, and aborts the process anywhere else.

- **The Agent runtime** (a `ContainedRuntime` of `hanafubuki-agent-runtime`, threads `agent-rt`), one per Agent instance: the slot's start builds it and the slot keeps it until that instance's stop (shutdown, a restart, a turn off) stops it last. It runs every call a host makes into the Agent, the whole start (construction and recovery on its blocking pool, the plugins' start, the MCP servers' background start), the async shutdown stages, and what those spawn: turns and compactions, kardia's effects and disposals, scoped workers, the host's fault, retire, remount and reconfigure tasks, MCP and model clients. Its blocking pool runs `BlockingService` and every `BlockingOperationPort` call of the Agent.
- **Contained by the Agent's own foundation.** These marks and guards are thread-locals of `hanafubuki-agent-foundation`, which a host's foundation cannot see. A host's panic hook therefore takes `hanafubuki_agent::panic::is_panic_contained` as its second containment check: a panic is contained when either foundation says so.
- **The Agent's worker threads**, all in `BackgroundWorkerGroup::contained` groups: history writers, MCP stdio readers, the memory supervisor (whose own current-thread runtime marks its blocking pool too), the `execution` plugin's activity monitors and the Skill catalog watcher; and the slot's supervisor thread (`agent-supervisor`).

Not Agent threads, so their panics still abort: the host's threads and the threads of the services the Agent calls (an executor's reader and waiter threads). kardia-hmr's own threads (a process guest's `guest-stdin`, `guest-stdout` and `guest-stderr`, a WebAssembly engine's `wasm-epoch` ticker) catch their panics, which kill the guest they serve (its exit report gives the reason, and it restarts as after any fault); kardia-hmr marks them itself, and the guest host registers kardia-hmr's check (`kardia_hmr::is_panic_contained`) with the foundation's `register_containment_check` when it is built, so `is_panic_contained` is true there too. A WebAssembly guest's code itself runs on the Agent runtime's blocking pool, where a trap is an error, not a panic. A new spawn in Agent code lands on the ambient runtime or in a contained group, never on a plain thread.

### Panics in plugin code [#panics-in-plugin-code]

The kernel calls plugin code only through a guard: `RegistryEntry::guard` or `guard_async` (the entry knows its owner), or `PluginFaults::guard` and `guard_async` where no entry is at hand; so does the facade's feature call ([Host, configuration and status](#host-configuration-and-status)). A panic there is logged at error, reported to `PluginFaults` as a `PluginFault` of the entry's owner (plugin, `ExtensionPoint`, bounded panic message), and becomes `PluginPanicked`, which the caller turns into that call's own error path:

| Call                                                | A panic means                                                                         |
| --------------------------------------------------- | ------------------------------------------------------------------------------------- |
| tool `availability` (registered or sourced)         | the tool is `Omitted` from the step                                                   |
| tool `permission`, `invoke`                         | the tool error "the tool failed with an internal error", as any failing tool          |
| tool source `contribute`                            | the source failed: its trust decides (an `Optional` one is omitted)                   |
| context and turn admission `contribute`             | that contributor is left out of the admission                                         |
| prompt `prepare`                                    | the contributor's values are left out with a warning                                  |
| prompt `contribute`                                 | the contributor renders no fragment                                                   |
| approval rule `evaluate`                            | a denial naming the plugin: a rule fails closed, never "no opinion"                   |
| continuation hook                                   | the hook failed: its failure policy decides                                           |
| tool lifecycle hook                                 | the hook failed and has no say: the call runs, its output stands                      |
| a hook's `applies` (continuation or tool lifecycle) | the hook does not apply                                                               |
| observer `observe`                                  | that observer is skipped; the others are told and the committing thread never unwinds |
| a `spawn_scoped_worker` body                        | the worker ends, logged with its label                                                |
| a feature call (`feature call`)                     | the call is `FeatureUnavailable`                                                      |

The panic message reaches the log and the plugin's status, never the model. The `mcp` plugin contains one panic itself: `McpTool::invoke` runs its server's call under `catch_panic_async`, so a panic there is that call's error and **that server's** fault, never the plugin's. The kernel never holds a lock across a guarded call, so the guards change no lock ordering. The identity accessors (`id`, `descriptor`, `kinds`, `rank`, `trust`) are data and are not guarded.

After a fault the plugin is stopped and reports `failed` (`panicked in <extension point>: <message>`), and the host mounts it again by itself after the restart policy's next delay (2 s, 10 s, 30 s, three in ten minutes); past that, until `retry_plugin`, a new configuration or turning it off and on mounts it anew, once its teardown has ended. A plugin whose start failed, rather than one that panicked, is not restarted by itself.

### Bounds on plugin calls [#bounds-on-plugin-calls]

No async kernel call into a plugin can hold up a turn for good: each has a deadline; past it the kernel cancels the call's token, drops its future and takes the call's error path, so a hung plugin costs only what it would have contributed. The deadline the kernel sets itself is `AgentHardLimits::plugin_call_deadline` (10 s):

| Call                                                                                                       | Bounded by                                                                      | Past the bound                                                                                       |
| ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| context and turn admission `contribute`                                                                    | `plugin_call_deadline`; the admission's cancellation, or dropping the admission | that contributor is left out, recorded as its plugin's issue; a cancelled admission fails            |
| tool source `contribute`                                                                                   | `plugin_call_deadline`                                                          | the source failed: its trust decides (an `Optional` one is omitted, a `Required` one fails the plan) |
| prompt `prepare`                                                                                           | `plugin_call_deadline`                                                          | the contributor's values are left out with a warning                                                 |
| tool `permission`                                                                                          | `plugin_call_deadline`                                                          | the tool error "the tool's permission check did not finish within N s and was stopped"               |
| tool `invoke`                                                                                              | `ToolDescriptor::timeout`, else the turn's `tool_idle_timeout` (10 min)         | the tool error "the tool did not finish within N s and was stopped"                                  |
| continuation hook, tool lifecycle hook                                                                     | the turn's `tool_idle_timeout`                                                  | a continuation hook's failure policy decides; a tool lifecycle hook has no say                       |
| tool `availability`, a hook's `applies`, prompt `contribute`, approval rule `evaluate`, observer `observe` | none: synchronous, pure and bounded by contract                                 | (a hang here blocks its caller; these calls do no I/O)                                               |

The turn's own cancellation ends every call of the turn too; context and turn admission calls run before the turn exists, so they observe a child of the admission's token instead, which is also cancelled when the admission is dropped. Built-in and host rows are bounded like any other plugin: one that answers in time behaves as before. A plugin's start and stop have bounds of their own ([Host, configuration and status](#host-configuration-and-status)).

## Tools [#tools]

- A tool's `ToolDescriptor` fixes the model-visible spec, exposure, execution class, effect (`ReadOnly` tools, registered or sourced, are the only ones in Plan mode), activity action, memory effect and timeout for the lifetime of the registration (for a sourced tool, of the step). `availability` may offer it as a freeform tool or omit it for a step (`ToolPlanContext`).
- The kernel owns the pipeline and plugins cannot reorder it: mode policy, `permission`, approval when review is required (the approval rules, then the session's allowance, then the permission mode's flow), then `invoke` with the one-shot approval. `invoke` re-checks that the approval matches the call it runs.
- The pipeline runs under the step's gate: an in-flight permit, then read access for a `ConcurrentRead` tool or exclusive access, first come, first served, so `permission` sees what the step's earlier calls did. An approval that waits (the user, or the reviewer model) releases the gate and takes it again once approved; the step's other calls run meanwhile, and the user is asked one prompt at a time per step. An approved action can be stale once other calls ran in the gap; the re-check in `invoke` (`verify_tool_approval`, a domain's own check) turns that into the call's error, never a run of something unapproved. A call admitted after its turn was cancelled does not start.
- `invoke` runs within `ToolDescriptor::timeout`, or the turn's `tool_idle_timeout` (10 min) when it is `None`; neither `permission` (bounded by `plugin_call_deadline` itself, [Bounds on plugin calls](#bounds-on-plugin-calls)) nor an approval wait counts. A call past it is cancelled and its future dropped, and the model reads "the tool did not finish within N s and was stopped"; the turn continues. Work the call left on the `BlockingService` observes the cancellation and ends itself. A tool whose own bound pauses while it waits for the user sets the timeout above that bound: an MCP tool's is its server's call timeout plus one elicitation wait (`MAXIMUM_MCP_ELICITATION_WAIT`).
- Outputs commit in call order, each as soon as every earlier call's has. A call that ends in an error (the turn's cancellation among them) commits nothing; the step's other calls still run to their end and commit, since their effects happened, then the step returns the first error. On a cancel only the unfinished calls get the synthetic interrupted output, which the model reads right after its call.
- A turn samples at most `AgentHardLimits::maximum_sampling_steps` (32) times; the next step fails it with `LimitExceeded { "sampling steps" }` (`budget_exceeded`), every earlier output committed. At `turn_deadline` (30 min) the kernel cancels the turn as a user's cancel would (pending approvals and questions aborted, finished calls committed) and ends it `Failed` with `TurnDeadlineExceeded` (`deadline_exceeded`). Neither limit is shown to the model.
- Blocking work runs on the injected `BlockingService`; a call observes `ToolInvocation::cancellation`. `ToolInvocation::progress` only queues (`report` never waits), from the call or from a monitor thread that outlives it; the kernel commits the session's progress in order.
- A tool that exists only while something outside the Agent offers it (an MCP server's catalog, the memory settings) comes from an `AgentToolSource`. The kernel asks each source once per sampling step with a `ToolSourceStep`, and it returns `SourcedTool`s: an `AgentToolHandler` built for that step plus the identity the plan records (provider id, tool id, generation, namespace description, activity subject) and its `ToolSourceTrust`. Keep the identity stable while the tool does not change, and change it when the tool does: a deferred-tool selection (the `ToolSelection` history item) names the identity, and the kernel validates a tool's schema and spec once per identity (`AgentToolSpecCache`).
- A sourced tool is planned and run like a registered one, with two differences: the kernel checks the model's arguments against its schema before `permission`, and its trust is external: an `Optional` tool that cannot be planned is omitted (reported in `tool_catalog_omissions`), a `Required` one fails the plan. A name collision is neither (see [Tool names](#tool-names)). A source whose plugin stops while it is asked is omitted whatever its trust, so turning a plugin off never fails a step; one that does not answer within `plugin_call_deadline` fails like a source that returned an error. Over the direct catalog budget only sourced tools are deferred.
- A tool source may return a `ToolPlanLease` with its contribution; the plan keeps every lease and each call receives them as `ToolInvocation::plan_leases`. Find yours with `ToolInvocation::plan_lease::<T>()`, never by downcasting the `Arc`.
- Per-turn data reaches a call as `ToolInvocation::turn` (`TurnExtensions`, keyed by type): what the turn admission contributors froze for the turn. Read yours with `turn.get::<T>()` and treat a missing value as a tool error. Contracts name only the values the kernel itself reads (`SelectableSkills`).
- A tool adds instructions to the conversation by returning a `ToolContextFragment` with its `ToolResult`. The kernel commits it right after the output as the context of the Skill `source` names, once per turn and Skill, and turns a `source` that is not a Skill id into a tool error.
- The kernel's own tools (`AgentCoreTool`: `new_context`, `update_plan`, `request_user_input`, and the compression tools `compress`, `decompress`, `search_context`, `acp_status`, `acp_cache`, `absorb`, `acp_retrieve`, `acp_rule`) act on the turn or on the session's compression state and are not plugins; the compression tools are planned only while the session's compaction strategy is `hierarchical`, in Plan mode too, the last three only while their features are on. Nor is `tool_search`, the plan's search over deferred tools. Their twelve names are `RESERVED_TOOL_NAMES`: no plugin may register a tool by one of them.
- An activity action is an open identifier (`AgentActivityAction`); an interface labels the names it knows and shows the generic tool label otherwise, so a new tool needs no frontend change.

### Tool names [#tool-names]

- A tool's name is its `ToolName` (namespace segments and a local name). The registry and the planner key it by its flattened form (`namespace__name`); that string is never parsed back.
- `ToolRegistry::admit` refuses a registration whose flattened name is reserved, already registered, or longer than a tool id (128 bytes). The `RegistrationError` fails the registering plugin at its start, with nothing registered; the other plugins and the turns are unaffected.
- The wire name is per request: `assign_provider_names` writes it into each planned tool's provider spec when the plan is built for the step's protocol. Where the protocol takes namespaces (Responses) a namespaced function keeps its namespace and local name; elsewhere, and for a namespace another provider already uses, the name is flattened. Every name is fitted to `ToolProviderCapabilities::maximum_tool_name_bytes` (Responses 128, counted over `namespace__name`; Anthropic Messages 128; Chat Completions 64, OpenAI's function-name limit).
- Names are unique over their flattened form, with `tool_search` held for the plan's search. In planning order (trust, then name, provider id, tool id) the first tool keeps its name; a later one that collides, or one too long, is cut and ends with `_` and 12 hex digits of a hash of its `(provider id, tool id)`, so it is the same on every step. A collision (only a sourced tool can collide, since registration refuses the others) is reported in `tool_catalog_omissions` with the reason "renamed to `<name>`"; the tool stays planned. Nothing about a name fails a step.
- A returned call is resolved by lookup of its `(namespace, name)` in the plan (`AgentToolPlan::resolve_call`); a name the request did not carry is an unknown tool. The decoders return the provider's namespace and name apart, and history records both, so Responses replays a call with its namespace and a protocol without namespaces replays it as `namespace__name`.
- Schemas are lowered by the same per-protocol rule: a protocol whose `strict_json_schema` capability is set (Responses) gets each tool's schema whole; one without it gets the portable keywords (`portable_model_schema`). Tools are never sent `strict`. The kernel validates arguments against the whole schema either way.

### Model tool arguments [#model-tool-arguments]

The model's arguments are read tolerantly; a mistake is a field-named error the model reads back as the tool result, never a failed turn.

- No argument type uses `deny_unknown_fields`, and no helper rejects a key it does not know: an unknown key is ignored. Ignoring it never widens what runs, because capabilities (approvals, receipts, resolved paths, executor ids) are never arguments, and the call still goes through `permission` and approval. The one exception is a value meant for another action of the same tool: Hanafubuki's `provision_instance` rejects a non-null property its selected action does not take, since its actions create and delete instances.
- A missing or `null` optional field is absent. A field that is semantically required (`cmd`, `path`, `recursive` of `delete_path`) stays required.
- A limit out of range is clamped into its bounds with a note (`clamped_u64`/`clamped_usize`, `ArgumentNotes`, appended to the result by `ToolResult::with_argument_notes`); a limit that guards safety (a byte or depth cap) clamps to the cap and never past it, and an omitted one takes its default. Containment is not a limit: a path is passed as given and the domain resolves and contains it.
- `decode_arguments` names the field an error is about (`invalid tool argument plan[1].status: ...`).
- A sourced tool's arguments are checked against its schema (`validate_dynamic_tool_arguments`); a `type` the check does not know constrains nothing, and an integral number is an `integer`.
- A call the step cannot run is answered, never a protocol failure, and its output keeps the call/output pair valid for every protocol: a name the step does not offer (unknown, `Hidden`, mode-hidden, provider-incompatible) gets one identical error, "no tool named `<name>` is available in this step", so a hidden tool stays indistinguishable from an absent one; a Deferred tool not yet admitted gets the discovery error with the `tool_search` recovery; arguments that could not be parsed or are over `maximum_tool_argument_bytes` get an error with a 512-byte preview; a malformed `tool_search` gets a field-named error.

## Context [#context]

- A `ContextContributor` declares the kinds it produces (`ContextSectionKind`) and returns at most one `ContextSection` per declared kind. Two contributors declaring one kind, or a contributor declaring `tool_catalog_omissions` (the kernel writes it every sampling step), fail the registering plugin.
- At turn admission the sections are collected from one registry snapshot (`collect_world_state`; contributors run one after another under an entry lease, each within `plugin_call_deadline`). A contributor that fails (an error, a panic, no answer within the deadline, its plugin stopping) is left out of that turn; so is a section of a kind it did not declare, a kind already produced, or a plugin kind past `MAXIMUM_AGENT_PLUGIN_WORLD_STATE_SECTIONS` (7, a host's kinds among them; the Agent's six known kinds have their own slots). Each is recorded as an issue of its plugin (`PluginFaults::set_issue`), which the plugin's status shows as its `warning` (and the Agent as degraded) until that contributor succeeds again or the plugin is mounted anew; the turn is never refused over it. A kind no contributor returns is removed from the world state on that turn, so a contributor plugin that failed to start leaves its sections absent rather than failing every turn.
- A host context never refuses the message or steering it came with: one this build cannot use is dropped with a warning, and one over `MAXIMUM_HOST_CONTEXT_BYTES` (4 KiB) is cut on a UTF-8 boundary.
- The result is collected in kind name order, so history records it the same way every time; the model is shown it in its renderers' order.
- A `ContextRequest` carries the session id, the session mode, the turn's permission mode, the text of the user's message the turn was submitted with (`user_message`, `None` for a turn without one, such as implementing a plan) and the host input's `TurnExtensions`, which the Agent passes on unread but for the turn's `SandboxPolicy`, which the facade adds (the `sandbox` section is rendered from it). Treat a missing value as "not supplied for this turn". Long work runs on the `BlockingService`.
- Text rendered from JSON goes through `ContextSection::from_json`, which sorts object keys so the version digest is stable.
- A section is at most 32 KiB, and all of them 64 KiB.

### Context renderers [#context-renderers]

- Everything model-visible that is neither history nor a tool is a context section of a `ContextSectionKind`: a world-state section (persisted, from a `ContextContributor`) or a prompt fragment (per request, from a `PromptContributor`). The model is shown a section by the `ContextRenderer` of its kind, which the plugin that owns the kind registers in the `ContextRendererRegistry` (one per kind; an invalid or repeated kind fails the registering plugin).
- A renderer is data: the `ContextSlot`, its `order` within the slot, the `ContextRole`, a `preamble` (what the section is and what authority it **lacks**), an `epilogue`, and `versioned`, which puts the content in an `<agent_world_state kind=".." version="..">` element. A kind's wrapper text lives in the plugin that owns it, never in `hanafubuki-agent-model-api`, which sends a fragment's role and rendered text as they are and matches on no section kind. Sections without a framing of their own use `WORLD_STATE_PREAMBLE`.
- The kernel registers the renderer of the kind it writes itself (`tool_catalog_omissions`) when its registries are built; the `workspace-context`, `permission-mode`, `skills`, `memory`, `goal`, `subagents`, `review`, `hooks` and `plugins` plugins, the guest host and a host's plugins register theirs with their contributors. The kernel knows no host kind.
- The kernel takes a renderer snapshot for every model request. A section whose kind has no renderer (its plugin stopped) is left out of that request; a world-state section stays in history, and the next admission removes it if no contributor produces it.
- Order: every run of adjacent sections in a request is ordered by slot (`Instructions`, `WorldState`, `Capabilities`, `Memory`), then by the renderer's `order`, then by kind name; every other item keeps its place. Registration and mount order never show: a plugin that restarts (a fault, a reconfiguration, turned off and on) shows its sections where they were, so the provider's cached prefix survives it, and rows can be added to the manifest or moved in it for mount reasons alone. The prompt fragments join the run the conversation opens with. A world-state section that changes later is shown where it changed. Only the latest version of a kind is ever shown, so there is no "replaces previously provided" notice and no section-changed event: the persisted `WorldStateUpdate` is the change record.
- The ranks are bands by owner; a renderer takes a free rank in its owner's band at the place its section belongs, and a plugin with two renderers in one slot gives each its own. The bands are a convention, not checked at registration.

| `order` | Renderers                                                                                                                                                                                                                                                                                         |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0       | the kernel: `tool_catalog_omissions`                                                                                                                                                                                                                                                              |
| 100–499 | the Agent's capability plugins, 100, 110, … in manifest order: `memory` 100 (`agent_memory`), `skills` 110 (`skill_catalog`), `goal` 120 (`goal`), `subagents` 130 (`subagent_guidance`), `review` 140 (`review_instructions`), `hooks` 150 (`hook_context`), `plugins` 160 (`available_plugins`) |
| 500–599 | a host's plugins ([Host plugins](/docs/host-plugins#context-sections-and-renderers))                                                                                                                                                                                                              |
| 700–899 | the Agent's context plugins: `workspace-context` 700 (`workspace_instructions`, `workspace_roots`) and 701 (`environment`), `permission-mode` 710 (`permission_mode`) and 711 (`sandbox`)                                                                                                         |
| 900     | installed plugins' code: every guest's context sections and prompt, so they come after the Agent's and the host's and among themselves in kind order                                                                                                                                              |

### Turn admission [#turn-admission]

- A `TurnAdmissionContributor` produces per-turn data once, when a turn is admitted, as `TurnExtensions`. The kernel freezes them on the turn and hands them to every tool call and prompt contributor of the turn; a turn restored after a restart has none.
- Contributors run before the kernel admits the turn, one after another in `(rank, id)` order under an entry lease, each within `plugin_call_deadline` (`collect_turn_extensions`). An error, a panic, no answer within the deadline, a contributor whose plugin is stopping, or a value of a type another contributor already returned leaves that contributor out of the turn, recorded as its plugin's issue as for a context contributor; the result never depends on registration order. The one admission that still fails is a Skill the user referenced explicitly that the turn cannot resolve: without the `skills` plugin's values it is refused ("the Skill catalog is unavailable") rather than run without it.
- The kernel reads one value itself: `SelectableSkills`, the Skills an explicit reference or a `$mention` may select, with its `mention_exclusions`, the names a plain `$mention` names instead of a Skill.

### Prompt fragments [#prompt-fragments]

- A `PromptContributor` renders model-visible fragments from the turn's `TurnExtensions`, what the contributors prepared for the request's sampling step and the session's context window (`PromptRequest`). A `PromptFragment` has a kind (a `ContextSectionKind` whose renderer the same plugin registers), an optional version (shown only by a versioned renderer) and content.
- `prepare` is the one async, I/O-allowed call: once per sampling step, when it starts, the kernel asks every contributor of the step's snapshot, one after another in `(rank, id)` order, with a `PromptStep`, under a lease on its entry, with a child of the turn's cancellation and within `plugin_call_deadline`. It returns typed values, merged into the step's prepared values. A contributor whose plugin is stopping prepares nothing; an error, no answer within the deadline, or a value of a type an earlier contributor prepared, leaves that contributor's values out of the step with a warning. Only the turn's cancellation fails the step.
- `contribute` is pure and bounded (no I/O, no blocking, no per-call state, never a call into the kernel), so the kernel calls it without a lease. It returns nothing for a request that lacks what it renders. Values it needs from outside the turn are loaded in `prepare`, never in `contribute`.
- The kernel never runs a contributor under the session's lock: it reads the turn's extensions and context window under the lock, releases it, prepares the step and renders the fragments, and builds the request under the lock again. It does so once when a sampling step is prepared, and every request counted for that step uses that one rendering.
- A budget a plugin measures in tokens uses `hanafubuki_agent_contracts::{estimate_tokens, token_budget_bytes}`, the estimate the kernel admits requests by.
- The kernel reads one prepared value itself: `AgentMemoryStep`, the step's memory policy. A step without one (the `memory` plugin is off) shows answers as they are, commits no citations and marks no pollution.
- Instructions are not prompt fragments: the session's instructions and the kernel's Plan-mode prompt are session configuration.

## Approval rules [#approval-rules]

- A plugin that owns an action tightens its approval with an `ApprovalRule`, registered next to the tools that produce the action. A rule no single plugin owns would stay in the kernel.
- `evaluate` inspects the `ApprovalAction` and the origin of the session that asks (`Option<AgentSessionOrigin>`: `None` for a session without a parent), so a rule can hold for one kind of child session only (the `review` plugin's). It is pure and bounded, so the kernel calls it without a lease. Every call of a step is judged by the step's frozen `ApprovalRuleSnapshot`, so a rule cannot disappear under a call that is still draining.
- A rule returns `None` (no opinion), `RequireUser` or `Deny { reason }`. They combine monotonically: any denial rejects the call with the reason as its model-visible error (several give their distinct reasons sorted and joined); otherwise any `RequireUser` makes the action `Manual` even under `AutoReview` or `FullAccess`; otherwise the turn's permission mode decides.
- A rule never relaxes approval. An action a tool declares `NotRequired` or `Forbidden` never reaches the rules; a hard refusal belongs in the tool's `permission`.
- The user may answer a `Manual`-mode prompt with `AllowForSession`: later actions of the same tool (`(provider id, tool id, generation)`) in the session are authorized without asking whatever the turn's mode, but only where the rules have no opinion. A rule's `Deny` still rejects and its `RequireUser` still asks, and that prompt does not offer `AllowForSession`. The allowance lives in the session's runtime state only.

## Continuation hooks [#continuation-hooks]

- A hook asks to keep a turn going after a candidate final answer. The kernel snapshots the registry when it starts a sampling step and, if the step ends with a final answer, asks the hooks in order. Each call holds an entry lease and observes a child of the turn's cancellation, bounded by the turn's tool idle timeout. A hook whose plugin is stopping is skipped.
- `Pass` asks the next hook, `Stop` ends the turn without the remaining hooks, and `Continue` returns 1 to `MAXIMUM_CONTINUATION_FRAGMENTS_PER_HOOK` non-blank fragments of at most `MAXIMUM_CONTINUATION_FRAGMENT_BYTES`, which the kernel commits as `ContinuationContext` before it samples again. A failure or timeout fails the turn under `FailTurn` and is skipped under `Ignore`. The `hooks` plugin registers one for the user's Stop hooks (priority 0), and the `goal` plugin one that keeps an active goal going (priority 100, so a Stop hook that ends the turn comes first); both are `Ignore`.
- `applies(context)` is a pure, bounded inspection the kernel asks before the lease (by default a hook applies): a hook that does not apply is neither called nor reported, so a hook with nothing to decide adds no event.
- The kernel commits one `ContinuationContext` of its own, outside any hook and any turn: the note that the user approved an action automatic permission review denied (`approve_denied_action`), under provider `kernel` and hook `approved-denied-action`. A plugin hook does not use those ids: the permission reviewer reads a fragment under them as the user's authorization ([Permissions and approvals](/docs/permissions#approve-denied)).

## Tool lifecycle hooks [#tool-lifecycle-hooks]

- A `ToolLifecycleHook` runs around each tool call of a sampling step that the step offers with usable arguments: registered and sourced tools, the kernel's own tools and `tool_search` alike (a rejected call has none). The kernel freezes an ordered snapshot of the registry with each step's tool plan, in `(priority, provider id, hook id)` order, never registration order.
- `applies(phase, call)` is a pure, bounded inspection the kernel asks first, without a lease: a hook that does not apply to a call is neither called nor reported, so a plugin with nothing to do costs a call nothing and adds no event.
- **Before the call** (`before_tool_use`): ahead of the mode check, `permission` and approval, and outside the step's gate, so a slow hook holds up no other call. The hooks are asked in order and the first `Deny { reason }` ends it: the call does not run, and `reason` is its model-visible error. The combination is deny-only: a hook can refuse a call, never allow one that the permission mode or the approval rules would not.
- **After the call** (`after_tool_use`, with the call's output, an error output included; not after a denial): `AddContext { fragments }` gives 1 to `MAXIMUM_CONTINUATION_FRAGMENTS_PER_HOOK` non-blank fragments of at most `MAXIMUM_CONTINUATION_FRAGMENT_BYTES`, which the kernel commits as `ContinuationContext` under the hook's provider and hook id once every output of the step is committed: a fragment between two outputs would split a protocol's batch of tool results. Fragments out of those bounds are the hook's failure.
- Each call holds an entry lease and observes a child of the turn's cancellation, bounded by the turn's tool idle timeout. A hook that fails, times out, panics or whose plugin stops has **no say**: the call runs and its output stands. Hooks are the user's policy scripts, and a broken one must not stop the Agent's tools; a rule that must fail closed is an [approval rule](#approval-rules). The turn's own cancellation ends the turn.
- Every hook called is reported to the turn's events: `hook_started` before it and `hook_completed` after it, with its provider and hook id, the call id, the event (`pre_tool_use` or `post_tool_use`) and the outcome (`passed`, `denied`, `added_context`, `failed`, `timed_out`) ([exec --json events](/docs/json-events#session)).
- A hook takes a continuation hook's identity types, since its fragments are committed under them; it does not use the kernel's `kernel`/`approved-denied-action`.

## Observers [#observers]

- An `AgentObserver` learns what the kernel committed through `AgentNotification`: `TurnAdmitted` (with the turn's `AgentTurnOrigin` and the provisional title its admission committed), `SamplingCommitted` (with the answer's memory citations), `TurnFinished`, `MemoryContributionChanged` (with its cause), `SessionArchived` / `SessionRestored`. A notification is added with its first consumer.
- The kernel notifies after the commit is durable and its events are emitted, never under a session's lock, and in commit order. A failed commit notifies nothing.
- `observe` is synchronous and runs on the committing thread: it signals a worker or does a small bounded local update, and never waits for the kernel. It returns nothing, so it cannot change an outcome; what must be durable or reach the model is not an observation.
- A call holds no lease: an observer whose plugin is stopping is skipped from the moment its retirement starts.
- Background work an observer starts runs in a worker the plugin owns, spawned with `spawn_scoped_worker` from `apply` and fed through a bounded channel the observer only `try_send`s to; the worker is cancelled and awaited when the plugin stops. It reaches the kernel through a narrow port the application constructs (`AgentTitleApplication` for the `titles` plugin), never through the facade, and the kernel mutations it makes are compare-and-swap, so what the user did meanwhile wins.

## Capability scope [#capability-scope]

A session's capability scope (`AgentCapabilityScope`, kept in its `AgentSessionConfig`) is what its [role](/docs/roles#sessions) narrows: which tools it allows and denies, which plugins' contributions it turns off, and the permission mode it caps. It is data the kernel owns and reads where it already takes its snapshots, not an extension point: a plugin neither sees nor sets it.

- **It narrows and never widens.** A scope only removes tools and plugin contributions and tightens the mode. A child's scope is its parent's narrowed by its own (the allow lists of both, the deny patterns and the plugins off of either, the stricter cap), so a child is never wider than its parent (a sub-agent's own is the role `spawn_agent`'s `agent_type` names); a fork keeps its source's.
- **Where the kernel applies it**, each at a snapshot it takes anyway:

| Point                                | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tool plan                            | After the mode policy, a plugin's registered or sourced tool is planned only when its plugin is not off, every allow list has a pattern that matches it and no deny pattern does. **The kernel's own tools (`RESERVED_TOOL_NAMES`) and `tool_search` are never filtered.** A tool left out is absent: a call to it gets "no tool named `<name>` is available in this step", it is not in `tool_search`'s index, and it is **not** in `tool_catalog_omissions` (it was left out on purpose, not lost). A deferred selection of it in the history is ignored |
| Tool sources                         | A source of a plugin that is off is not asked                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Context contributors, turn admission | A contributor of a plugin that is off is not asked: its kinds leave the session's world state and its values are absent, as for a stopped plugin                                                                                                                                                                                                                                                                                                                                                                                                           |
| Prompt contributors                  | Neither prepared nor asked, in every request of the session (a compaction's estimate included)                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Continuation hooks                   | Left out of the step's snapshot                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Permission mode                      | The turn freezes the stricter of its mode (the session's, or the configured one) and the cap. `AllowForSession` is unaffected: it never widens past a rule anyway                                                                                                                                                                                                                                                                                                                                                                                          |

- **Never filtered**, whatever a scope says:
  - [approval rules](#approval-rules): removing one would widen approval;
  - [tool lifecycle hooks](#tool-lifecycle-hooks): the user's PreToolUse/PostToolUse policy, deny-only;
  - [observers](#observers): instance services such as memory and titles, not model-facing;
  - [renderers](#context-renderers): data.
- **Owners.** A pattern `plugin:<owner>` and an entry of `plugins_off` match a registry entry's owner: a row's name, or `guest:<id>` for an installed plugin's code. An entry naming no plugin is kept and means nothing; the core rows (`agent-kernel`, `agent-host-services`) are never off.
- **One form.** Every creation, update and recovery canonicalizes it (`normalize_session_config`): the allow lists sorted, each once, the core rows dropped from `plugins_off`. A tool scope over 128 patterns, or with one over 256 bytes, allows no tool but the kernel's own: dropping any of its patterns could widen it.
- **Persisted** in the session's configuration, read field by field: a field that cannot be read falls back to its default, and a pattern this build cannot read is dropped from its list. The empty scope (`default`) is left out of the record, so a session without a role writes the bytes it wrote before roles existed, and a history without the field opens with it. The role's instructions are kept beside it (`role_instructions`) and appended to the base instructions in every request, so a model selection keeps them.
- **The two plugins whose values the kernel reads.** With `skills` off the turn has no `SelectableSkills`: an explicit Skill reference is refused with "the Skill catalog is unavailable" ([Turn admission](#turn-admission)), a `$mention` selects no Skill, and the Skill tools are absent. With `memory` off the memory summary and the memory tools are absent and the step has no `AgentMemoryStep` (answers shown as they are, without citations); the session still contributes to memory as its contribution mode says, since observers are never filtered.
- The kernel's `loop_contract` suite (`scope.rs`, and `sources.rs` for sources) and the facade's `tests/sessions/roles.rs` pin these rules; the `explorer` golden pins a scoped request.

## External producers: MCP servers, Skills, web, memory [#external-producers-mcp-servers-skills-web-memory]

What an MCP server, a Skill author or an extraction model produces is read tolerantly; one bad item costs only itself, and the strict rules (MCP configuration, credentials and OAuth, path containment, URL validation, persisted formats) are unchanged.

- **The MCP catalog** is built tool by tool. Each name segment is sanitized per character to `[A-Za-z0-9_-]`, and one still over 128 bytes is cut and given a hash suffix. A tool with an invalid or oversized input schema, a name that cannot be encoded or a later duplicate is skipped; a description over 16 KiB is cut on a character boundary and an invalid output schema dropped. Each is a Warning diagnostic of the server; the server stays connected, with zero tools if none is usable.
- **MCP annotations are hints from a server the user configured, never a grant.** A tool whose `readOnlyHint` is true and whose `destructiveHint` is not is `ConcurrentRead` and `ReadOnly`; every other is `Exclusive` and `Mutating`. Every MCP tool's memory effect is `PollutesContribution`. Approval does not read the read-only hint: the server's (or the tool's) approval policy decides, and `Allow` skips the review only for a tool whose `destructiveHint` is false, a missing hint counting as destructive.
- **MCP liveness**: a connection's transport says when rmcp's loop ended; when the server's side ended it, the server is `Failed` with the reason, its entry is retired, and the manager reconnects it under the module host's `RestartPolicy` with the configuration and secrets the closed connection was opened with. A connect from outside (the user's Connect or Refresh, a settings, credential or proxy change) empties the window, and shutdown cancels a scheduled one. A step keeps the connection it was planned with; a call on a lease whose connection closed returns `McpError::CatalogChanged` without asking for approval.
- **MCP output**: a content block the client cannot decode becomes the text `[unsupported MCP content: <type>]`; over 64 items keeps 63 and a note; a mime type with parameters is its base type, and unpadded base64 is accepted.
- **Skills**: `SKILL.md` frontmatter and `openai.yaml` are read field by field: a wrong type on an optional key drops that key with an issue, a name over 96 characters or a description over 4096 bytes is cut with an issue, and an unreadable directory below a root is skipped. `name` and `description` stay strict on type. `allowed-tools` is an unknown key: Skills never add or restrict tools. A Skill whose declared MCP server is not Ready is not usable in the turn and is listed as unavailable, with why.
- **Web**: a search endpoint configuration the service cannot use leaves the `web` row running with `web_search` omitted from every step; `fetch_web_page` keeps working.
- **Memory**: a notes line that cannot be read is skipped (logged by line number, never its content). Phase-one extraction output ignores fields its schema does not name and keeps what the named ones still give; only output that is not an extraction object at all fails the job. The consolidation agent may write only what publish accepts, and a write over a bound is a tool error naming it, so the model can shorten and retry.

## Host, configuration and status [#host-configuration-and-status]

- The Agent is optional to its host. It is built once the host's interface is up, on the runtime its start builds, from the captured launch (`AgentLaunch`); the slot keeps the launch, so every later instance (a restart, an automatic restart, turning it back on) starts the same way, with the next generation. A construction, recovery or start failure leaves the slot `Failed`.
- A fault is either a plugin's or the kernel's ([Faults](/docs/architecture#faults)). A panic in one of the plugin host's own tasks (the fault follower, a remount) is reported to the kernel fault sink as a kernel fault at `plugin host`, and rebuilds the Agent.
- A capability that cannot come up fails its plugin, not the Agent: a Skill catalog that did not open fails the `skills` plugin, a required MCP server that did not connect is its MCP status, a `web` configuration that does not derive is that row's error. A session recovery rejects is quarantined.
- `AgentHost` is the Agent's configuration of the generic module host (`AgentPlugins`, its `HostProfile`): the mount order, bounds, enablement, reconfiguration, retry, safe mode, fault handling, status and shutdown are the host's. What is the Agent's: its rows and their descriptors, their configuration from its own settings, the host's proxy and the rows' options (`AgentPluginSettings`), its enablement from `disabledPlugins`, its groups, the contributions in its status, its `AgentPluginEventSink`. Its options: `module_faults` off (its rows are plugins, not application modules, and their faults reach it through `PluginFaults` alone), and `automatic_restarts` the default restart policy.
- A row is `AgentPluginRow::unconfigured` or `AgentPluginRow::from_settings` and declares its `AgentPluginGroup`: `Capability` (tools, tool sources and their rules, and the features the facade calls) or `Context` (world-state sections). Configuration that is not derived from settings does not exist; a service a plugin adapts is captured in its `PluginDef` constructor (through `AgentPluginInputs`), not passed as configuration.
- **Descriptors and options.** Every row has exactly one `AgentPluginDescriptor` (`crates/agent/src/host/descriptors.rs`): its name, which is its `PluginDef`'s; a one-line summary of what it gives the model or the user; and the options it takes, a `PluginOptionSchema` (`None` for none). An option is a boolean, an integer or a number within bounds, a text (secret or not, within a length), a choice among texts, or a list of texts, and a row's option always has a default. A host's row brings its own descriptor (`AgentHostPorts::plugins`); a row without one, or a name described twice, keeps the Agent from being built. The options are set in `[pluginOptions.<row>]` of `config.toml`, layered per row and key ([`pluginOptions`](/docs/config-reference#plugin-options)). `AgentPluginSettings` carries them resolved against the schema, so a row derives its configuration with a non-capturing closure, `AgentPluginRow::from_settings(group, plugin, |settings| settings.options_value("<row>"))`, which is the generic host's `SettingsConfig` function pointer, and decodes it with `PluginDef::typed` without failing: a value the file sets that does not fit was replaced by its default, or clamped when an integer or a number is out of range, with a configuration warning naming the layer, the row and the key (`/warnings`, `AgentPluginStatus::options`). `set_plugin_options` is the writer: it checks every value against the schema and refuses the write, with the reason, before anything is written. The options of `subagents` are the first (its running-agent limit and its wait bounds, which choose within the bounds its code keeps); `web` keeps deriving from the shared settings, which the network form shares.
- A settings-derived plugin follows the settings. After a settings write, `apply_settings_to_plugins` is scheduled on the running Agent's runtime, and the host reconfigures its rows from the latest published settings. `disabledPlugins` is the enablement: a re-enabled row mounts only once its previous fiber stopped, so its registrations cannot collide with the old ones. `set_plugin_enabled` is the one writer and refuses an unknown name and disabling a core row. Disabling a plugin is not a way to deny a tool: approval stays with the rules and the permission mode.
- **Feature calls.** A feature the facade offers as a call of its own (`recap_session`, `suggest_session_title`, the goal calls, the `worktree_*` calls, `hooks_list`, `set_hook_enabled`, `trust_hooks`, `subagents`, `interrupt_subagent`, `start_review`, `cancel_review`, `review_targets`) is a plugin row's: the row provides one service under its name (`ctx.provide_arc_as(NAME, Arc<Service>)`, declared in its `provides`), and the facade resolves it per call through `ModuleHost::service::<T>(NAME)`, never keeping the `Arc`, since a retried row provides a new instance. Every such call goes through one helper, `AgentApplicationService::feature`: it starts the plugins if nothing did, turns a row that is not running into `AgentError::FeatureUnavailable { feature, reason }` (the reason says why: "the recap Agent plugin is unavailable: it is turned off"), and runs the service call under `PluginFaults::guard_async`, so a panic is that row's fault (`panicked in feature call: ...`) and restart while the caller gets `FeatureUnavailable`. Only that feature is lost, never the Agent. A feature service reaches the kernel through a narrow port the application constructs (`AgentConversationReader` for the recap and the title suggestion, `AgentGoalApplication` for the goal, whose writes are compare-and-swaps under the session's lock so a change the user made in the meantime wins, `AgentSessionDriver` for the subagents and the reviews, `AgentRoleCatalogReader` for the roles a sub-agent is spawned as), and cancels its model requests when its plugin stops. A plugin crate's service is declared in that crate (`WorktreeService`, `HooksService`): the facade depends on every plugin crate, so no contracts type is needed.
- A plugin that absorbs a change without restarting registers a kardia update hook (`Context::on_update`, over the type its `PluginDef::typed` decodes, or it is never offered the change); otherwise the plugin restarts, which drains its running calls. `subagents` takes a new running-agent limit in place, keeping its service, and restarts for new wait bounds, which `wait_agent`'s spec states; the runs it tracks outlive either. A tool's descriptor is fixed per registration, so the spawnable roles `spawn_agent`'s `agent_type` lists are those of the plugin's start; the guidance and each spawn read the role catalog per step and per call, and no role change restarts the plugin.
- `plugin_status` returns every plugin's `AgentPluginStatus`: name, its descriptor's `summary`, group, state (`pending`/`active`/`failed`/`disabled`/`disposed`), error text, an active plugin's `warning`, enabled, lock (`core` for the core rows), `restart`, its current contributions and, for a plugin with options, `options` (`AgentPluginOptionsStatus`: the schema, each option's value with the layer that set it, `None` for its default, and what its table sets that could not be used).
- **Bounds**: the host bounds every wait it makes on kardia: a start within `PLUGIN_START_TIMEOUT` (20 s), a disposal within `PLUGIN_STOP_BOUND` (10 s), a remount within the disposal's bound. A fiber stuck for good is dropped with its Agent instance's runtime.
- Shutdown disposes the kardia root once, bounded by the caller's deadline; a plugin still stopping then is reported as an `agent-plugins` shutdown diagnostic. MCP connections, memory workers, history and executions are owned by the application and stop in its own shutdown steps, never in a plugin's teardown.

## The host interface [#the-host-interface]

An embedding application (the host) adds to the Agent only through `AgentHostPorts`, a field of `AgentServiceInputs` built for every Agent instance. Each port's use and default is in [Embedding the Agent](/docs/embedding#the-host-interface); the rules are:

- The interface takes plain values (`PathBuf`, strings, maps) or the Agent's own types, never a host's foundation, process or module-host types: they are distinct types on the two sides, and the host adapts at the edge (the Agent's shutdown diagnostics, for one, are mapped to the host's at the call).
- A host's plugin rows are plugins like any other, each with its descriptor: written against contracts, every rule of this page applies, `disabledPlugins` turns them off, safe mode leaves them unmounted. They mount after the Agent's capability plugins and before its context plugins.
- Host input (the `host` of `AgentTurnRequest`, `AgentSteeringRequest` and `AgentFileSearch`) travels as `TurnExtensions`, passed on unread to the context contributors, `HostContextPort` and `WorkspaceRootsPort`. The IPC inputs that carry it are the host's and are converted on its side.
- The data directory's lock is held from the first start until shutdown, in both modes; a host does nothing for it.
- A host reads the Agent's runs through `AgentSlot::list_run_projections` and `get_run_projection` and maps them to its own view.

## Code plugins [#code-plugins-rules]

An installed plugin's code is a guest ([Code plugins](/docs/architecture#code-plugins)): a program out of process, or a WebAssembly module in wasmtime, that the Agent reaches only through the proxies the guest host builds from its manifest's `contributes`, never from the guest's word. Each proxy calls one method of the service every guest provides (`plugin`) and has a deadline; past it the guest is killed (a module interrupted, as when it traps or exhausts its fuel or memory) and restarts under the restart policy, and the call takes the error path of its extension point, so a guest that fails or hangs costs only its own contributions and never fails a turn.

### What a guest contributes [#guest-contributions]

The proxies of a guest are registered when its fiber becomes active, as effects of that fiber (owner `guest:<id>`, so the kernel's issues and faults name it): they retire when it fails, stops or restarts, and its next start registers them again. A guest whose fiber is active is `running` only once they are registered. A declaration the host cannot honour is left out with an issue of the package (`AgentPackageGuest.status.issues`, with the kernel's issues for `guest:<id>`); the rest is registered.

| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

### What a guest may reach [#guest-host-calls]

- **`view`** reaches two services, each in a realm the guest's loader entry shares with its host-services entry (`<id>#host`, `isolate` with the label `guest:<id>`), which the guest's entry declares (`inject`), so a guest starts once they run: `workspace`, `{ "access": "none" | "read" | "write", "roots": [...] }`, the Agent's workspace roots (native paths, read at each view) only when it may read them (never for a WebAssembly module, which reads no file); and `settings`, its settings (`[plugins."<id>"].settings`), which are also the configuration its `apply` gets.
- **Everything else is refused.** kardia's checked access finds only what the guest's chain of fibers provides or declares, and nothing else on that chain has a JSON view (`view`) or is a guest's service (`invoke`); a guest reaches no other guest (decision 6).
- **A guest provides only `plugin`.** Its metadata must declare exactly that (or its start fails), and kardia-hmr refuses it any other service (`cannot provide "<key>": the plugin does not declare it in provide`) before anything reaches the realm every plugin shares. The refusal is the guest's error, as any host call's is: an `apply` that returns it fails the start; a call that returns it fails only that call, and the guest keeps running, since nothing was provided.

### The guest protocol [#guest-protocol]

A guest is a Kardia guest (`kardia-guest/2` for a program, the guest ABI for a WebAssembly module) whose metadata is `{ "name": <manifest name>, "provide": ["plugin"] }`; its `apply` gets `{ config: <its settings>, imports: {} }` and provides `plugin`. The Agent calls `plugin`'s methods with one JSON object of camelCase fields; ids are numbers. A method the guest does not declare in its manifest is never called.

| Method          | Arguments                                                                              | Answer                                                                                         |
| --------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `tool`          | `{ name, arguments, call: { sessionId, turnId, callId } }`                             | the output: a string is text, any other value structured content; an error is the call's error |
| `context`       | `{ kind, sessionId, mode, userMessage }`                                               | the section's text, or `null` (or a blank string) for none                                     |
| `prompt`        | `{ sessionId, turnId, samplingStep }`                                                  | the fragment's text, or `null`                                                                 |
| `beforeToolUse` | `{ call: { sessionId, turnId, callId, toolName, arguments } }`                         | `null` to let it run, or `{ "deny": reason }`                                                  |
| `afterToolUse`  | `{ call, output }` (`output` a tool output: `content`, `structuredContent`, `isError`) | `null`, or `{ "context": [text, …] }`                                                          |
| `continuation`  | `{ sessionId, turnId, samplingStep, candidateFinalAnswer }`                            | `null` or `"pass"`, `"stop"`, or `{ "continue": [text, …] }`                                   |
| `observe`       | `{ event, sessionId, turnId? }`                                                        | ignored                                                                                        |

Another answer is that call's failure. The calls of one guest run one at a time. The SDKs and the wire beneath these methods are in [Writing plugins](/docs/writing-plugins#guest).

## Logging [#logging]

kardia's logs reach the `log` facade through the `LogExporter` the host installs on its root. kardia has no `trace` level, so content the content-logging rule confines to `trace` is never logged through a kardia logger, but for a guest's: a plugin named `guest:<id>` (`GUEST_LOGGER_PREFIX`) is an installed plugin's code, and what its loggers write (its stderr, its log lines, its failures) is its content, which the exporter forwards only at `trace`, bounded, whatever its kardia level ([Plugin guests](/docs/internals#plugin-guests)).

## Writing a plugin [#writing-a-plugin]

This section is about the Agent's own plugins and a host's, compiled in. An installable plugin, a package whose code runs as a guest, is written as in [Writing plugins](/docs/writing-plugins).

Choose where it lives:

- A **plugin crate** `crates/plugin-<name>` (`hanafubuki-agent-plugin-<name>`) when it binds one domain crate and needs only contract types (`web`, `workspace-fs`, `execution`, `mcp`; a tool source too; `worktree` and `hooks`, whose services the facade calls).
- A **plugin in the facade**, under `crates/agent/src/plugins/`, when it needs the Agent's own services (image normalization, `AgentSkillApplication`, `AgentMemoryApplication`, `AgentTitleApplication`, `AgentConversationReader`, `AgentSessionDriver`). It is exported from `plugins/mod.rs`, with no Cargo change.
- A **host plugin** in the host's own crate when it needs the host's domains. It is written against contracts and the facade's public API only, and is one of the host's rows in `AgentHostPorts::plugins`; the rules here apply to it unchanged. See [Host plugins](/docs/host-plugins).

Checklist:

<Steps>
  <Step>Crate: a `Cargo.toml` with `hanafubuki-agent-contracts`, `kardia-core`, and the `hanafubuki-agent-approval`, `hanafubuki-agent-tool-contracts` and domain crates the tools use; a `src/lib.rs` with module declarations and `pub use plugin::<name>_plugin;` only.</Step>
  <Step>`<name>_plugin() -> PluginDef`: `PluginDef::new` (`PluginDef::typed` for a settings-derived configuration), `.name("<name>")`, and `.inject(..)` with the `NAME` of every registry or host service it uses (`PluginFaults::NAME` for `spawn_scoped_worker`). `apply` gets each with `ctx.get::<T>()?`, registers with `register(Arc::new(..))?`, spawns long work with `spawn_scoped_worker`, and returns.</Step>
  <Step>Each tool: a `ToolDescriptor` with a `ToolName::parse` name, a JSON schema with `additionalProperties: false`, the exposure, execution class, effect, activity action and memory effect; `permission` returns `NotRequired` for a read or the `ApprovalAction` of a mutation; `invoke` validates the arguments, observes cancellation, re-checks a mutation's approval (`verify_tool_approval`), and runs blocking work on the `BlockingService`.</Step>
  <Step>No `.unwrap()`/`.expect(` in production sources; map errors into `kardia_core::Error`.</Step>
  <Step>Wire it: an entry in the root `Cargo.toml`'s `[workspace.dependencies]` (with both `path` and `version`), a dependency in `crates/agent/Cargo.toml`, a row in the layer table (`xtask/src/dependencies.rs`), one row in `crates/agent/src/host/manifest.rs` (a service it adapts goes through an `AgentPluginInputs` field) and its descriptor in `crates/agent/src/host/descriptors.rs`, named as its `PluginDef`, with its summary. `Cargo.lock` follows.</Step>
  <Step>Options, when it has tunables: its schema in the descriptor, each option with a default and within bounds its code keeps as hard limits; its row `from_settings` with `|settings| settings.options_value("<name>")`, its configuration `PluginDef::typed`, and `ctx.on_update` when it can take a change in place. The configuration center's generic form edits them with no interface code.</Step>
  <Step>Test it as in [Testing a plugin](#testing-a-plugin), and regenerate the goldens if the model sees the change.</Step>
  <Step>Document it: the crate row in [Architecture](/docs/architecture#crates-and-layers) and the [plugins today](#the-plugins-today) table and tool count on this page.</Step>
  <Step>Validate from the repository root with `cargo xtask check`, `cargo fmt --all --check`, `cargo test -p hanafubuki-agent-plugin-<name>` and `cargo test -p hanafubuki-agent --lib`.</Step>
</Steps>

A new plugin changes no kernel or contracts file.

## Testing a plugin [#testing-a-plugin]

- Mount it on a fresh `kardia_core::Context` under a plugin that provides the registries it injects, and `PluginFaults` when it uses `spawn_scoped_worker` (or `hanafubuki_agent::test_support::mount` for a facade or host plugin, which provides both), wait for `settled()`, and assert `state()`: `settled()` also resolves while a plugin is still `Pending` on a missing service.
- Assert its registrations, update its config, dispose it, and assert that every registration is gone. A configuration the plugin rejects leaves it `Failed` with nothing registered.
- Test handlers and domain logic without kardia where they do not need it.
- **The request goldens** (`crates/agent/src/tests/golden.rs`, over the Agent's own plugins with a host that adds no rows, context or instructions) pin what the model receives: the instructions, the tool catalog and the input items in Default and Plan mode, with a Skill catalog, workspace instructions, the memory summary, after a compaction, with MCP tools from a scripted in-process server, in a session with the `explorer` role, and around a tool call and a `tool_search`, plus the presentation events of a tool round trip and that a session's first request after `workspace-context` restarts is the Default-mode one, byte for byte; `compaction_golden.rs` and `compression_golden.rs` pin the compactions and the `hierarchical` strategy's requests (its prompt, tools, tags and nudge, after a fold, after a tier-2 distillation, after switching away). A change the model sees changes the request goldens **on purpose**: regenerate them with `HANAFUBUKI_AGENT_UPDATE_GOLDEN=1 cargo test -p hanafubuki-agent --lib golden` and review the fixture diff.
- **The history corpora** (`golden/history/` and `golden/history-reasoning/`) are re-recorded only with `HANAFUBUKI_AGENT_UPDATE_GOLDEN_HISTORY=1`, after an intended history-format change; otherwise they keep proving that older history opens.
- A host keeps goldens of its own over its rows (Hanafubuki's are in `hanafubuki-agent-integration`), which a model-visible change here changes as well. The fixtures are Linux-only.

The commands and update rules are in [Building and testing](/docs/building-testing).
