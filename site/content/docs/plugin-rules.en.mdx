The Agent is composed of plugins on [kardia](https://github.com/licyk/kardia), the Rust implementation of Cordis. This page holds the **rules** of that composition: read the sections a change touches before changing any tool, context section, approval rule, continuation hook or observer, the plugin host, its manifest or the plugin configuration, the crate boundaries or the host interface, or the goldens; update this page when the design changes. The repository-wide rules (locks, paths, decoding strictness, content logging, layout) are in [Contributing](/docs/contributing) and [AGENTS.md](https://github.com/licyk/hanafubuki-agent/blob/main/AGENTS.md); how the parts fit together, and why, is [Architecture](/docs/architecture).

## Composition rules [#composition-rules]

1. **The kernel depends on nothing a plugin can replace.** kardia restarts a plugin when an injected service is replaced, and a kernel restart would drop every live session. The kernel plugin injects nothing; it publishes registries created before the runtime starts, and the kernel reads them as snapshots per turn or per sampling step.
2. **Registrations are effects of the caller.** Contribute through `hanafubuki_agent_contracts::Register` on an injected registry service. The entry belongs to the calling plugin (`Svc::caller`) and is removed when that plugin stops; a plugin never keeps a handle to undo it. A refused registration (`RegistrationError`, a duplicate id for one) fails the plugin.
3. **Running calls keep their entry's plugin alive, bounded.** A call takes an `EntryLease` from a snapshot entry and observes its cancellation. A tool a source planned leases its source's entry, and so does the source while it contributes. A stopping plugin first hides its entries from new snapshots, waits `DRAIN_GRACE` for leased calls, cancels them, waits `RETIRE_CANCEL_BOUND`, then continues its teardown.
4. **The kernel reaches plugins only through the contracts' registries.** A hook that changes an outcome is a kernel-owned registry with a documented ordering and combination (deny-only, tighten-only, first match, ordered by priority and id), never a kardia event: the kernel holds no kardia context. The result never depends on registration order, because plugins start concurrently. A new extension point is added with its first real user.
5. **No long async effect bodies.** kardia never cancels `apply` or an async effect, so a loop there keeps its plugin and every ancestor from stopping; the host only bounds the damage (the row fails after `PLUGIN_START_TIMEOUT`, and the fiber stays stuck until its Agent instance's runtime stops). `apply` validates config, registers and spawns; long-lived work runs through `spawn_scoped_worker` (the plugin injects `PluginFaults::NAME`, which the kernel plugin provides), or in a worker group the plugin stops from a `ctx.defer` disposer (the `execution` plugin's activity monitors).
6. **Unchecked root access stays in the host.** Only the module host that owns the kardia root (`hanafubuki-agent-host`, configured by the facade's `AgentHost`) and the facade read plugin state from it. Plugins declare what they use (`PluginDef::inject`); domains never see a kardia context.
7. **Plugins return errors, never panic.** Production plugin sources contain no `.unwrap()` or `.expect(`; a failing `apply` leaves the plugin `Failed`, which the host reports and a configuration update or `retry_plugin` restarts. A panic is a bug, but it stays in its plugin (which the host restarts after a backoff): kardia catches it in `apply`, effect bodies, disposers and event listeners, and the kernel guards every call it makes into plugin code. That holds in release builds too: they unwind, and the panic hook lets a panic on an Agent thread unwind to its catch. Locks are `parking_lot`, never std.
8. **Every kardia mutation runs on the Agent runtime.** kardia spawns on the ambient runtime and panics without one; host methods that mount or update plugins are async, and their callers send them to the Agent runtime.

## Where Agent code runs [#where-agent-code-runs]

Everything the Agent runs is on a thread where a panic is contained: the panic hook lets it unwind to its catch there, and aborts the process anywhere else.

- **The Agent runtime** (a `ContainedRuntime` of `hanafubuki-agent-runtime`, threads `agent-rt`), one per Agent instance: the slot's start builds it and the slot keeps it until that instance's stop (shutdown, a restart, a turn off) stops it last. It runs every call a host makes into the Agent, the whole start (construction and recovery on its blocking pool, the plugins' start, the MCP servers' background start), the async shutdown stages, and what those spawn: turns and compactions, kardia's effects and disposals, scoped workers, the host's fault, retire, remount and reconfigure tasks, MCP and model clients. Its blocking pool runs `BlockingService` and every `BlockingOperationPort` call of the Agent.
- **Contained by the Agent's own foundation.** These marks and guards are thread-locals of `hanafubuki-agent-foundation`, which a host's foundation cannot see. A host's panic hook therefore takes `hanafubuki_agent::panic::is_panic_contained` as its second containment check: a panic is contained when either foundation says so.
- **The Agent's worker threads**, all in `BackgroundWorkerGroup::contained` groups: history writers, MCP stdio readers, the memory supervisor (whose own current-thread runtime marks its blocking pool too), the `execution` plugin's activity monitors and the Skill catalog watcher; and the slot's supervisor thread (`agent-supervisor`).

Not Agent threads, so their panics still abort: the host's threads, and the threads of the services the Agent calls (an executor's reader and waiter threads). A new spawn in Agent code lands on the ambient runtime or in a contained group, never on a plain thread.

### Panics in plugin code [#panics-in-plugin-code]

The kernel calls plugin code only through a guard: `RegistryEntry::guard` or `guard_async` (the entry knows its owner), or `PluginFaults::guard` and `guard_async` where no entry is at hand. A panic there is logged at error, reported to `PluginFaults` as a `PluginFault` of the entry's owner (plugin, `ExtensionPoint`, bounded panic message), and becomes `PluginPanicked`, which the caller turns into that call's own error path:

| Call                                        | A panic means                                                                         |
| ------------------------------------------- | ------------------------------------------------------------------------------------- |
| tool `availability` (registered or sourced) | the tool is `Omitted` from the step                                                   |
| tool `permission`, `invoke`                 | the tool error "the tool failed with an internal error", as any failing tool          |
| tool source `contribute`                    | the source failed: its trust decides (an `Optional` one is omitted)                   |
| context and turn admission `contribute`     | that contributor is left out of the admission                                         |
| prompt `prepare`                            | the contributor's values are left out with a warning                                  |
| prompt `contribute`                         | the contributor renders no fragment                                                   |
| approval rule `evaluate`                    | a denial naming the plugin: a rule fails closed, never "no opinion"                   |
| continuation hook                           | the hook failed: its failure policy decides                                           |
| observer `observe`                          | that observer is skipped; the others are told and the committing thread never unwinds |
| a `spawn_scoped_worker` body                | the worker ends, logged with its label                                                |

The panic message reaches the log and the plugin's status, never the model. The `mcp` plugin contains one panic itself: `McpTool::invoke` runs its server's call under `catch_panic_async`, so a panic there is that call's error and **that server's** fault, never the plugin's. The kernel never holds a lock across a guarded call, so the guards change no lock ordering. The identity accessors (`id`, `descriptor`, `kinds`, `rank`, `trust`) are data and are not guarded.

After a fault the plugin is stopped and reports `failed` (`panicked in <extension point>: <message>`), and the host mounts it again by itself after the restart policy's next delay (2 s, 10 s, 30 s, three in ten minutes); past that, until `retry_plugin`, a new configuration or turning it off and on mounts it anew, once its teardown has ended. A plugin whose start failed, rather than one that panicked, is not restarted by itself.

## Tools [#tools]

- A tool's `ToolDescriptor` fixes the model-visible spec, exposure, execution class, effect (`ReadOnly` tools, registered or sourced, are the only ones in Plan mode), activity action, memory effect and timeout for the lifetime of the registration (for a sourced tool, of the step). `availability` may offer it as a freeform tool or omit it for a step (`ToolPlanContext`).
- The kernel owns the pipeline and plugins cannot reorder it: mode policy, `permission`, approval when review is required (the approval rules, then the session's allowance, then the permission mode's flow), then `invoke` with the one-shot approval. `invoke` re-checks that the approval matches the call it runs.
- The pipeline runs under the step's gate: an in-flight permit, then read access for a `ConcurrentRead` tool or exclusive access, first come, first served, so `permission` sees what the step's earlier calls did. An approval that waits (the user, or the reviewer model) releases the gate and takes it again once approved; the step's other calls run meanwhile, and the user is asked one prompt at a time per step. An approved action can be stale once other calls ran in the gap; the re-check in `invoke` (`verify_tool_approval`, a domain's own check) turns that into the call's error, never a run of something unapproved. A call admitted after its turn was cancelled does not start.
- `invoke` runs within `ToolDescriptor::timeout`, or the turn's `tool_idle_timeout` (10 min) when it is `None`; neither `permission` nor an approval wait counts. A call past it is cancelled and its future dropped, and the model reads "the tool did not finish within N s and was stopped"; the turn continues. Work the call left on the `BlockingService` observes the cancellation and ends itself. A tool whose own bound pauses while it waits for the user sets the timeout above that bound: an MCP tool's is its server's call timeout plus one elicitation wait (`MAXIMUM_MCP_ELICITATION_WAIT`).
- Outputs commit in call order, each as soon as every earlier call's has. A call that ends in an error (the turn's cancellation among them) commits nothing; the step's other calls still run to their end and commit, since their effects happened, then the step returns the first error. On a cancel only the unfinished calls get the synthetic interrupted output, which the model reads right after its call.
- A turn samples at most `AgentHardLimits::maximum_sampling_steps` (32) times; the next step fails it with `LimitExceeded { "sampling steps" }` (`budget_exceeded`), every earlier output committed. At `turn_deadline` (30 min) the kernel cancels the turn as a user's cancel would (pending approvals and questions aborted, finished calls committed) and ends it `Failed` with `TurnDeadlineExceeded` (`deadline_exceeded`). Neither limit is shown to the model.
- Blocking work runs on the injected `BlockingService`; a call observes `ToolInvocation::cancellation`. `ToolInvocation::progress` only queues (`report` never waits), from the call or from a monitor thread that outlives it; the kernel commits the session's progress in order.
- A tool that exists only while something outside the Agent offers it (an MCP server's catalog, the memory settings) comes from an `AgentToolSource`. The kernel asks each source once per sampling step with a `ToolSourceStep`, and it returns `SourcedTool`s: an `AgentToolHandler` built for that step plus the identity the plan records (provider id, tool id, generation, namespace description, activity subject) and its `ToolSourceTrust`. Keep the identity stable while the tool does not change, and change it when the tool does: a deferred-tool selection (the `ToolSelection` history item) names the identity, and the kernel validates a tool's schema and spec once per identity (`AgentToolSpecCache`).
- A sourced tool is planned and run like a registered one, with two differences: the kernel checks the model's arguments against its schema before `permission`, and its trust is external: an `Optional` tool that cannot be planned is omitted (reported in `tool_catalog_omissions`), a `Required` one fails the plan. A name collision is neither (see [Tool names](#tool-names)). A source whose plugin stops while it is asked is omitted whatever its trust, so turning a plugin off never fails a step. Over the direct catalog budget only sourced tools are deferred.
- A tool source may return a `ToolPlanLease` with its contribution; the plan keeps every lease and each call receives them as `ToolInvocation::plan_leases`. Find yours with `ToolInvocation::plan_lease::<T>()`, never by downcasting the `Arc`.
- Per-turn data reaches a call as `ToolInvocation::turn` (`TurnExtensions`, keyed by type): what the turn admission contributors froze for the turn. Read yours with `turn.get::<T>()` and treat a missing value as a tool error. Contracts name only the values the kernel itself reads (`SelectableSkills`).
- A tool adds instructions to the conversation by returning a `ToolContextFragment` with its `ToolResult`. The kernel commits it right after the output as the context of the Skill `source` names, once per turn and Skill, and turns a `source` that is not a Skill id into a tool error.
- The kernel's own tools (`AgentCoreTool`: `new_context`, `update_plan`, `request_user_input`) act on the turn and are not plugins; neither is `tool_search`, the plan's search over deferred tools. Their names are `RESERVED_TOOL_NAMES`.
- An activity action is an open identifier (`AgentActivityAction`); an interface labels the names it knows and shows the generic tool label otherwise, so a new tool needs no frontend change.

### Tool names [#tool-names]

- A tool's name is its `ToolName` (namespace segments and a local name). The registry and the planner key it by its flattened form (`namespace__name`); that string is never parsed back.
- `ToolRegistry::admit` refuses a registration whose flattened name is reserved, already registered, or longer than a tool id (128 bytes). The `RegistrationError` fails the registering plugin at its start, with nothing registered; the other plugins and the turns are unaffected.
- The wire name is per request: `assign_provider_names` writes it into each planned tool's provider spec when the plan is built for the step's protocol. Where the protocol takes namespaces (Responses) a namespaced function keeps its namespace and local name; elsewhere, and for a namespace another provider already uses, the name is flattened. Every name is fitted to `ToolProviderCapabilities::maximum_tool_name_bytes` (Responses 128, counted over `namespace__name`; Anthropic Messages 128; Chat Completions 64, OpenAI's function-name limit).
- Names are unique over their flattened form, with `tool_search` held for the plan's search. In planning order (trust, then name, provider id, tool id) the first tool keeps its name; a later one that collides, or one too long, is cut and ends with `_` and 12 hex digits of a hash of its `(provider id, tool id)`, so it is the same on every step. A collision (only a sourced tool can collide, since registration refuses the others) is reported in `tool_catalog_omissions` with the reason "renamed to `<name>`"; the tool stays planned. Nothing about a name fails a step.
- A returned call is resolved by lookup of its `(namespace, name)` in the plan (`AgentToolPlan::resolve_call`); a name the request did not carry is an unknown tool. The decoders return the provider's namespace and name apart, and history records both, so Responses replays a call with its namespace and a protocol without namespaces replays it as `namespace__name`.
- Schemas are lowered by the same per-protocol rule: a protocol whose `strict_json_schema` capability is set (Responses) gets each tool's schema whole; one without it gets the portable keywords (`portable_model_schema`). Tools are never sent `strict`. The kernel validates arguments against the whole schema either way.

### Model tool arguments [#model-tool-arguments]

The model's arguments are read tolerantly; a mistake is a field-named error the model reads back as the tool result, never a failed turn.

- No argument type uses `deny_unknown_fields`, and no helper rejects a key it does not know: an unknown key is ignored. Ignoring it never widens what runs, because capabilities (approvals, receipts, resolved paths, executor ids) are never arguments, and the call still goes through `permission` and approval. The one exception is a value meant for another action of the same tool: Hanafubuki's `provision_instance` rejects a non-null property its selected action does not take, since its actions create and delete instances.
- A missing or `null` optional field is absent. A field that is semantically required (`cmd`, `path`, `recursive` of `delete_path`) stays required.
- A limit out of range is clamped into its bounds with a note (`clamped_u64`/`clamped_usize`, `ArgumentNotes`, appended to the result by `ToolResult::with_argument_notes`); a limit that guards safety (a byte or depth cap) clamps to the cap and never past it, and an omitted one takes its default. Containment is not a limit: a path is passed as given and the domain resolves and contains it.
- `decode_arguments` names the field an error is about (`invalid tool argument plan[1].status: ...`).
- A sourced tool's arguments are checked against its schema (`validate_dynamic_tool_arguments`); a `type` the check does not know constrains nothing, and an integral number is an `integer`.
- A call the step cannot run is answered, never a protocol failure, and its output keeps the call/output pair valid for every protocol: a name the step does not offer (unknown, `Hidden`, mode-hidden, provider-incompatible) gets one identical error, "no tool named `<name>` is available in this step", so a hidden tool stays indistinguishable from an absent one; a Deferred tool not yet admitted gets the discovery error with the `tool_search` recovery; arguments that could not be parsed or are over `maximum_tool_argument_bytes` get an error with a 512-byte preview; a malformed `tool_search` gets a field-named error.

## Context [#context]

- A `ContextContributor` declares the kinds it produces (`ContextSectionKind`) and returns at most one `ContextSection` per declared kind. Two contributors declaring one kind, or a contributor declaring `tool_catalog_omissions` (the kernel writes it every sampling step), fail the registering plugin.
- At turn admission the sections are collected from one registry snapshot (`collect_world_state`; contributors run one after another under an entry lease). A contributor that fails (an error, a panic, its plugin stopping) is left out of that turn; so is a section of a kind it did not declare, a kind already produced, or a plugin kind past `MAXIMUM_AGENT_PLUGIN_WORLD_STATE_SECTIONS` (7, a host's kinds among them; the Agent's five known kinds have their own slots). Each is recorded as an issue of its plugin (`PluginFaults::set_issue`), which the plugin's status shows as its `warning` (and the Agent as degraded) until that contributor succeeds again or the plugin is mounted anew; the turn is never refused over it. A kind no contributor returns is removed from the world state on that turn, so a contributor plugin that failed to start leaves its sections absent rather than failing every turn.
- A host context never refuses the message or steering it came with: one this build cannot use is dropped with a warning, and one over `MAXIMUM_HOST_CONTEXT_BYTES` (4 KiB) is cut on a UTF-8 boundary.
- The result is collected in kind name order, so history records it the same way every time; the model is shown it in its renderers' order.
- A `ContextRequest` carries the session id, the session mode, the turn's permission mode and the host input's `TurnExtensions`, which the Agent passes on unread. Treat a missing value as "not supplied for this turn". Long work runs on the `BlockingService`.
- Text rendered from JSON goes through `ContextSection::from_json`, which sorts object keys so the version digest is stable.
- A section is at most 32 KiB, and all of them 64 KiB.

### Context renderers [#context-renderers]

- Everything model-visible that is neither history nor a tool is a context section of a `ContextSectionKind`: a world-state section (persisted, from a `ContextContributor`) or a prompt fragment (per request, from a `PromptContributor`). The model is shown a section by the `ContextRenderer` of its kind, which the plugin that owns the kind registers in the `ContextRendererRegistry` (one per kind; an invalid or repeated kind fails the registering plugin).
- A renderer is data: the `ContextSlot`, the `ContextRole`, a `preamble` (what the section is and what authority it **lacks**), an `epilogue`, and `versioned`, which puts the content in an `<agent_world_state kind=".." version="..">` element. A kind's wrapper text lives in the plugin that owns it, never in `hanafubuki-agent-model-api`, which sends a fragment's role and rendered text as they are and matches on no section kind. Sections without a framing of their own use `WORLD_STATE_PREAMBLE`.
- The kernel registers the renderer of the kind it writes itself (`tool_catalog_omissions`) when its registries are built; the `workspace-context`, `permission-mode`, `skills` and `memory` plugins and a host's plugins register theirs with their contributors. The kernel knows no host kind.
- The kernel takes a renderer snapshot for every model request. A section whose kind has no renderer (its plugin stopped) is left out of that request; a world-state section stays in history, and the next admission removes it if no contributor produces it.
- Order: every run of adjacent sections in a request is ordered by slot (`Instructions`, `WorldState`, `Capabilities`, `Memory`), then by renderer registration order (the kernel's, then the manifest's mount order, the host's rows after the Agent's capability plugins and before its context plugins; a remounted plugin's renderers move to the end of their slot); every other item keeps its place. The prompt fragments join the run the conversation opens with. A world-state section that changes later is shown where it changed. Only the latest version of a kind is ever shown, so there is no "replaces previously provided" notice and no section-changed event: the persisted `WorldStateUpdate` is the change record.

### Turn admission [#turn-admission]

- A `TurnAdmissionContributor` produces per-turn data once, when a turn is admitted, as `TurnExtensions`. The kernel freezes them on the turn and hands them to every tool call and prompt contributor of the turn; a turn restored after a restart has none.
- Contributors run before the kernel admits the turn, one after another in `(rank, id)` order under an entry lease (`collect_turn_extensions`). An error, a panic, a contributor whose plugin is stopping, or a value of a type another contributor already returned leaves that contributor out of the turn, recorded as its plugin's issue as for a context contributor; the result never depends on registration order. The one admission that still fails is a Skill the user referenced explicitly that the turn cannot resolve: without the `skills` plugin's values it is refused ("the Skill catalog is unavailable") rather than run without it.
- The kernel reads one value itself: `SelectableSkills`, the Skills an explicit reference or a `$mention` may select, with its `mention_exclusions`, the names a plain `$mention` names instead of a Skill.

### Prompt fragments [#prompt-fragments]

- A `PromptContributor` renders model-visible fragments from the turn's `TurnExtensions`, what the contributors prepared for the request's sampling step and the session's context window (`PromptRequest`). A `PromptFragment` has a kind (a `ContextSectionKind` whose renderer the same plugin registers), an optional version (shown only by a versioned renderer) and content.
- `prepare` is the one async, I/O-allowed call: once per sampling step, when it starts, the kernel asks every contributor of the step's snapshot, one after another in `(rank, id)` order, with a `PromptStep`, under a lease on its entry and with a child of the turn's cancellation. It returns typed values, merged into the step's prepared values. A contributor whose plugin is stopping prepares nothing; an error, or a value of a type an earlier contributor prepared, leaves that contributor's values out of the step with a warning. Only the turn's cancellation fails the step.
- `contribute` is pure and bounded (no I/O, no blocking, no per-call state, never a call into the kernel), so the kernel calls it without a lease. It returns nothing for a request that lacks what it renders. Values it needs from outside the turn are loaded in `prepare`, never in `contribute`.
- The kernel never runs a contributor under the session's lock: it reads the turn's extensions and context window under the lock, releases it, prepares the step and renders the fragments, and builds the request under the lock again. It does so once when a sampling step is prepared, and every request counted for that step uses that one rendering.
- A budget a plugin measures in tokens uses `hanafubuki_agent_contracts::{estimate_tokens, token_budget_bytes}`, the estimate the kernel admits requests by.
- The kernel reads one prepared value itself: `AgentMemoryStep`, the step's memory policy. A step without one (the `memory` plugin is off) shows answers as they are, commits no citations and marks no pollution.
- Instructions are not prompt fragments: the session's instructions and the kernel's Plan-mode prompt are session configuration.

## Approval rules [#approval-rules]

- A plugin that owns an action tightens its approval with an `ApprovalRule`, registered next to the tools that produce the action. A rule no single plugin owns would stay in the kernel.
- `evaluate` inspects the `ApprovalAction` only. It is pure and bounded, so the kernel calls it without a lease. Every call of a step is judged by the step's frozen `ApprovalRuleSnapshot`, so a rule cannot disappear under a call that is still draining.
- A rule returns `None` (no opinion), `RequireUser` or `Deny { reason }`. They combine monotonically: any denial rejects the call with the reason as its model-visible error (several give their distinct reasons sorted and joined); otherwise any `RequireUser` makes the action `Manual` even under `AutoReview` or `FullAccess`; otherwise the turn's permission mode decides.
- A rule never relaxes approval. An action a tool declares `NotRequired` or `Forbidden` never reaches the rules; a hard refusal belongs in the tool's `permission`.
- The user may answer a `Manual`-mode prompt with `AllowForSession`: later actions of the same tool (`(provider id, tool id, generation)`) in the session are authorized without asking whatever the turn's mode, but only where the rules have no opinion. A rule's `Deny` still rejects and its `RequireUser` still asks, and that prompt does not offer `AllowForSession`. The allowance lives in the session's runtime state only.

## Continuation hooks [#continuation-hooks]

- A hook asks to keep a turn going after a candidate final answer. The kernel snapshots the registry when it starts a sampling step and, if the step ends with a final answer, asks the hooks in order. Each call holds an entry lease and observes a child of the turn's cancellation, bounded by the turn's tool idle timeout. A hook whose plugin is stopping is skipped.
- `Pass` asks the next hook, `Stop` ends the turn without the remaining hooks, and `Continue` returns 1 to `MAXIMUM_CONTINUATION_FRAGMENTS_PER_HOOK` non-blank fragments of at most `MAXIMUM_CONTINUATION_FRAGMENT_BYTES`, which the kernel commits as `ContinuationContext` before it samples again. A failure or timeout fails the turn under `FailTurn` and is skipped under `Ignore`. None is registered today.

## Observers [#observers]

- An `AgentObserver` learns what the kernel committed through `AgentNotification`: `TurnAdmitted` (with the turn's `AgentTurnOrigin` and the provisional title its admission committed), `SamplingCommitted` (with the answer's memory citations), `TurnFinished`, `MemoryContributionChanged` (with its cause), `SessionArchived` / `SessionRestored`. A notification is added with its first consumer.
- The kernel notifies after the commit is durable and its events are emitted, never under a session's lock, and in commit order. A failed commit notifies nothing.
- `observe` is synchronous and runs on the committing thread: it signals a worker or does a small bounded local update, and never waits for the kernel. It returns nothing, so it cannot change an outcome; what must be durable or reach the model is not an observation.
- A call holds no lease: an observer whose plugin is stopping is skipped from the moment its retirement starts.
- Background work an observer starts runs in a worker the plugin owns, spawned with `spawn_scoped_worker` from `apply` and fed through a bounded channel the observer only `try_send`s to; the worker is cancelled and awaited when the plugin stops. It reaches the kernel through a narrow port the application constructs (`AgentTitleApplication` for the `titles` plugin), never through the facade, and the kernel mutations it makes are compare-and-swap, so what the user did meanwhile wins.

## External producers: MCP servers, Skills, web, memory [#external-producers-mcp-servers-skills-web-memory]

What an MCP server, a Skill author or an extraction model produces is read tolerantly; one bad item costs only itself, and the strict rules (MCP configuration, credentials and OAuth, path containment, URL validation, persisted formats) are unchanged.

- **The MCP catalog** is built tool by tool. Each name segment is sanitized per character to `[A-Za-z0-9_-]`, and one still over 128 bytes is cut and given a hash suffix. A tool with an invalid or oversized input schema, a name that cannot be encoded or a later duplicate is skipped; a description over 16 KiB is cut on a character boundary and an invalid output schema dropped. Each is a Warning diagnostic of the server; the server stays connected, with zero tools if none is usable.
- **MCP annotations are hints from a server the user configured, never a grant.** A tool whose `readOnlyHint` is true and whose `destructiveHint` is not is `ConcurrentRead` and `ReadOnly`; every other is `Exclusive` and `Mutating`. Every MCP tool's memory effect is `PollutesContribution`. Approval does not read the read-only hint: the server's (or the tool's) approval policy decides, and `Allow` skips the review only for a tool whose `destructiveHint` is false, a missing hint counting as destructive.
- **MCP liveness**: a connection's transport says when rmcp's loop ended; when the server's side ended it, the server is `Failed` with the reason, its entry is retired, and the manager reconnects it under the module host's `RestartPolicy` with the configuration and secrets the closed connection was opened with. A connect from outside (the user's Connect or Refresh, a settings, credential or proxy change) empties the window, and shutdown cancels a scheduled one. A step keeps the connection it was planned with; a call on a lease whose connection closed returns `McpError::CatalogChanged` without asking for approval.
- **MCP output**: a content block the client cannot decode becomes the text `[unsupported MCP content: <type>]`; over 64 items keeps 63 and a note; a mime type with parameters is its base type, and unpadded base64 is accepted.
- **Skills**: `SKILL.md` frontmatter and `openai.yaml` are read field by field: a wrong type on an optional key drops that key with an issue, a name over 96 characters or a description over 4096 bytes is cut with an issue, and an unreadable directory below a root is skipped. `name` and `description` stay strict on type. `allowed-tools` is an unknown key: Skills never add or restrict tools. A Skill whose declared MCP server is not Ready is not usable in the turn and is listed as unavailable, with why.
- **Web**: a search endpoint configuration the service cannot use leaves the `web` row running with `web_search` omitted from every step; `fetch_web_page` keeps working.
- **Memory**: a notes line that cannot be read is skipped (logged by line number, never its content). Phase-one extraction output ignores fields its schema does not name and keeps what the named ones still give; only output that is not an extraction object at all fails the job. The consolidation agent may write only what publish accepts, and a write over a bound is a tool error naming it, so the model can shorten and retry.

## Host, configuration and status [#host-configuration-and-status]

- The Agent is optional to its host. It is built once the host's interface is up, on the runtime its start builds, from the captured launch (`AgentLaunch`); the slot keeps the launch, so every later instance (a restart, an automatic restart, turning it back on) starts the same way, with the next generation. A construction, recovery or start failure leaves the slot `Failed`.
- A fault is either a plugin's or the kernel's ([Faults](/docs/architecture#faults)). A panic in one of the plugin host's own tasks (the fault follower, a remount) is reported to the kernel fault sink as a kernel fault at `plugin host`, and rebuilds the Agent.
- A capability that cannot come up fails its plugin, not the Agent: a Skill catalog that did not open fails the `skills` plugin, a required MCP server that did not connect is its MCP status, a `web` configuration that does not derive is that row's error. A session recovery rejects is quarantined.
- `AgentHost` is the Agent's configuration of the generic module host (`AgentPlugins`, its `HostProfile`): the mount order, bounds, enablement, reconfiguration, retry, safe mode, fault handling, status and shutdown are the host's. What is the Agent's: its rows, their configuration from its own settings and the host's proxy (`AgentPluginSettings`), its enablement from `disabledPlugins`, its groups, the contributions in its status, its `AgentPluginEventSink`. Its options: `module_faults` off (its rows are plugins, not application modules, and their faults reach it through `PluginFaults` alone), and `automatic_restarts` the default restart policy.
- A row is `AgentPluginRow::unconfigured` or `AgentPluginRow::from_settings` and declares its `AgentPluginGroup`: `Capability` (tools, tool sources and their rules) or `Context` (world-state sections). Configuration that is not derived from settings does not exist; a service a plugin adapts is captured in its `PluginDef` constructor (through `AgentPluginInputs`), not passed as configuration.
- A settings-derived plugin follows the settings. After a settings write, `apply_settings_to_plugins` is scheduled on the running Agent's runtime, and the host reconfigures its rows from the latest published settings. `disabledPlugins` is the enablement: a re-enabled row mounts only once its previous fiber stopped, so its registrations cannot collide with the old ones. `set_plugin_enabled` is the one writer and refuses an unknown name and disabling a core row. Disabling a plugin is not a way to deny a tool: approval stays with the rules and the permission mode.
- A plugin that absorbs a change without restarting registers a kardia update hook (`Context::on_update`); otherwise the plugin restarts, which drains its running calls.
- `plugin_status` returns every plugin's `AgentPluginStatus`: name, group, state (`pending`/`active`/`failed`/`disabled`/`disposed`), error text, an active plugin's `warning`, enabled, lock (`core` for the core rows), `restart` and its current contributions.
- **Bounds**: the host bounds every wait it makes on kardia: a start within `PLUGIN_START_TIMEOUT` (20 s), a disposal within `PLUGIN_STOP_BOUND` (10 s), a remount within the disposal's bound. A fiber stuck for good is dropped with its Agent instance's runtime.
- Shutdown disposes the kardia root once, bounded by the caller's deadline; a plugin still stopping then is reported as an `agent-plugins` shutdown diagnostic. MCP connections, memory workers, history and executions are owned by the application and stop in its own shutdown steps, never in a plugin's teardown.

## The host interface [#the-host-interface]

An embedding application (the host) adds to the Agent only through `AgentHostPorts`, a field of `AgentServiceInputs` built for every Agent instance. Each port's use and default is in [Embedding the Agent](/docs/embedding#the-host-interface); the rules are:

- The interface takes plain values (`PathBuf`, strings, maps) or the Agent's own types, never a host's foundation, process or module-host types: they are distinct types on the two sides, and the host adapts at the edge (the Agent's shutdown diagnostics, for one, are mapped to the host's at the call).
- A host's plugin rows are plugins like any other: written against contracts, every rule of this page applies, `disabledPlugins` turns them off, safe mode leaves them unmounted. They mount after the Agent's capability plugins and before its context plugins.
- Host input (the `host` of `AgentTurnRequest`, `AgentSteeringRequest` and `AgentFileSearch`) travels as `TurnExtensions`, passed on unread to the context contributors, `HostContextPort` and `WorkspaceRootsPort`. The IPC inputs that carry it are the host's and are converted on its side.
- The data directory's lock is held from the first start until shutdown, in both modes; a host does nothing for it.
- A host reads the Agent's runs through `AgentSlot::list_run_projections` and `get_run_projection` and maps them to its own view.

## Logging [#logging]

kardia's logs reach the `log` facade through the `LogExporter` the host installs on its root. kardia has no `trace` level, so content the content-logging rule confines to `trace` is never logged through a kardia logger.

## Writing a plugin [#writing-a-plugin]

Choose where it lives:

- A **plugin crate** `crates/plugin-<name>` (`hanafubuki-agent-plugin-<name>`) when it binds one domain crate and needs only contract types (`web`, `workspace-fs`, `execution`, `mcp`; a tool source too).
- A **plugin in the facade**, under `crates/agent/src/plugins/`, when it needs the Agent's own services (image normalization, `AgentSkillApplication`, `AgentMemoryApplication`, `AgentTitleApplication`). It is exported from `plugins/mod.rs`, with no Cargo change.
- A **host plugin** in the host's own crate when it needs the host's domains. It is written against contracts and the facade's public API only, and is one of the host's rows in `AgentHostPorts::plugins`; the rules here apply to it unchanged. See [Host plugins](/docs/host-plugins).

Checklist:

<Steps>
  <Step>Crate: a `Cargo.toml` with `hanafubuki-agent-contracts`, `kardia-core`, and the `hanafubuki-agent-approval`, `hanafubuki-agent-tool-contracts` and domain crates the tools use; a `src/lib.rs` with module declarations and `pub use plugin::<name>_plugin;` only.</Step>
  <Step>`<name>_plugin() -> PluginDef`: `PluginDef::new` (`PluginDef::typed` for a settings-derived configuration), `.name("<name>")`, and `.inject(..)` with the `NAME` of every registry or host service it uses (`PluginFaults::NAME` for `spawn_scoped_worker`). `apply` gets each with `ctx.get::<T>()?`, registers with `register(Arc::new(..))?`, spawns long work with `spawn_scoped_worker`, and returns.</Step>
  <Step>Each tool: a `ToolDescriptor` with a `ToolName::parse` name, a JSON schema with `additionalProperties: false`, the exposure, execution class, effect, activity action and memory effect; `permission` returns `NotRequired` for a read or the `ApprovalAction` of a mutation; `invoke` validates the arguments, observes cancellation, re-checks a mutation's approval (`verify_tool_approval`), and runs blocking work on the `BlockingService`.</Step>
  <Step>No `.unwrap()`/`.expect(` in production sources; map errors into `kardia_core::Error`.</Step>
  <Step>Wire it: an entry in the root `Cargo.toml`'s `[workspace.dependencies]` (with both `path` and `version`), a dependency in `crates/agent/Cargo.toml`, a row in the layer table (`xtask/src/dependencies.rs`), and one row in `crates/agent/src/host/manifest.rs` (a service it adapts goes through an `AgentPluginInputs` field). `Cargo.lock` follows.</Step>
  <Step>Test it as in [Testing a plugin](#testing-a-plugin), and regenerate the goldens if the model sees the change.</Step>
  <Step>Document it: the crate row in [Architecture](/docs/architecture#crates-and-layers) and the [plugins today](#the-plugins-today) table and tool count on this page.</Step>
  <Step>Validate from the repository root with `cargo xtask check`, `cargo fmt --all --check`, `cargo test -p hanafubuki-agent-plugin-<name>` and `cargo test -p hanafubuki-agent --lib`.</Step>
</Steps>

A new plugin changes no kernel or contracts file.

## Testing a plugin [#testing-a-plugin]

- Mount it on a fresh `kardia_core::Context` under a plugin that provides the registries it injects, and `PluginFaults` when it uses `spawn_scoped_worker` (or `hanafubuki_agent::test_support::mount` for a facade or host plugin, which provides both), wait for `settled()`, and assert `state()`: `settled()` also resolves while a plugin is still `Pending` on a missing service.
- Assert its registrations, update its config, dispose it, and assert that every registration is gone. A configuration the plugin rejects leaves it `Failed` with nothing registered.
- Test handlers and domain logic without kardia where they do not need it.
- **The request goldens** (`crates/agent/src/tests/golden.rs`, over the Agent's own plugins with a host that adds no rows, context or instructions) pin what the model receives: the instructions, the tool catalog and the input items in Default and Plan mode, with a Skill catalog, workspace instructions, the memory summary, after a compaction, with MCP tools from a scripted in-process server, and around a tool call and a `tool_search`, plus the presentation events of a tool round trip. A change the model sees changes the request goldens **on purpose**: regenerate them with `HANAFUBUKI_AGENT_UPDATE_GOLDEN=1 cargo test -p hanafubuki-agent --lib tests::golden` and review the fixture diff.
- **The history corpora** (`golden/history/` and `golden/history-reasoning/`) are re-recorded only with `HANAFUBUKI_AGENT_UPDATE_GOLDEN_HISTORY=1`, after an intended history-format change; otherwise they keep proving that older history opens.
- A host keeps goldens of its own over its rows (Hanafubuki's are in `hanafubuki-agent-integration`), which a model-visible change here changes as well. The fixtures are Linux-only.

The commands and update rules are in [Building and testing](/docs/building-testing).
