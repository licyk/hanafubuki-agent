A role is a named definition of how the Agent works: instructions, a model, a reasoning effort, a permission-mode cap, and the tools and plugins it may use. A role only ever **narrows** the Agent it runs in: it can take tools and plugins away and tighten the permission mode, never add or widen anything, so no role is more capable than the instance itself. Approval rules, your hooks and the sandbox are out of every role's reach.

Roles are defined in TOML, by you, a profile or a trusted project, beside two built-in ones; an [installed plugin](#plugins) can bring roles too. The Agent reads, checks and lists them (`hanafubuki-agent roles`, `doctor`, `/warnings`), and a session runs with the one you choose ([Roles in sessions](#sessions)), and a sub-agent with the one its parent's model gives it ([Roles for sub-agents](#subagents)).

## Defining a role [#define]

A role file is a `.toml` file in an `agents/` directory: the user's beside `config.toml` (`~/.config/hanafubuki-agent/agents/` on Linux), or a trusted project's `.hanafubuki-agent/agents/`.

```toml
# ~/.config/hanafubuki-agent/agents/reader.toml
description = "Reads the code and reports findings; never edits files."
extends = "explorer"
instructions = """
Answer with file paths and line numbers.
"""
model = "gpt-5.4-mini"
reasoningEffort = "low"
permissionModeCap = "manual"

[tools]
allow = ["read_file", "search_text", "list_directory"]
deny = ["fetch_web_page"]

[plugins]
off = ["titles", "goal"]
```

The role's name is the file's `name` key, else its file name without `.toml` (`reader`). Files in subdirectories of `agents/` are read too.

## Keys [#keys]

| Key                 | Type and values                                                                | Default                          | Means                                                                                                        |
| ------------------- | ------------------------------------------------------------------------------ | -------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `name`              | A role name                                                                    | the file's stem                  | The role's name, in a role file. An `[agents.NAME]` entry is named by its key                                |
| `description`       | Text                                                                           | the parent's                     | What the role is for, as the guidance that offers it will show. A role needs one, its own or one it inherits |
| `extends`           | A role's name                                                                  | none                             | The role it builds on ([below](#extends))                                                                    |
| `instructions`      | Text                                                                           | none                             | What the role adds to the Agent's instructions                                                               |
| `instructionsMode`  | `"append"` or `"replace"`                                                      | `"append"`                       | Whether the instructions follow those of the roles it extends, or replace them                               |
| `model`             | A model id                                                                     | the parent's, else the session's | The model the role runs                                                                                      |
| `reasoningEffort`   | `minimal`, `low`, `medium`, `high`, `xhigh`, or another effort the model takes | the parent's                     | The reasoning effort                                                                                         |
| `permissionModeCap` | `"manual"`, `"auto_review"` or `"full_access"`                                 | none                             | The widest permission mode the role runs in; it only tightens                                                |
| `spawnable`         | `true` or `false`                                                              | the parent's, else `true`        | Whether a sub-agent may be given the role ([below](#subagents))                                              |
| `tools.allow`       | An array of [tool patterns](#tool-patterns)                                    | everything the parent allows     | The only tools the role may use                                                                              |
| `tools.deny`        | An array of tool patterns                                                      | none                             | Tools the role may not use, whatever `allow` says                                                            |
| `plugins.off`       | An array of plugin names (`guest:<id>` for an installed plugin's code)         | none                             | Plugins whose tools and context the role's sessions do not get                                               |

A role name holds 1 to 128 bytes without spaces, control characters or `:`, which an installed plugin's roles use (`<plugin>:<role>`, [below](#plugins)).

## Tool patterns [#tool-patterns]

Each entry of `tools.allow` and `tools.deny` is one of:

- **a tool name**, as the model calls it (`read_file`, `mcp__github__list_issues`), where `*` matches any run of characters (`mcp__github__*`, `read_*`);
- **`plugin:NAME`**: every tool the plugin `NAME` registers or provides (`plugin:web`; `plugin:guest:demo@my-mkt` for an installed plugin's code);
- **`provider:ID`**: every tool a tool provider supplies, `*` allowed (`provider:mcp.github`, `provider:plugin.demo.*`).

An entry that is none of these (empty, with a space, or with another `kind:`) is left out, with an issue. A pattern that matches no tool is not an error: tools come and go.

## Where roles come from [#sources]

Roles come from these sources, lowest first. A role of a higher source **replaces** a role of the same name below it, whole: nothing of the lower one is kept. To build on a role, give yours another name and `extends` it.

1. **The built-in roles**, `default` and `explorer` ([below](#built-in)).
2. **The installed plugins'**, each named `<plugin>:<role>`, while the plugin is on ([below](#plugins)).
3. **The user's**: the role files of the user's `agents/` and the `[agents]` entries of the user's `config.toml`.
4. **The profile's**: the `[profiles.NAME.agents]` entries of the profile `-p NAME` selects.
5. **The trusted project's**: the role files of `.hanafubuki-agent/agents/` and the `[agents]` entries of `.hanafubuki-agent/config.toml`, read only when the user's `config.toml` trusts the project ([The project's file](/docs/config-layers#projects)).

Within one source, the `[agents]` entries come first, by name, then the role files, by path. When two define the same name, the first keeps it and the other is ignored, with an issue. A role that cannot be used still takes its name: it never lets a lower role of that name through.

An embedding application's configuration has the user's source alone: its `agents/` and `[agents]`.

## Entries in config.toml [#inline]

A role can be written in any layer's `config.toml` instead of a file, with the same keys:

```toml
[agents.reviewer]
description = "Reviews a change and lists the problems it finds."
extends = "explorer"
reasoningEffort = "high"

[agents.reader]
configFile = "agents/reader.toml"
model = "gpt-5.4"
```

`configFile` (Codex's `config_file`) names a role file, relative to the folder of the `config.toml` that names it: the entry's keys are read over the file's, and the entry's key is the name. That file is the entry's, so the directory does not read it a second time. A `configFile` that cannot be read makes the role unusable.

`[agents]` is not a setting: `config get` and `config set` do not reach it, and a `-c agents.…` override is an unknown key.

## extends and the merge [#extends]

`extends` names one parent, found by name among every source's roles after precedence. A chain holds at most 8 roles (the role and the roles it extends). A role whose parent is missing or unusable, whose chain is a cycle (a role extending itself included) or longer than 8, is unusable, and says why; it never falls back to something else.

The chain is merged field by field, from the root to the role, each rule only narrowing:

| Field                                                  | Rule                                                                                                                                                       |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `description`, `model`, `reasoningEffort`, `spawnable` | The role's if it sets it, else its parent's                                                                                                                |
| `instructions`                                         | `append`: the parent's, a blank line, then the role's. `replace`: the role's alone (none, if it has none)                                                  |
| `permissionModeCap`                                    | The stricter of the two: `manual`, then `auto_review`, then `full_access`                                                                                  |
| `tools.allow`                                          | A tool must be allowed by every role of the chain that sets `allow`: a role's own list never adds a tool its parent leaves out. No `allow` is the parent's |
| `tools.deny`, `plugins.off`                            | Every role's, together                                                                                                                                     |

So a role removes any one inherited tool with `deny`, and an allow list narrows what its parent allows: a child of `explorer` with `allow = ["read_*"]` may use `read_file` and nothing else.

## The built-in roles [#built-in]

| Role       | Narrows                                                                                                     | Spawnable |
| ---------- | ----------------------------------------------------------------------------------------------------------- | --------- |
| `default`  | Nothing: the Agent as it is configured. The role a session has without one                                  | yes       |
| `explorer` | Its tools: `list_directory`, `search_text`, `read_file`, `view_image`, `web_search`, `fetch_web_page` alone | yes       |

`explorer`'s description is Codex's, adapted: explorers answer specific questions about the codebase, are trusted without being checked again, and run in parallel for independent questions. A role of yours named `explorer` replaces the built-in one. The name `default` is reserved: `default` always narrows nothing, so a role of yours with that name is not usable, with an issue (give it another name; it can still `extends = "default"`).

## Roles in sessions [#sessions]

A session has one role, `default` unless you choose another:

- **When it starts**: `--role NAME` for the terminal interface's new sessions and for [`exec`](/docs/exec), or the `role` of `create_session` when the Agent is [embedded](/docs/embedding#sessions).
- **Between turns**: `/role NAME` in the [terminal interface](/docs/terminal-interface#role) (`/role` alone lists the usable roles), or `set_session_role`. It is refused while a turn runs. `/role default` takes every narrowing away again.

A role no source defines, or one that cannot be used, is refused, and the message names the usable ones.

What the session takes of its role:

- **Instructions.** The session's instructions are always the Agent's base instructions, which carry the approval guidance, followed by the role's chain merged: `instructionsMode = "replace"` replaces only the instructions of the roles it extends, never the base. Selecting another model keeps them.
- **Model and reasoning effort**, when the role sets them, through the model selection, so the context window is resolved as for any model. `--model` (or `/model`) afterwards still chooses another.
- **Its narrowing**, as the session's capability scope ([Capability scope](/docs/plugin-rules#capability-scope)):
  - only the tools the role allows and does not deny are offered; the kernel's own (`update_plan`, `request_user_input`, `new_context`, the compression tools) and `tool_search` always are. A call to a tool the role leaves out gets the same answer as a call to a tool that does not exist;
  - a plugin in `plugins.off` gives the session nothing: no tools, no context sections, no prompt, no continuation. With `skills` off, a Skill you reference explicitly is refused ("the Skill catalog is unavailable"), a `$mention` selects no Skill (it stays text), and the Skill tools are absent; with `memory` off, the memory summary and tools are absent, but the session still contributes to memory as its contribution mode says;
  - every turn runs in the stricter of its permission mode and the role's `permissionModeCap`.

  Approval rules, your hooks, the plugins' observers and the sandbox apply whatever the role says. Plan mode still keeps only the read-only tools among those the role keeps.

The session keeps all this in its own record: editing or deleting the role file later changes no session that has it (a restart keeps it too), until you choose the role again. A [sub-agent or side conversation](/docs/sessions#children) is never wider than its parent's role, and a fork keeps its source's.

## Roles for sub-agents [#subagents]

The model gives a [sub-agent](/docs/sessions#subagents) a role with `spawn_agent`'s `agent_type` (Codex's name for it): one of the **spawnable** roles, those whose `spawnable` is `true` (both built-in roles are).

- **What the model reads.** The guidance on sub-agents lists the spawnable roles by name with their descriptions (`agent_type`'s description points at it): at most 16 roles, in name order, each description on one line and cut at 200 characters. Write a role's `description` for that reader: when to choose it.
- **Without `agent_type`**, or with `default`, the sub-agent keeps its parent's role: its narrowing and its instructions.
- **With a role**, the sub-agent's instructions are the base instructions and that role's; its narrowing is its parent's narrowed further by the role's, so a sub-agent never has a tool its parent lacks; its model is the role's `model` (of the parent's Provider), else its parent's, and its reasoning effort the role's `reasoningEffort`, else its parent's. It always runs with its parent's permission mode, capped by the role's `permissionModeCap`.
- A role that is unknown, cannot be used or is not spawnable is refused: the model reads an error naming `agent_type` and listing the spawnable roles, and no sub-agent is made.
- `list_agents` names each sub-agent's role (`agent_type`).

A spawn reads the roles as they are then, and so does the guidance at every step. The guidance is shown only to a session whose step offers `spawn_agent`: a session in a role that leaves the tool out (such as `explorer`) does not read it.

## Plugins' roles [#plugins]

An [installed plugin](/docs/plugins) brings roles with its `agents` component ([Writing plugins](/docs/writing-plugins#roles)):

- a plugin in this project's format, role files: the `.toml` files of its `agents/` (or of the paths its manifest's `agents` names), read exactly as yours are, every key included;
- a Claude Code plugin, agent files: the `.md` files of its `agents/`, whose frontmatter's `name`, `description`, `tools`, `disallowedTools`, `permissionMode` and `model` and whose body (the instructions) are read as a role, its Claude tools mapped to this Agent's and its `permissionMode` to a `permissionModeCap` ([the tables](/docs/writing-plugins#claude-agents));
- a Codex, Cursor or Agent Plugins plugin has none.

**Names.** A plugin's role is named `<plugin>:<role>`: the plugin name of its id (`demo` for `demo@my-mkt`), then the role's own name (its `name`, else its file name). No role of yours can take that name, since yours have no `:`. Two plugins of the same name from different marketplaces, both on: the first by id (`demo@alpha` before `demo@beta`) keeps the name, and the other brings no role, with an issue. An `extends` names a role as the catalog names it, so a plugin's role extending another of its own writes `extends = "demo:base"`.

**Lifetime.** A plugin's roles are in the catalog while the plugin is on: turning it on or off (or installing, updating or removing it) reads the roles again, without a restart. In safe mode no plugin brings a role. A session that already has a plugin's role keeps what it took, as for any role.

**Only narrowing.** A plugin's role goes through the same merge as yours: it can only take tools and plugins away and tighten the mode, so it is never wider than the instance it runs in. A role of yours that `extends` it narrows it further, and may set its `spawnable` again.

What reading a plugin's role files left out (an unknown key, a Claude tool with no counterpart) is the **plugin's** issue, shown with it in `plugins info` and `/plugins`; a plugin's role that cannot be used is a role issue, as yours are. The plugins' roles are part of the running Agent's catalog: sessions (`--role demo:reviewer`, `/role`) and sub-agents (`agent_type`) take them, and `/plugins` lists them per plugin. `roles list`, `roles show` and `doctor` show them too, without starting the Agent: they read the installed plugins as they are on disk, writing nothing to the plugins' directory and taking no lock, so they work beside a running Agent, and only a plugin that is on (and none with `--safe-mode`) brings its roles, as in a running Agent. There, what reading a plugin's roles left out is listed with the role issues, each naming its plugin.

## Codex role files [#codex]

A Codex role file works unchanged in `agents/`: its `developer_instructions`, `model` and `model_reasoning_effort` are read as `instructions`, `model` and `reasoningEffort`. When both a key and its Codex name are set, ours is used, with an issue. Its other Codex keys (`sandbox_mode`, `nickname_candidates` and the rest) are settings of the whole Agent here, so they are ignored, each with an issue. Codex's `[agents]` settings (`max_threads` and the like) are not roles, and are ignored with an issue.

## What cannot be used [#issues]

A role file is configuration you wrote, so it is read tolerantly and never rewritten:

- Each key is read on its own. A key of the wrong type (a `model` that is a number) is left out, with an issue, and the parent's value or the default is used. An unknown key is ignored, with an issue.
- An array item of `tools.allow`, `tools.deny` or `plugins.off` that is not text is left out alone, which narrows a list, never widens it.
- A key that narrows and cannot be read at all (an `extends` that is not a name, a `permissionModeCap` that is not a mode, a `tools` or `plugins` that is not a table, an `allow`, `deny` or `off` that is not an array) makes the role **unusable**: leaving it out would allow more than the role says.
- A file that is not valid TOML is an unusable role of its file name; a file whose name cannot be a role's is ignored, with an issue.
- A role without a description, of its own or inherited, is unusable.
- A role whose chain holds more than 128 tool patterns (its allow lists and deny patterns together) is unusable: a session holds no more.

The issues and the unusable roles, with why, show in `hanafubuki-agent roles list` (on standard error), in the `roles` lines of [`doctor`](/docs/troubleshooting#doctor), and in the terminal interface's [`/warnings`](/docs/terminal-interface#warnings), under **roles**. A role that cannot be used never stops the Agent.

## Seeing the roles [#inspect]

```sh
hanafubuki-agent roles list
hanafubuki-agent roles show reader
hanafubuki-agent -p review roles show reader   # with the profile's roles
```

```text
reader  user file /home/me/.config/hanafubuki-agent/agents/reader.toml
chain: reader (user file /home/me/.config/hanafubuki-agent/agents/reader.toml) → explorer (built-in)
description: Reads the code and reports findings; never edits files.  [from reader]
instructions: Answer with file paths and line numbers.  [from reader]
model: gpt-5.4-mini  [from reader]
reasoningEffort: low  [from reader]
spawnable: true  [from explorer]
permissionModeCap: manual  [from reader]
tools.allow: every one of [list_directory, read_file, search_text] and [fetch_web_page, list_directory, read_file, search_text, view_image, web_search]  [from reader, explorer]
tools.deny: fetch_web_page  [from reader]
plugins.off: goal, titles  [from reader]
```

`roles show` prints each field as the chain resolves it, and which roles of the chain decide it, nearest first. Neither command starts the Agent ([CLI reference](/docs/cli-reference#roles)).

## When roles are read [#reload]

A running Agent reads the roles when it starts, and again each time it reloads its installed plugins (with the plugins' roles as the reload left them), which it does after every settings write it makes and after every change to the installed plugins. A role file you edit by hand takes effect then, or at the next start, for the sessions that choose it from then on; a session that has it already keeps what it took. `roles list`, `roles show` and `doctor` read the files each time they run.
