hanafubuki-agent 有两种运行方式，背后是同一套组合：

- **独立运行**：`hanafubuki-agent` 命令行与终端界面。门面 crate 的 `AgentRuntime::standalone` 为每个宿主端口提供默认实现（工作目录作为工作区、操作系统钥匙串、配置文件里的代理）。
- **嵌入运行**：宿主应用（例如 [Hanafubuki](https://github.com/licyk/Hanafubuki)）自己组合 Agent，通过**宿主接口**提供插件、工作区、上下文、指令、网络设置和密钥存储。Agent 不知道宿主的任何领域，也不依赖宿主的任何 crate；依赖方向只有一个：宿主依赖 Agent。

本页说明嵌入方式。编写宿主插件见[宿主插件](/docs/host-plugins)，各部分如何协作见[架构](/docs/architecture)。

## 添加依赖 [#adding-the-crates]

```toml
[dependencies]
hanafubuki-agent = "0.2"
hanafubuki-agent-contracts = "0.2"
hanafubuki-agent-runtime = "0.2"
# 宿主插件的工具还需要：
hanafubuki-agent-approval = "0.2"
hanafubuki-agent-tool-contracts = "0.2"
kardia-core = "0.2.0"
```

| crate                             | 用途                                                                                          |
| --------------------------------- | --------------------------------------------------------------------------------------------- |
| `hanafubuki-agent`                | 门面：组合、槽位（slot）、服务 API、宿主接口、配置（`AgentConfig` 由它重新导出）              |
| `hanafubuki-agent-contracts`      | 插件 API：注册表、工具与上下文契约、`TurnExtensions`（实现 `WorkspaceRootsPort` 需要它）      |
| `hanafubuki-agent-runtime`        | `ContainedRuntime`：每个 Agent 实例的运行时，出现在 `AgentConstructor` 的签名里               |
| `hanafubuki-agent-approval`       | 宿主插件的工具需要的审批类型（`ApprovalAction`、`PermissionRequirement`、`AuthorizedAction`） |
| `hanafubuki-agent-tool-contracts` | 工具名与工具规格类型（`ToolName`、`ToolExposure`、`ToolExecutionClass`）                      |

插件用 kardia 的 `PluginDef` 定义，所以需要 `kardia-core`。宿主不应依赖内核（`hanafubuki-agent-kernel`）、模型 API 或其他内部 crate；门面重新导出了宿主需要的类型。

<Callout title="版本">
  1.0 之前，次版本号的升级可以包含破坏性变更（Cargo 对 `0.x` 的规则），所以依赖写 `"0.1"`
  这样的次版本要求，随每个次版本手动升级。首个版本发布到 crates.io 之前，宿主用 git 依赖固定一个
  revision（Hanafubuki 目前就是这样）。
</Callout>

## 组合 [#composition]

嵌入时宿主自己组装独立模式也在用的几个部件：

| 部件                      | 作用                                                                                                       |
| ------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `AgentSlot`               | Agent 的状态机与监督者：启动、内核故障后的自动重启、崩溃循环停止、开关、状态                               |
| `AgentStartMarker`        | 崩溃循环标记（`start-marker.json`），并持有数据目录锁                                                      |
| `DesktopAgent`            | 槽位、标记和 Agent 子进程的环境；`start` 与 `shutdown`                                                     |
| `AgentLaunch`             | 构造每个 Agent 实例的闭包（`AgentConstructor`）和进程组台账的路径                                          |
| `AgentServiceInputs`      | 构造闭包交给 `AgentApplicationService::open` 的输入：配置、存储、Skill 根目录、阻塞池、事件 sink、宿主端口 |
| `AgentApplicationService` | 运行中的 Agent 的服务 API：会话、轮次、设置、Provider、MCP、Skill、记忆、插件状态                          |

构造闭包在每次启动时都会运行：首次启动、用户重启、内核故障后的自动重启、模块重新开启。所以宿主端口要在闭包里**为每个实例重新构建**：每个实例只挂载一次它拿到的插件行。

一个完整的最小例子：

```rust
use std::collections::{BTreeMap, HashMap};
use std::path::PathBuf;
use std::sync::Arc;
use std::time::{Duration, Instant};

use hanafubuki_agent::{
    agent_workspace_roots_from, AgentApplicationService, AgentConfig, AgentConstructor, AgentEvent,
    AgentEventKind, AgentEventSink, AgentHostInstructions, AgentHostPorts, AgentInstanceInputs,
    AgentLaunch, AgentPluginDescriptor, AgentPluginGroup, AgentPluginRow, AgentProxy,
    AgentServiceInputs,
    AgentSessionMode, AgentSlot, AgentStartMarker, AgentStatusEventSink, AgentStoragePaths,
    AgentTurnRequest, AgentWorkspaceRoots, DesktopAgent, NetworkSettingsPort, NoHostContext,
    NoopAgentPluginEventSink, NoopMcpEventSink, SecretFuture, SecretKey, SecretStore, SkillRoots,
    WorkspaceRootsPort, AGENT_SHUTDOWN_BUDGET,
};
use hanafubuki_agent_contracts::TurnExtensions;
use hanafubuki_agent_runtime::ContainedRuntime;
use parking_lot::Mutex;

fn main() -> Result<(), String> {
    // 0. 最先、在任何线程启动之前：沙箱辅助进程（见下文）。
    hanafubuki_agent::sandbox::helper_dispatch();
    let config_dir = PathBuf::from("/var/lib/my-app/config/agent");
    let storage = AgentStoragePaths::under(PathBuf::from("/var/lib/my-app/data/agent"));
    let project = PathBuf::from("/srv/project");

    // 1. 槽位与崩溃循环标记，然后是宿主旁边的 Agent。
    let marker = AgentStartMarker::new(storage.start_marker_file.clone())
        .with_crash_record(storage.crash_record_file.clone());
    let slot = AgentSlot::new(marker.disabled_reason(true), Arc::new(LogStatus));
    let agent = DesktopAgent::new(slot, marker, HashMap::new())?;

    // 2. 构造每个 Agent 实例：首次启动和每次重启。
    let process_groups_file = storage.process_groups_file.clone();
    let construct: AgentConstructor = Arc::new(
        move |runtime: &ContainedRuntime, instance: AgentInstanceInputs| {
            let blocking = runtime.blocking_port();
            AgentApplicationService::open(AgentServiceInputs {
                config: AgentConfig::new(&config_dir),
                storage_paths: storage.clone(),
                skill_roots: SkillRoots {
                    system: storage.skills_root.join("system"),
                    user: storage.skills_root.join("packages"),
                    install_bundled_system_skills: true,
                    state_file: storage.skill_state_file.clone(),
                },
                blocking,
                mcp_event_sink: Arc::new(NoopMcpEventSink),
                plugin_event_sink: Arc::new(NoopAgentPluginEventSink),
                host: AgentHostPorts {
                    plugins: vec![(
                        AgentPluginRow::unconfigured(
                            AgentPluginGroup::Capability,
                            app_info_plugin(),
                        ),
                        AgentPluginDescriptor::new("app-info", "What My App is"),
                    )],
                    workspace: Arc::new(ProjectRoots(project.clone())),
                    steering_context: Arc::new(NoHostContext),
                    instructions: AgentHostInstructions {
                        identity: "You are My App's coding agent.".to_string(),
                        application: "My App".to_string(),
                        ..AgentHostInstructions::default()
                    },
                    network: Arc::new(SystemProxy),
                    secrets: Arc::new(MemorySecrets::default()),
                },
                instance,
            })
        },
    );

    // 3. 启动，等待 Agent 运行。
    agent.start(AgentLaunch {
        construct,
        process_groups_file,
    });
    let handle = agent
        .slot()
        .wait_until_started(Instant::now() + Duration::from_secs(120))
        .map_err(|unavailable| unavailable.to_string())?;

    // 4. 对 Agent 的每次调用都在它自己的运行时上执行。
    let turn = handle
        .runtime()
        .block_on({
            let handle = handle.clone();
            async move {
                let session = handle.create_session(AgentSessionMode::Default, None).await?;
                let request = AgentTurnRequest {
                    text: "Summarize the README.".to_string(),
                    images: Vec::new(),
                    skills: Vec::new(),
                    host: TurnExtensions::default(),
                };
                handle
                    .submit_turn_with_sink(session.id, request, Arc::new(PrintEvents))
                    .await
            }
        })
        .map_err(|failure| failure.to_string())??;
    println!("turn {:?} accepted", turn.turn_id);

    // 5. 在预算内关闭，调用方不在任何异步上下文中。
    for diagnostic in agent.shutdown(AGENT_SHUTDOWN_BUDGET) {
        eprintln!("{} did not stop: {}", diagnostic.worker, diagnostic.message);
    }
    Ok(())
}
```

例子里的 `ProjectRoots`、`SystemProxy`、`MemorySecrets`（见[宿主接口](#the-host-interface)）与 `LogStatus`、`PrintEvents`（见[事件与历史](#events-and-history)）是宿主自己的小类型，和上面的代码在同一个文件里，用的是上面的 `use`；`app_info_plugin` 是[宿主插件](/docs/host-plugins)一页的示例插件。

要点：

- `AgentSlot::new` 的第一个参数是 `Option<AgentDisabledReason>`：`None` 表示 Agent 会启动。`AgentStartMarker::disabled_reason(module_enabled)` 在宿主关闭了 Agent，或者前几次启动都没有完成（崩溃循环，`CRASH_LOOP_STARTS` 为 3）时给出停用原因。
- `DesktopAgent::new` 的第三个参数是 Agent 子进程继承的环境（代替本进程的环境，`HashMap<String, Option<String>>`，`None` 表示移除）。宿主的代理改变时用 `DesktopAgent::replace_child_environment` 替换最后应用的覆盖层。
- `start` 立即返回：启动在 Agent 实例自己的运行时上进行（构造与恢复在它的阻塞池上，插件作为它的任务，MCP 服务器在后台连接）。失败时槽位变为 `Failed`，不会影响宿主。
- `wait_until_started` 返回运行中的 `AgentHandle`，或者 Agent 为什么没有运行（`AgentUnavailable`，它的 `Display` 就是“the Agent is unavailable: …”）。
- `AgentHandle` 解引用为 `AgentApplicationService`。异步方法必须在 `handle.runtime()` 上运行（`ContainedRuntime::block_on`，或者在它的 handle 上 `spawn`）：kardia 与 Agent 的任务只能在那里运行，panic 也只在那里被隔离。

### 独立模式的同一组合 [#the-same-composition-standalone]

没有宿主时，`AgentRuntime::standalone` 组合同样的槽位、标记、`DesktopAgent` 和 `AgentLaunch`，并为每个端口提供默认值。命令行就是这样用的：

```rust
use std::time::Duration;

use hanafubuki_agent::{
    logging, panic, AgentDirs, AgentRuntime, AgentRuntimeHost, AgentRuntimeOptions,
    AgentStartOptions, ConfigOverrides, AGENT_SHUTDOWN_BUDGET,
};

fn main() -> Result<(), String> {
    // 最先、在任何线程启动之前（见“沙箱辅助进程”）。
    hanafubuki_agent::sandbox::helper_dispatch();
    let runtime = AgentRuntime::standalone(
        AgentRuntimeOptions {
            dirs: AgentDirs::standalone()?,
            bundled_skills: None,
            cwd: std::env::current_dir().map_err(|error| error.to_string())?,
            add_dirs: Vec::new(),
            profile: None,
            overrides: ConfigOverrides::default(),
            start: AgentStartOptions::default(),
        },
        AgentRuntimeHost::default(),
    )?;
    panic::configure_crash_record(runtime.storage_paths().crash_record_file.clone());
    panic::install_panic_hook(logging::logging_blocked);

    runtime.start();
    let agent = runtime
        .wait_until_started(Duration::from_secs(120))
        .map_err(|unavailable| unavailable.to_string())?;
    // … 像嵌入时一样在 agent.runtime() 上调用 agent 的方法 …
    drop(agent);
    runtime.shutdown(AGENT_SHUTDOWN_BUDGET);
    Ok(())
}
```

`AgentRuntimeOptions` 是目录（`AgentDirs`，遵循 `HANAFUBUKI_AGENT_HOME`）、可选的 System Skills 目录、工作目录和 `--add-dir`、配置 profile、`-c` 覆盖和首次启动的选项。`AgentRuntime::standalone` 会立即读取一次分层配置，所以错误的 profile 在这里就失败。独立模式的首次启动总会运行：命令行启动 Agent 就是在请求它，之前未完成的启动不会让它保持关闭（崩溃标记仍然计数）。

`AgentRuntime::set_working_directory(path)` 在 Agent 运行时把 `path`（相对于当前工作目录，或绝对路径）设为工作目录，并返回新的根目录：它、它的 Git 根目录，然后是 `--add-dir`。运行中的 Agent 的文件工具和命令立即移到这些根目录，会话保持活着，每个会话在下一个轮次的上下文中看到新的根目录。有轮次、压缩或后台终端在运行时它被拒绝，什么都不改变，错误说明是哪一个。配置的项目层仍是启动时读取的那一个。它只用于独立模式：嵌入的宿主通过自己的 `WorkspaceRootsPort` 提供工作区。

`AgentRuntimeHost` 是独立模式的使用者可以替换的部分：

| 字段            | 默认值                                | 说明                                              |
| --------------- | ------------------------------------- | ------------------------------------------------- |
| `secrets`       | `None`：操作系统钥匙串（`keyring` 4） | 服务名 `org.licyk.hanafubuki-agent.secrets`       |
| `status`        | `NoopAgentStatusEventSink`            | 槽位状态改变时调用 `status_changed()`，不携带负载 |
| `plugin_events` | `NoopAgentPluginEventSink`            | 插件状态的提示，以及每次已安装插件的变化          |
| `mcp_events`    | `NoopMcpEventSink`                    | MCP 状态与工具目录变化                            |

轮次与会话事件不经过这里，而是发给每次调用传入的 `AgentEventSink`（见[事件与历史](#events-and-history)）。

## 宿主接口 [#the-host-interface]

宿主只能通过 `AgentHostPorts` 向 Agent 添加东西。接口只接受普通值（`PathBuf`、字符串、映射）或 Agent 自己的类型：Agent 带有自己的 foundation、process 和模块宿主的副本，与宿主的同名类型是不同的类型，宿主在边界处做转换。

| 字段               | 类型                                           | 作用                                                           | 独立模式默认                           |
| ------------------ | ---------------------------------------------- | -------------------------------------------------------------- | -------------------------------------- |
| `plugins`          | `Vec<(AgentPluginRow, AgentPluginDescriptor)>` | 宿主插件行，各带其描述符                                       | 无                                     |
| `workspace`        | `Arc<dyn WorkspaceRootsPort>`                  | 工作区根目录、受保护的目录、指令查找的选中目录、文件搜索根目录 | 工作目录、它的 Git 根目录、`--add-dir` |
| `steering_context` | `Arc<dyn HostContextPort>`                     | steering 消息携带的宿主上下文                                  | `NoHostContext`                        |
| `instructions`     | `AgentHostInstructions`                        | 身份、应用名，以及宿主加入基础指令的段落                       | `AgentHostInstructions::default()`     |
| `network`          | `Arc<dyn NetworkSettingsPort>`                 | Web 工具、MCP 与 OAuth 使用的代理                              | 配置文件的 `[network] proxy`           |
| `secrets`          | `Arc<dyn SecretStore>`                         | MCP OAuth 令牌的存放处                                         | 操作系统钥匙串                         |

### 插件行 [#plugin-rows]

`AgentPluginRow::unconfigured(group, plugin)`，`group` 为 `AgentPluginGroup::Capability`（工具、工具源及其规则）或 `AgentPluginGroup::Context`（世界状态段）。宿主行挂载在 Agent 自己的能力插件之后、上下文插件之前，所以宿主的世界状态段排在工作区根目录、环境和权限模式之前。宿主插件与 Agent 自己的插件遵守同一套规则：`disabledPlugins` 可以关闭它们，安全模式不挂载它们。写法见[宿主插件](/docs/host-plugins)。

每一行都带着它的 `AgentPluginDescriptor`：`AgentPluginDescriptor::new(name, summary)`，`name` 是它的 `PluginDef` 的名字，`summary` 是一行说明它给模型或用户提供什么，`plugin_status` 和 `/plugins` 显示它。没有描述符的行，或 Agent 或另一行已经描述过的名字，会让 Agent 无法构建。有选项的行加上 `.with_options(schema)`（一个 `PluginOptionSchema`，每个选项带默认值），用 `AgentPluginRow::from_settings(group, plugin, |settings| settings.options_value("名字"))`，并用 `PluginDef::typed` 解码它的配置；这些选项就是 Agent 配置中的 `[pluginOptions.名字]`，按模式检查，用 `set_plugin_options` 编辑（[插件选项](/docs/config-reference#plugin-options)）。

### `WorkspaceRootsPort` [#workspacerootsport]

```rust
/// 一个项目目录就是整个工作区。
struct ProjectRoots(PathBuf);

impl WorkspaceRootsPort for ProjectRoots {
    fn roots(&self) -> Result<AgentWorkspaceRoots, String> {
        agent_workspace_roots_from([self.0.clone()]).ok_or_else(|| "no workspace".to_string())
    }

    fn protected_roots(&self) -> Vec<PathBuf> {
        Vec::new()
    }

    fn selected(&self, _host: &TurnExtensions) -> Option<PathBuf> {
        None
    }

    fn search_roots(&self, _host: &TurnExtensions) -> Result<Vec<(String, PathBuf)>, String> {
        Ok(vec![("project".to_string(), self.0.clone())])
    }
}
```

- `roots()` 在每个轮次和每次 Skill 目录读取时重新读取；第一个根目录是相对路径请求的基准。文件工具的策略和没有 `workdir` 的命令运行的目录在构建 Agent 实例时从它取得，所以新的根目录随下一个实例（重启）到达工具。`agent_workspace_roots_from` 去重（按路径身份），并去掉嵌套在前面某个根目录里的根目录。
- `protected_roots()`：文件工具拒绝访问的目录，包括读取，即使它们位于工作区根目录之下；其下的请求在任何审批之前以 `ProtectedPath` 失败（Hanafubuki：应用的数据与日志目录，其凭据就在那里）。独立运行的 Agent 不指定任何目录。
- `selected(host)`：轮次的宿主输入所选中的目录，`AGENTS.md` 从根目录一直查找到这里（Hanafubuki：用户正在看的实例）。
- `search_roots(host)`：`@` 文件搜索要遍历的目录及其标签。
- 每个方法都可能阻塞，Agent 在自己的阻塞池上调用它们。

### `HostContextPort` [#hostcontextport]

steering 消息（追加到正在运行的轮次的消息）携带的宿主上下文：`steering_context(host)` 返回 `Option<AgentHostContext>`（一个 `ContextSectionKind` 和内容，最多 `MAXIMUM_HOST_CONTEXT_BYTES`，4 KiB）。内核在它变化时把它作为该类型的段写入世界状态；这个类型的渲染器由宿主的插件注册。不需要时用 `NoHostContext`。

### `AgentHostInstructions` [#agenthostinstructions]

| 字段          | 作用                                                       | 默认（独立模式）                         |
| ------------- | ---------------------------------------------------------- | ---------------------------------------- |
| `identity`    | 基础指令开头的句子（`prompts/base.md` 中的 `{identity}`）  | `You are a coding and operations agent.` |
| `application` | 环境段报告的应用名                                         | `hanafubuki-agent`                       |
| `sections`    | 放在工具说明之后的 Markdown 段落：宿主的工具与上下文怎么用 | 空                                       |
| `ownership`   | “Approval and ownership”一节结尾的段落：宿主拥有什么       | 空                                       |

各块之间用一个空行连接。这些文本是模型可见的，宿主应当用自己的 golden 测试固定它们（Hanafubuki 的在 `hanafubuki-agent-integration`）。

### `NetworkSettingsPort` 与 `SecretStore` [#networksettingsport-and-secretstore]

```rust
struct SystemProxy;

impl NetworkSettingsPort for SystemProxy {
    fn proxy(&self) -> Result<AgentProxy, String> {
        Ok(AgentProxy::System)
    }
}

/// 把 MCP OAuth 令牌放在内存里；真实的宿主使用平台的安全存储。
#[derive(Default)]
struct MemorySecrets(Mutex<BTreeMap<SecretKey, Vec<u8>>>);

impl SecretStore for MemorySecrets {
    fn get<'a>(&'a self, key: &'a SecretKey) -> SecretFuture<'a, Option<Vec<u8>>> {
        Box::pin(async move { Ok(self.0.lock().get(key).cloned()) })
    }

    fn set<'a>(&'a self, key: &'a SecretKey, value: Vec<u8>) -> SecretFuture<'a, ()> {
        Box::pin(async move {
            self.0.lock().insert(key.clone(), value);
            Ok(())
        })
    }

    fn delete<'a>(&'a self, key: &'a SecretKey) -> SecretFuture<'a, ()> {
        Box::pin(async move {
            self.0.lock().remove(key);
            Ok(())
        })
    }
}
```

- `NetworkSettingsPort::proxy()` 在 Agent 启动时读取，宿主调用 `AgentSlot::apply_saved_settings` 时再次读取；它必须从内存回答，不能阻塞。`AgentProxy` 是 `System`、`Disabled` 或 `Explicit(url)`。
- `SecretStore` 的调用可能阻塞（钥匙串），宿主应把它们放到 Agent 的阻塞池上（`ContainedRuntime::blocking_port`，配合 `run_blocking_operation`），Hanafubuki 的 `KeyringSecretStore` 就是这样做的。
- 锁使用 `parking_lot`：Agent 的 panic 会在被隔离的线程上展开，std 的锁会因此中毒。

### 宿主输入 [#host-input]

`AgentTurnRequest`、`AgentSteeringRequest` 和 `AgentFileSearch` 都有一个 `host: TurnExtensions` 字段：宿主随消息或搜索提交的数据，按类型存放。Agent 原样传递、从不读取：它交给上下文贡献者（`ContextRequest::turn`）、`HostContextPort` 和 `WorkspaceRootsPort`。宿主的插件和端口读取它们自己放入的类型。

## 沙箱辅助进程 [#sandbox-helper]

在 Linux 和 Windows 上，沙箱中的命令（[沙箱](/docs/permissions#sandbox)）以嵌入 Agent 的那个程序运行：程序被再次启动，第一个参数是 `--hanafubuki-agent-sandbox`。在 Linux 上，这次运行先限制自身，再变成那个命令；在 Windows 上，它用受限令牌在一个随它结束的作业中启动命令，并以命令的退出状态退出。所以程序的 `main` 要最先、在启动任何线程之前调用 `hanafubuki_agent::sandbox::helper_dispatch()`：

```rust
fn main() {
    hanafubuki_agent::sandbox::helper_dispatch();
    // ……程序其余部分不变……
}
```

- 作为辅助进程启动时，这个调用不会返回。否则它记下这个程序（`std::env::current_exe()`）可以充当辅助进程，并立即返回。
- 不调用它，Agent 就没有沙箱：`AgentApplicationService::sandbox_status()`（以及 `sandbox::Sandbox::detect().status()`）为 `Unavailable`，沙箱模式不是完全访问的每个命令都会失败，不会运行。Linux 上 `sandboxMode` 的默认值是 workspace-write，所以不调用它的宿主必须配置 `sandboxMode = "full-access"` 才能运行命令。
- `ExecutorManager` 像启动其他命令一样启动辅助进程；不涉及宿主自己的进程代码。
- 在 macOS 上不需要辅助进程：沙箱中的命令在 `/usr/bin/sandbox-exec` 下运行，所以这个调用在那里只是返回。
- 在 Windows 上，沙箱在 `windows.sandbox`（`AgentSettings::windows`）设为 `"unelevated"` 之前是关闭的；回合连同沙箱模式一起取得它（`SandboxSettings::windows_sandbox`），由 `Sandbox::with_windows_sandbox` 应用。

## panic hook 桥 [#the-panic-hook-bridge]

Agent 的故障隔离依赖展开（unwinding）：插件或内核代码里的 panic 在被标记为“已隔离”的线程上展开到它的捕获点，变成一次工具错误、一个插件故障或一次内核重启。所以：

- 宿主**不能**用 `panic = "abort"` 构建。
- 宿主如果安装了自己的 panic hook，并且 hook 对它认为没有被隔离的 panic 中止进程，就必须同时询问 Agent：Agent 在**它自己的** foundation 里标记线程与守卫，宿主的 hook 看不到。

```rust
// 宿主 hook 判断 panic 是否被隔离时：
let contained = host_says_contained() || hanafubuki_agent::panic::is_panic_contained();
```

WebAssembly 插件访客在宿主的进程内、在 wasmtime 中运行。加载第一个 WebAssembly 访客时，wasmtime 会为访客陷阱引发的信号安装自己的处理器（Unix 上是 `SIGSEGV`、`SIGBUS`、`SIGILL` 和 `SIGFPE`），并把不属于访客的信号交给在它之前安装的处理器。为这些信号安装自己处理器的宿主，应在此之前安装，或在替换时链接到被替换的处理器。

在 macOS 上，Agent 让 wasmtime 用这些信号处理陷阱，而不是通过 Mach 异常端口：在生成第一个 WebAssembly 引擎之前，访客宿主调用 kardia-hmr 的 `set_macos_mach_ports(false)`。信号是 Agent 的检查在 Linux 上走的路径，宿主也已经链接了它们（见上）；Mach 端口会再加一套进程级机制，并且是 macOS CI 上第一个 WebAssembly 检查间歇性挂起（在一个已经启动过访客进程的进程中）的嫌疑原因。这个设置是进程级的，由第一个引擎固定：自己生成 wasmtime 引擎的宿主，也要用 `Config::macos_use_mach_ports(false)` 生成它们（之后的引擎请求另一种设置时 wasmtime 会 panic）；如果宿主使用 Mach 端口的引擎先出现，Agent 的访客就沿用 Mach 端口，访客宿主记录一条警告。

kardia-hmr 自己的线程（进程访客的 `guest-stdin`、`guest-stdout` 和 `guest-stderr`，WebAssembly 的 `wasm-epoch` 线程）会捕获自己的 panic，并杀死它所服务的访客。访客宿主把 kardia-hmr 的检查注册到 Agent 的 foundation（`register_containment_check`），所以上面的 `hanafubuki_agent::panic::is_panic_contained` 在这些线程上也为真：宿主的 hook 不需要第三个检查。

没有这个桥，每个 Agent panic 都会中止宿主应用。Hanafubuki 在 `platform::panic_hook` 里安装了带第二个检查的 hook，并在子进程里测试两种结果（有桥时展开，没有时中止）；这个测试是宿主的责任。

宿主的 hook 在致命 panic 中止进程前应写下崩溃记录，路径为 `AgentStoragePaths::crash_record_file`（`<data>/crash-record.json`）：Agent 的崩溃循环标记会读它，判断上一次未完成的启动是不是因为宿主自己的致命 panic。没有自己 hook 的宿主可以直接安装 Agent foundation 的 hook，就像独立的二进制那样：`panic::configure_crash_record(...)`，然后 `panic::install_panic_hook(logging::logging_blocked)`。

在 Agent 没有启动的线程上（例如终端界面的主线程）调用自己代码的前端，可以用 `panic::catch_panic` 或 `panic::catch_panic_async` 隔离一段代码：它们在 Agent 的 foundation 中把这段代码标记为受隔离，并把 panic 的消息作为错误返回。终端界面的每个命令模块都在它们之下运行。

## 数据目录锁 [#the-data-directorys-lock]

`<data_dir>/.lock` 是一个建议锁（Unix 上是 `flock`，Windows 上是 `LockFileEx`），从 Agent 的首次启动一直持有到关闭，嵌入与独立模式相同。历史的 SQLite 索引、记忆存储和进程组台账都假定只有一个写进程，两个进程使用同一个数据目录会损坏历史，并互相杀掉对方的进程。

- 宿主不需要为锁做任何事：启动标记持有它。
- 另一个进程持有锁时，启动在构造阶段失败，错误里写明目录；宿主应用继续运行，只是没有 Agent。
- 关闭宿主的 Agent（`AgentSlot::turn_off`）会保留锁直到应用退出，所以这期间同一数据目录上的独立 Agent 会被拒绝。

## 启动、开关与关闭 [#start-on-and-off-shutdown]

槽位的状态（`AgentStatus::availability`）是 `Disabled`（`setting` 或 `crashLoop`）、`Starting`、`Running`、`Faulted`、`Stopping`、`Failed { stage, reason }`（`construct`、`recover`、`start`）或 `Stopped`。`AgentStatusEventSink::status_changed()` 不携带负载：收到后重新读取 `AgentSlot::status()`。状态还包含 `generation`（本次运行的第几个实例）、`safe_mode`、`degraded`（有插件失败、拆除卡住或带有警告）和被隔离的会话。

| 调用                                      | 作用                                                                                                     |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `DesktopAgent::start(launch)`             | 交出启动组合并启动第一个实例；立即返回                                                                   |
| `AgentSlot::wait_until_started(deadline)` | 等待启动结束，返回 `AgentHandle` 或原因                                                                  |
| `AgentSlot::agent()`                      | 运行中的 Agent 或原因；持有者应在**每次调用时**重新解析，而不是缓存 handle                               |
| `AgentSlot::restart(options)`             | 用户的重启，可选安全模式（`AgentStartOptions { safe_mode, rebuild_history_index }`），并清空崩溃循环标记 |
| `AgentSlot::enable()` / `disable()`       | 打开 / 关闭 Agent；`turn_off(deadline)` 关闭并等待到期限                                                 |
| `AgentSlot::apply_saved_settings()`       | 宿主的设置（例如代理）保存后调用：在 Agent 的运行时上重新配置插件，立即返回                              |
| `AgentSlot::list_run_projections()`       | Agent 的运行（`AgentRunProjection`），供宿主的活动视图使用                                               |
| `DesktopAgent::shutdown(budget)`          | 在预算内关闭；阻塞调用方，调用方不能在异步上下文中                                                       |

内核代码的 panic（轮次任务、Agent 的工作线程组、宿主任务）会让槽位把 Agent 标为 `Faulted`、停止它，并在 2 秒、10 秒、30 秒后启动新实例（10 分钟窗口内最多三次，`AgentRestartPolicy`），从磁盘重建会话。重启后旧实例上进行中的调用会失败；正在运行的 `AgentHandle` 的 `generation()` 与 `status().generation` 不同就说明 Agent 已经换了实例。

`AGENT_SHUTDOWN_BUDGET` 为 20 秒，关闭按固定阶段进行，每个阶段有自己的期限：

<Steps>
  <Step>停止 Skill 监视器（2 秒）；关闭槽位，取消进行中的启动并最多等待 8 秒。</Step>
  <Step>
    停止接受新轮次，取消轮次与压缩（包括后台压缩）并等待它们（5
    秒）：已完成的后台压缩先记录它的用量。
  </Step>
  <Step>MCP：取消后台连接，关闭每个连接并确认其进程已退出（4 秒）。</Step>
  <Step>停止插件：一次性释放 kardia 根（5 秒）。</Step>
  <Step>停止记忆工作线程，关闭历史，停止服务工作线程（取消进行中的模型列出）与执行（3 秒）。</Step>
  <Step>清理实例的进程所有者组：终止 Agent 自己启动、仍在运行的进程（1 秒）。</Step>
  <Step>停止实例的运行时，阻塞池有 2 秒上限。</Step>
</Steps>

Agent 启动的进程归 Agent 所有：它有自己的 `ExecutorManager`，与宿主的进程分属两个所有权域。宿主不需要（也不能）替 Agent 终止它们。

## 宿主中的配置 [#configuration-in-a-host]

宿主为 Agent 指定一个配置目录，用 `AgentConfig::new(dir)` 打开（Hanafubuki 用 `<app_data>/config/agent/`）。目录里有三个 TOML 文件，各自是一个修订域、各有一把锁：

| 文件             | 内容                                                                                       |
| ---------------- | ------------------------------------------------------------------------------------------ |
| `config.toml`    | 权限模式、沙箱、记忆、`disabledPlugins`、Web 搜索与抓取、`[compaction]`、`[modelMetadata]` |
| `providers.toml` | Provider 注册表及其修订号，令牌原样保存（仅所有者可读）                                    |
| `mcp.toml`       | MCP 服务器与凭据值及其修订号（仅所有者可读）                                               |

与独立模式不同，嵌入的配置**没有分层**（没有 profile、项目文件和 `-c`），并忽略 `[network]` 与 `logLevel`（报告为未知键）：代理和日志由宿主提供。宿主通过服务 API 读写设置（`settings_view`、`write_settings`、Provider 与 MCP 的方法），写入后服务会把设置应用到插件。其中：

| 调用                                                           | 作用                                                                                                                                                                                                    |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `test_provider_draft(draft)`                                   | 读取一个未保存 Provider 的模型目录，方式与 `list_provider_models` 读取已保存的相同，或返回 Provider 的错误；不写入任何设置（列表像其他列表一样记录到[模型元数据](/docs/architecture#model-metadata)中） |
| `model_reasoning_efforts(provider_id, model)`                  | 该 Provider 上的 `model` 已知接受的推理强度，来自它的模型目录：一无所知、模型不接受推理参数或目录没有列出档位时为空（[推理强度](/docs/providers-models#reasoning)）                                     |
| `mcp_set_credential(key, value)`、`mcp_remove_credential(key)` | 修改一个 MCP 凭据并保留其他凭据；删除启用的服务器依赖的凭据会被拒绝。`McpCredentialKey::for_server_secret(server, name)` 是表单保存秘密变量或请求头所用的键：`服务器-名称`，其他字符换成 `_`            |
| `mcp_oauth_login(server, open_url, cancelled)`                 | MCP 服务器的 OAuth 登录：在 `127.0.0.1` 的空闲端口上监听，把授权 URL 交给 `open_url` 显示或打开，最多等待 5 分钟浏览器重定向到 `/callback`，或直到 `cancelled` future 完成；没有等到时取消这次登录      |

会话在每次模型操作（轮次、压缩、实现计划）之前按当前设置激活：`[compaction]` 的 `strategy` 通过内核的 `set_session_compaction_strategy` 应用到会话，模型策略的 `remoteCompaction` 随 Provider 的传输一起写入会话配置。两者都只在会话空闲时改变、都会持久化，但都不推进会话的 revision，所以调用方在调用前读到的 revision 仍然有效。轮次的扩展带有 `[compaction.background]` 的 `thresholdPercent`（`AgentBackgroundCompactionThreshold`），在轮次准入时读取；直接通过内核准入轮次的宿主需要自己放入它，否则这个轮次不会启动后台压缩。后台压缩运行期间或其结果等待安装时，会话的运行时快照会表明（`backgroundCompaction`：`running` 或 `ready`）；它不是会话的操作，不拒绝任何东西。归档或删除会话会取消它并最多等待 5 秒，改变策略或 `remoteCompaction` 会取消它。

读取是容错的：无效值取默认值，未知键记录日志并保留在文件里，需要修复的文件先复制到 `.recovery/` 再写入修复后的值；无法保留原件时，修复后的值只用在内存里，文件在重启前拒绝写入。每次修复都是一条 `AgentConfigRecovery`（文件、问题、是否只读、时间），`AgentConfig::recoveries()` 返回本次打开以来的修复（每个文件最近 20 条），宿主应当把它们展示给用户。键名、默认值和修复规则见[配置](/docs/configuration)与[配置参考](/docs/config-reference)。

配置目录中还可以有[角色](/docs/roles)：它的 `agents/` 和其 `config.toml` 中的 `[agents]` 条目，这是嵌入的 Agent 唯一的配置角色来源，此外还有内置角色和开启期间的[已安装插件的角色](/docs/roles#plugins)。`roles()` 返回服务最近一次读取的 `AgentRoleCatalog`（构建时读取，之后每次 `reload_packages` 再读）：可用的角色（`AgentResolvedRole`，含继承链、合并后的字段、`AgentCapabilityScope` 和每个字段的来源）、不可用的角色及原因，以及问题；宿主应把这些问题与配置的问题放在一起展示。`AgentRoleCatalog::load(&config, plugins_root, safe_mode)` 不需要服务即可读取角色：配置中的角色，以及 `plugins_root`（`AgentStoragePaths::plugins_root`）下设置开启的已安装插件的角色（安全模式下没有），读取时不打开包存储，所以可以在 Agent 运行时使用；读取插件角色时略去的内容列在它的问题中，并写明该插件。会话在创建或切换时取得角色（[会话与角色](#sessions)）。

Agent 会自己列出各 Provider 的模型（[模型发现](/docs/architecture#model-metadata)）：构建服务时列出默认 Provider 的模型；每当在某个 Provider 上创建会话、选用它的模型或为一个轮次激活会话时，列出该 Provider 的模型，每个 Provider 每天最多一次（失败后每 15 分钟最多一次），使用该 Provider 自己的端点、令牌和请求头。所以宿主的 Agent 会在启动时和这些时候自己发出 `GET {baseUrl}/models`；它从不延迟任何调用，失败只记录日志，从不作为结果返回。它得知的信息是会话在下一个轮次采用的上下文窗口，会话的配置也记住窗口的来源（`AgentSessionConfig.context_window_source`，未知时为 `None`，此时不写入记录；自己构建配置的宿主传 `None`，由内核设置）。宿主在 Agent 的 `config.toml` 中设置 `modelMetadata.discovery = "off"` 即可关闭模型发现，可以手写，也可以调用 `AgentConfig::set_user_value("modelMetadata.discovery", "off")`；设置补丁不包含它。宿主自己请求的 Provider 模型列表（`list_provider_models`、`test_provider_draft`）无论如何都会读取并记录。

从旧格式迁移设置是宿主自己的事：Hanafubuki 在 `config.toml` 不存在时（`AgentConfig::exists`），由它的构造闭包运行 `import_legacy_agent_settings`，用 `AgentConfig::create` 一次写入整份配置（`config.toml` 最后写，所以中途停止的导入会重来），旧文件保持不变。

## 事件与历史 [#events-and-history]

```rust
struct LogStatus;

impl AgentStatusEventSink for LogStatus {
    fn status_changed(&self) {
        eprintln!("the Agent's status changed");
    }
}

struct PrintEvents;

impl AgentEventSink for PrintEvents {
    fn emit(&self, event: AgentEvent) {
        if let AgentEventKind::TurnCompleted { .. } = event.kind {
            println!("turn completed");
        }
    }
}
```

- **轮次事件**发给每次调用传入的 `AgentEventSink`：`submit_turn_with_sink`、`steer_turn_with_sink`、`submit_plan_implementation_with_sink`、`compact_session_with_sink`。`emit` 在 Agent 的线程上调用，只能做有界的工作（例如送进通道），不能阻塞。事件类型（`AgentEventKind`）与 `exec --json` 输出的相同，见[JSON 事件](/docs/json-events)。
- **审批与提问**：`ApprovalRequested` 用 `resolve_approval` 回答，`UserInputRequested` 用 `resolve_user_input` 回答，取消轮次用 `cancel_turn`。
- **事件日志**：每个会话保留一份有界的事件日志，`events_since(session, after)` 返回某个序号之后的 `AgentEventBatch`，适合断开后补读；`snapshot(session)` 返回会话当前的运行状态。
- **历史**：`list_sessions_page`（分页、可搜索）、`open_session`（会话及其最近的转录）、`read_transcript_page` 和 `read_turn_page` 读取已提交的 `ConversationItem`。列表只包含没有父会话的会话，除非请求的 `parent` 是 `AgentSessionParentFilter::ChildrenOf(session)`；不带这个字段的请求列出前者。`AgentSessionSummary` 带有会话的 `parent_session_id` 和 `origin`（`AgentSessionOrigin`：`Side`、`Subagent`、`Review`），以及创建时的 `cwd` 和 `branch`，未知或在这些字段出现之前创建的会话为 `None`；运行时快照带有 `parent_session_id`、`origin` 和 `ephemeral`。思考内容是 `ConversationItem::Reasoning { text, duration_millis, sampling_step, truncated }`，只用于展示，从不作为模型输入回放。
- **导出**：`export_session_markdown(session)` 返回会话完整对话的 Markdown，读取其历史的全部页面：每条消息和计划一个 `## User`、`## Assistant` 或 `## Plan` 小节，每次工具调用一个 `## Activity` 小节（工具名和参数，以及输出的前几行），不含思考过程（[会话](/docs/sessions#export)）。没有可显示内容的会话返回 `InvalidInput`。它不提交任何内容；它会读取历史，所以要在异步运行时之外调用，与 `rename_session` 一样。
- **运行投影**：`AgentSlot::list_run_projections` 与 `get_run_projection`（活动 ID、轮次号、阶段、时间、错误），Hanafubuki 把它们映射到任务中心。

## 会话与角色 [#sessions]

| 调用                                          | 作用                                                                                                                                                                                                                                                                                |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `create_session(mode, role)`（async）         | 以 `mode` 和 `roles()` 中的角色 `role`（`None` 即 `default`）新建会话：角色合并后的指令跟在基础指令之后，角色的模型和推理强度优先于 Provider 的，角色的收窄成为会话的 `AgentCapabilityScope`。没有任何来源定义的角色或不可用的角色被拒绝（一个列出可用角色的无效输入错误）          |
| `set_session_role(session_id, role)`（async） | 在轮次之间设置会话的角色：它的范围和指令作为新的修订持久提交，然后（角色设置了的话）通过 `set_session_model` 和 `set_session_reasoning_effort` 设置模型和推理强度；返回快照。有轮次运行时返回 `TurnAlreadyRunning`，有压缩运行时返回 `CompactionAlreadyRunning`。`default` 清除范围 |

快照（`AgentSessionRuntimeSnapshot`）带有会话的 `role` 和它范围的摘要（`AgentCapabilityScopeSummary`：多少个允许列表和模式、多少个拒绝模式、关闭的插件、上限）；对 `default` 两者都是 `None`，在序列化的快照中不出现。会话把范围和角色的指令保存在自己的配置中，所以之后编辑或删除角色文件、或重启，都不改变什么。范围的作用见[能力范围](/docs/plugin-rules#capability-scope)；宿主的会话除非提供角色，否则传 `None`。

## 权限 [#permissions]

轮次的权限模式在它开始时确定：启动时给定的模式，否则是会话自己的模式（如果有），否则是配置的 `permissionMode`，再收紧到会话角色的 `permissionModeCap`。`submit_turn_with_sink` 和 `submit_plan_implementation_with_sink` 不给定模式；`start_turn` 给定它的输入中的模式（`AgentTurnInput { text, images, skills, permission_mode }`，一个 `Option<AgentPermissionMode>`），由文本构造的输入（`AgentTurnInput::from`）不给定（`None`）。各模式和审批的行为见[权限与审批](/docs/permissions)。

| 调用                                            | 作用                                                                                                                                                                                                                                                                                         |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `set_session_permission_mode(session_id, mode)` | 会话的模式，代替 `permissionMode`，直到会话结束；只保存在内存中，不持久化，也不随分叉复制。正在运行的轮次保持原来的模式，下一个轮次使用这个模式                                                                                                                                              |
| `session_permission_mode(session_id)`           | 会话被设置的模式；仍使用 `permissionMode` 时为 `None`                                                                                                                                                                                                                                        |
| `set_session_sandbox_mode(session_id, mode)`    | 会话的 `AgentSandboxMode`（`ReadOnly`、`WorkspaceWrite`、`FullAccess`），代替 `sandboxMode`，直到会话结束；只保存在内存中，不持久化，也不随分叉复制；子代理沿用父会话的。正在运行的回合保持它的沙箱，下一个回合使用新的。与权限模式无关                                                      |
| `session_sandbox_mode(session_id)`              | 会话被设置的沙箱模式；仍使用 `sandboxMode`（或平台默认值）时为 `None`                                                                                                                                                                                                                        |
| `sandbox_status()`                              | `SandboxStatus::Available { backend }`（Linux 上为 `"Landlock (ABI n) and seccomp"`，macOS 上为 `"Seatbelt (/usr/bin/sandbox-exec)"`）或 `Unavailable { reason }`，已应用配置的 `[windows] sandbox`：需要沙箱的命令能否运行（[沙箱辅助进程](#sandbox-helper)）                               |
| `approve_denied_action(session_id, review_id)`  | 用户批准自动审查 `review_id`（来自 `PermissionReviewCompleted { status: Denied }`）拒绝的操作，必须是会话最近十次拒绝之一：提交一条模型和下一次审查都会读到的上下文说明，并把不带轮次 ID 的 `HistoryCommitted` 发给会话最近一个轮次的 sink。它不开始轮次，也不执行任何操作；重试仍会再次审查 |

审查不是这些拒绝之一时，`approve_denied_action` 返回 `ApprovalNotFound`；轮次或压缩运行期间返回 `TurnAlreadyRunning` 或 `CompactionAlreadyRunning`。除只读取设置的 `sandbox_status` 外，这些调用可能加载会话的历史或等待它正在暂存的提交，所以要像 `rename_session` 和 `set_session_mode` 一样在异步运行时之外调用。

## 子会话 [#child-sessions]

子会话记录它的父会话和创建它的原因；子会话和旁路对话是什么，见[会话](/docs/sessions#children)。

| 调用                                    | 作用                                                                                                                                                                             |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `open_side_conversation(parent)`        | 父会话的旁路对话，以 `AgentSessionRuntimeSnapshot` 返回：从父会话最近的回合边界临时分叉出来，模型先读到旁路策略。再次打开返回已打开的那个。父会话还没有轮次时返回 `InvalidInput` |
| `close_side_conversation(side)`（异步） | 中断旁路对话正在运行的轮次，停止它的后台终端并丢弃它；对不是旁路对话的会话返回 `InvalidInput`                                                                                    |
| `archive_session`                       | 同时归档会话尚未归档的持久化后代（子会话在先），并关闭它存活的临时子会话                                                                                                         |
| `delete_session_confirmed`              | 在同一次删除中一并删除会话的持久化后代（不论是否已归档），并关闭它存活的临时子会话；任何一个不能释放，整个删除都会被拒绝                                                         |

旁路对话上的轮次和其他会话一样，通过 `submit_turn_with_sink` 运行，使用各自的 `AgentEventSink`。临时会话从不被列出、归档（`InvalidInput`）或恢复；关闭它、归档或删除它的父会话、或 Agent 停止时，它就消失了。`open_side_conversation` 会阻塞，和 `rename_session` 一样，要在异步运行时之外调用。

## 编辑之前的消息 [#edit-from-turn]

`edit_from_turn(session_id, turn_id)` 像终端界面的 Esc 那样编辑开始 `turn_id` 这个轮次的消息（见[会话](/docs/sessions#edit)）。它在该轮次之前分叉会话（与 `fork_session_before_turn` 相同，使用会话当前的 generation 和 revision），归档原会话（与 `archive_session` 相同，因此连同它的持久化后代），并返回 `AgentEditFromTurn { session, restored_prompt, restored_images }`：分叉出的会话的运行时快照，以及这条消息的文本和图片附件，用于放回输入框。

- `turn_id` 是 `ConversationItem::TurnStart` 的 `turn_id`，用 `read_transcript_page` 读取；它之后的 `UserMessage` 就是被恢复的消息。没有这样一条消息的轮次（不是由消息开始的）会被拒绝。
- 对已归档的会话、会话中有轮次运行时、对子会话或临时会话、以及对会话中不存在的轮次，它返回 `Err` 并说明原因。
- 如果分叉已经完成但原会话无法归档（例如某个后台终端停不下来），错误会说明这一点并给出分叉出的会话；两个会话都会保留。
- 文件不会恢复。它会阻塞，和 `rename_session` 一样，要在异步运行时之外调用。

子代理是持久的子会话（来源 `Subagent`），它的回合、事件和历史和任何会话一样读取：状态动态从 `subagents(parent)` 读子代理，用 `events_since` 读每个子代理的事件；父会话一侧不新增事件。它的回合不使用调用方的 `AgentEventSink`：事件记在它自己的日志中。用户在子代理上开始的回合和任何会话一样经过 `submit_turn_with_sink`。

## 已安装的插件 [#installed-plugins]

[已安装的插件](/docs/architecture#installed-plugins)位于数据目录的 `plugins/` 中，Agent 设置中的 `[plugins]` 说明哪些启用。服务在构建时读取它们，并在每次重新加载时再次读取：

- `reload_packages()` 按设置重新加载已安装的包，并在不重启的情况下更新 Agent：Skill 目录读取启用的包的 Skill，下一轮的钩子包含它们的钩子，它们的 MCP 服务器运行（返回时，新增或变更的服务器已经连接或失败；不再存在的已断开）。服务在 `write_settings`、`set_plugin_enabled`、`mcp_write_server` 和 `mcp_delete_server` 之后在后台调用它，`plugins` 行在已链接包的目录改动之后也会调用它；以其他方式写入 `[plugins]` 或改变存储的宿主自己调用它。
- `packages()` 返回 `Vec<AgentPackageStatus { id, version, format, display_name, description, source, enabled, content, hooks_to_trust, guest, issues }>`：每个已安装的包，无论启用与否；`source` 是它的安装来源（`PackageSource`，没有安装记录时为 `None`）；`content`（`AgentPackageContent { skills, mcp_servers, hooks, roles }`）是它启用时贡献的内容（Skill ID、它运行的 MCP 服务器名称、钩子键、它的角色名 `<插件>:<角色>`）；`hooks_to_trust` 是它等待信任的钩子的键（`trust_hooks`）；`guest` 是它的代码的状态，只有带运行时的本项目格式的包才有（`AgentPackageGuest { runtime, permissions, granted_permissions, status, settings, config_schema }`，`runtime` 是 `RuntimeKind`（`Process` 或 `Wasm`），`status` 是 `GuestStatus { state, error, last_exit, stderr_tail, restarts, process_id, issues }`；`ungranted()` 是它请求但尚未授予的权限，WebAssembly 模块永远没有）；`issues` 是无法读取或使用的部分。`package(id)` 是其中一个，未安装时为 `None`。安全模式下这些包会被列出，但都不加载。
- `grant_package_permissions(id, permissions)` 记录用户授予包的代码 `permissions`（`PackagePermissions { network, workspace, env }`，即同意时展示的权限），然后重新加载包；程序访客只在清单请求的权限都已授予后才启动，WebAssembly 访客什么也不请求。`retry_package(id)` 以空的重启窗口再次启动失败的访客（[代码插件](/docs/architecture#code-plugins)）。
- `set_package_settings(id, settings)` 替换包的代码的设置（`[plugins."<id>"].settings`，一个 JSON 对象；`null` 表示移除），按其清单的 `configSchema` 校验，然后重新加载包：它的访客以这些设置重新启动，并把它们视为自己的 `settings`。`AgentPackageGuest` 给出 `settings`、`config_schema`，以及在 `status.issues` 中给出其声明的贡献中被略去的部分（[代码插件](/docs/plugin-rules#code-plugins-rules)）。
- `validate_package(dir)` 是一个自由函数，在安装之前检查一个插件目录，与 `plugins validate` 相同（[检查](/docs/writing-plugins#validate)）：像安装那样读取它的清单、它声明的路径，并像访客宿主运行它那样检查它的代码，但不启动任何东西。它返回 `AgentPackageValidation { name, version, format, manifest, code, issues }`；目录中没有安装能接受的清单时返回错误。
- 访客在平台的沙箱中运行，而在 Linux 和 Windows 上沙箱就是程序自己作为[沙箱辅助进程](#sandbox-helper)再次启动：不调用 `helper_dispatch()` 的程序不运行任何访客。

生命周期调用通过服务打开的那个存储改变已安装的插件，写入设置，重新加载，并在结果生效后返回。每个调用都用包的 ID（`<plugin>@<marketplace>`）指明包；错误是 `String`。

| `marketplaces()`                                                            | `Vec<AgentMarketplace { name, display_name, source_type, source, ref_name, sparse_paths, enabled, last_updated, last_revision, root, plugins, issues, error }>`：已添加的市场（`[marketplaces]`）及其每个插件（`AgentMarketplacePlugin { id, name, display_name, description, version, installable, installed, enabled }`）；读不了的市场带 `error`                                                                                                                                                                                                                                                                                                                                       |
| `add_marketplace(MarketplaceAddRequest { source, ref_name, sparse_paths })` | 本地目录（原地使用），或 git 仓库（URL、`owner/repo[@ref]`），克隆到 `plugins/marketplaces/` 下；写入它的记录。返回 `AgentMarketplaceAdded { name, root, already_added }`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `upgrade_marketplace(name)`                                                 | 把 git 市场 `name`（为 `None` 时是每个已添加的 git 市场）更新到远程的提交：返回 `Vec<AgentMarketplaceUpgrade { name, upgraded, error }>`；指定名字时，它的失败就是调用的失败                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `remove_marketplace(name)`                                                  | 删除它的记录以及 git 市场的检出；从它安装的包仍然保留                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

对包的每个生命周期调用都会在重新加载之后告诉插件事件接收器：`AgentPluginEventSink::package_changed(&AgentPackageChange { id, kind, error })`，`kind` 为 `Installed`、`Removed`、`Enabled`、`Disabled`、`Updated`，或 `Failed`（调用失败，`error` 说明原因；包保持原样）。这个方法有空的默认实现，所以只在 `plugins_changed` 时刷新的接收器无需修改。`retry_plugin(name)` 重新启动失败的内置行或宿主行；命令行通过 `--safe-mode`（`AgentStartOptions::safe_mode`）进入安全模式。

- 插件的钩子由 `hooks_list()` 列出，`source` 为 `{"plugin": {"id", "root", "data"}}`（`HookSource::Plugin`）；用户和项目的钩子仍是 `"user"` 和 `"project"`。
- `mcp_snapshot()` 把插件的服务器列为 `plugin_servers`（`McpPluginServerSnapshot { plugin, server, status }`）；`settings` 仍是 `mcp.toml` 的内容。
- `plugin_status()` 中有 `plugins` 行，它把启用的包告诉模型。

## 日志 [#logging]

门面默认不安装日志器：宿主保留自己的 `log` 实现，Agent 的记录进入其中。独立二进制使用 `logging::install_file_logger`（`hanafubuki-agent.log`，超过 8 MiB 轮转到 `.1`…`.3`）。Agent 自己的记录遵守内容日志规则：模型内容、推理、工具参数和工具结果只在 `trace` 级别出现，并截断到上限，从不记录请求头和凭据。所以宿主的日志级别就是用户选择 `trace` 的方式（Hanafubuki 的 `log_level` 设置）。

## 测试 [#testing]

- 在 `[dev-dependencies]` 中为 `hanafubuki-agent` 打开 `test-support` feature，得到 `hanafubuki_agent::test_support`：`mount`（在一个提供注册表与 `PluginFaults` 的上下文中挂载插件）、`test_host`、脚本化的模型服务器与 MCP 服务器。给了模型列表时（`FakeServer::with_listings`、`FakeListing`），脚本化的模型服务器用它们回答 `GET …/models`；否则像对待其他请求一样用下一个响应回答。测试用 Agent（`new_with_host`）不自己发现模型，`configure_test_provider` 也会写入 `modelMetadata.discovery = "off"`，所以即使测试像宿主那样自己构建 Agent（`AgentApplicationService::open`），脚本化服务器也只看到测试自己的请求。
- 宿主应保留自己的 golden 测试，固定加上宿主插件与指令后模型收到的内容；Agent 一侧模型可见的变化也会改变它们，需要有意地重新生成。
- panic hook 桥由宿主在子进程中测试。
