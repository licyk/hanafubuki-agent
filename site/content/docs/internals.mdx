## 暂存提交与 drop guard [#staged-commits]

会话的每次修改都先持久化才对外可见（[会话与轮次](/docs/architecture#sessions-and-turns)）。具体做法如下（内核的 `service/durable.rs`、`service/state/cell.rs`）：

- 会话记录把身份与五组状态分开保存：设置、状态、对话、事件日志和运行时（`service/state/record.rs`）。回滚时整组恢复。
- **暂存。** 修改在会话单元的锁下改动记录，并暂存为一个 `StagedPersistence`：要追加的检查点（`AgentConversationCommit`）或增量（`AgentConversationDelta`），以及回滚用的状态。有提交暂存时，记录的 `persisting_revision` 挡住其他所有写入者：它们只在没有暂存的提交时才锁定记录（`lock_after_persistence`）。
- **结算。** 追加的确认（`AgentHistoryAppendAck`）结算这次提交：成功则发布持久化的修订号（清除 `persisting_revision`）；失败则回滚记录，前提是记录的修订号仍是暂存的那一个。此后调用方才能发出这次提交的事件。存储未作回应就丢弃的确认会回滚记录，并以 `ShuttingDown` 失败。
- **异步调用方**（轮次循环、它在内核 `start_turn` 中的准入、压缩、执行进度）把追加排入队列（`AgentHistoryStore::enqueue_commit` 或 `enqueue_delta`），再等待结算的答复。结算在确认中运行，也就是在完成追加的那个历史写入线程上，而不是在等待的 future 里：即使 future 在此期间被丢弃，结算照样发生；等待这个会话的任何东西都不依赖轮次的运行时能否推进。
- **同步调用方**在调用线程上追加（`append_commit` 或 `append_delta`）并就地结算：宿主在异步运行时之外调用的服务会话修改，以及门面在其阻塞边界上运行的轮次提交（`submit_turn_with_sink`），这样轮次的准入和其托管任务的创建从不分开。

**drop guard。** 在结束之前被丢弃的轮次或压缩（任务被中止，或者 `start_turn` 在追加准入时被丢弃）通过它的 guard（`TurnExecutionGuard`、`CompactionExecutionGuard`）结束，guard 既不能 await 也不能阻塞。轮次的 guard 先中止该轮次待处理的审批。随后 guard 暂存取消，并把它交给存储，不由任何人等待（`StagedPersistence::into_follow_up`）；确认在写入线程上发布它，然后自己让它可见：唤醒等待终态的调用方、发出事件、通知观察者（`TurnFinished`）。

如果 guard 被丢弃时已有提交暂存，guard 无法等它，就把自己的提交推迟到单元上（`SessionCell::stage_or_defer`）。无论什么结算了那次暂存的提交（发布或回滚），都会在同一把锁下暂存第一个仍然适用的推迟提交，确认再把它作为 `AgentHistoryFollowUp` 交回存储。写入线程在接下一条命令之前先追加这个后续提交，并依次确认，所以一串后续提交按顺序追加。停止追加的存储会让后续提交随它所跟随的提交一起失败。

## 执行进度 [#execution-progress]

工具通过 `AgentToolProgressSink::report` 报告进度（进程的启动、输出、状态、释放），这个调用保持同步：它从轮次异步工作线程上的工具调用中被调用，也可能来自比调用活得更久的监视线程。因此 `report` 只把更新排入会话单元的队列（`service/progress.rs`）：

- **每个会话一个消费者。** 报告时如果没有消费者在运行，就在创建这个 sink 的轮次的运行时上启动一个；它按顺序应用并提交排队的更新，逐个等待追加，队列空了就结束。队列未空就停止的消费者（被中止，或它的运行时已关闭）让它已取出的那条更新自行结算；下一次报告，或在自身运行时上的一次刷新，会启动新的消费者。
- **上限。** 队列容纳 64 条更新（`EXECUTION_PROGRESS_QUEUE_CAPACITY`）。超过之后，如果同一执行在队列中没有排在后面的更新，新的输出更新就合并进该执行已排队的输出：文本追加上去，只保留最新的 16 KiB（`MAXIMUM_COALESCED_OUTPUT_BYTES`），并从它们第一次能像原始输出那样渲染的位置开始：第一个换行之后，否则第一个完整的转义序列之后（`terminal_text::aligned_start`），所以保留的文本从不从序列中间开始。其他更新（执行的启动、状态、释放、清理失败）即使这时也照常排队，所以队列最多是容量加上这些更新，再加每条之后的一条输出。
- **与轮次的顺序。** 轮次在终态提交之前等待之前排入的所有更新（`flush_execution_progress`），所以它的调用报告的内容先提交。被丢弃的轮次无法等待，这时仍在排队的更新在它的取消之后提交，顺序不变。
- **应用自己的报告**（后台终端的停止、启动时的恢复）经过 `report_session_execution_progress`，它最多等待 5 秒，让排在它之前的更新先完成，然后在调用线程上提交。
- **关闭。** 会话被移除和 `shutdown_history` 会关闭它的队列并中止消费者；此后 `report` 返回 `false`。`stop_operations` 先在关闭期限内刷新此前排入的内容。

## 请求中的图片 [#request-images]

模型请求中的图片附件在不持有会话锁的情况下读取（`service/sampling/images.rs`）。采样步骤、自动压缩的估算和压缩都这样做：

<Steps>
  <Step>在会话锁下收集历史引用的附件（每个一次，保持顺序）；</Step>
  <Step>
    释放锁，由历史存储加载它们（`AgentHistoryStore::enqueue_image_attachment_load`）：文件存储在该会话的写入线程上读取附件，连同摘要与图片检查，并按顺序确认它们的字节，所以内核自己从不读取附件文件；对放在内存中的存储，trait
    的默认实现直接内联加载；
  </Step>
  <Step>再次加锁，检查要构建的内容没有变化，然后用加载到的字节组装请求。</Step>
</Steps>

历史引用了但没有加载到的附件，说明历史在此期间变了，请求以 `StaleRevision` 失败。附件按内容寻址，所以这个请求与在锁下读取所构建的请求逐字节相同。加载失败的附件只有在请求用到它时才让请求失败。压缩会保留它加载的图片，供远程替换（Responses 压缩）和对下一个请求的估算使用。

## 会话上的等待 [#session-waits]

会话单元有两个信号：`persisted` 在暂存的提交结算时推进，`terminal` 在轮次或压缩到达终态时推进。会话被移除时两者都推进，被移除的单元对仍持有它的调用方回答 `SessionNotFound`。每个信号都有异步的一侧（一个 `watch` 纪元）和阻塞的一侧（单元锁上的 `Condvar`）；`wait_until` 在有提交暂存时等待 `persisted`，否则等待 `terminal`。

- **异步等待：** 轮次循环、它的准入和压缩（`lock_after_persistence`），取消的确认（Tokio 超时下的 `wait_until`），以及需要压缩时对后台压缩的等待（`wait_until`，轮次的取消通过推进 `terminal` 唤醒它）。
- **阻塞等待**只给异步运行时之外的调用方：宿主在阻塞工作线程上运行的同步服务方法，以及门面的阻塞边界（它也负责模型操作前的会话激活和轮次提交）；`list_snapshots`；`flush_for_diagnostics`；还有关闭线程上的 `stop_operations` 和 `shutdown`，在那里每个会话的等待、它的进度刷新，以及之后对托管轮次任务和后台压缩任务（各自的 `Condvar`）的等待共用一个期限。
- **从不阻塞：** drop guard、执行进度和内核的异步 `start_turn` 不在任何阻塞的一侧上等待。

`cancel_turn_confirmed` 请求取消后，先等待 500 毫秒让轮次协作地结束（`COOPERATIVE_GRACE`），然后中止它的托管任务（除非轮次已在记录的锁下暂存了它的结束：那次提交持久化后它才发出结束的事件，慢速磁盘可能让这超过宽限时间，此时中止会丢掉这些事件），并在 5 秒期限（`CONFIRMATION_DEADLINE`）的剩余时间里等待取消持久化；超过则返回 `CancellationNotConfirmed`。两次等待都是异步的，所以取消不占用阻塞工作线程。

## 历史存储的拒绝规则 [#history-refusals]

`FileAgentHistoryStore`（`hanafubuki-agent-history`）：每个会话一份 JSONL rollout，它是权威的；SQLite 索引（`index.sqlite3`）是 rollout 的投影（[存储](/docs/architecture#storage)）。存储无法使用的东西只损失它自己的会话，从不损失整个存储，也从不损失文件。只有索引或布局（其 schema、SQL、目录 I/O）的问题会让存储打开失败，并因此让 Agent 的构造失败。

### 打开时无法接受的内容 [#history-open]

| 打开时发现                                                                                   | 处理方式                                                                                                                                                                       |
| -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 无法使用的索引                                                                               | 丢弃并从 rollout 重建，所有会话重新判断；`open_rebuilding_index`（带 `rebuild_history_index` 的重启）按请求丢弃它                                                              |
| 另一种格式的 rollout（`IncompatibleFormat`）                                                 | 连同会话的附件目录一起移入旁边的 `.recovery` 目录（`quarantine_file`：`<name>.<pid>.<n>.invalid`，任何扫描都不读它）；新路径记入日志，也写进会话的原因；移动失败则文件留在原处 |
| 无法投影的 rollout（无法解码，或没有通过会话、序号和检查点身份的记录检查，这些检查保持严格） | 留在原处，并记下一项待修复（`agent_projection_repairs` 表），以后每次启动都重试                                                                                                |
| 文件缺失、同一会话在活动树和归档树中各有一份、路径在存储之外                                 | 保持原样；如果只是 rollout 的生命周期与所在的树不一致（归档中途停止），则把它移到正确的树中                                                                                    |
| 已提交的条目或它引用的图片附件无法读取                                                       | 保持原样                                                                                                                                                                       |

每个这样的会话都保留它的 ID（`next_session_id` 被抬到它之后，所以新会话从不与它共用 ID、rollout 名或附件），转录和运行时读取都会拒绝它（带原因的 `ProjectionUnavailable`），并作为失败交给恢复，由恢复隔离它；其他会话照常打开，Agent 也照常打开。它的任何内容都不改写、不删除。

### 被拒绝的会话 [#history-refused]

会话的投影不可用有两种原因（`ProjectionLag`），各由不同的事情清除：

- **追加的滞后。** 记录已持久但投影失败的追加，只在它的写入线程再次投影 rollout 之前拒绝该会话的读取：在之后的某次追加时，或写入线程停止时。
- **拒绝。** 索引无法接受的会话（打开时，或之后被会话列表拒绝）一直被拒绝，直到修复（`repair_session_projection`）或下一次启动重新判断它。拒绝从不由写入线程清除。

会话列表略去摘要无法解码的行，并以同样方式拒绝那个会话。它只记录一次日志，并告知存储的 `AgentHistoryRefusalSink`（`open_reporting_refusals`），槽位通过它把该会话连同原因加入 Agent 状态中的已隔离会话；这一行在分页中保留位置，所以游标照样越过它，列表的其余部分照常返回。重建的索引会重新投影这个摘要。

### 附件清理 [#attachment-sweep]

清理未被引用的附件 blob（打开时，以及轮次准入失败的会话）只做垃圾回收：只有当磁盘上仍在的会话文件都不引用某个 blob 时才删除它。

- blob 存放在暂存它的会话下，但任何会话都可能引用它（分叉出的子会话保留恢复的提示中图片的来源会话）。所以清理保留任何已投影条目引用的 blob，以及移入 `.recovery` 的 rollout 中出现的每一串 64 位十六进制数字，不管 blob 属于哪个会话。这些文件每次打开时读取一次，按字节读，从不解码；有一个无法读取就保留所有 blob。这样保留的 blob 在那个文件被恢复或删除后释放。
- 只要有会话的投影不可用（那个会话的引用未知），清理就什么都不删；也不删索引中没有的会话的任何东西；无法清理的会话跳过并记录警告。会话 blob 中意外出现的文件保留。

### 删除会话 [#history-deletion]

删除（`delete_sessions_confirmed`）在删除范围之外仍有会话需要其中某个会话时被拒绝：

- `ReferencedByFork`：谱系表（`agent_session_lineage`）中不随之一起删除的分叉；
- `ReferencedByQuarantinedSession`：索引中没有的会话文件（移入 `.recovery` 的 rollout，或打开时被拒绝、带待修复项留在原处的 rollout），它从这个会话分叉（`forkedFromSessionId` 或 `historyBase` 的 `sessionId`），或提到了这个会话某个 blob 的摘要。错误中列出每个这样的文件及其会话。这些文件按字节读取、不解码（`store/kept_files.rs`），无法读取的文件会拒绝删除，因为它需要什么是未知的。

两边会话的任何内容都不改动。这样的分叉被恢复并打开后重新进入谱系表；被删除后则不再保留任何东西。内核的 `prepare_session_deletion` 先询问存储（`check_sessions_deletable`），所以被拒绝的删除在应用撤销会话的记忆或停止它的终端之前就停下，拒绝的原因就是删除命令的错误。

会话的持久化后代随它一起删除，在同一次 `delete_sessions_confirmed` 中：外观层通过索引的 `parent_session_id` 列出它们（两种生命周期，递归），逐个加载，并作为会话的 `descendants` 传给 `prepare_session_deletion`，它检查整个集合并把每个成员标记为正在释放。所以从父会话分叉出来的子会话从不阻止父会话的删除，而集合之外的分叉仍然会。外观层随后停止每个成员的终端、撤销它的记忆，任何一步失败都会取消整个删除。`complete_session_deletion_confirmed` 在删除任何东西之前，先确认每个成员仍处于准备好的状态、没有正在运行的轮次；有一个不满足就取消删除，什么都不删。归档则是逐个普通归档的级联，子会话先于父会话，已归档的跳过。两者都会先关闭每个成员仍然存活的临时子会话。

获准的删除先写一份删除记录（`trash/delete-<millis>-<n>/obligation.json`），把 rollout 和每个会话的整个附件目录移入该目录，在一个事务中删除会话的索引行，删除移入的文件，最后删除这份记录。中途停止的删除留下的记录在下次打开时完成；无法解码的记录被隔离。

### 写入线程 [#history-writers]

写入经过每个会话一个的写入线程（`agent-history-writer-<id>`，队列容纳 64 条命令），它在追加和它的投影都写好之后确认这次追加。

- `append_commit` 和 `append_delta` 等待确认。`enqueue_commit` 和 `enqueue_delta` 只找到或启动写入线程（没有运行时从索引读取会话的文件）并排队，持有会话闸门的时间不超过这些；写入线程的队列满了时，调用方要等到有空位。
- 线程已结束的写入线程（panic，由它的 `BackgroundWorkerGroup` 记录并作为内核故障报告）被撤下，由下一条持有会话闸门的命令换一个新的，所以一次写入失败不会让会话的历史停下。
- `shutdown(deadline)` 把每个写入线程的停止排在它已有的命令之后，等到期限为止；届时仍在忙的写入线程被报告（`WriterDidNotStop`）并放任其分离。持久的内容不会丢失：提交只在写入磁盘后才被确认，所以只有写入线程尚未确认的追加（对任何轮次都从未持久；恢复会还原最后确认的修订）没有写入。

## MCP 设置的修复与诊断 [#mcp-settings-diagnostics]

### 修复 [#mcp-settings-repairs]

`mcp.toml`（[它的键](/docs/config-reference#mcp-toml)）是 Agent 自己的数据，所以 `McpSettingsStore`（`hanafubuki-agent-config`）通过 `hanafubuki_agent_mcp::repair_settings` 逐个条目地容错读取：

| 发现                                                                                                                                                                                                                | 修复（`McpSettingsRepairKind`）                           |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| 文件不是 TOML、不是 UTF-8 或超过 8 MiB                                                                                                                                                                              | 用默认值替换（`reset`）                                   |
| 五个超时之一不在 1–86400 内，`maximumConcurrentCalls` 或 `toolMaximumConcurrentCalls` 中的值不在 1–64 内，凭据的 `generation` 小于 1 或不是整数                                                                     | 移到最近的边界；范围内的小数截断为整数（`value_clamped`） |
| 第 64 个之后的服务器，无法解码的服务器，没有通过 `McpServerConfig::validate` 的服务器（带凭据或片段的 URL、公开与凭据的请求头或变量重叠、stdio 程序、参数与环境变量规则、过滤器与策略上限），同一 ID 的第二个服务器 | 只去掉那台服务器（`server_dropped`）                      |
| 键无效、无法解码或值不可用的凭据                                                                                                                                                                                    | 只去掉那条凭据（`credential_dropped`）                    |

该是数字的地方不是数字时，留给解码器处理，解码器会去掉整个条目。未知的键记入日志并保留在文件中。写入修复后的值之前，原文件先保存在 `.recovery/` 中（[配置恢复](/docs/recovery#backup)）。写入保持严格：用户添加或编辑的服务器要通过校验，从不被调整。

每项修复是一个 `McpSettingsRepair`：类型、对象（条目带有有效 ID 时为服务器 ID 或凭据键）、调整改动的字段，以及原因，从不包含文件中的值。下一次读取看到的已是干净的文件，所以存储在打开它的 Agent 运行期间保留这些修复（最多 256 项，`MAX_RETAINED_REPAIRS`）。它们以 `McpApplicationSnapshot.settingsRepairs` 交给宿主（Hanafubuki 的 MCP 设置面板显示它们，直到用户关闭），独立二进制的 `doctor` 把它们列在配置的恢复记录中。快照中的 `serverDefaults`（`McpServerDefaults::default()`：启用、非必需、旧版协议、超时 15/30/30/120/10 秒、4 个并发调用、`ask`、`deferred`、OAuth `disabled`）是宿主新建服务器表单的初始值，所以默认值不属于任何前端。

### 诊断 [#mcp-diagnostics]

`McpDiagnosticStore` 为每台服务器保留最近 128 条诊断的环形缓冲（`MCP_DIAGNOSTIC_CAPACITY`）：每条有阶段（`spawn`、`initialize`、`discover_tools`、`tool_call`、`connection_lost` 等）、结果（`success`、`warning`、`error`、`cancelled`、`outcome_unknown`）、代码、消息、传输、配置与连接的代次、工具、能否重试和下一步。消息截断到 2 KiB 并做清洗：`Bearer` 之后的词、以 `token=`、`password:` 或类似键（`access_token`、`refresh_token`、`secret`、`authorization`、`code`、`verifier`）开头的词，以及 URL 的查询部分，都替换为 `[redacted]`。stdio 服务器的标准错误保留最后 128 行、最多 16 KiB 的尾部，以同样方式清洗。

服务器的状态行是它的 `McpDiagnosticSummary`：它当前的诊断，即最近一次连接尝试开始（`begin_attempt`；第一次之前则是全部）以来记录的诊断，分别计为错误（`error`、`outcome_unknown`）和警告，并以其中最严重、同等严重中最近的一条作为标题。它带有当前的每一条，所以宿主可以把这一行展开为全部条目；整个环形缓冲保留在服务器的诊断快照中。它通过 `McpApplicationSnapshot.diagnostics` 交给宿主，每台已配置的服务器一项，按设置中的顺序。终端界面的 `/mcp` 显示每台服务器的阶段和最近的错误，不显示这个摘要。

## Skill 文件的问题 [#skill-file-issues]

`SKILL.md` 的 frontmatter 和 `agents/openai.yaml` 由人和其他工具编写，所以 `hanafubuki-agent-skills` 一次读取一个已知的键（`yaml_fields.rs`）：类型不对的值只损失那个键，`null` 视为没有。用户写什么、有哪些[字段](/docs/skills#skill-md)见 Skill 页面；按字段的规则如下：

| 位置                                                                    | 发现                                                                                                          | 结果                                                                                                                                                      |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SKILL.md`                                                              | 不是 UTF-8，没有 `---` frontmatter，frontmatter 不是映射                                                      | Skill 加载失败                                                                                                                                            |
| `SKILL.md`                                                              | frontmatter 不是合法的 YAML                                                                                   | 把看起来是文字、却被解析成 YAML 结构的标量加上引号后再读（值中带有 `: `，或以 `[`、`{`、`@`、`*`、`&` 或反引号开头且无法解析）；仍然无效则 Skill 加载失败 |
| `name`、`description`                                                   | 不是字符串；没有 description                                                                                  | Skill 加载失败：这两个字段决定它能否被选中                                                                                                                |
| `name`                                                                  | 超过 96 个字符                                                                                                | 截断，并记一个问题                                                                                                                                        |
| `description`                                                           | 超过 4096 字节                                                                                                | 按字符边界截断，并记一个问题                                                                                                                              |
| `license`、`metadata`、`metadata.version`、`metadata.short-description` | 类型不对                                                                                                      | 忽略那个键，并记一个问题（`ignored metadata.version: expected a string, found a number`）                                                                 |
| `license`、`metadata.version`                                           | 超过 256 或 128 字节                                                                                          | 去掉，不记问题                                                                                                                                            |
| `openai.yaml`                                                           | 不是 UTF-8、不是 YAML、不是映射                                                                               | 忽略整个文件，记一个问题；Skill 照常从 `SKILL.md` 加载                                                                                                    |
| `openai.yaml`                                                           | 超过 64 KiB、无法读取                                                                                         | 忽略，不记问题                                                                                                                                            |
| `openai.yaml`                                                           | `interface.*`、`policy.allow_implicit_invocation`、`dependencies.tools` 或其中某一项的类型不对                | 忽略那个字段，并记一个问题                                                                                                                                |

| Skill 根目录                                                            | 其下无法读取的目录                                                                                            | 跳过，并记一个问题；无法读取的根目录让那个根目录失败                                                                                                      |

问题是 `SkillCatalogSnapshot::issues` 中的 `SkillLoadIssue`，带有文件或目录的路径和 `severity`：`warning` 表示照样加载了（某个字段被忽略或截断、Skill 被更近的同 ID Skill 遮蔽、监视器的诊断），`error` 表示有目录没有加载（加载失败的 Skill、无法读取的目录或根目录）。因此根目录下无法读取的目录是 `error` 问题，尽管它只损失自己。扫描最多深入 8 层目录，读取的 `SKILL.md` 最大 1 MiB。不解析 `allowed-tools`。

Provider 的流是外部输入（[模型 API](/docs/architecture#the-model-api)）：Agent 无法使用的值，只要响应的其余部分可用，就不让整个响应失败（`hanafubuki-agent-model-api` 的 `tolerant_decode.rs` 和各协议的解码器）。身份（响应、条目和调用的 ID）保持严格。

| 位置               | 发现                                                                                                                                                                                      | 读作                                                                                                                                                                                                   |

| 所有协议           | 用量缺少某个计数或为 `null`                                                                                                                                                               | 该计数为 0，另一个保留                                                                                                                                                                                 |
| 所有协议           | 用量不是对象、计数不是整数、两个计数都没有                                                                                                                                                | 没有用量                                                                                                                                                                                               |
| Chat Completions   | 没有 `choices` 的块（`stream_options.include_usage`）                                                                                                                                     | 记录其用量；只读取 choice 0                                                                                                                                                                            |

## 模型元数据 [#model-metadata]

注册表（[模型元数据](/docs/architecture#model-metadata)）在 `kernel/src/model_metadata/`；facade 的存储在 `model_metadata_store.rs`。

- **列表逐个模型合并。** 列表列出的模型采用该条目的事实，包括它不再报告的（变为未知）；列表没列出的模型保留之前列表报告的内容，直到最后一次被列出后 7 天，而最新列表列出的模型会一直保留，直到某次列表不再列出它。注册表记录的列表总是替换该端点（协议和 base URL）的模型清单。
- **缩水保护**（来自 Hoshimi）：如果一份列表的模型数不到该端点上次记录的列表的一半（更可能是列表被截断，而不是 Provider 下架了一半模型），它不会被记录，仅此一次；下一份列表无论内容如何都会记录，所以真的下架了模型的 Provider 第二次会被相信。只看数量：换成同样多个其他模型的列表（比如换了模型重启的本地服务）会立即记录。无论哪种情况，`list_provider_models` 都返回该列表。草稿 Provider 的列表（`test_provider_draft`）和其他列表一样会被记录。
- **过期与上限。** 学到的事实从学到时起保留 7 天，除非在此之前被遗忘（`forget_learned`，针对一个路由或一个端点的全部路由：`providers forget`、`/model forget`、facade 的 `forget_learned_model_facts`）：丢弃这些路由学到的事实，保留报告的事实，像其他变化一样保存（没有可遗忘的就不保存）。注册表最多保留 4096 个路由和 32 个端点的列表，超出时丢弃观察或列出时间最早的，但从不丢弃刚学到事实的路由。过期的事实在下一次变化时丢弃，在那之前被忽略。
- **models.dev**（`model-api/src/models_dev.rs`）是外部数据，宽容读取：`api.json` 逐个提供商读取；不是对象的提供商、不是对象的模型，以及类型不对的字段（`limit.context`、`limit.output`、`reasoning`、`modalities.input`）被略去或视为未知，1024 到 20,000,000 token 之外的窗口和为 0 的输出视为未知，略去的数量以 debug 级别记录。只有正文不是 JSON 对象或没有可用的模型、超过 32 MiB、超过一分钟或状态码不是 2xx 时才失败；这时继续使用已保存的副本。每个提供商保存的是其 `api` 的主机名，以及按规范化 ID 保存的窗口、最大输出和对推理、读图的“是”（不保存“否”）；同一提供商中规范化后相同的两个 ID 像两个提供商的条目那样合并（取较小的限制和任何一个“是”）。副本自下载起有效一周（下载时间晚于当前时钟时从现在算起），过期后在下一次变化时丢弃；`forget_learned` 从不动它。
- **文件**（`model-metadata.json`）的结构是 `{"version": 1, "routes": [...], "listings": [...], "modelsDev": {...}}`：每个路由有它的键（端点的协议和 `baseUrlSha256`，以及模型 ID）和它的 `reported`、`learned` 事实，每项事实有值、来源和 `observedAtMs`；每个列表有它的端点、`listedAtMs`、`models`，以及是否正在 `held` 一份缩水的列表；models.dev 的副本（有的话）有它的 `fetchedAtMs` 和 `catalog`，读不出的副本被略去（会重新下载）。文件只在构建 Agent 时读取一次：未知字段被忽略，读不出的路由或列表被略去，读不出的事实视为未知，事实的来源取自它所在的分组，时间不会晚于当前时间。超过 16 MiB、不是 JSON 对象或版本不是 1 的文件会被隔离到 `.recovery/`，本次运行从一无所知开始。
- **写入**不让任何调用方等待：注册表每次变化后把快照交给存储（在它的锁内，所以有序），存储再交给 Agent 工作线程组中的写入线程，它写入排队中最新的快照（先写临时文件再重命名覆盖），Agent 停止时写入最后一份。写入失败会以 warn 级别记录，不影响其他任何事情。没有记录任何内容的运行不写文件。

## “请求过长”的拒绝 [#context-refusals]

Provider 的错误是否以超出模型上下文窗口为由拒绝请求，由 `hanafubuki-agent-model-api` 判断（`context_overflow.rs`，源自 Hoshimi 的 `core/failure.py`），适用于每种协议的错误，无论是 HTTP 拒绝还是流中的错误（`classify_remote_model_error`，它先于图片拒绝询问这一判断）。依次读取：

| 步骤                   | 规则                                                                                                                                                     |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 429                    | 无论代码或消息是什么，都不算                                                                                                                             |
| 代码                   | `context_length_exceeded`、`context_window_exceeded`、`prompt_too_long`（不区分大小写）：算，无论状态码                                                  |
| 状态码                 | 400、413、422 以外的都不算；流中的错误没有状态码，照常读取                                                                                               |
| 限流或配额             | 消息或代码中有 `rate limit`、`rate_limit`、`ratelimit`、`quota`、`tokens per min`、`requests per min`、`too many requests`、`限流`、`限速`、`额度`：不算 |
| 代码和消息（转为小写） | 任一含有下列措辞之一时算（`token_limit_exceeded` 是 OpenRouter 的代码）                                                                                  |

这些措辞是：`context_length_exceeded`、`context_window_exceeded`、`context window exceeded`、`maximum context`、`input exceeds the context window`、`exceeds the context length`、`exceed`、`exceeds` 或 `exceeded` 后接 `context limit` 或 `the context limit`、`prompt is too long`、`input is too long`、`too many tokens`、`too many input tokens`、`token limit exceeded`、`token_limit_exceeded`、`input token count`、`exceeds the maximum number of tokens`、`maximum input length`、`maximum prompt length`、`上下文长度`、`上下文窗口`、`超出最大长度`、`超过最大长度`、`超过了最大`、`输入过长`、`超出` 之后至多六个字符内出现 `长度限制`，以及 `token` 后接 `数` 或 `数量` 再接 `超过` 或 `超出`（`token` 之后可有空格）。Hoshimi 中单独的 `context length` 和 `context window` 没有采用，因为关于别的事情的拒绝也可能提到窗口（`context length must be a positive integer`）；`request too large` 也没有采用，因为 OpenAI 也这样描述每分钟的限流，按字节计的大小限制也这样措辞。这类错误照旧是 `ModelError::Remote`。

`context_limit_in(message)` 读取拒绝中写明的窗口。各模式依次尝试，每个只看第一处匹配；值不在 1024..=20,000,000（`PLAUSIBLE_CONTEXT_WINDOW`）之内时转到下一个模式；数字以一位数字开头，后面是数字和逗号，逗号忽略：

| 模式                                                                                                                      | 示例                                                     |
| ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| `maximum context length is N`（或 `prompt`、`input length`）                                                              | `This model's maximum context length is 131072 tokens`   |
| `context window`、`length` 或 `limit`，然后 `of` 或 `is`，然后 N                                                          | `exceeds the context window of 200,000 tokens`           |
| `> N maximum`                                                                                                             | `prompt is too long: 210000 tokens > 200000 maximum`     |
| `maximum number of tokens allowed`、`maximum allowed tokens`、`maximum input token(s)`，然后可有 `is`、`(` 或 `:`，然后 N | `exceeds the maximum number of tokens allowed (1048576)` |
| `limit` 或 `最大`，之后至多十二个不含数字的字符，然后是至少四个字符的 N，然后 `tok`                                       | `输入超过最大长度限制 32768 tokens`                      |

内核据此学习（[学到的窗口](/docs/architecture#model-metadata)，`service/context_window.rs`）：写明的窗口，否则被拒请求的估算，同样限定在这个范围内（不到 1024 token 的请求被当作过长拒绝，更可能是误读了拒绝）。注册表只在新窗口小于路由当前有效的学到的窗口时才保留它（`learn_context_window`；已过 7 天的不再计入，不更小的窗口不做更改也不保存）。被拒会话的提交改写它的窗口和用量的窗口；只有会话采用了学到的窗口时才记录事件 `model_context_window_learned`（[exec --json 事件](/docs/json-events#session)）：配置了窗口的会话、学到的窗口比报告的大、会话已是这个窗口，这些情况都不提示。学习过程不写日志。

## 推理参数被拒 [#reasoning-refusals]

Provider 的错误是否拒绝了请求的推理参数，由 `hanafubuki-agent-model-api` 严格判断（`reasoning_refusal.rs`），在上下文溢出和图片拒绝之后（`classify_remote_model_error`）：宽松的匹配会在无关的拒绝上重试，并让路由学到“不推理”。以下条件全部满足时才是 `ModelError::UnsupportedReasoning`：

| 步骤       | 规则                                                                                                                                                                                                                                                                         |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 状态码     | 400 或 422；流中的错误没有状态码，从不计入                                                                                                                                                                                                                                   |
| 指名了参数 | 小写后的消息包含 `reasoning`、`thinking`、`effort`（因此也包括 `reasoning_effort`、`reasoning.effort` 和 `output_config.effort`）或 `output_config`                                                                                                                          |
| 是拒绝     | 代码是 `unsupported_parameter` 或 `unsupported_value`（不区分大小写），或消息包含 `unsupported`、`not supported`、`does not support`、`doesn't support`、`do not support`、`unknown`、`unrecognized`、`unrecognised`、`not allowed`、`not permitted` 或 `unexpected keyword` |

因此 OpenAI 的 `Unsupported parameter: 'reasoning.effort' is not supported with this model.`（见 openai/openai-python#2532 的报告）和 Anthropic 文档中的 `adaptive thinking is not supported on this model` 计入，而被拒的 `temperature`、因过小被拒的预算和 Anthropic 文档中的 `Invalid signature in thinking block` 不计入；测试中的其他措辞（无法识别或意外的参数、不允许的参数）只是示例，并非实际记录。被拒的档位（`unsupported_value`）也作为对该参数的拒绝计入。不匹配中文措辞：在 Provider 的拒绝中没有找到这样的例子。

内核（`run_sampling_request`）只在轮次请求携带了推理参数且轮次未被取消时，去掉推理参数重试一次，发出 `ModelRetryScheduled { stage: ReasoningFallback }`，注册表把该路由的推理学为 `Unsupported`（`learn_reasoning_unsupported`，学到的“否”优先于报告的“是”，保留 7 天）。第二次拒绝，或对不带推理参数的请求的拒绝，会让轮次以 `AgentError::UnsupportedReasoning` 失败。压缩自己的请求不重试。传输层给不出路由时什么也学不到，所以它的每个请求都会被拒绝一次。

## 崩溃循环标记 [#crash-loop-marker]

`AgentStartMarker`（数据目录中的 `start-marker.json`，用 `write_atomic` 写入，带缩进格式）记录从未完成的启动次数：

```json
{
  "unfinishedStarts": 2,
  "lastAttempt": {
    "pid": 41237,
    "atUnixMillis": 1793260800000
  }
}
```

- 启动在构造任何东西之前读取计数，加一，连同本进程的 `pid` 和时间一起写入。没有拿到数据目录锁的启动不记录尝试。
- 在 Agent 已 `Running` 满 `AGENT_START_SETTLE`（60 秒）后、启动有序失败时、实例有序停止时（重启、故障后的停止、关闭模块）以及有序关闭时，写入 `{"unfinishedStarts": 0}`（没有 `lastAttempt`）来清除这次尝试。没有记录过尝试的运行（Agent 处于关闭状态）不清除它，所以崩溃循环导致的停止在有序退出后依然有效。
- 如果崩溃记录属于同一进程且不早于最后一次尝试，就不计入最后一次尝试：致命的 panic 从不发生在 Agent 的线程上（Agent 的线程都被隔离），所以那次运行不是死于 Agent。崩溃记录（`crash-record.json`）在 `configure_crash_record` 指定它之后，由 panic hook 在致命 panic 中止进程之前写入：

```json
{
  "pid": 41237,
  "atUnixMillis": 1793260803512,
  "thread": "main",
  "location": "src/main.rs:42:9",
  "message": "…"
}
```

- 计入的启动达到 `CRASH_LOOP_STARTS`（3）次时，`AgentStartMarker::disabled_reason` 让槽位进入带 `crashLoop` 的 `Disabled`，并记录一条提示。用户的重启，或者把 Agent 关闭再打开，会重置标记；单纯的挂载不改变崩溃循环导致的停止。无法读取的标记不计任何启动：它从不让 Agent 保持关闭。独立模式的第一次启动无论计数是多少都会运行（[独立模式的同一组合](/docs/embedding#the-same-composition-standalone)）。

## 分层压缩 [#hierarchical-compression]

`hierarchical` 策略（[压缩](/docs/architecture#compaction)）是内核的 `service/compression/`（`mod.rs` 中的投影、`adapter.rs` 中的适配器、`inherit.rs` 中的分叉、`runtime.rs` 中的内容存储和中断、`tools/` 与 `receipts.rs` 中的工具、`status.rs` 中的状态），建立在纯 crate `hanafubuki-agent-compression` 之上。

**状态。** `PersistedAgentRuntimeState.compression` 保存该 crate 的 `State`，以 `AgentCompressionState` 重新导出：在窗口上生成的引用、块（只失效，从不删除）、token 快照和提醒的基线。它以追加为主：引用从不重新分配，块从不删除，其余部分（提醒、统计、锁存、计数器）很小。所以它写成一条链（`model/compression/chain.rs`），每个改变了它的运行时检查点带一个链节，即 `PersistedAgentRuntimeState.compression_update`（`AgentCompressionUpdate`，没有变化时省略，所以 `standard` 的记录没有新字段）：

- **`snapshot`**：整个状态，引用映射只写一个方向（`by_raw`；读取时推导出 `by_ref`，不含 `BLOCKED` 和分叉的 `REF_FLOOR_ID`）。它开始一条链。
- **`delta`**（`AgentCompressionDelta`）：它在快照之后的位置（`seq`，从 1 开始）、新生成或改变的引用绑定、新建或除了年龄之外有变化的块（整个）、只是变老的块的年龄（`survived`：每个活动块每个请求老一步）、首次渲染的 token 计数和被去掉的计数，以及其他字段中有一个变化时的全部其他字段。
- **`dropped`**：状态结束了（切换离开并压缩过的会话）。

内核对照链头做差分（`SessionRuntime.compression_head`，`conversation_commit` 中的 `next_link`）：它暂存的最后一个链节的状态和 `seq`。回滚连同运行时的其余部分一起恢复链头，所以下一个链节接在最后一个持久的链节之后。加载之后，或者对于新会话（分叉、子会话），没有链头，所以它们的第一个链节是快照；差分无法表达的变化（绑定或块消失、块重新排序）也写成快照；自上次快照以来的差分将超过快照本身时也写快照，这让读取链的开销与状态成正比。没有改变状态的检查点不带链节，所以一个步骤只写一次状态，而不是它的每个检查点各写一次。历史存储把链节保存在 `agent_compression_links` 中（每个链节一行，快照或 `dropped` 替换会话的所有行），并从 `runtime_json` 中去掉状态；加载运行时（`load_runtime_state`、恢复）时把这些行折叠（`AgentCompressionChain`）进 `compression`。内存存储以同样方式折叠。折叠不了的链（之前没有快照的差分、跳号的 `seq`、提到状态中不存在的块或 token 计数的差分、无法读取的链节 `Unreadable`）加载为没有状态，由内核重建（见下文）。链出现之前写入的记录在 `compression` 中带着整个状态，存储把它当作快照读取。历史格式及其版本没有变化；索引的模式版本是 6。切换到 `hierarchical` 时，如果还没有状态，就装入一个空状态。

**分叉、子会话和加载。** 条目 ID 在分叉中保留，所以状态映射的消息 ID 也保留。在头部创建的分叉，以及在父会话头部创建的子会话（包括 `/side`），原样沿用源会话的状态。在某个轮次之前创建的分叉（因此也包括 `edit_from_turn`），以及在父会话运行中的轮次之前创建的子会话，从源会话的状态中采纳（`inherited_state`，基于该 crate 的 `adopt_fork_state`，仿照 billion-context 的分叉采纳）：覆盖的消息全部在分叉中的块被保留，并且是活动的，层级块消耗过的块作为原来那样的非活动记录随之保留；已展开或已被消耗的块，或覆盖了分叉中没有的消息的块，被丢弃。分叉持有的每条消息保留它的引用和冻结的 token 计数，源会话的最高引用被保留下来（引用映射中的 `REF_FLOOR_ID`），所以分叉自己的消息从它之上编号。孤立调用、截断、渲染延迟和视图的锁存随之保留；提醒的基线、统计和终止计数重新开始。空的子会话没有状态。源会话没有状态，或者会话加载时没有状态（没有写入，或者无法读取）时，通过重放窗口中的 `compress` 调用重建状态（`rebuild_state`），使用源会话最近一次的调优（加载时用默认值），并放宽压缩限制和最近区，因为这些调用已经通过过它们一次；回执表明失败、被拒绝或无操作的调用不重放。含有压缩（`CompactionSummary`、`ProviderCompaction`）的窗口不重建：压缩之后，引用从窗口里已经看不到的编号继续，重放可能折叠错误的消息。没有 `compress` 调用的窗口不得到状态，所以 `standard` 的分叉仍然没有状态。

**哪些请求。** `CompressionMode::of` 按请求决定：策略为 `hierarchical` 时是 `Hierarchical`；已切换走的会话仍有有效的块时是 `Carry`，保留投影，但没有提示、提醒和工具；其余情况，以及轮次已回退时（`compression_fallback`），是 `Off`。

**适配器。** `MessageLog` 把窗口的历史条目映射为该 crate 的消息：

| 历史条目                                                                                                                                            | 消息                                                            |
| --------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `UserMessage`、`SteeringMessage`                                                                                                                    | 用户文本，图片作为附件句柄                                      |
| `AssistantMessage`                                                                                                                                  | 助手文本（有 `model_text` 时用它）                              |
| `ToolCall`                                                                                                                                          | 工具调用：调用 ID、名字、作为 JSON 文本的参数                   |
| `ToolOutput`                                                                                                                                        | 以其调用的名字表示的工具结果：它的文本部分，结构化部分作为 JSON |
| `CompactionSummary`、`ProviderCompaction`                                                                                                           | 受保护的用户文本                                                |
| `TurnStart`、`WorldStateUpdate`、`SkillContext`、`ContinuationContext`、`PermissionReview`、`ToolSelection`、`CanonicalInitialContext`、`Reasoning` | 无：条目在请求中保持它在投影条目之间的位置                      |

窗口第一个 `TurnStart` 之前的每条消息（压缩过的前缀）也受保护：它从不折叠。消息的 ID 是 `<来源会话 ID>:<条目 ID>`，在会话的谱系内唯一。模型读到的引用（`m00001`……）不是这些 ID，因为压缩之后条目 ID 不再按历史顺序排列：该 crate 按历史顺序生成引用，从不重用。

**投影。** `regular_model_request` 从 `projected_history` 构建输入，后者对消息日志、状态、配置和上下文大小（上一个响应中 Provider 报告的 `context_consumed_tokens`，否则是窗口历史的估算）运行该 crate 的 `process_turn_with`，并传入会话的内容存储（没有消息过滤器：Agent 没有任何过滤器）。`apply_view` 把该 crate 的视图变回条目：

- 被覆盖的条目被省略；
- 视图改变了文本的消息得到新文本：用户、助手或工具输出文本前面的 `<acp tokens="…" type="…">mNNNNN</acp>` 标签（助手消息写入它的 `model_text`；工具输出的文本部分合成一段文本，图片和资源保留），或者仍然有效的 `compress` 调用的参数被压缩到仍然有效的范围。工具调用的参数从不带标签；
- 视图渲染的每个摘要（`[Compressed conversation section] — topic`，对应没有可见载体的块）作为 `CompactionSummary` 条目插入到它的锚点处，模型 API 把它包装为用户文本。

保存的条目从不改变。随后 `project_model_tool_outputs` 像对任何请求一样限制历史工具输出的大小。在 `Hierarchical` 下，请求还在指令之后（计划模式的后缀之后）追加 `build_compress_system_prompt` 的文本（只构建一次，每个请求的字节都相同），并把提醒（在 Anthropic Messages 上用它的 Anthropic 措辞）或者状态行作为最后一条输入：一段用户文本，从不持久化。

**哪个请求保留状态。** 构建请求会在内存中推进状态：为新消息生成的引用、token 快照、提醒的基线。只有步骤自己的请求（在 `begin_sampling` 中构建）保留它：状态存到记录上，由步骤的提交持久化。自动压缩的估算和安装之后的检查构建同样的请求（`step_model_request_projected`），但丢弃状态，所以计算一个请求的大小从不改变状态。一个步骤仍只投影一次：投影连同它的输入保存在会话上（`compression/cache.rs`，只在内存中）——历史条目、状态和内容存储按身份比较，设置和 token 数按值比较——下一个由相同输入构建的请求（估算之后步骤自己的请求）直接取用它，不再重新投影。开启消息时间戳时，它标记的消息保留估算时的时间。

**工具。** `compress`、`decompress`、`search_context`、`acp_status` 和 `acp_cache` 是 `AgentCoreTool`，在模式为 `Hierarchical` 时被规划（目录上下文中的 `compression_tools`，即 `planned_tools` 生成的列表），计划模式下也是；功能开启时，其后还有 `absorb`、`acp_retrieve` 和 `acp_rule`（见下文）；这八个名字都在 `RESERVED_TOOL_NAMES` 中。每个工具都在会话记录的锁下对记录运行（`execute_compression_tool`），让它的钩子得到一个结果。随后，`compress`、`decompress` 和三个可选工具在写入其输出的那次提交的锁下（`commit_history_with`），针对那一刻的状态再应用一次：提交的输出就是提交的状态所对应的输出，像第一次运行的输出一样受限（`canonicalize_tool_output`），同一步骤中的两次调用按调用顺序应用。被拒绝的调用让状态保持原样。

- **`compress`** 用 billion-context 的回执回答：带摘要指纹的 `[Compressed …]`、`[Compression FAILED`、`[Compression no-op`。
- **`decompress`** 用 billion-context 宿主的措辞回答，有四种方式。默认把块的内容（上一层，或用 `full` 时的全部原文）作为输出原地返回，并把有效的块标记为已原地恢复（只有第一次恢复改变状态）；之后对它的范围调用 `compress` 会以同一个 ID 原地重新折叠它。带 `startId` 和 `endId` 时（它们和 `imageRef` 一起出现在 schema 中，是宿主的扩展，见 `core_tools/compression_spec.rs`），只返回块中引用落在范围内的消息，从历史读取（宿主为此需要它的内容存储；Agent 保留完整历史），且不改变任何东西。带非空的 `toFile` 时，文本改写到会话的导出文件：这个值只表示要一个文件，因为写到模型指定的位置就是一次未经批准的写入。工具提出请求（`CompressionToolRun.export`）；`execute_compression_tool` 在释放记录的锁之后通过 `AgentHistoryStore::write_session_export` 写入，输出给出路径；写入失败时说明这一点，并原地附上前 4 000 个字符。文件存储写 `history/attachments/<session>/exports/decompress-<block>[-full|-<start>-<end>].txt`，同名的下一次导出替换它，删除会话时一并删除；不保存文件的存储（内存中的那个，因此每个临时会话都是）拒绝，这是该 trait 方法的默认行为。不像宿主那样在超过 10 000 个字符时不经请求就写到文件：请求会限制它的历史工具输出（`project_model_tool_outputs`），大的原地恢复也在内。带 `imageRef` 时取回图片：`list` 列出窗口中每条带图片的消息（引用、类型、大小，最多 50 条）；`mNNNNN` 引用或摘要的 MEDIA REFS 列出的句柄（适配器作为消息图片句柄传入的附件 ID，crate 在折叠时把它追加到块的摘要中）把该消息的图片附在输出上。`full` 恢复和范围恢复也附上它们返回的消息的图片。提交把输出和附在它上面的每张图片计入本轮的工具输出预算（`maximum_tool_output_bytes`），超出预算就使本轮失败，所以恢复按历史顺序附上图片，只附到它们连同输出还装得进提交应用它时剩余的预算为止。正文之前的一段说明按句柄列出每张未附上的图片及其类型、大小和尺寸（最多 50 张），供用 `imageRef` 逐张恢复，本轮没有余量时在之后的一轮中恢复；一张图片都装不下的 `imageRef` 恢复被拒绝，本轮继续。这些是历史自己的附件（`CompressionToolRun.images`，写入所提交的 `ToolOutput` 的 `images`），所以之后的每个请求都像加载任何工具输出的图片一样加载它们，不接受图片输入的模型会被去掉它们；此时图片恢复被拒绝。
- **`search_context`** 先搜索块摘要（包括有效的和已被折叠掉的），再搜索被折叠的原文（crate 的 `folded_message_inputs`，即有效块覆盖的消息），两者都和 billion-context 的宿主一样按查询词的字面出现（`Algorithm::Substring`，最低分 1e-9）：出现一次就是命中，没有出现就是不匹配，而混合搜索的模糊 n-gram 会把什么都不匹配的查询变成弱匹配。摘要行给出块覆盖的引用，以及它最有区分度的词周围的一段，用 【】 标出；原文行给出一个没有被摘要行列出的块、它最佳消息的引用和那一段；三个及以上词的查询，在某个词只有排名靠后的块包含时，得到宿主的提示。文档特征按会话缓存（`SessionRuntime.compression_search`，crate 的 `DocCache`，最多 8 Mi 个 UTF-16 单元的文本），从不持久化。宿主的计划感知引导没有移植：它默认关闭，而 Agent 没有这样的设置。
- **`acp_status`** 是该 crate 的状态报告。**`acp_cache`** 根据 Agent 记录的内容报告：上一个响应的用量和各次折叠。模型 API 的 `ModelUsage` 只有输入和输出 token，没有缓存的 token，所以没有 token 算作缓存。

**可选功能。** `[compaction.hierarchical]` 的 `absorb`、`contentStore`、`crush` 和 `rules` 设置该 crate 的 `Config` 中同名的部分（它们的其他设置保留该 crate 的默认值：4 000 个 token 的门槛、96 个字符的开头、50 条规则、每条 300 个字符），`process_turn_with` 按内核的顺序应用它们：内容存储、隐藏已吸收的调用和结果、crush（只在 `absorb` 开启时）、吸收要求。它们只在 `Hierarchical` 下起作用：已切换走的会话（`Carry`）仍隐藏已吸收的调用和结果，但重新显示已保存的原文，也不再有吸收要求，因为它们的工具已不再被规划。

- **`absorb`。** 4 000 个 token 及以上、不受保护且不属于 ACP 工具的工具结果，在视图中被附加 `[ACP absorb]` 要求（从不保存），指令中加入 `build_absorb_system_prompt` 的一节。`absorb` 调用（`parse_absorb_input`、`apply_absorb`）在状态中记录一条 `AbsorbRecord`，从下一个请求起，目标的调用和结果被去掉；`absorb` 调用本身留下作为记录。
- **`crush`。** 在决定是否要求吸收之前，大结果中的 JSON、代码或日志被确定性地折叠（`apply_crush_to_messages`）；折叠后低于门槛的结果不再被要求吸收。
- **内容存储。** 大的工具结果第一次出现时，在视图中被替换为它的占位符（`📦 [acp-stored #mNNNNN · kind · tokens tok] …`），一次折叠保存它的块所覆盖的原文（`store_covered_originals`，随 `compress` 在其提交时应用）。存储（`AgentContentStore`，即该 crate 的 `ContentStore`）保存在 `SessionRuntime.compression_runtime` 中，不在记录里：与状态一样，只有步骤自己的请求保留它的投影返回的存储。在使它增长的提交之后（步骤开始、一次 `compress`），内核在释放记录锁后，通过 `AgentHistoryStore::write_compression_store` 把它整个写出；文件存储写入 `history/attachments/<session>/compression-store.json`（先暂存再发布），blob 清扫从不读取它，删除会话时将它移除。加载会话时用 `load_compression_store` 读取；无法读取的文件被移到一旁，名为 `compression-store.unreadable-<millis>.json`，读作没有。分叉或子会话取得源会话的存储。每个条目只在状态把它的 ref 绑定到同一条消息时保留（从 `compress` 调用重建的状态可能编号不同）。存储是历史的缓存：占位符只由原文构建，所以丢失的条目（写入前崩溃、写入失败、被丢弃的条目）会在下一个显示该消息的请求中再次保存，逐字节相同；只有窗口已不再包含的被折叠原文会丢失，此时 `acp_retrieve` 回答该 ref 没有保存的原文。`acp_retrieve`（`apply_retrieve`、`note_retrieval`）把原文作为不可信数据内联返回，或者从 4 000 个 token 起把它写入会话的导出文件 `<ref>.txt`（`write_session_export`，与 `decompress` 的 `toFile` 相同），并以 `build_retrieval_pointer` 给出路径；不保存文件的存储把它内联返回。
- **`rules`。** `acp_rule`（`execute_rule`）在状态中记录、删除、清空或列出 `RuleRecord`。指令中加入 `RULES_USAGE_PROMPT`，有规则后再加入 `format_rules_for_prompt` 的列表，位于静态提示和吸收一节之后：规则改变之前字节相同。

**被中断的轮次。** 用户中断一个 `hierarchical` 轮次时，`stage_terminal` 记下它最后一个请求投影时的 token 数（`CompressionRuntime`，从不持久化）。之后的每次投影，一旦计数超过它，就用 `NudgeState::absorb_aborted_turn_growth` 把它记入提醒（billion-context 的 #5415）：增长基准向前移动，从第二次中断起，跳过的增长作为欠账偿还。重启后它被遗忘。

**此策略下的压缩。** 在 `Hierarchical` 下，自动检查（`maybe_auto_compact`）不看阈值：它像以前一样在轮次有预算压力时压缩，或者在投影报告最终出口时压缩（该 crate 统计的、超过紧急阈值且已没有可折叠或可截短内容的请求数达到三），并且只在 `autoCompactionEnabled` 开启时。标准压缩的来源是对有效块的投影（`project_compaction_source`：去掉被覆盖的条目，摘要作为文本，没有标签）。安装时，`after_standard_compaction` 在 `hierarchical` 下重新开始最终出口的计数，块所覆盖的条目已离开窗口，这些块在下一次投影时失效；已切换走的会话丢弃它的状态。

**Panic。** 对该 crate 的每次调用都在 `catch_panic` 下运行。请求投影中的 panic 让这个请求带完整历史发送，并设置轮次的 `compression_fallback`：轮次之后的步骤按 `standard` 运行（没有提示、工具和提醒，阈值恢复），这一步在它的 `ReasoningUpdated` 之后记录带 panic 消息（限制在 4 KiB 之内）的 `ContextCompressionFailed`，并记录一条警告日志，下一轮次再尝试。投影压缩来源时的 panic 让压缩读取完整历史。工具中的 panic 是这次调用的错误 `[Compression FAILED: … (internal error)]`，状态保持原样。

**设置。** facade 每个轮次读取 `[compaction.hierarchical]`，作为 `AgentHierarchicalCompression` 放进轮次扩展；内核把它映射到该 crate 的 `Config` 上，以会话的上下文窗口作为模型的上限：`maxContextLimitPercent` 设定压力区间，`emergencyThresholdPercent` 设定紧急提醒和截短阈值（从不低于压力区间），`nudgeGrowthTokens` 设定增长步长，其余按名字映射。没有它的轮次取默认值；上下文窗口未知时什么都不施加压力。`absorb`、`contentStore`、`crush` 和 `rules` 开启该 crate 中同名的部分。

**消息时间戳。** `messageTimestamps` 作为 `AgentHierarchicalCompression.message_timestamps` 到达内核，同时带有 `utc_offset_seconds`，即 facade 准入轮次时读取（`chrono::Local`）的本地偏移。历史条目不记录时间，所以消息的时间是首次所见的时间戳，与 billion-context 的纯内存通道相同：投影把时钟传给该 crate（`TurnInput.clock`：当前时刻，采用该轮次的偏移），`process_turn` 在分配引用之前，为引用映射尚不认识的每个消息 id 打上时间戳（`State.ts_stamps`，以消息 id 为键）；映射已认识但没有时间戳的 id 是在开启该设置之前显示过的，永远不会得到时间戳。时间戳是一个 `LocalTime`（毫秒数和读取时的偏移），从不改变，所以标签在每个请求中、重启之后以及偏移改变（夏令时、出行）之后都渲染出相同的 `time="yyyy-mm-dd hh:mm:ss"`（`format_tag_time`，位于 `type` 之后）；渲染只读取时间戳。只有该步骤自己的请求保留其投影的状态，所以发送的时间戳就是保留的时间戳。消息由它提交之后的下一个请求首次显示：轮次的最终回答取下一个轮次的时间。指令中的标签一节换成带时间的版本（缓存两份提示）。折叠的回执在每个块的指纹行后加上 `[start – end]`，即它覆盖的消息以及其范围两端所指消息的最早和最晚时间戳；其中有一个没有时间戳时则不加（billion-context 的 `blockCoverageTimes`）。时间戳在链中作为增量里单独的一张映射传递（只含新的时间戳；有时间戳改变或消失时写快照），分叉或子会话保留它所含消息的时间戳，从 `compress` 调用重建的状态没有时间戳，所以它编号的消息不再显示时间。关闭该设置时不传时钟：不打时间戳也不显示，请求与没有时间戳时逐字节相同；重新开启后，已保存的时间戳再次显示。缓存报告的时刻使用同一偏移。没有移植：精简提示包的 TIMELINE（"Occurred:"）规则，因为 Agent 发送的是默认提示包，其中没有这条规则。

**宿主看到的内容。** 折叠了内容的 `compress` 调用在提交其输出的同一次提交中、紧跟该提交的 `HistoryCommitted` 之后记录 `ContextCompressed`（它的调用 ID、生成的块数、这些块替换的 token 数，以及它生成或重新折叠的块中最高的层级）（`CompressionToolRun.fold`，由 `CompressionChange` 带进 `commit_history_with`）；什么也没折叠的调用不记录。快照的 `compression`（`AgentCompressionSummary`：活动块数和 `Stats.tokens_compressed`）在读取快照时从状态计算，没有状态时省略。`AgentService::compression_status`（facade 的同名调用，`/compression` 使用它）在记录的锁下复制窗口、状态、内容存储和用量；释放锁之后，像 billion-context 的 `/acp` 那样在状态的副本上重新决定提醒（`process_turn_with`，不加标签），所以上次请求之后的折叠也会显示，再生成 `build_status_panel` 的面板和完整的缓存报告。它使用轮次会得到的 `[compaction.hierarchical]` 设置，什么也不提交，其中的 panic 是 `AgentError::Internal`。既不运行 `hierarchical`、也没有保留状态的会话没有状态。`compress_call_ranges` 用该工具的宽松解析器读取 `compress` 调用的参数，供终端界面的折叠单元格使用。

## 已安装插件的内容 [#package-content]

- **加载一次，然后各来源跟随。**一次加载读取 `install.json`、`linked.json` 和缓存一次（已链接的包从其 `linked.json` 条目所指的目录读取；最早支持链接的版本写在 `install.json` 中、来源为 `linked` 的条目也按链接读取，存储的下一次写入把它移到 `linked.json`；缓存中有的 id 即使 `linked.json` 也有，仍是缓存中的包），按键排序包，读取每个启用的包的清单和组件；两次加载之间不做缓存。它为每个启用的包创建数据目录，钩子和服务器会被告知这个目录。Skill 根目录在目录服务上替换（集合改变会丢弃缓存的扫描，与工作区改变相同），钩子来源在引擎上替换（下一轮的发现读取它们），`plugins` 行的摘要被替换；然后协调 MCP 服务器，并把代码包以及启用的已链接包交给访客宿主（[插件访客](#plugin-guests)）。
- **重新加载是串行的。**一次重新加载从读取设置到最后一次更改都持有它的门，所以两次重新加载中后一次的集合会保留。写入设置会在后台启动一次重新加载，并不等待它。
- **MCP 一侧只改变有变化的部分。**在 MCP 配置门之下，不再存在、已改变或现已关闭的插件服务器被断开，除非用户的同名服务器已经接管了连接；新增或改变的服务器连接，最多同时四个，连接失败就是它的状态。未改变的服务器保持连接。之前和之后都没有插件服务器时，不获取这个门。
- **钩子的包在需要时才计算哈希。**每轮的运行时发现不计算包的哈希：凭定义哈希被信任的插件钩子是可运行的，运行时计算它的包的哈希（每个事件每个包一次），哈希不是被信任的那个时拒绝该钩子。列出钩子时每个包计算一次哈希，所以对改变了的包 `/hooks` 显示 `modified`；信任时从这次列出中记录两个哈希。无法计算哈希的包，其钩子列为不受信任，也不能被信任。
- **包的组件无法使用时，记为该包的问题**：清单字段、读不了的 Skill 根目录（与任何根目录一样是 Skill 目录的问题）、MCP 文件或服务器、钩子文件（钩子诊断）。

## 插件访客 [#plugin-guests]

访客宿主（[代码插件](/docs/architecture#code-plugins)）的细节。

- **状态来自 fiber。** 监督者（`plugin-guest-supervisor`，与加载器同在 `plugin-guests` 之下）监听根上的 `StatusChanged`、`GuestStarted` 和 `GuestExited`，通过加载器的条目把访客 fiber 对应到它的包，忽略条目已经替换掉的 fiber。`Loading` 即 `starting`，`Active` 即 `running`，`Disposed` 即 `stopped`；`Failed` 在 fiber 自上次加载以来没有变为活动时是启动失败，否则是故障。`GuestStarted` 保存进程的句柄（进程 id、stderr 尾部），`GuestExited` 保存退出报告；启动失败时从句柄取退出报告，因为访客桥只在 `apply` 返回之后才监视退出。刚结束的进程会让访客暂时保持 `running`（没有进程 id），直到它的 fiber 失败。
- **重启循环。** 故障向访客的 `RestartWindow` 询问下一次延迟。有延迟时访客进入 `restarting`，一个任务交给监督者的 worker；延迟之后它检查此后没有对该访客做出新的决定（每个决定，新的包、重试或停止，都会改变它的纪元），并且条目的 fiber 仍是失败的那个；然后计入这次重启，用 fiber 自己的配置更新它而不保存（`update_with(config, true)`：Kardia 的 `restart` 会让失败的 fiber 保持失败，而保存的更新会被写回树中）。没有延迟时访客保持 `failed`。`retry_package` 清空窗口并以同样方式更新失败的 fiber。关闭后再开启的包以空窗口启动。
- **进程。** 启动器在每次启动时在阻塞池上运行（访客桥在异步 worker 之外实例化访客）：它对包求哈希并与记录的哈希比较（已链接的包没有哈希，不比较），创建数据目录，解析命令（`./` 路径必须解析到包内；`interpreter` 是绝对路径或 Agent 的 `PATH` 上的名字，之后访客也可读取它），把命令行包进插件配置，预留所有者，启动一个预留的管道执行器，并把它的 stdin、stdout 和 stderr 交给访客桥（`start_reserved_pipe_executor`；会话不在其上保留读写者）。访客桥的 `GuestChild` 是基于收据的适配器：`kill` 即 `terminate_reserved_executor`（向进程组发 SIGTERM，然后 SIGKILL；Windows 上为作业对象），`try_wait` 和 `wait` 读取会话的结束（`wait_reserved_executor`，带真实的 `ExitStatus`，包括信号），观察到结束之后释放执行器，从而释放所有者。访客桥在确认结束之前丢弃的子进程在丢弃它的线程之外被释放；已被所有者组清扫带走的则已不存在。
- **上限。** 握手和每个导出（`apply`、调用、`dispose`）都受 `plugin_call_deadline`（10 秒）约束，除非调用者设置了自己的期限；超过它进程会被杀死。访客发来的一行至多 4 MiB。监督者的 worker 随它的插件停止：插件的释放器在 worker 的释放器之前丢弃重启通道，所以 worker 立即结束。
- **WebAssembly 访客。** 解析器为每个条目名保存一个单元，第一次解析时在阻塞线程池上填充它：内容检查，以及读取模块（一个在包内解析的 `./` 路径），并在包的限制所对应的 `WasmSource` 上把它编译为 kardia-hmr 的 `WasmGuest`（时间总是设置，所以引擎的 epoch 中断是开启的；内存；给出时还有燃料）。限制相同的访客共享这个 source，因而共享一个引擎和一个 `wasm-epoch` 线程；只要还有包需要这组限制，解析器就保留它的 source，运行中的访客在停止之前也会让自己的引擎保持存活。插件是带清单元数据（它的名字，提供 `plugin`）的 `WasmGuest::plugin`，改名为 `guest:<id>`：生成它不实例化任何东西，每个实例启动时自己的元数据必须与之相符，否则启动失败；模块的 `deps` 从不被读取。无法读取或编译的模块解析为一个每次启动都以原因失败的插件，所以它的访客是 `failed`，而不是停在 `starting`。每个 fiber 在自己的 store 中实例化模块，所以重启从新的内存开始；它的调用在阻塞线程池上一次一个地运行，每次调用都有自己的燃料和 epoch 期限（它自己的期限与限制中较早的那个，以 10 毫秒为一格）。在生成引擎之前，访客宿主请求 kardia-hmr 在 macOS 上用信号处理陷阱（`set_macos_mach_ports(false)`，在其他平台上不改变任何东西；见 [panic hook 桥](/docs/embedding#the-panic-hook-bridge)）。模块没有句柄、进程 ID、stderr 或退出报告。
- **失败的访客实例。** kardia-hmr 以带类型的 `GuestFailure`（`Trap`、`OutOfFuel`、`Timeout`、`OutOfMemory`、`Exited`、`Killed`、`Panicked`）交出实例的失败，`GuestHost::call` 在调用的错误中找到它（`GuestFailure::of`），并以使 fiber 失败来回应，再由重启循环处理：除进程访客的 `Exited`、`Killed` 和 `Timeout` 以外的任何类型都如此；这三种情况下进程已经结束或被杀死，由 kardia-hmr 的退出监视器以退出报告使 fiber 失败。访客自己的错误（带消息、状态不为 0）不是 `GuestFailure`：它只是那次调用的错误。无论哪种情况，调用的错误文本都是 kardia-hmr 的消息，保持不变。
- **辅助程序命令行上的插件配置。** `--restrict-reads` 和每个根一个 `--readable-root` 跟在可写根之后。Landlock 随后只在平台目录（`/bin`、`/sbin`、`/usr`、`/etc`、`/lib`、`/lib64`、`/nix/store`、`/run/current-system/sw`，沿用 Codex）、可读设备（`/dev/null`、`/dev/zero`、`/dev/random`、`/dev/urandom`）、可读根和可写根之下授予读取，而不是在 `/` 之下。Seatbelt 在 `(allow file-read* (subpath …))` 中以参数命名每个根，加入 Codex 的受限读取平台默认值，并去掉偏好设置策略，因为它能触及读取根之外的数据。
- **日志。** 访客的插件名为 `guest:<id>`，所以 kardia 为它记录的一切（它的 stderr 行、任何级别的 `log` 调用、可能引用其内容的 fiber 失败）都带有这个前缀，宿主的 `LogExporter` 只在 `trace` 级别转发这样的消息，并像任何内容一样截断（`bounded_trace_content`）。访客宿主以 `info` 和 `warn` 记录它自己的决定（运行、未启动、失败并重启、以何种状态退出或被杀死），不带访客的原话，原话跟在 `trace` 级别。
- **贡献。** 监督者在 `StatusChanged(Active)` 的监听器中、把访客标为 `running` 之前，通过访客 fiber 自己的上下文注册它的代理：`plugin-guests` 插件声明了七个注册表和 `PluginFaults`，所以访客的受检访问能找到它们，每次注册都是该 fiber 的副作用（所有者 `guest:<id>`）。被略去的部分保存在访客的记录上，并与内核记在 `guest:<id>` 下的问题一起显示。访客不运行时代理立即回答（工具源失败，作为 `Optional` 被略去；钩子不生效）。调用每 50 毫秒检查一次调用者的取消，取消时丢弃（从而取消）对访客的调用。提示贡献者同时询问每个带提示的运行中访客（`join_all`），各自限制在调用期限的 80% 内，并按 kind 排序片段。观察者的 worker 是访客 fiber 的一个作用域 worker，读取一个容量为 64 个事件的通道。
- **宿主服务与提供。** 每个包有两个 loader 条目：`<id>#host`，其插件（`guest-host:<id>`）提供 `workspace`（每次读取时序列化的视图，所以根总是最新的）和 `settings`（它的配置）；以及访客的条目，它把 `plugin` 隔离到私有 realm，把这两个服务以标签 `guest:<id>` 隔离，并 `inject` 它们，所以 kardia-loader 在一个外层 fiber 中暂缓它的启动，直到它们运行。访客不提供其他任何东西：kardia-hmr 拒绝其元数据未声明的键，所以访客提供的东西都不会到达共享 realm。
- **已链接的包。** 门面在构建时以及每次重新加载时，把启用的已链接包（有代码或没有）交给访客宿主（`GuestHost::follow_linked`）；访客宿主从监督者启动到它的释放器运行期间监视它们，集合（按 id 和路径键）改变时替换监视。监视是实例的受控 worker 组中的一个线程（`plugin-linked-watcher`），它在每个存在的目录上建立递归的系统监视（`notify`），所以在它建立之前发生的改动看不到；不存在、被删除（收到它的 `Remove` 事件）或已消失的目录在每次检查时重试，一旦它重新成为目录就再次监视，这算作它的改动，所以替换整个目录的导出也能跟随；它每 100 毫秒检查一次令牌，所以 worker 组的关闭或访客宿主的停止都会结束它。事件按路径键归属：读取（`Access`）或目录的 `.git` 中的路径不算改动，不指向任何目录下路径的事件（溢出、重新扫描）算作所有目录都改动了。改动停止 500 毫秒后，每个改动过的目录修订号加一，`GuestHost::linked_changes` 随之变化。`plugins` 行的受控作用域 worker（`plugins-linked`）等待这个计数器，并在后台启动门面的重新加载（`PackageReload`，`reload_packages` 运行的也是它：先读取包，再重建角色目录），所以重新加载期间发生的改动由下一次重新加载处理。重新加载的 `apply` 发现访客的修订号变了：新的纪元和新的条目名（被摘要的内容中加入 `linked <修订号>`），kardia-loader 对此的处理是释放旧的 fiber 并启动新的插件，模块也重新编译。已安装包的名字不包含修订号，所以保持不变。
- **什么会进入设置。** 组更新不写回任何东西，故障、重启或启动失败都不改变配置；只有加载器自己的写回（自行释放的插件）会以 `enabled = false` 进入 `[plugins]`。访客的环境仍带有执行器的最终覆盖（代理变量），这是宿主为每个子进程设置的。

## 其他细节 [#other-details]

### 实例、槽位与启动 [#instance-and-start]

- **运行时。** 每个 Agent 实例的 `ContainedRuntime` 有 2 到 4 个工作线程（机器的并行度，限制在这个范围内）和最多 128 个阻塞线程，都命名为 `agent-rt`（`AGENT_RUNTIME_THREAD_NAME`）并标记为被隔离。槽位保存它（`AgentSlot::take_runtime` 把它交给停止流程），实例停止时最后用 `ContainedRuntime::shutdown` 结束它，这是硬停止，丢弃实例仍在运行的一切（从未返回的插件 `apply`、等待它的释放），不触及宿主。Agent 的 `BlockingOperationPort` 是 `ContainedRuntime::blocking_port`。
- **每个实例的 sink。** 每个实例通过绑定其代次的 sink 向槽位报告：内核故障经 `AgentSlot::fault_sink(generation)`，历史拒绝经 `AgentSlot::refusal_sink`（`AgentInstanceInputs::history_refusals`）。过时实例的报告被忽略，启动期间的故障让那次启动失败。已隔离的会话（启动时恢复跳过的，或之后被拒绝的）只加入状态一次并通知。状态中的 `generation` 计算本次运行中已领取的启动次数；`degraded` 由插件状态推导。
- **内核故障**来自轮次的任务（`execute_admitted_turn` 在循环外围捕获 panic，托管轮次任务的 `JoinError` 也会检查；sink 通过 `AgentService::without_default_model_reporting_faults` 注入内核）、宿主的命令守卫、Agent 工作线程组的成员（`BackgroundWorkerGroup::contained_with_panic_handler`：历史写入线程、记忆监督线程、MCP stdio 读取线程；以 `worker <name>` 报告），以及宿主和服务自己的任务（`spawn_kernel_task`：插件故障跟随任务、重新挂载、设置的后续处理、MCP 启动）。槽位把 Agent 标为 `Faulted`，在它的监督线程（`agent-supervisor`）上停止它，并对 10 分钟内的前三次故障分别在 2 秒、10 秒、30 秒后启动下一个实例（`AUTOMATIC_RESTART_DELAYS`、`AUTOMATIC_RESTART_WINDOW`）；此后它保持 `Faulted`，没有 `nextRestartAt`，直到用户重启，重启会清空这个窗口。
- **状态转换。** `AgentSlot::restart(AgentStartOptions { safe_mode, rebuild_history_index })` 在 Agent 启动中、宿主关闭中和宿主关闭了 Agent 时（带 `setting` 的 `Disabled`）被拒绝，但会启动因崩溃循环而停止的 Agent；`enable` 和 `turn_off`（先 `disable`，再有界等待）是宿主的打开与关闭。每个转换都交给监督线程安排。重启用关闭的步骤和预算停止实例（`stop_instance`），清扫它的进程所有者组，停止它的运行时，重置崩溃循环标记（用户的重启时），然后重新启动。安全模式让该实例中核心以外的行都不挂载（`AgentHostOptions::safe_mode`；`disabledPlugins` 不变）。`disable` 取消正在进行的启动，留下带 `setting` 的 `Disabled`。Skill 监视器在每个新实例的根目录上重新开始。
- **失去 Agent 的调用。** `AgentSlot::interrupted(generation, command)` 为 Agent 已不再运行的调用给出错误："the Agent was turned off; `<command>` did not finish"、"the Agent stopped after an internal error; `<command>` did not finish"（故障且没有安排重启），否则 "the Agent restarted; `<command>` did not finish"。
- **启动。** `DesktopAgent::start` 加上 Agent 自己的 `ExecutorManager`（基于构建 `DesktopAgent` 时给的子进程环境）和 Skill 监视器，把它们交给槽位供以后每个实例使用，并启动第一个实例。启动（`startup`）领取一个代次，构建运行时和进程所有者组（`ProcessOwnerGroup::recorded_in`），每次运行取一次数据目录锁，记录一次崩溃循环尝试，回收上一次运行留下的进程组（`ProcessGroupRecord::reap_leftovers`），在阻塞池上构造服务（`AgentConstructor` 得到运行时和实例的 `AgentInstanceInputs`，其中的 Executor 已限定在所有者组内），在那里运行 `recover`（它也结算上一个进程留下的仍在运行的执行活动），启动插件，安排 MCP 连接，并把服务装为 `Running`；随后 Skill 监视器在实例的根目录上启动。任一阶段失败都以 error 级别记录，让槽位进入 `Failed` 并清除这次尝试。
- **会让构造失败的：** 设置（I/O 错误）、工作区根目录端口和工作区策略、网络端口的代理、MCP 设置文件（只有 I/O 错误；它会自我修复）和无效的 MCP 代理策略、历史存储的布局或索引，以及记忆存储。构造中途失败时会停止它已经启动的工作线程组。不会让构造失败的：无法打开的 Skill 目录（每个 Skill 命令返回原因，`skills` 插件以此失败）、没有连上的必需 MCP 服务器（体现在它的 MCP 状态 `Failed`，以 error 级别记录；启动在报告前会尝试每一台服务器）、配置无法推导的 `web` 行（那一行的错误）。
- **取消启动。** `AgentSlot::close`（关闭时）和 `disable` 取消启动的令牌。构造和恢复是阻塞的，无法取消，所以启动在阶段之间检查令牌；插件的启动在原处被取消。已构建却不会运行的 Agent（恢复或启动失败，或在此期间启动被取消、槽位被关闭）先被退役：轮次、MCP（取消后台连接，释放它们的进程）、插件和工作线程按关闭顺序在 `RETIRE_BOUND`（5 秒）内停止，这比关闭等待启动的时间（`START_WAIT`，8 秒）短，所以它的运行时只在拆除完成之后才停止。这时仍阻塞在构造或恢复中的启动还没有启动任何插件、连接或进程，所以运行时的硬停止只留下它分离的阻塞线程。

### 插件宿主 [#plugin-host-details]

- **挂载。** `AgentHost` 自己不创建注册表：组合创建 `AgentKernelRegistries`，用它们构造内核（这样 `titles` 插件的 `AgentTitleApplication` 才能持有内核），再交给宿主。在 `PLUGIN_START_TIMEOUT` 内没有就绪的行以 "did not start within 20 s" 失败，它的 fiber 在后台释放，下一行接着挂载。每个模型操作（轮次、计划实施、压缩）在宿主尚未启动时启动它；内核从注册表快照做计划，从不等待宿主。宿主任务（故障跟随任务、重新挂载）中的 panic 是 `plugin host` 处的内核故障。
- **每个注册表都用内核唯一的 `PluginFaults` 构建**（`AgentKernelRegistries::faults`，也由内核插件发布），每个条目都持有它。自己组合条目的注册表对每个条目分别加守卫：`ObserverRegistry::notify`、`ApprovalRuleSnapshot::verdict`、`PromptContributorSnapshot::fragments`。`ExtensionPoint` 转换为故障的 `FaultPoint`。最多可以注册 64 个继续钩子（`MAXIMUM_CONTINUATION_HOOKS`）。
- **应用设置。** 宿主保存设置后，`AgentSlot::apply_saved_settings` 在运行中的 Agent 的运行时上安排 `apply_settings_to_plugins`；Agent 自己的设置写入（`write_settings`、`set_plugin_enabled`）在写完后调用它。两者都不等待。宿主在它的插件锁下读取最新的设置，所以两次快速保存中后一次生效；释放 `disabledPlugins` 新列入的行；在先前的 fiber 停止后，用当前配置挂载不再列入的行；只在由设置派生的行的配置变化时调用 `Fiber::update`。它不等待这些转换完成，每个结果都记入日志。尚未挂载的行在挂载时采用新的配置和启用状态。
- **设置 API。** `settings_view` 返回一个 `AgentSettingsView`：设置和它们的默认值；它们的描述在[设置目录](/docs/architecture#settings-catalog)中。`write_settings` 接受一个 `AgentSettingsPatch`（权限模式、记忆、Web 搜索服务、`searxngBaseUrl`（`null` 清除它，缺少这个键则保持不变）、`webFetchUseJinaReader` 和 `webFetchResolveThroughProxy`），这是拒绝未知字段的 IPC 请求，其中没有 `disabledPlugins`，它由 `set_plugin_enabled` 单独写入文件，按键写入（`write_setting_values`）也可以写它。它要么整体应用补丁，要么完全不应用，然后让插件跟上新设置，并发出记忆扫描信号。Provider 注册表只能通过 `AgentConfig::mutate_providers` 并带上调用方预期的修订号来修改。
- **MCP 代理的后续处理**作为单独的任务运行：它在 MCP 配置闸门下读取最新的设置，代理策略变化时并发地重连已启用的 Streamable HTTP 服务器，所以挂起的重连既不占住命令，也不挡住之后的变化，后者在它之后应用。
- **上限。** 重新启用的行只等待先前的 fiber `PLUGIN_STOP_BOUND`（10 秒），之后以 "its previous instance has not stopped yet" 失败，直到拆除结束后的一次重试。
- **启用与状态。** 核心行忽略 `disabledPlugins`；没有任何行使用的名字保留并忽略。`set_plugin_enabled` 拒绝未知名字和核心名字，在阻塞边界上通过 `AgentConfig::set_plugin_disabled` 写入，由文件锁串行化。启动完成后，宿主把每个已启用但不是 `Active` 的插件记入日志。状态中的 `contributions` 从每个内核注册表的一份快照中按条目所有者读取：工具名、工具源 ID、上下文贡献者及其类型、轮次准入与提示贡献者 ID、审批规则 ID 和观察者 ID。`restart` 是待进行的自动重启，或窗口已计入的次数。
- **插件事件 sink。** 宿主在以下时刻通知它的 `AgentPluginEventSink`：启动完成时，某行被启用、禁用、重试或重新配置时，这样的转换完成时，被禁用的行拆除完毕时（这时它的注册才真正移除），以及插件的问题出现、变化或消失时（`PluginFaults::set_issues_listener`，所以每个轮次都以同样方式失败的贡献者不会再重复通知）。

### 会话与轮次 [#turn-details]

- **配置。** `normalize_session_config` 在创建、每次更新和恢复时运行：协议不是 Responses 时远程压缩被去掉（`ModelApiProtocol::supports_remote_compaction`），会话尚未配置时推理强度和远程压缩被去掉，都给出警告（每种协议都携带推理强度）；为零的上下文窗口变为未知；自动压缩阈值和流重试策略被限制在范围内。恢复会重新规范化较旧的会话，而不是隔离它；身份（Provider ID、模型）和完整性检查保持严格。会话的压缩策略，以及它的传输携带的压缩能力，在每次激活时于会话空闲时与设置对齐，提交时不产生新的修订号：快照不显示它们，所以调用方在操作前读到的修订号仍然有效。在压缩策略出现之前写入的配置，或带有本版本不认识的策略的配置，读作 `standard`。
- **恢复**（`service/recovery/`：校验、持久化的记录、`repair.rs` 中的重启修复）。校验拒绝持久化了某个内核之后会递增、且大于 `u64::MAX / 2` 的计数器的会话（修订号、代次、消息、历史条目、轮次、压缩和活动的 ID，steering 序号，模型会话代次，记忆贡献和历史条目的修订号；`validation/counters.rs`），所以内核的 `checked_add(1)` 预期是不变量。`load_recovery_candidates` 分别加载每个候选，并把历史存储打开时拒绝的会话作为失败返回，无论它们的恢复状态如何；`recover_sessions` 把每个跳过的会话以 error 级别记入日志后，返回一个 `AgentRecoveryReport`（恢复的数量，以及带原因的 `AgentQuarantinedSession`）。打开已隔离的会话会以它未解决的恢复义务或存储给出的原因失败，直到之后的某次启动恢复了它。记忆来源投影略去运行时无法解码的会话。只有读取历史索引失败才会让恢复失败。
- **ID。** 轮次和压缩的 ID 来自原子计数器。
- **步骤无法运行的调用**（`service/tool_execution/rejection.rs`、`CallDisposition`）：调用了步骤没有提供的名字时，历史把这个调用记在 `unavailable` 提供者和工具 ID 下。超过 `maximum_tool_argument_bytes`（64 KiB）的参数以 `{}` 代替模型发送的内容保存（[模型工具参数](/docs/plugin-rules#model-tool-arguments)）。
- **`tool_search` 的选择。** `ConversationItem::ToolSelection`（`call_id`、选中的 `AgentToolSelection`）不是模型输入：在不支持原生搜索的提供者上，选中的工具在计划中变为 `Direct`；在支持的提供者上，回放的搜索输出会显示它们。工具已不存在或代次已变化的选择不匹配任何东西；这种条目出现之前的历史里自然没有它。
- **轮次限制**给用户看的文字是："agent turn stopped at its time limit of 30 minutes; send a message to continue"（`TurnDeadlineExceeded`），以及 "the conversation is still too long for the model's context window after it was compacted; start a new conversation or attach less context"（`ContextWindowExceededAfterCompaction`）。
- **世界状态。** 世界状态最多有 12 个段（`MAXIMUM_AGENT_WORLD_STATE_SECTIONS`：每种已知类型一个，共 5 个，加上 7 个插件类型）；一次持久化的更新最多可以提到它的两倍，即每种类型一次替换和一次删除。指令不是世界状态：会话配置的指令（默认是基础指令加上宿主的 `AgentHostInstructions`），计划模式下再加上内核的 `plan.md`。
- **内核负责包装的上下文条目。** 内核包装那些属于历史而不是段的上下文条目：压缩后窗口的初始上下文、任务清单和选中 Skill 的指令（`SkillContext`）。模型 API 只包装它自己的条目：继续上下文、压缩摘要和远程压缩条目。
- **宿主上下文。** 恢复时，持久化的 steering 被限制在 `MAXIMUM_HOST_CONTEXT_BYTES`（4 KiB）之内。在宿主上下文还没有类型时记录的 steering（作为 `applicationContext`）读回时不带上下文。
- **压缩。** 独立的压缩在任何采样步骤之外，构建下一个请求本应有的工具计划和提示，但不做任何准备，所以它的请求没有记忆上下文（`PromptRequest::prepared` 为 `None`）。
- **后台压缩**（`service/compaction/background/`）。槽位（`SessionRuntime.background_compaction`）保存上次尝试的输入（窗口、当前轮次之前的条目数、模型、实现），相同的输入不会再次启动，所以失败的运行要等另一个轮次完成后才会重试；还保存它的运行，通过 `Arc` 共享：回滚的提交会恢复记录的运行时状态，但结果（运行中、带着计划和样本就绪、正在安装、带着结果已安装、或已用掉）在运行里，任务不持有记录的锁写入它，然后推进 `terminal`。取走结果的检查点把它标为正在安装，结束时标为已安装或已用掉，并推进 `terminal`；正在等待的 `/compact` 发现结果已被期间接纳的轮次安装时，返回那次安装的结果，而不用它读到的修订号去压缩。任务在释放记录的锁之前登记到服务的 `managed_background` 集合，所以 `stop_operations` 要么看到要取消的槽位，要么启动看到服务已停止接受；关闭等待整个集合，归档和删除等待会话自己的条目（5 秒）。计划像轮次前压缩的计划一样构建，使用步骤的模型、工具计划和提示，不在 `runtime.compaction` 中预留任何东西，检查自己的取消令牌。它带着样本结束时，用量提交到会话的用量中（不是修订号，并保留 `context_consumed_tokens`），所以安装不再添加。
- **变基安装**（`InstallMode::Rebase`）代替比较并交换：没有压缩在运行，窗口是快照的窗口，历史以快照的条目 ID（启动时的全部历史）开头。安装的历史是：未压缩部分开始处的世界状态（边界之前历史的 `full_world_state_checkpoint`：之后的更新，包括删除，仍按顺序适用；计划把这个边界 `source_boundary` 与压缩读到的条目分开保存，因为有活动压缩块的会话读到的是投影后的历史，条目更少），替换内容，然后是从启动时当前轮次的 `TurnStart` 开始的历史，保留原来的 ID，就像轮次前安装保留当前轮次一样（在同样的检查点之后：该轮次开始处的世界状态）。检查点的截止点仍是展示摘要的 ID，所以每个替换 ID 都不大于它，恢复和分叉像对待任何压缩一样重放它；因此在它之后条目 ID 不再按历史顺序排列。安装记录阶段为 `background` 的 `Completed` 快照（触发 `automatic`，原因 `context_limit`，启动轮次的代号）及其事件，不计入任何轮次的预算，并用采用它的步骤的工具计划和提示估算下一个请求：在这里仍超过阈值不是错误，调用方会再在线压缩。没有减少上下文的结果和其他压缩一样被拒绝。
- **上下文窗口。** 再次选择模型会重新解析它的窗口，并把已记录的用量移到新窗口上。
- **继续钩子。** 因插件停止而被取消的钩子以 `IgnoredFailure` 完成。
- **观察者。** `TurnAdmitted` 带有轮次的来源（`User` 或 `Programmatic`）和准入时提交的临时标题；`MemoryContributionChanged` 带有原因（`Initial`、`User` 或 `Polluted`）。`start_turn` 和计划实施是 `Programmatic` 的。
- **子会话**（`service/session/child.rs`）。子会话沿用父会话的模型、配置、预算策略和工作区，它的范围再按请求的范围收窄；请求指定了角色时，它的角色指令是请求中的（它们不来自父会话，所以按会话的界限检查）；从父会话头部开始的子会话还沿用它的标题，所以 `titles` 插件不会给它起标题；它的记忆贡献从默认值开始。持久子会话作为头部分叉（`create_fork_at_head`）或运行中轮次之前的分叉（`create_fork`）持久化，空的子会话作为新会话持久化。历史以轮次开始，所以上下文只能跟在继承来的历史之后：会以空历史开始却带有上下文的子会话会被拒绝（`InvalidInput`），不是继续上下文的上下文也一样。临时会话的临时子会话从最近的持久祖先读取图片。持久子会话像分叉一样初始化记忆贡献，临时子会话从不初始化。
- **临时会话。** `close_ephemeral_session` 取消会话的轮次或压缩，中止它待处理的审批，最多等待 5 秒让它结算，然后移除单元、它的事件接收器和内存中的历史；到时仍未结算的轮次会因会话不存在而失败。归档或恢复临时会话会被拒绝（`InvalidInput`）。内存存储像持久存储一样对记录分页（降序时最新的在前，游标是下标），并按轮次 ID 过滤轮次页，但不保留修订号：一页总是会话最新的状态。
- **旁路对话的条目**是两个 `ContinuationContext` 条目，provider 为 `agent`，钩子分别是 `side-conversation`（策略，包在 `<side_conversation>` 标记中）和 `side-conversation-boundary`（边界），代次为 1（`crates/agent/src/side_conversation.rs`，移植自 Codex 的 `context-fragments/src/side_conversation.rs`）。外观层在一道闸门下从内核存活的临时子会话（`ephemeral_children`）中找父会话的旁路对话，所以同时打开两次也只会得到一个。

### 思考 [#thinking-details]

[思考](/docs/architecture#thinking)之外的细节：

- 内核的 `AgentReasoningId` 取自会话的消息计数器（`service/sampling/stream/reasoning.rs`）。
- 新的摘要部分随分隔它的空行一起到达。保留的文本是已完成条目的摘要（有的话），否则是原始文本，两者都优先取已完成条目中携带的内容，没有则取流出的内容；已完成条目比已显示内容多出的文本，在完成之前显示出来。
- 只有推理的响应仍然不提交任何东西。
- 要回传的推理块作为 `replay` 附在它的 `ConversationItem::Reasoning` 上，不计入历史的字节数。Anthropic 的思考块（`Thinking`、`RedactedThinking`）只在内存中：从不持久化，不出现在快照中。步骤的请求把本轮（最后一个 `TurnStart` 之后）的思考块作为 `ModelInputItem::Reasoning` 放入，只有使用思考预算的 Anthropic Messages 会发送它们；压缩的请求不带它们。
- Chat Completions 的 `reasoning_content`（`ReasoningContent`）超出它的轮次（`ModelReasoningReplay::outlives_its_turn`，由 `ConversationItem::reasoning_input` 读取）：每个请求都从投影后历史的每一轮放入它，压缩的请求也一样；只有 Chat Completions 发送它，Responses 两种都略去。它随条目持久化，形如 `"replay": {"type": "reasoning_content", "text": "…"}`，没有时不写这个字段；无法解码、属于其他种类或超过 1 MiB 的 `replay` 读作没有，从不让条目失败。转录页（`AgentTranscriptPage`，`sessions show --json` 输出的就是它）略去它，就像略去 `modelText`。分叉或子会话复制条目，文本也随之复制，因为它们延续这段对话。条目的 token 估算（`estimate_conversation_items_tokens`：流的输出估算、压缩的计数、`hierarchical` 的后备）计入它的字节；请求的估算本来就计入，因为它序列化整个请求。
- 计时快照（`ReasoningUpdated`、`AgentReasoningSnapshot`）保存在条目旁边，供状态显示和恢复使用。

### 标题 [#titles]

- 门面的提交把轮次标为 `User`，对没有标题的会话，把提交的文本折成一行、截到 36 个字符，作为内核的 `AgentTurnInput::provisional_title` 传入。如果会话仍然没有标题，准入就把它随轮次一起提交（`session_title_updated` 在 `turn_started` 和 `history_committed` 之后）。来源和临时标题都不随轮次持久化。
- `titles` 插件的观察者把每个提交了临时标题的 `User` 轮次的 `TurnAdmitted` 排入有界队列（`try_send`）。它的工作线程（`spawn_scoped_worker`，一次处理一个标题，随插件停止）通过 `BlockingService` 上的 `AgentTitleApplication` 读取轮次的用户消息（`AgentService::turn_user_message`）和当前设置中该会话的 Provider，让一个私有的模型会话生成标题（提示截到 960 字节，30 秒），并用 `replace_automatic_session_title_if_expected` 提交，这是对临时标题的比较并交换，所以期间的重命名优先。插件关闭时临时标题保留。
- 这个请求是共用的结构化请求（`plugins/structured_request.rs`）：提供者支持时用 JSON schema 输出（`ModelStructuredOutputCapability::NativeJsonSchema`），否则强制调用一个以该对象为参数的工具；有时间上限，随插件停止而取消。概要和标题建议也使用它。
- 标题建议（`suggest_session_title`）通过 `AgentConversationReader` 读取会话最近 8 条用户和助手消息（从记录中由新到旧），每条截到 960 字节的平均份额，不提交任何东西。
- 概要（`recap_session`，`recap` 插件）以同样的方式读取最近 8 次有回答的往来（引导并入它的请求，保留一个更新的未回答请求，不含工具输出和推理），提示在估算 8192 个 token 以内（先省略最旧的往来，再把每段文本摘录为保留首尾），返回 `AgentRecap { summary, next_action }`（60 秒）。回答被宽容地读取：忽略未知字段，缺少 `next_action` 即为空，超过 700 个字符的摘要或超过 200 个字符的下一步会被截断。

### 存储布局 [#storage-layout]

[数据目录](/docs/data-directory#contents)之外的细节：

- `history/active/YYYY/MM/DD/session-<YYYY-MM-DD>T<HH-MM-SS>-<id>.jsonl`（创建时的本地时间）、`history/archived/`、`history/attachments/<id>/blobs/<sha256>.blob`、`history/attachments/<id>/exports/`（会话的导出文件，`decompress` 的 `toFile`）、`history/trash/` 和 `history/index.sqlite3`。分叉通过谱系表共享父会话的前缀。索引的模式版本是 6：5 为会话列表的父会话过滤增加了 `agent_sessions.parent_session_id`（带索引），6 增加了分层压缩链的 `agent_compression_links`；其他版本的索引（包括更旧的）在打开时被丢弃，并从 rollout 重建一次。
- `memory/memory.sqlite3`、`memory/ad-hoc-notes.jsonl`（模型留下的笔记）、`memory/artifacts/`（发布的制品，包括 `MEMORY.md` 和 `memory_summary.md`）、`memory/staging/` 和 `memory/reset-trash/`。

### 记忆存储 [#memory-store]

[记忆](/docs/memory#how)之外的细节：

- **一轮处理**按从新到旧分页浏览空闲的历史会话（`AgentMemoryHistoryQuery::older_than`，每页 100 个，每轮最多 1000 个），最多领取 `maxSessionsPerPass` 个。会话能否被提取（参与贡献、有尚未提取的修订、没有退避、没有租约）由记忆存储决定，所以已经提取过的较新会话从不让较旧的会话一直等待。
- **阶段一的证据预算**是提取模型的上下文窗口（按会话会得到的方式解析：`AgentService::model_context_window`，即配置的值，否则[模型元数据](/docs/architecture#model-metadata)中的值，否则 160K）的 70%，最多 120K token。
- **退避**从 30 秒翻倍到一天：阶段一按来源（`memory_sources.retry_count`、`next_retry_at`），阶段二全局（`memory_meta.global_retry_count`、`global_next_retry_at`）；成功或重置会清除它。引用用量的变化如果移动了正在进行的整合的排名截止点，会让那次发布因过时而失败，由退避重试。
- **发布**先暂存并校验制品（`MEMORY.md` 最多 128 KiB，`memory_summary.md` 最多 16 KiB 且以 `v1` 行开头），提交数据库（新代次这时就是已发布的代次），然后才换入制品。提交之后的崩溃或重命名失败会把它们留在 `staging/generation-<n>` 中，下次打开或下次整合领取时，在任何东西把制品读作基线之前安装它们。
- **打开时**就地迁移版本 4 的数据库（它缺少阶段二的退避；丢弃路径还会删除已发布的制品）。只有当数据库不是数据库、已损坏（`SQLITE_CORRUPT`、`SQLITE_NOTADB`）或是其他 schema 时，才连同派生的制品一起丢弃它；繁忙、被锁或 I/O 失败会让打开失败，于是 Agent 的构造带着原因失败，由重启再试。每个连接最多等待 5 秒获得锁（`busy_timeout`），与历史索引的连接相同。schema 版本是 5。`memory reset` 是用户触发的唯一丢弃。
- **容错。** 笔记日志跳过无法读取的行（按行号记录，从不记录内容）；超过 64 MiB 的日志仍是 `Corrupt`。阶段一的输出忽略 schema 没有列出的字段：`hasMemory: false` 是表示什么都不做的开关，优先于多余的字段；否则缺失的文本为空，过长的文本按字符边界截断，NUL 被去掉，不合格的 `rolloutSlug` 被改写为小写 kebab-case（什么都不剩时为 `memory`）；只有根本不是提取对象的输出才让任务失败。存储不认识的贡献模式读作 `disabled`。
- **贡献模式**只有一个类型 `hanafubuki_agent_foundation::agent_settings::AgentMemoryContributionMode`（默认 `Disabled`），内核随会话持久化它，存储按来源保存它，契约和记忆 crate 重新导出它。
- **信号。** `memory` 插件的观察者在轮次结束时发出扫描信号（所以一轮处理从不与正在进行的轮次争用模型），在回答提交后把引用用量排入队列，记录已提交的贡献变化（用户切换时以及会话停止贡献时发出扫描信号；开始贡献的新会话或分叉会话由之后的扫描处理），并在会话归档或恢复时发出扫描信号。记忆自己的操作（启动、笔记、重置、撤销会话）和设置变化直接发出扫描信号。

### MCP 连接、目录与输出 [#mcp-details]

[MCP](/docs/architecture#mcp) 和[外部生产者](/docs/plugin-rules#external-producers-mcp-servers-skills-web-memory)之外的细节：

- **启动。** Agent 的启动在后台连接已启用的服务器（`service/mcp/startup.rs`），同时最多 4 个（`MCP_CONNECT_CONCURRENCY`），每个受它自己的连接和初始化超时限制，所以 Agent 在它们连上之前就已 `Running`；挂起的服务器最终以 "MCP operation timed out" 进入 `failed`。每次连接都观察 MCP 的生命周期令牌，关闭时最先取消它，被取消的连接会释放它创建的进程。
- **关闭连接。** `McpManager::shutdown(deadline)` 关闭每个连接，每个在它的 `shutdown_timeout` 之内，全部在期限之前；没有确认关闭的连接保持退役，带着它的清理义务（状态中的 `cleanup_pending`）。服务器一侧已结束的连接被退役，在没有步骤持有它之后，凭回执释放它的进程。
- **重连。** 每台服务器一个重启窗口（`McpManager::with_reconnect_policy`）；状态带有 `reconnect`（下一次尝试，用完后为空）。如果外部的连接、刷新或断开先到一步，重连就不再开始；关闭开始之后才完成的重连会释放它的进程，而不是装上它。stdio 服务器的原因会说明它是怎么结束的（`the MCP server process exited with code 3`）。
- **panic。** 工具调用的客户端路径中的 panic 让这次调用得到 "the tool failed with an internal error"，`McpManager::fail_after_panic` 退役该连接并像上面一样重连服务器（以 "the MCP client panicked during a tool call: `<message>`" 进入 `failed`，诊断代码 `tool_call_panicked`）。
- **身份。** 工具的代次是服务器配置、其凭据代次以及工具自己的目录条目和策略的摘要。未改变的服务器重连后它不变，所以会话对该工具的 `AllowForSession` 在重连后依然有效；改变服务器的设置、凭据的 `generation` 或工具本身，才会重新询问。
- **目录。** 从分页的 `tools/list` 结果逐个工具构建。被跳过的工具（无效或过大的 schema、无法编码的名字、清理后重复的名字，例如 `my.tool` 变成 `my_tool`）是一个 `McpCatalogIssue`，作为警告记录，带工具名（每次列表最多 16 个），并附一条 `tool_discovery_partial` 摘要。每台服务器 2048 个工具的上限保持严格，计入无法解码的条目，只检查一次；`nextCursor: ""` 结束分页；超过 4 MiB 的页或过大的游标是错误。调用按原始的远程名字发出。
- **列表与读取。** `tools/list`、两种资源列表和 `resources/read` 都通过 `Peer::send_request` 请求（`listing.rs`、`request::read_resource`），所以 rmcp 的类型化结构拒绝的结果以 `ServerResult::CustomResult` 到达，并逐个条目解码：无法解码的工具是 `tool_skipped_undecodable` 目录问题；无法解码的资源或模板被略去，并记一条 `resource_skipped_undecodable` 或 `resource_template_skipped_undecodable` 警告（每次列表最多 16 条），计入 `resource_discovery_partial`；无法解码的读取条目是文本 `[unsupported MCP content: resource]`。这些请求绕过 rmcp 的响应缓存。
- **输出。** 带参数的 MIME 类型存为它的基本类型，接受没有填充的 base64，两者都以规范形式保存（`canonical_media_type`、`canonical_base64`）。

### 执行与文件 [#execution-files]

- `exec_command` 通过预留的 Executor 进程运行；`execution` 插件的活动监视器作为执行的观察者挂上，释放已结束的执行时会有界地等待，直到监视器报告了最终的输出和状态。活动预览只提交以换行结尾的行，未完成的行临时显示。结果是纯文本：管道的输出经过 `render_plain_text`，PTY 的输出经过每个执行各自的 `TerminalScreen`（`vt100`），轮询一个、监视器一个；它分片喂入输出，并在回滚缓冲可能丢掉一行之前把屏幕状态重放到一个新的解析器中。一次轮询读取它尚未读取的全部输出（`output_window`）：在上限之内就全部返回，否则返回在换行处截断的开头和结尾，中间是 `[… N bytes omitted …]`；一个会话保留 4 MiB（`EXEC_RETAINED_OUTPUT_BYTES`），从缓冲已不再保留的位置开始的读取会从它保留的第一个换行之后开始（`resume_point`），跳过的字节计入标记。通用的 argv `start` 只在 `test-support` 下存在。
- 一个执行只由一个调用方释放：`dispose` 先认领它，对其他所有调用方而言，已被认领或已释放的执行就是不存在（`NotFound`），即使它们之前已取得其回执。因此被后台终端的停止抢先的模型等待以 `NotFound` 结束，或在等待先看到时以停止造成的终止结果结束，而不会是进程错误或清理错误。释放失败会放弃认领并保留该执行（仍欠清理），以便重试。
- `WorkspaceFsService` 把每个请求解析为策略根目录内不可变的计划，在 I/O 之前重新校验，并原子地写入；`preview_patch` 是纯函数。`WorkspaceRootsPort::protected_roots` 指定的目录是策略的受保护根目录：每个文件工具，包括读取，都拒绝其下的路径（"direct filesystem tools cannot access application-owned path …"，`ProtectedPath`）。

### 关闭 [#shutdown-details]

[关闭的各阶段](/docs/embedding#start-on-and-off-shutdown)之外的细节：

- 每个阶段在它自己的期限或预算结束时（以先到者为准）结束，错过期限的阶段会被报告，同时下一个阶段开始。只有 `Running` 的 Agent 才经历关闭槽位之后的各阶段。
- 最坏情况也在 20 秒之内：正在进行的启动最多 8 秒，加上运行时的 2 秒；运行中的 Agent 最多 5 + 4 + 5 + 3 + 1 + 2 = 20 秒。Skill 监视器的线程通常立即结束；卡在目录失效处理中的线程从剩余时间中最多占用它的 2 秒。
- MCP 和插件阶段在 Agent 的运行时上运行，用 `ContainedRuntime::block_on_until` 等待，这种等待不依赖运行时能否推进，所以工作线程全部阻塞的运行时也挡不住退出。
- 之后是宿主自己的拆除（Hanafubuki 随后停止它的展示分发器，有自己 2 秒的期限）。

### 终端界面 [#tui-details]

[终端界面的移植改动](/docs/architecture#what-the-port-of-the-terminal-interface-changed)之外的细节：

- **思考。** 桥把 `ReasoningStarted`、`ReasoningDelta` 和 `ReasoningCompleted` 映射到思考单元格（`history_cell/thinking.rs`），每个推理条目一个。它和工具调用一样是一个实时条目（`LiveCell`，`history_cell/live.rs`）：聊天组件和转录共享它，每次变化都提高它的修订号，转录视图按条目的修订号、宽度和呈现方式缓存它的布局。它从开始起就在对话中并在原处就地更新，收到 `ReasoningCompleted` 时带上内核的 `durationMillis`；在 Scrollback 中它位于尾部（`app/scrollback.rs`），完成（`LiveEntryCompleted`）并离开尾部时按显示的样子写入回滚区。轮次结束时，仍在进行的单元格以到那时为止的时间完成，因为在流中途失败的轮次不发送完成事件。没有更新排在流式输出的消息后面：会添加条目的更新先提交消息到那时为止的各行，两种呈现方式都是如此，Scrollback 的尾部按顺序写出它的条目。它的活动 ID 是 `thinking:{推理 ID}`，回放的条目为 `thinking:h{历史条目 ID}`，并且只在收到文本后才有：展开状态属于转录视图，只在本次运行内有效，从不持久化，所以 ID 只需从进行中保持到完成，而这在同一个条目中自然成立。折叠时它是标题行；展开时（`expanded_lines`）后面跟着文本。Ctrl-O 请求应用（`AppCommand::ToggleThinking`）在转录视图中展开它所显示的单元格（Fullscreen 的对话、Scrollback 的尾部）里的每一个 `thinking:` ID，全部已展开时则全部折叠；正在阅读的位置保持视图顶部的条目不动。进行中标题的刷新间隔是 100 ms，工具调用旋转图标的是 600 ms。桥把 `ReasoningUpdated` 的 `AgentReasoningSnapshot` 转给状态行，状态行显示本轮的 `turn_completed_millis`，条目进行中时再加上自 `active_since` 起的时间（纪元毫秒，收到时换算到单调时钟一次）；回答前的分隔线取同一个总数。转录分页器绘制每个单元格的 `transcript_lines`，对思考单元格来说其中总是包含文本；恢复时的回放把 `ConversationItem::Reasoning` 映射为已完成的单元格。实时显示的是流出的文本：在少见的同时流出摘要和原始文本的条目中，提交的条目保留摘要，恢复的会话显示的是摘要。
- **展开与折叠。** 还有更多内容可显示的条目有一个活动 id（`HistoryCell::activity_ids`）和一个控件：`tool:{call id}`、`thinking:…`，以及本身没有标识的条目在每次运行中依次取得的编号，任务计划为 `plan:{n}`，你的消息为 `user:{n}`（`next_activity_id`）。单元格说明它的详情增加了什么（`activity_disclosure`，按宽度）：带说明或超过三个步骤的计划（紧凑行是三个步骤，进行中的在前），换行后超过 12 行的消息（紧凑时为前 12 行）。转录视图保存已展开的 id，在 Fullscreen 中、Scrollback 的尾部和 Ctrl-T 对话记录中都是如此。按下控件即切换。按下条目的标题行（`TextLayout::header_row`，第一行有文字的行）时记下条目的 id，松开时如果在同一个格子上、且该格子仍显示同一条目的标题行，才切换，所以变成拖动的按下会进行选择；Fullscreen 下按下也会开始选择，只有松开后没有选中文本时才切换，并结束多击计数，所以紧接着的第二次点击会再切换回来。Scrollback 的尾部除了按下也转发松开（尾部不做选择），Ctrl-T 对话记录接收 Ctrl-O（`toggle_thinking`）。
- **会话。** 界面通过桥打开每个会话（`AgentBridge::open`，基于 `open_session`）：新会话、`resume` 指定的会话、最近的会话，或在恢复选择器中选中的会话。最新的转录条目在头部之后读回，作为聊天回放的内容（`agent_bridge/replay.rs`：消息、思考、计划、工具调用及其输出，以及从已提交条目读出的 `apply_patch` diff）。`/new` 和 `/resume` 切换桥的会话，离开的会话的事件被忽略。
- **命令**在 `agent_bridge/commands.rs` 中映射到门面：`/new` 对应 `create_session`；`/resume` 对应 `list_sessions_page`（按标题搜索、按游标分页，选择器滚动时在循环上读取）；`/compact` 对应 `compact_session_with_sink`；`/model` 对应 `list_provider_models` 和 `set_session_model`；`/mode` 对应 `set_session_mode`；`/status` 对应 `settings_view`、`provider_registry_snapshot` 和 `workspace_roots`；`/skills` 对应 `list_skills`。设置中心只通过 `write_setting_values` 和 `run_settings_action` 写入（`agent_bridge/catalog.rs`），`/raw` 以及主题、状态栏和标题页面也是（`write_tui_settings`）；没有 spec 的按键映射和预设用 `write_tui_preferences` 写入 `[tui]`。作为页面的浏览器也通过目录写入：插件浏览器（`agent_bridge/plugins.rs`）执行 `packages`、`marketplaces`、`plugins` 和 `hooks` 集合的动作，并按键写入选项，但授予代码插件的权限（`grant_package_permissions`，针对它所显示内容的同意）和没有 `configSchema` 的代码插件的原始 JSON 设置（`set_package_settings`）除外；钩子浏览器执行 `hooks` 集合的 `save` 和 `trust`（`agent_bridge/hooks.rs`）。记忆存储页面保留会话的参与设置和重置。页面保存的内容除了写入对话记录，也会在设置中心中显示。需要读取动作不返回的内容的页面各有一个模块：Provider 的模型页面对应 `list_provider_models`（`agent_bridge/providers.rs`），它的选择是设置中心执行的一次模型策略保存；`/mcp verbose` 对应 `mcp_snapshot`，MCP 服务器的登录对应在 Agent 运行时上执行的 `mcp_oauth_login`，丢弃它的 `cancelled` future 所等待的发送端即取消登录（`agent_bridge/mcp.rs`）。审批和回答的调用不会等待，在循环上运行。
- **压缩。** 桥把每个状态为 `completed` 的 `CompactionUpdated` 变成 `Context compacted` 单元格，无论压缩由什么启动，并刷新状态行。`/compact` 的回复只带失败，所以手动压缩只显示一次，`/compact` 从后台采用的压缩也是。状态为 `failed`、触发为 `automatic` 的 `CompactionUpdated` 变成警告单元格，并保留在 `/warnings` 中（来源 `compaction`）；手动压缩的失败是 `/compact` 的回复，被取消的压缩不显示任何内容。消息流式输出期间，该单元格立即添加，放在消息到那时为止的内容之后。`/status` 从它运行时读取的快照中读 `backgroundCompaction`：后台槽位变化时修订号不变。
- **覆盖层。** 转录分页器、`/diff` 分页器和恢复选择器占用备用屏幕；期间提交的单元格在 Scrollback 的尾部等待，覆盖层关闭前尾部不写入任何内容；有覆盖层打开时，终端的恢复会离开备用屏幕（致命 panic 时的恢复也是如此）。
- **文件搜索**用 `ignore` 遍历工作区根目录（嵌套在另一个根目录中的根目录作为它自己只遍历一次），送入在自己线程上运行的 `nucleo` 匹配器，随 `@token` 变化重新排序。
- **二进制**像 `exec` 一样组合并启动 Agent，使用界面的状态 sink（`TuiEvents::status_sink`），把运行中的句柄交给界面（`hanafubuki_agent_tui::run`），在界面恢复终端后用 `AGENT_SHUTDOWN_BUDGET` 关闭 Agent。轮次进行中 Agent 的状态变化（内核故障）会让 `exec` 结束，因为重启后的 Agent 有新的代次。
- **panic hook。** 二进制传给 `install_panic_hook` 的 `logging::logging_blocked` 说明线程是否在文件日志器内部；这时 hook 只写标准错误。

### 已知的限制 [#internal-limits]

- 在步骤开始时第一次追加的 `tool_catalog_omissions` 更新不在该步骤的准入估算之内。
- rmcp 的无标签 `ServerResult` 会把带有 `_meta` 和无法解码条目的结果解码为 `CallToolResult`，其中的条目已经丢失，所以这样的列表页仍会整页失败。

### 宿主的一侧 [#host-side]

宿主围绕 Agent 构建的东西由宿主自己记录；Hanafubuki 的部分（`src/agent/commands/guard.rs` 中的命令守卫、它的事件 sink 和窗口事件、来自 `AgentSlot::list_run_projections` 的任务中心行、诊断包中来自 `flush_for_diagnostics` 和 `plugin_status_for_diagnostics` 的 `app/agent-status.json` 与 `app/agent-plugins.json`、它的 `agent` 模块行和退出顺序、旧设置文件的一次性导入）见它的 [agent-integration.md](https://github.com/licyk/Hanafubuki/blob/main/docs/agent-integration.md)。每个宿主的命令层都以同样的方式工作：每次调用时解析槽位，在 Agent 的运行时上运行调用，把其中的 panic 变成这次调用的错误和一次内核故障，并用 `AgentSlot::interrupted` 回答 Agent 在调用期间停止的调用。
