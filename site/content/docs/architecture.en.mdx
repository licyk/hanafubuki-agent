This page is for someone reading the code for the first time: how the parts work together, and why the choices the code does not explain were made. The rules to follow are in [Plugin rules](/docs/plugin-rules) and the repository's [AGENTS.md](https://github.com/licyk/hanafubuki-agent/blob/main/AGENTS.md); embedding is [Embedding the Agent](/docs/embedding); the exact bounds, failure rules and file formats behind this page are in [Internals](/docs/internals).

## Goals [#goals]

The Agent is a **kernel** (`hanafubuki-agent-kernel`) that owns sessions, turns, history and the per-step snapshots, with its capabilities supplied by **plugins** on [kardia](https://github.com/licyk/kardia). The kernel reaches plugins only through the registries in `hanafubuki-agent-contracts`. The design serves three goals:

- **Fault isolation.** A failure stays with its owner: a failing tool call is a model-visible error; a plugin fault stops and restarts that plugin; an MCP server fault makes that server `Failed`, then reconnects it. Only a kernel fault rebuilds the whole Agent, and the Agent failing never stops its host application.
- **Extensibility.** A new capability is a plugin and a manifest row; the kernel, the contracts and the frontend do not change.
- **What the model sees is pinned.** The goldens record every model-visible surface; a change the model sees regenerates them on purpose.

## Crates and layers [#crates-and-layers]

Dependencies point down. `cargo xtask check-dependencies` checks against the layer table (`LAYERS` in `xtask/src/dependencies.rs`) that each member depends only on the members its row allows.

| Layer              | Crates                                                                                                                                                   | Role                                                                                                                                                                                                                          |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Neutral mechanisms | `foundation`, `tool-contracts`, `process`, `runtime`, `host`                                                                                             | paths, cancellation, the blocking boundary, panic containment, the settings vocabulary; tool-spec types; process ownership; the contained Tokio runtime; the generic module host (registries, leases, faults, restart policy) |
| Domains            | `approval`, `skills`, `web-search`, `model-api`, `workspace-fs`, `execution`, `mcp`, `memory`, `worktree`, `hooks`, `sandbox`, `compression`, `packages` | independent capabilities, each testable on its own                                                                                                                                                                            |
| The plugin API     | `contracts`                                                                                                                                              | the registries and extension-point contracts; re-exports `host`'s registration and fault mechanisms, so a plugin depends on it alone                                                                                          |
| Kernel and history | `kernel`, `history`                                                                                                                                      | sessions, the turn loop, tool planning and the pipeline, request assembly, world state, compaction and hierarchical compression, approval flows, recovery; the JSONL history and its SQLite index                             |
| Plugins            | `plugin-web`, `plugin-workspace-fs`, `plugin-execution`, `plugin-mcp`, `plugin-worktree`, `plugin-hooks`, `plugin-packages`                              | each binds one domain crate to the extension points, or serves it to the facade's calls; `plugin-packages` is the guest host, which runs installed plugins' code out of process or as WebAssembly                             |
| Configuration      | `config`                                                                                                                                                 | the Agent's own configuration (`AgentConfig`): three TOML files, layered when standalone                                                                                                                                      |
| The facade         | `hanafubuki-agent` (`crates/agent`)                                                                                                                      | the composition: the plugin host and manifest, the Agent's own plugins, the slot, the service API, the host interface, the standalone runtime, the data directory's lock, logging                                             |
| Interfaces         | `tui`, `cli`                                                                                                                                             | the terminal interface (over the facade alone) and the `hanafubuki-agent` binary (over the facade and the interface)                                                                                                          |

(The `hanafubuki-agent-` prefix is left out.) Beside the table the check holds rules the table cannot express: no dependency on any Hanafubuki crate, from any source; the kernel on no plugin; every plugin on the plugin API and on neither the kernel, the facade nor another plugin; every plugin crate a dependency of the facade (which mounts it); no member but the facade on the configuration crate; `host` on no member but `foundation`; kardia only in `host`, the plugin API, the kernel, the plugins and the facade, its loader and guest bridge (`kardia-loader`, `kardia-hmr`) only in the guest host (`plugin-packages`), and never the `kardia` facade crate (it pulls in WASM/dylib hot reload).

Three boundaries carry most of the design:

- **The kernel and plugins meet only in the contracts.** The kernel depends on no plugin, and no plugin on the kernel, the composition or another plugin. The kernel injects nothing a plugin can replace, so replacing a plugin never restarts the kernel and drops no session.
- **The model API is the wire and nothing more.** It sends a `ModelInputItem::ContextFragment { role, kind, content }` as given and treats `kind` as a label. A section's wrapper text belongs to the plugin that owns the section; `check-model-api-context` keeps every context section kind out of the model API's sources.
- **The Agent knows no host domain.** What is the host's (in Hanafubuki: instances, the Task Center, the UI context, its part of the instructions) reaches the Agent through the host interface.

## The plugin host [#the-plugin-host]

```text
the host (Hanafubuki's module host, for one)
└── AgentSlot                 per-start runtime, kernel-fault restarts, crash-loop stop
    └── AgentHost = ModuleHost<AgentPlugins>
        ├── Core:       agent-host-services (BlockingService)
        │               agent-kernel (publishes AgentKernelRegistries)
        ├── Capability: web, workspace-fs, view-image, execution, mcp, memory, skills, titles,
        │               recap, goal, subagents, worktree, hooks
        ├── host rows:  Hanafubuki's tasks, instances (Capability), ui-context (Context)
        └── Context:    workspace-context, permission-mode
```

- **`AgentSlot`** holds the Agent's state (`Disabled`, `Starting`, `Running`, `Faulted`, `Stopping`, `Failed`, `Stopped`) and supervises it: each start builds its own contained runtime, constructs and recovers the service, starts the plugins, then connects the MCP servers in the background. Holders resolve the slot per call, so no old Agent stays reachable.
- **`AgentHost`** is the Agent's profile of the generic `ModuleHost`: two core rows, then every enabled row of the manifest (`host/manifest.rs`), the host's rows among them, each mounted once the previous one settled or timed out (`PLUGIN_START_TIMEOUT`, 20 s). Configuration derives from the Agent's settings and the host's proxy; enablement from `disabledPlugins`.
- **The kernel creates the registries before the runtime starts**, and the `agent-kernel` plugin publishes them; plugins inject them and register entries. There are ten: tools, tool sources, context contributors, context renderers, turn admission, prompt contributors, approval rules, continuation hooks, tool lifecycle hooks and observers. The kernel reads each as a snapshot at a fixed point (per sampling step, per request, at turn admission, after a commit).
- **A registration is an effect of its caller.** An entry belongs to the plugin that registered it and leaves with it: a stopping plugin first hides its entries from new snapshots, waits for leased calls (`DRAIN_GRACE`), then cancels them. A registration that cannot be admitted (a duplicate id, a reserved or colliding tool name, a second contributor or renderer for a kind) fails the registering plugin at its start and affects no turn.

### Faults [#faults]

Three owners, three outcomes:

| Fault                                | Caught by                                                                                                                               | Outcome                                                                                                                                                                                            |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| a panic in plugin code               | the guard on every kernel call into a plugin (`RegistryEntry::guard`, `PluginFaults::guard`); kardia for `apply`, effects and disposers | that call's own error path; a `PluginFault` of the owner; the host stops the plugin and mounts it again under `RestartPolicy` (2 s, 10 s, 30 s, three in ten minutes, then `failed` until a retry) |
| a panic in a feature call            | `PluginFaults::guard_async` in the facade's feature helper (`AgentApplicationService::feature`)                                         | the call is `FeatureUnavailable`; a `PluginFault` of the row that provides the feature, which the host stops and mounts again as above; every other feature and the Agent run on                   |
| a panic in an MCP server's tool call | `catch_panic_async` in `McpTool::invoke`                                                                                                | the call's "internal error"; that server `Failed` and reconnected; the `mcp` plugin and the other servers run on                                                                                   |
| a panic in kernel code               | a turn's task, a command guard, the Agent's worker groups, the host's tasks (`spawn_kernel_task`)                                       | reported to the instance's `AgentKernelFaultSink`; the slot marks the Agent `Faulted`, stops it and starts a new instance after 2 s, 10 s, 30 s, rebuilding the sessions from disk                 |

**A feature plugin's failure costs only its feature.** A feature the facade offers as a call (a recap, a title suggestion, a worktree, the hooks' list and trust) is served by the service its plugin row provides, resolved per call; while the row is off, starting, failed or restarting, the call is `FeatureUnavailable` with why, and nothing else changes ([Host, configuration and status](/docs/plugin-rules#host-configuration-and-status)).

**Why a kernel fault rebuilds the whole Agent:** the locks do not poison (they are all `parking_lot`), so nothing rolls back after a panic and in-memory session state may be half-changed; the history on disk is the consistent copy.

All of it rests on unwinding. The process's panic hook lets a panic unwind only when it is known to be caught: the Agent's threads run on a contained runtime (`ContainedRuntime`, threads `agent-rt`) and in contained worker groups, and its guards mark themselves too. Those marks live in the Agent's own foundation, so a host's hook must ask `hanafubuki_agent::panic::is_panic_contained` ([the panic-hook bridge](/docs/embedding#the-panic-hook-bridge)). kardia-hmr's guest threads catch their own panics and mark themselves in kardia-hmr; the guest host registers that check with the foundation, so the same function answers for them.

### Start and shutdown [#start-and-shutdown]

A start claims a generation, builds the runtime and the process owner group, reaps the process groups an earlier run left (`process-groups.json`), constructs the service (which starts the [model discovery](#model-metadata), listing the default Provider in the background) and runs recovery on the runtime's blocking pool, starts the plugins, schedules the MCP connects (four at a time, each with its own timeouts) and installs the service as `Running`. The crash-loop marker (`start-marker.json`) stops automatic starts after three unfinished ones. Shutdown runs in fixed stages within a 20 s budget: close the slot, stop turns, MCP, plugins (one disposal of the kardia root), memory, history and executions, the process group, the runtime. Plugins own no MCP, memory, history or execution lifecycle, so the order of their teardowns does not matter.

## Sessions and turns [#sessions-and-turns]

- **A session** has a configuration (Provider, protocol, model, instructions, mode, reasoning effort, context window, compaction settings), a mode (`Default` or `Plan`), a lifecycle (`Available`, `Archived`), a title, a memory contribution mode and a [role](/docs/roles#sessions). A session can be forked before a turn or at its head. The configuration is normalized in one place (`normalize_session_config`), at creation, every update and recovery.
- **The capability scope.** The role a session is created with (`create_session(mode, role)`, `default` without one) or switched to between turns (`set_session_role`) gives it a scope (`AgentCapabilityScope`) and the role's instructions, kept in its configuration: a role file edited or deleted later changes no session that has it, and recovery reads no role file. The scope only narrows, and the kernel applies it where it already takes its snapshots: the tool plan, the tool sources, the context and turn admission contributors, the prompt contributors, the continuation hooks, and the mode each turn freezes; approval rules, tool lifecycle hooks, observers and renderers always apply ([Capability scope](/docs/plugin-rules#capability-scope)). A child's scope is its parent's narrowed by its own; a fork keeps its source's.
- **Lineage.** A session records, at creation, the workspace it was created in (the primary root and its Git branch) and, if it is a child, its parent and origin (`Side`, `Subagent`, `Review`); a fork or a child takes its source's workspace. `create_child_session` makes a child with its parent's model and configuration (its scope the parent's narrowed by the one asked for, never wider; its role instructions those of the role it is given, else the parent's), empty or from the parent's last turn boundary (its head, or as it stood before a running turn), and commits the context items it is given (continuation context) with the creation.
- **Ephemeral sessions** live in the same session table and run turns exactly as the others do; only their history store differs. The kernel's store is `SessionStores`: it routes each session's commits and reads, by id, to the durable store or to an in-memory `EphemeralAgentHistoryStore`. Every id comes from the durable store, so the two never share one; the session list and recovery read the durable store only, so an ephemeral session is never listed nor recovered, and `close_ephemeral_session` (or the end of the process) drops it. Its transcript holds only what it committed itself, while its model history starts with what it inherited; images it inherited are read through the durable session they came from. A flag on every commit path would have touched each of them; routing the store touches none.
- **A turn** runs as a managed Tokio task through `Sampling`, `RunningTools` and `WaitingForUserInput`, ending `Completed`, `Cancelled`, `Failed` or `Interrupted`. Each loop iteration may auto-compact, samples the model with a frozen tool plan, runs tools (each between the tool lifecycle hooks that apply to it), consumes steering input and asks the continuation hooks. A panic in the turn's own work ends the turn `Failed` (`InternalFailure`), and the session takes its next turn.
- **The session driver.** `AgentSessionDriver` is the narrow port through which the application drives child sessions: create one, name it, select its model (the facade's `set_session_model` is the same code), list a parent's children, give a child its parent's permission mode, run a turn and wait for its outcome, steer or interrupt that turn, read its last answer, and close it (stop its background terminals, drop it if ephemeral). It also prepares every turn the facade admits (the session's Provider, permission mode, world state and turn extensions), so a turn it runs is prepared like a user's. A side conversation and the `subagents` plugin use it; the review plugin will.
- **Subagents.** The `subagents` plugin's tools make a sub-agent a durable child (origin `Subagent`, its task name as title) and run its turns with `run_turn` in a task of their own on the Agent runtime, so the parent's tool call returns at once and a `wait_agent` only awaits a notification the task gives when the turn ends: the parent's turn never holds what the child's needs, and both run on the runtime side by side. What the plugin tracks (running turns, finished ones the parent has not waited for, messages for an idle agent's next turn) is in memory and outlives a restart of the plugin within the Agent instance; who the agents are is read from the kernel (the parent's children), so a sub-agent of an earlier run is still listed and messaged. A turn is interrupted with the kernel's confirmed cancellation, and its outcome recorded only if no later turn of the agent started. A sub-agent's role (`spawn_agent`'s `agent_type`) is read through `AgentRoleCatalogReader`, a second narrow port the application builds over its role catalog and the plugin reads at each call, so a spawn sees the roles as they are and the plugin keeps no catalog: the child is created with the role's scope and instructions in one commit (the kernel narrows the scope), then given the role's model and reasoning effort through the model selection, the parent's effort kept when the role sets none. The guidance lists the spawnable roles at every step, and only when the step's plan offers `spawn_agent` (the kernel's `PromptStep.tools`), so a role that leaves the tool out leaves the guidance out too; `spawn_agent`'s descriptor, fixed per registration, names no role and points at the guidance, so it is never stale.
- **Durable before visible.** Every mutation commits durably to history before it is visible, and a failed commit restores the in-memory state. A commit is staged under the session cell's lock and settles when its append is acknowledged: the persisted revision is published, or the record rolled back, and only then are its events emitted. The settlement runs inside the acknowledgement, on the history writer, not in the awaiting future, so it happens even if the future is dropped.
- **Sessions never wait for one another.** `SessionTable` holds its lock only to look a cell up, insert or remove one; each cell has its own lock, held only for in-memory work, never across an await, a history append or other I/O, and never with another cell's lock.
- **Cancellation** is cooperative first, then aborts the task, confirmed within 5 s. Turns interrupted by a restart are recovered as `Interrupted`. A session recovery rejects is **quarantined**, not fatal: none of its files is rewritten or deleted, and the other sessions open.
- **The workspace can move in a standalone run.** `AgentRuntime::set_working_directory` changes the standalone workspace (its roots behind a lock) without a new instance: the filesystem tools' `WorkspaceFsPolicy` is rebuilt from the new roots and a command without a `workdir` runs in the new first root, so live sessions stay live, and each sees the new roots in its next turn's `workspace_roots` section; no other note is needed. It is refused while a turn, a compaction or a background terminal runs, each started and approved in the old workspace. The configuration's project layer stays the one read at start. An embedded host owns its `WorkspaceRootsPort`, so the call is standalone only. A worktree (`hanafubuki-agent-worktree`, served by the `worktree` row) is a detached checkout under the data directory that a consumer moves into this way.
- **Limits** (`AgentHardLimits`): a turn samples at most 32 times, then fails `budget_exceeded` with every earlier output committed; its 30-minute deadline cancels it as a user's cancel would and fails it `deadline_exceeded`. Neither is shown to the model. A kernel call into a plugin that has no bound of its own (a context, turn admission, tool source or prompt `prepare` contribution, a tool's `permission`) runs within `plugin_call_deadline` (10 s), so a hung built-in, host or guest plugin costs only its contribution, never the turn ([Bounds on plugin calls](/docs/plugin-rules#bounds-on-plugin-calls)).

## Tools [#tools]

### A plan per step [#a-plan-per-step]

Every sampling step builds one immutable `AgentToolPlan`: the kernel's core tools (`new_context`, `update_plan`, `request_user_input`, and while the session's compaction strategy is `hierarchical` the five compression tools), the registered tools (each handler's `availability` for the step), the tools each tool source contributes for the step, and `tool_search` when anything is deferred. The session's capability scope then leaves out every plugin tool it does not allow, and every source of a plugin it turns off is not asked; a tool left out is absent as an unknown one is, and is not an omission ([Capability scope](/docs/plugin-rules#capability-scope)). The kernel's own tools and `tool_search` are never left out. The plan freezes the step's approval-rule snapshot and the sources' plan leases with it; a call runs against the plan that advertised it, and the leases keep what a tool was planned from (an MCP connection) alive until the step ends. Plan mode keeps only `ReadOnly` tools, `request_user_input` and the compression tools, of those the scope keeps.

### Names on the wire [#names-on-the-wire]

A tool's identity inside the Agent is its `ToolName` (namespace segments and a local name), keyed by the flattened `namespace__name`, which is never parsed back. The wire name is chosen per request (`ProviderToolTable`): Responses takes namespaces, so a namespaced function keeps its namespace and local name; the other protocols get the flattened name. Every name is fitted to the protocol's limit (128 bytes for Responses and Anthropic Messages, 64 for Chat Completions); a later one that collides or is too long is cut and suffixed with `_` and 12 hex digits of a hash of its `(provider id, tool id)`, the same on every step. A returned call is resolved by lookup of its `(namespace, name)`, and history records both.

Schemas follow the same per-protocol rule: a protocol with `strict_json_schema` (Responses) gets each schema whole, the others the keywords every OpenAI-compatible endpoint accepts (`portable_model_schema`). `strict` is never sent, and the kernel validates arguments against the whole schema either way.

**Registration refuses, planning renames.** What registration can refuse it refuses (reserved names, a flattened name already registered, an over-long name), so only sourced tools, whose catalogs come from outside, can collide at planning time, and those are renamed deterministically instead of failing the step: refusing a colliding registration fails one plugin once, while failing the step would fail every turn until the plugin was turned off.

### Exposure and deferred tools [#exposure-and-deferred-tools]

`ToolExposure` is `Direct`, `Deferred`, `DirectModelOnly` or `Hidden`. When the direct catalog is over budget, only sourced direct tools are deferred, fairly across providers. A deferred tool is found through `tool_search` (a BM25 index over name, description and schema); the search commits its output, then a `ConversationItem::ToolSelection`. The planner admits the selections in the model context since the last compaction, so a selection lasts across turns until the next compaction.

### The call pipeline [#the-call-pipeline]

The kernel owns the pipeline, and plugins cannot reorder it:

<Steps>
  <Step>
    **Stream and commit.** The response streams to its end; each tool call is committed to history
    before anything runs.
  </Step>
  <Step>
    **Disposition.** An unknown, hidden or unadmitted name, or arguments that did not parse or are
    too large, becomes a model-visible error output, and the turn goes on.
  </Step>
  <Step>
    **Arguments** are normalized against the tool's input schema (integral floats and numeric
    strings to numbers, a non-nullable optional `null` removed, an undeclared key removed under
    `additionalProperties: false`), then decoded tolerantly by the handler.
  </Step>
  <Step>
    **The gate.** The call takes the step's gate: an in-flight permit, then read access for a
    `ConcurrentRead` tool or exclusive access, first come, first served. Under it run mode policy,
    the schema check of a sourced tool and the handler's `permission` (within the plugin call
    deadline, past which the call is a tool error), so classification sees what the step's earlier
    calls did.
  </Step>
  <Step>
    **Approval routing.** Any rule's `Deny` rejects; else any `RequireUser` asks the user; else the
    session's allowance of the tool authorizes; else the turn's permission mode decides (`Manual`
    asks, `AutoReview` asks a reviewer model, `FullAccess` allows). A decision that waits releases
    the gate and retakes it once approved, so the step's other calls proceed.
  </Step>
  <Step>
    **Invoke** under an entry lease and a child cancellation, bounded by `ToolDescriptor::timeout`
    or the turn's tool idle timeout (10 min). `invoke` re-checks that the approval matches the call
    it runs.
  </Step>
  <Step>
    **Commit in call order, each as soon as possible.** An output commits once every earlier call's
    has. A call that ends in an error (cancellation included) commits nothing; the others still
    finish and commit, since their effects happened. On a cancel only unfinished calls get the
    synthetic "interrupted" output.
  </Step>
</Steps>

**No streaming dispatch.** Calls start once the response has streamed and its items are committed. Starting each call as its item completes, as Codex does, would shorten some steps; the commit and cancel rules are written so it could be added without changing them, and nothing needs it yet.

### Approval [#approval]

`AgentPermissionMode` is `Manual` (the default), `AutoReview` or `FullAccess`, frozen per turn from the session's own mode when it was given one (`set_session_permission_mode`, runtime state only, like the session's allowances), else from the setting. Each tool call is classified by its handler's `permission` into an `ApprovalAction` (kind, risk class, canonical digest). Rules can only tighten. The user may answer a `Manual`-mode prompt with `AllowForSession`: later calls of the same tool (by `(provider id, tool id, generation)`) are not asked again for the rest of the session, which is kept in runtime state only, so a restart, a fork and a changed tool ask again (for an MCP tool: a change to its server's configuration, credentials or catalog entry; a reconnect of an unchanged server keeps the allowance). Approval yields a one-shot `AuthorizedAction`; mutating tools recompute their action in `invoke` and require an exact match. Approval decides who allows a command; the [sandbox](/docs/permissions#sandbox) what it reaches. An action that asks to leave the sandbox carries `sandbox_escalation` (in its canonical digest, so the sandboxed command's approval never runs it outside): `FullAccess` refuses it, as Codex's `never` does, and its `AllowForSession` allows only the same action again (keyed by the tool and the action's details), apart from the tool's. An `AutoReview` denial the user approves afterwards (`approve_denied_action`, one of the session's ten latest denied `PermissionReview` items, between turns) becomes a kernel `ContinuationContext` note under provider `kernel`, hook `approved-denied-action`: the model reads it as trusted context, and the review evidence keeps it as a `user approval` entry beside the user's messages. It authorizes nothing by itself, so a retry is reviewed again; the history format does not change.

## Context [#context]

### Sections, slots and renderers [#sections-slots-and-renderers]

Everything model-visible that is neither history nor a tool is a **context section** of a `ContextSectionKind`, an open identifier persisted by its snake_case name:

- **World-state sections** come from `ContextContributor`s at turn admission, are versioned by a SHA-256 of kind and content, and are committed as a `WorldStateUpdate` holding only the changes. The kernel writes `tool_catalog_omissions` itself every step, and steering replaces the host context it carries mid-turn.
- **Prompt fragments** come from `PromptContributor`s per request: `prepare` (async, once per step, may do I/O), then `contribute` (pure). The `skills` plugin renders the Skill catalog (`skill_catalog`), the `memory` plugin the memory summary (`agent_memory`).

A section is shown to the model by its kind's `ContextRenderer`: a slot, an order within it, a role, a preamble, an epilogue and whether it is versioned. **A renderer is data**, so rendering runs no plugin code: it needs no guard, lease or timeout, and no request can fail because of one. Every run of adjacent sections is ordered by slot (`Instructions`, `WorldState`, `Capabilities`, `Memory`), then by the renderer's `order`, then by kind name; stable slots first and the memory summary, which may change every step, last keeps the cached prefix long. The order is explicit, in bands by owner (the kernel 0, the Agent's capability plugins from 100, a host's 500–599, the Agent's context plugins from 700, installed plugins 900; [Context renderers](/docs/plugin-rules#context-renderers)), rather than registration order, so a plugin's restart never reorders a request and invalidates the provider's cached prefix, and the manifest's order is not model-visible.

**Change detection:** only the latest version of each kind is shown, where it last changed; earlier versions are no longer in the request. So there is no "replaces previously provided" notice and no section-changed event: the persisted `WorldStateUpdate` is the change record.

### AGENTS.md [#agentsmd]

The `workspace-context` plugin's `workspace_instructions` section is read at every turn admission: first the user's own file (`AGENTS.override.md` in the data directory, else `AGENTS.md`), then each workspace root's from the root down to the directory the host selects, under one 32 KiB budget with a fair share per group (at most 16 KiB). Because it is read every turn and diffed by digest, an edit mid-session reaches the next turn.

### The context window and the token estimate [#the-context-window-and-the-token-estimate]

A session's `context_window_tokens` is resolved when it is created or its model selected, and again as each turn starts: the configured window, else what the [model metadata](#model-metadata) knows of its model (a window learned from a refusal while it is the smaller, a window a Provider's model listing reported, one models.dev gives when it is on, else a small table of known model families); without one there is no automatic compaction. The Agent has one token estimate (`hanafubuki_agent_contracts::tokens`, bytes / 4). The counts agree because they count the same request: the admission check, the step's request and an automatic compaction's check of the next request all build it with `step_model_request` and count it with `estimate_model_request_tokens`, tools and memory included.

### Model metadata [#model-metadata]

What the Agent knows about each model it reaches is the kernel's `ModelMetadataRegistry`, one per Agent, keyed by route (`ModelRouteKey`: the protocol, the canonical base URL and the model id, so two Providers serving one model id are kept apart). Each fact (context window, largest output, reasoning and its efforts, image input) is optional and carries its source and when it was observed (`ModelMetadata`). The registry keeps two sources per route, one copy of models.dev's catalogue looked up by model id, and resolves each fact on its own, in this order:

1. **Configured**: what the person set, passed in by the caller (the registry reads no configuration). A session keeps it in `AgentSessionConfig.configured_facts` (`AgentConfiguredModelFacts`: window, largest output, image input, reasoning levels), which the facade fills from the model's own settings in `providers.toml` (`providers[].models."<id>"`) and, for the window, the policy's `contextWindowTokens`, when the session is created, given a model and activated for each turn, so an edit reaches a session at its next turn. The policy's `imageInput = "disabled"` is a configured "no" over all of it.
2. **Learned**, from a Provider's refusal, and only in the safe direction: a learned window only while it is smaller than the one the other sources give, a learned "no" over a reported "yes". A learned fact holds for 7 days.
3. **Reported**, by the route's own model listing (`list_provider_models`, whose every entry is recorded whole).
4. **Catalog**: models.dev's catalogue, when `modelMetadata.modelsDev` is on, shown as `models.dev`. It only fills what nothing else says, and only adds: its "no" is never kept. The model id is normalized (lowercase, without a `vendor/` prefix, `-latest` or a `-YYYYMMDD` date) and looked up under the Provider's own entry first: `ModelProviderNames` (the Provider's id and its endpoint's host), which the kernel takes, per endpoint and for the run, wherever it is handed a Provider's id with its base URL (a session created, given a model or activated; `model_metadata`; `model_context_window`). Without an own entry, every provider's entries for the id are merged: the smallest limits and any "yes" (`hanafubuki-agent-model-api`'s `models_dev.rs`).
5. **Built-in**: the window table.

What is acted on so far: the window, at a session's creation, its model selection and each turn's start (below), the window learned from a refusal as too long (below), the largest output, for the room the threshold compaction keeps for a reply ([Compaction](#compaction)) and for Anthropic's `max_tokens` with thinking, image input and reasoning (both below). The kernel never touches the data directory: its owner injects a `ModelMetadataStore`, which the registry loads once and hands a snapshot after every change. The facade's store is `model-metadata.json` ([Data directory](/docs/data-directory#contents)); the kernel's other constructors keep the facts for the run only. The listing's merge, the expiry and the file are in [Internals](/docs/internals#model-metadata).

**Discovery.** The facade lists its Providers' models by itself, so a listing's facts are known before anyone opens a model list (`model_discovery.rs`). One worker in the Agent's worker group, with a runtime of its own, takes requests from a channel and lists one Provider at a time through the kernel's `list_provider_models`: the Provider's endpoint, token and headers, as its requests have, and a listing recorded as any other. A listing is asked for when the service is built (the default Provider), and whenever a session is bound to a Provider: created on it, given one of its models (`/model`, a role's model) or activated for a turn, which covers a resumed session on another Provider. Asking is a send on the channel, so it never delays a session's creation, a model selection or a turn. An endpoint is listed again only once its last recorded listing is a day old and, in this run, a day after its last listing or 15 minutes after a failed one. The day counts from the listing time the model metadata keeps (`listedAtMs`), so a new run, an `exec` among them, does not list again, and the listings the person asks for count too; the failures are remembered for the run only. A failure is logged at warn with the Provider's id and never what it answered (its content, which may echo a credential), and never fails a turn. Shutdown cancels a listing under way with the worker group; a cancelled listing records nothing. `modelMetadata.discovery = "off"` ([Configuration reference](/docs/config-reference#model-metadata)) leaves every request unanswered; the listings the person asks for (the model list, a Provider's test, `doctor --online`) still record. The same worker, at the same requests and whatever `discovery` says, downloads models.dev's catalogue when `modelMetadata.modelsDev` is on (`fetch_models_dev`: its own client, through the Providers' proxy (the kernel's `model_proxy`, which the facade sets from the host's `NetworkSettingsPort` at start and at each settings change), with the User-Agent `hanafubuki-agent/<version>`, no credential or header of a Provider's, a minute and 32 MiB at most, cancelled at shutdown) and records it in the registry (`record_models_dev_catalog`): again once the copy is a day old, after a failure once 15 minutes passed. The copy is saved in the snapshot and used for a week; a failure is logged at debug with what failed, never what models.dev answered, and the copy goes on being used. Off, the worker drops the copy (`forget_models_dev_catalog`). The facade's test constructors run no discovery, whatever the settings, and the test Provider (`test_support::configure_test_provider`) turns it off, so a scripted model server sees only the test's requests.

**Late resolution.** A session is created with whatever is known then and never waits for a listing. As each turn is admitted, under the session's lock and in the commit that admits it, the kernel resolves the session's route again (`service/context_window.rs`): a window that differs, in value or source, replaces `context_window_tokens`, and the session's recorded usage is measured against it in the same commit, so recovery's check that usage and window agree still holds. The session keeps where its window came from (`AgentSessionConfig.context_window_source`, left out when unknown, so a session written before is unchanged). The configured window is `configured_facts`' and wins; a window without a source (a host's, or a session written before sources were kept) counts as configured and is adopted into `configured_facts` when the session is created or loaded; a session without a window takes the one known. When the route resolves to no window at all (the listing that reported it expired and no other source knows the model), the session keeps the one it has, unless it was recorded as configured, learned or from models.dev (a window without a source is kept): a configuration that no longer names a window, a learned window forgotten, and models.dev turned off or its copy expired, leave the session's window unknown. A session not yet bound to its Provider has no route and is not resolved, so the built-in table alone never replaces what a Provider reported.

**Learned windows.** A Provider's refusal of a step's request as too long for the window (`ProviderContextWindowExceeded`, classified in `hanafubuki-agent-model-api`: [Internals](/docs/internals#context-refusals)) teaches the route a window, in `run_sampling_request`, before the turn loop compacts and retries: the window the refusal names (`context_limit_in`), else the refused request's own estimate (`estimate_model_request_tokens`), an upper bound, either only within 1024 to 20,000,000 tokens (`PLAUSIBLE_CONTEXT_WINDOW`). The route keeps the smallest it was taught while it lives (7 days), and resolution uses it only while it is smaller than what the other sources say. The refused session takes it at once, in a commit of its own under the session's lock, through the same rewrite as late resolution (`refresh_context_window`, so a configured window stays and the usage moves with the window), and records `ModelContextWindowLearned { tokens, previous }` when what it took is the learned window; so the compaction after the refusal, the retry and every later step compact by it. Every later session on the route starts with it, this run and the next (`model-metadata.json`). It is learned whether or not automatic compaction is on, from the turn's requests only (a compaction's own request that is too long is trimmed, as before, and teaches nothing), and not once the turn is cancelled.

**Image input.** Whether a session sends its model images (`effective_input_capabilities`, never persisted) is the person's policy over the route's image input fact (`service/image_capability.rs`). `imageInput = "disabled"` wins, passed to the registry as the configured "no", else the model's own `imageInput` (`configured_image_input`, in `service/model_facts.rs`); a configured "yes" beats a learned "no", so under it a refusal falls back for its request (and is still learned) and the next request sends images again. Otherwise a "no", reported by the listing or learned from a refusal (a learned "no" beats a reported "yes"), turns images off; a "yes" (models.dev's among them) or no fact leaves them on, as before; models.dev's "no" is never kept, since it only adds. A session takes it when it is created, given a model or recovered (so a compaction reads it before any turn), and again under its lock before a turn is admitted, a steering accepted, each sampling step prepared, each tool call run and each snapshot; a session whose transport names no route keeps what it has. With images off, the step's tool plan leaves `view_image` out (`ToolPlanContext.image_input`), the request is built with its images replaced by a placeholder (`sanitize_images_for_unsupported_input`), so no request is refused first, and a turn's start or a steering with an image is refused (`InvalidInput`). A fact that changes during a turn applies from the next step, and a `view_image` call planned before it is refused when it runs (`ToolCallContext.image_input`). The fallback from a refusal is unchanged: one retry with placeholders (`ModelRetryScheduled { stage: ImageInputFallback }`), after which the route learns the "no" for 7 days, kept in `model-metadata.json`. The snapshot of a session not loaded has no transport, so it shows the policy alone.

**Reasoning.** The effort a request carries is resolved per request, never stored (`service/reasoning.rs`): the session's configured effort narrowed by the route's resolved reasoning fact (`request_reasoning_effort` in `hanafubuki-agent-model-api`). Nothing known, or a model that reasons at levels its listing does not name: the effort as configured. Levels named: the configured one if listed, else its alias if listed, else the nearest on `minimal < low < medium < high < xhigh < max` (the lower on a tie), else none. A model that takes no reasoning (reported, or learned from a refusal, which beats a reported "yes"): none. The model's own `reasoningEfforts` is the configured fact over both (an empty list: no reasoning). No configured effort: none. The step's request (`begin_sampling`) and a compaction's own request take it, with the route's largest output, which Anthropic sizes its thinking under; the session logs once at warn when its effort was narrowed or dropped (a log rather than an event: the activity tracker's event dispatch is exhaustive and at its size limit). A transport that names no route has nothing known. A Provider's refusal of the parameter (`UnsupportedReasoning`, [Internals](/docs/internals#reasoning-refusals)) is retried once without it (`ModelRetryScheduled { stage: ReasoningFallback }`), composed with the image fallback, and the route learns "no reasoning" for 7 days, kept in `model-metadata.json`. `normalize_session_config` no longer drops an effort on any protocol: every protocol sends one ([The model API](#the-model-api)).

### Compaction [#compaction]

Compaction replaces history with a local summary or a Responses compaction, chosen by the session's compaction capability. It is staged on a clone of the session record and installed as a `Compacted { checkpoint }` boundary, so a failure discards the clone and leaves history unchanged. A local summary's request declares the turn's tools with the tool choice `none` (a tool call in its answer is an error), as a replayed request keeps its tools and only forbids calling them: it has the turn's cached prefix of instructions and tools, and its history's tool calls and results go out beside the tools that made them, on every protocol. It keeps user messages (newest first, within a budget) and the summary, and never summarizes sections: the next request re-renders every section from the registries, so a window compacted mid-turn still carries the Skill catalog and memory. Triggers: before a turn and mid-turn at the threshold, manual, and after a Provider's context-window error. The threshold (`AgentContextTokenStatus::calculate`) is `autoCompactThresholdPercent` of the window (80% by default), or less when what is left could not hold a reply, after Hoshimi: `min(window × percent / 100, window − headroom)`, the headroom being the route's largest output (32,768 when unknown) but at most `max(4096, window / 10)` and at most `window / 2`. The largest output is resolved from the model metadata where the threshold is checked (the session keeps none), so at the default 80% a window of 20,480 and more compacts at the percentage and a smaller one earlier (5,904 of 10,000). The same limit bounds the background band and an installed compaction's next request. The error trigger is capped: one compaction and retry per step, and a second error before a response succeeds fails the turn (`context_window_exceeded`). Each error first teaches the route a window ([Learned windows](#model-metadata)).

A session also has a compaction strategy (`AgentSessionConfig.compaction_strategy`): `standard`, the compaction above; `background`, which runs it on a snapshot while the session works and installs the result later; `hierarchical`, in which the model folds its own history into summaries projected at request time (after [billion-context](https://github.com/ranxianglei/billion-context)). Every strategy keeps this compaction as its floor (manual, the model's `new_context`, the context-error retry). The facade takes the strategy from `[compaction]` before each model operation and applies it while the session is idle (`set_session_compaction_strategy`); an ephemeral session (`/side`) always runs `standard`, and a child session (a sub-agent's, a review's) runs `standard` instead of `background` when `background.childSessions` is off. The same activation takes a changed `remoteCompaction` into the session's compaction capability, which compaction checks against its transport.

**Background compaction** (`background`, after Codex's `async_compaction`) runs the session's own implementation, any of the three, on any Provider. A turn launches it before its first request and after each of its requests, when its context is at or over `[compaction.background] thresholdPercent` of the window (the facade puts it in the turn's extensions) and under the foreground threshold, a turn has completed before it, the turn is neither cancelled nor under budget pressure and automatic compaction is on. It compacts the completed turns only, the history before the current turn's `TurnStart`, so what follows it always starts at a turn and the installed history keeps full turn structure. It runs on a task the session owns, not as the session's operation: turns, steering, `/model` and every other change go on meanwhile, and interrupting a turn only stops that turn's launches. Its slot is not persisted, so a restart drops it with no recovery obligation.

The result is installed at the next checkpoint: before a step's automatic compaction check, or before `/compact`. A compaction that is required (the threshold, a provider's context error, `/compact`) waits for one still running instead of sending its own, until the turn is interrupted; if the result fails, does not fit or is stale it compacts in line, and if the installed result still leaves the next request over the threshold it compacts in line once more. A new context the model asks for is always in line. The install is a rebase (`InstallMode::Rebase`): the window must still be the one it compacted and the history must still begin with the one it read, and the history added since stays after the replacement. Its usage is the session's, recorded when it ends, installed or not, and no turn's budget counts it. Shutdown, archiving and deletion cancel it and wait for its task; a strategy or compaction-capability change cancels it.

**Hierarchical compression** (`hierarchical`) is billion-context's algorithm, ported as the pure crate `compression` and driven by the kernel (`service/compression/`). It never rewrites history: each request is built from a projection of the window's history, in which the blocks the model folded replace the messages they cover. User, assistant and tool-output text carries ref tags (`<acp tokens="…" type="…">m00001</acp>`), by which the model names the ranges it folds; tool-call arguments never do. A live `compress` call stays in the request as the carrier of its summary, and a block whose carrier is gone is shown at its place as a `[Compressed conversation section]` summary. A compacted prefix and compaction summaries never fold. While the strategy is `hierarchical` the request also carries the algorithm's static prompt after the instructions, its nudge or status line as the last user input (never persisted), and five kernel core tools: `compress` and `decompress`, which change the state, and `search_context`, `acp_status` and `acp_cache`, which read it. `decompress` returns a block, a range of it or a message's images (attached to its output again) from the stored history, or writes the block to an export file of the session through the history store; `search_context` searches the summaries and the folded originals. The optional features, off by default, add `absorb` (a large tool result the model distils with the tool `absorb` and that then leaves the requests), `crush` (JSON, code and logs folded deterministically before `absorb` asks), the content store (a large tool result replaced on arrival by a placeholder, the original returned by `acp_retrieve` and kept in a file of the session's own beside its attachments, not in the records) and `rules` (reminders the model records with `acp_rule`, shown in the instructions). The state (refs, blocks, the nudge's baselines) is persisted incrementally: each runtime checkpoint that changed it carries a link of a chain, a snapshot or a delta since the previous link, with a new snapshot once the deltas outweigh the last one (`PersistedAgentRuntimeState.compression_update`); a `compress` or `decompress` is applied again under the lock of the commit that writes its output, so a fold and its receipt land in one commit. A fork or a child keeps the blocks whose messages it holds, with their refs, and a state that is missing or cannot be read is rebuilt from the `compress` calls in the window.

The model owns the window, so the threshold compaction, before a turn and mid-turn, is off. The standard compaction stays the floor: a provider's context-window error, `/compact`, `new_context`, and the terminal escape, when the context has stayed over the emergency threshold for three requests with nothing left to fold or clip, each run one. It compacts the projected view, the summaries as text; once it installs, the covered items have left the window and the blocks deactivate. Switching to `hierarchical` starts an empty state and mints refs over the window as it is. Switching away keeps the active blocks projecting, tags and carriers included, so the request changes only in its instructions and tools; no prompt, nudge or tool makes new blocks, and the next standard compaction ends them. Every call into the crate runs under `catch_panic`: a panic in the projection sends that request with the full history and runs the rest of the turn as `standard` (the next turn tries again), and a panic in `compress` or `decompress` is that call's error.

A host sees each fold as a `ContextCompressed` event (the blocks made, the tokens they replaced, the tier) in the commit of the call's output, and a projection's panic as `ContextCompressionFailed`. The session's snapshot carries the active blocks and the tokens compressed (`compression`), and the facade's `compression_status` reads the algorithm's status panel and cache report without changing the session. The terminal interface shows a `compress` call folded (its ranges and the first line of its receipt), and has `/compression` and a `compression` status-line item.

## Thinking [#thinking]

The thinking a model streams reaches consumers as typed events and is kept as a conversation item, whose text is **never** replayed as model input; Anthropic's signed thinking blocks are sent back within their turn, and Chat Completions' `reasoning_content` from every turn, as their protocols require (below).

- **The model API.** Thinking is `ModelEvent::ReasoningDelta { item_id, kind, index, delta }` (`kind` `Summary` or `Raw`) between a reasoning item's start and completion. Responses: `reasoning_summary_text.delta` and `reasoning_text.delta`, the request sending `reasoning: {effort, summary: "auto"}` whenever an effort is set (OpenAI sends no summary otherwise). Chat Completions: `delta.reasoning_content` or `delta.reasoning`, one item per stretch of thinking. Anthropic Messages: `thinking` blocks and `thinking_delta`, requested as adaptive thinking with `display: "summarized"` (Claude 4.6 and later) or with a budget ([Providers and models](/docs/providers-models#reasoning)).
- **The kernel.** Each reasoning item gets the kernel's own id (`AgentReasoningId`; provider ids never leave the stream) and is published as `ReasoningStarted { reasoning_id, sampling_step }`, `ReasoningDelta { reasoning_id, delta }` (Markdown) and `ReasoningCompleted { reasoning_id, duration_millis }`. The text kept is the item's summary when it has one, else its raw text.
- **A bound of its own.** Thinking does not count toward `maximum_model_output_bytes`: each item is cut at `maximum_reasoning_text_bytes` (256 KiB) on a character boundary, and the rest is neither shown nor kept. Otherwise a turn with 30 KB of thinking would start failing.
- **History.** The step commits each item as `ConversationItem::Reasoning { text, duration_millis, sampling_step, truncated, replay }` with its other items, in the order the model produced them. Its text is presentation only: `as_model_input` skips it, the token estimate does not count it (it counts only what `replay` sends back from every turn), compaction drops it, and permission reviews and memory never read it. A response that stops early completes its open items with what streamed.
- **Sending back Anthropic's blocks.** Manual thinking (`type: "enabled"` with a budget) refuses a tool result whose assistant message does not start with its thinking block, and refuses a block changed in any way. So the decoder keeps each `thinking` block whole with its `signature` (`signature_delta`), and each `redacted_thinking` block's `data`, as the item's `replay` (`ModelReasoningReplay`, at most 1 MiB a block, its `Debug` redacted). It is never serialized: not in the history, not in a snapshot, not in an event. A step's request places the current turn's blocks (after its last `TurnStart`) as `ModelInputItem::Reasoning` before the assistant items they preceded, and the Anthropic encoder sends them only with manual thinking; Responses and Chat Completions leave them out. A manual request that would continue tool calls whose message has no block to send back (a turn recovered after a restart, a compaction mid-turn, a first step that thought nothing) is sent without thinking, which Anthropic accepts. Adaptive thinking sends no block back: Anthropic allows leaving them all out, and its models from 5.1 on refuse a block once the system prompt, the tools or any message before it changed, which the Agent's requests do between steps (the task plan follows the history; a world-state section moves where it last changed; `tool_search` adds tools).
- **Sending back Chat's `reasoning_content`.** DeepSeek's thinking mode refuses (400) a request with tools in which an earlier assistant message, of any turn, comes without the `reasoning_content` it was produced with; without tools it ignores the field. So the Chat decoder keeps a stretch whose every delta came as `reasoning_content` whole, as `ModelReasoningReplay::ReasoningContent { text }` (at most 1 MiB; over it, or for a stretch that came as `reasoning`, OpenRouter's field, none). A server that sends the field takes it back, so no model id is read. The variant outlives its turn (`ModelReasoningReplay::outlives_its_turn`): a request places it from every turn of its projected history, a compaction's request too, and it is persisted with its item, unlike Anthropic's blocks, though left out of a transcript page. The Chat encoder (`chat_completions/assistant.rs`) sets the `reasoning_content` of the reasoning before an assistant message's text or first tool call, joined as it came with nothing between (the text a response not streamed carries whole), on that message, `content` `null` for calls alone, whatever `request.reasoning` says; reasoning no message follows in the request is left out, and so are Anthropic's blocks. A `hierarchical` projection keeps reasoning with the message after it, after the summaries placed before that message, and drops it with a folded one. An assistant message with nothing to send (a session from before this, thinking over the bound) goes without the field, and DeepSeek may refuse the session's requests while it is in the window, a compaction's included, since that request carries the tools too. DeepSeek's refusal names `reasoning_content`, which is no reasoning parameter: it stays a remote error (`reasoning_refusal.rs`) and never teaches the route "no reasoning". The Anthropic encoder leaves the variant out, and it is no thinking block to manual thinking's check; Responses leaves every block out.

## Storage [#storage]

The data directory (named by the host when embedded; Hanafubuki's is `<app_data>/data/agent`) is described in [Data directory](/docs/data-directory).

- **History** (`hanafubuki-agent-history`, format version 5): one JSONL rollout per session is canonical, and the SQLite index a projection rebuilt when needed. New items and fields are additive (`ToolSelection`, `Reasoning`, the optional namespace on `ToolCall`; a runtime's `parentSessionId`, `origin`, `cwd` and `branch`, absent from older records and read as none); a removed field is an ignored unknown key. What open cannot admit costs only its session: a rollout of another format moves into `.recovery`, one that does not project stays in place with a repair retried at every start, and the session is quarantined; the other sessions and the Agent open. Writes go through a per-session writer, which acknowledges an append once it and its projection are written.
- **Memory** (`hanafubuki-agent-memory`, ported from Codex) is derived from session history in two phases: phase one extracts each idle session with a small model, phase two runs a consolidation sub-agent over the extractions and publishes `MEMORY.md` and `memory_summary.md`. Eligibility comes before the limit, both phases back off (30 s doubling to a day), and publishing commits the database before it renames the files.
- **Skills** (`hanafubuki-agent-skills`): repository Skills come from `.agents/skills` in each workspace root and its ancestors up to the Git root, computed again for every catalog read; then the user root and the bundled System Skills. A Skill's body is delivered once per turn and Skill, as `ConversationItem::SkillContext`. Skills never register or restrict tools.
- **Configuration** (`hanafubuki-agent-config`): three TOML files, each its own revision domain with its own lock (`config.toml`, `providers.toml`, `mcp.toml`, the last two owner-only). Reads decode field by field: an invalid value takes its default, unknown keys stay, and a file that needed repair is copied into `.recovery/` first; writes edit the document on disk with `toml_edit` (comments, layout and unknown keys survive) and publish it by an atomic rename. Standalone, the settings are layered (profile, trusted project file, `-c`), but only the user's file is ever repaired or written. The terminal interface's configuration center is a view over these settings: its typed forms write through the same patches and atomic writers, and it parses no configuration itself. See [Configuration](/docs/configuration).
- **The data directory's lock**: `<data_dir>/.lock`, because the history index, the memory store and the process-group ledger assume one writer process.
- **Persisted formats are unstable.** The rule is that readers decode tolerantly, quarantine what they cannot use, and never delete user data.

## Installed plugins [#installed-plugins]

An installed plugin is a **package**: a directory with a manifest, installed from a directory or a marketplace and named `<plugin>@<marketplace>`. It is not a row of the plugin host. The package store (`hanafubuki-agent-packages`, ported from Codex's plugin store) holds them in the data directory's `plugins/` ([Data directory](/docs/data-directory#contents)); the configuration's `[plugins]` and `[marketplaces]` say which are on ([Plugins](/docs/config-reference#plugins)).

- **Five manifest formats**, probed in this order: this project's `.hanafubuki-plugin/plugin.json`, an Agent Plugins 1.0.0 root `plugin.json` (recognized by its `$schema`), then Codex's `.codex-plugin`, Claude Code's `.claude-plugin` and Cursor's `.cursor-plugin` `plugin.json`. A manifest or its directory that is a symbolic link or not a regular file stops the probe, so a benign manifest cannot hide another. Ours is Codex's manifest plus `runtime`, `contributes`, `permissions` and `configSchema` for code; the store keeps them for the code that will run them.
- **Read as an external producer's.** A manifest field or a component path that cannot be used is left out with an issue; only a manifest that is not a JSON object, or an Agent Plugins name or `$schema` that does not read, fails. A path must start `./` and stay in the package. Codex fails a manifest for some wrongly typed fields; here only the field is dropped.
- **Marketplaces** are `.agents/plugins/marketplace.json`, `.agents/plugins/api_marketplace.json`, `.claude-plugin/marketplace.json` or `.cursor-plugin/marketplace.json`, with local, `url` and `git-subdir` sources (not npm). An entry that cannot be used is skipped; only a file that does not read fails its marketplace. A marketplace is added from a directory, where it stays, or from a git repository, cloned into `plugins/marketplaces/`; upgrading one fetches its remote's revision and swaps the checkout. The store returns the `[marketplaces]` record; the configuration is written by its caller.
- **An install is staged and swapped.** The package is copied into staging (without symbolic links or `.git`), the marketplace entry's fields are written as its manifest when it has none, the staged manifest is checked byte for byte against the source, `commands/*.md` with a description become Skills, and the copy is renamed into `plugins/cache/<marketplace>/<plugin>/<version>/`, the previous copy of the same version kept until the swap succeeded and older versions pruned. The version in use is `local` when there is one, else the highest. The package's data directory survives uninstall unless it is purged.
- **A link is a record.** `plugins link` records a directory by reference: its entry is in `linked.json`, apart from the cache's `install.json`, so an older build's rewrite of `install.json` cannot drop it; nothing is copied, no content hash is taken and nothing is written into it (its commands do not become Skills). The store lists it after the cache's packages, read as the directory is now; a link and an install of one id refuse each other, an uninstall removes the record and keeps the directory, and `update_package` refuses it.
- **`git` runs through the Agent's `ExecutorManager`**, isolated as the worktrees' is: no inherited repository selectors, no hooks, no prompt, bounded by a timeout.

A package is content, not code: what it contributes flows into the domains' own sources, each a built-in row already. The facade (`crates/agent/src/packages`, after Codex's `load_plugin`) reads the installed packages the settings leave on, in key order, and turns each into:

- **Skill roots**: the manifest's `skills` (else `skills/`) and, but for Agent Plugins, the Skills its commands became. Their ids are `plugin:<plugin>@<marketplace>:<path>` and their names `<manifest name>:<name>`, as Codex names them ([Where Skills come from](/docs/skills#sources)). An Agent Plugins package's Skills are its root's direct children.
- **MCP servers** owned by the package ([Plugins' servers](/docs/mcp#plugin-servers)): `.mcp.json` (or the manifest's `mcpServers`) or an Agent Plugins `mcp.json`, never written to `mcp.toml`, restricted by `[plugins."p@m".mcpServers]` and run under the same supervision as the user's. The user's server of a name comes first, then the first package in key order; a server that gives way is the package's issue.
- **Hook sources** after the user's and the project's (`HookSource::Plugin`), trusted by their definition and their package's content hash, which a run checks again ([Plugins' hooks](/docs/configuration#hooks-plugins)). An Agent Plugins package's hooks never run, as in Codex.
- **Roles** (`packages/roles.rs`): the manifest's `agents` (else `agents/`), as role files for a package in this project's format, read by the configuration's role reader, or as Claude Code agent files, read by the packages crate (`read_claude_agents`: the frontmatter key by key, the Claude tools through a fixed table, a `tools` naming none of ours allowing none, `disallowedTools` as the deny list, `permissionMode` as the permission-mode cap, `plan` also denying the write tools Plan mode removes); a Codex, Cursor or Agent Plugins package has none. Each is named `<plugin>:<role>` after the id's plugin name; of two packages of one plugin name, the first by id keeps it and the other's roles are its issue. The role catalog ranks them above the built-in roles and below the user's, merged and narrowed as every role is ([Plugins' roles](/docs/roles#plugins)); what their reading left out is the package's issue.

A package that does not read, or a component of one, is an issue of that package; the others load. The set is loaded when the Agent is built (the MCP servers connect with the start) and again by `reload_packages`, which the facade runs after every settings write and `mcp.toml` write, and which each lifecycle call runs after its change: it swaps the Skill roots and the hook sources, connects or disconnects only the MCP servers that changed, and rebuilds the role catalog with the packages' roles, without a restart. `packages()` lists every installed package with its version, format, enablement, content and issues (`AgentPackageStatus`).

The model is told of the enabled packages by the `plugins` row: when a package contributes Skills to the turn's catalog or MCP servers, the Capabilities slot carries an "available plugins" section (Codex's `PluginCapabilitySummary`: the display name, the description on one line and at most 1,024 characters, the Skill prefix, the MCP server names); without one, no section, so the requests of an Agent with no packages do not change. The row owns that summary and mounts the guest host ([Code plugins](#code-plugins)), so turning it off hides the summary and stops every guest, while the content keeps flowing through the `skills`, `mcp` and `hooks` rows. In safe mode the packages are listed but none is loaded.

The lifecycle is the facade's (after Codex's plugin manager), over the one package store the Agent opened, since opening another sweeps its staging area:

- **Install** (`install_package`, from an added marketplace or a directory, filed under `local` when no marketplace is named) installs through the store, writes `[plugins."<id>"] enabled = true` (merged into the user's file, so the entry's `mcpServers` stay), reloads, and returns the package with what it asks for: its hooks to trust (and, for code, the permissions its manifest asks for, which `grant_package_permissions` records once the user consents: none for content).
- **Uninstall** removes the package and its `[plugins]` entry; its data directory stays unless purged. **Enable** and **disable** write `enabled`; a package whose marketplace is off cannot be enabled. **Update** installs again from its marketplace, as the marketplace is now, or from its directory. **Retry** reloads and starts a guest that failed again, with an empty restart window.
- **Marketplaces** (`marketplaces`, `add_marketplace`, `upgrade_marketplace`, `remove_marketplace`) are only those the user added (`[marketplaces]`): none is discovered from the home directory or the repository. Each call writes its record and reloads.
- **`package_changed`**: each lifecycle call on a package tells the plugin event sink (`AgentPluginEventSink::package_changed`) what happened, `installed`, `removed`, `enabled`, `disabled`, `updated`, or `failed` with why, after the reload. It is not in `exec --json`'s stream, whose events are a session's; nothing changes the packages during an `exec` turn.

The `plugins` command and `/plugins` ([Terminal interface](/docs/terminal-interface#plugins)) are the interfaces over these calls; `mcp list` and `/mcp` show the packages' servers, labelled, and `/warnings` their issues and a guest that failed. Using them is in [Plugins](/docs/plugins).

### Code plugins: the guest host [#code-plugins]

A package in this project's format may also carry code: its manifest's `runtime` names a program that speaks Kardia's guest protocol (`kardia-guest/2`, or version 1), which runs **out of process**, so its crash, abort or hang never reaches the Agent's process; or a **WebAssembly module** speaking the guest ABI, which runs in the Agent's process inside wasmtime, within limits of fuel, time and memory. The guest host (`hanafubuki-agent-plugin-packages`) runs both, mounted by the `plugins` row as its child fiber (`plugin-guests`).

- **A kardia-loader subtree.** The guest host is a kardia-loader whose tree has one entry per code package: its id is the package's, and its plugin is named by everything its start depends on (version, recorded content hash, command, asked and granted permissions, and for a linked package the count of its directory's changes), so a change of any starts it anew: the new name is the upgrade path, which kardia-loader answers by disposing the entry's fiber and starting the new plugin. After each reload the facade hands the guest host the code packages, on or off, and the guest host applies them to the tree with a group update: an entry is created on install, disabled when the package is off, removed on uninstall. The tree's `TreeBackend` writes what the loader changes on its own (a plugin that disposed itself is written back as off) to `[plugins]` through a settings port the facade provides, queued for its blocking writer and written only when it differs; the group update mirrors the settings and writes nothing back.
- **A resolver per package version.** An entry's name resolves to a cached kardia-hmr `ProcessGuest` whose metadata comes from the manifest (its `name`, and the service `plugin` every guest provides, in a realm of its own), so resolving starts nothing; the guest declares the same metadata when it starts, or its start fails. A module's entry resolves, the first time, to a kardia-hmr `WasmGuest`: on the blocking pool the module is compiled on the engine of its limits (guests with the same limits share one engine, and its epoch thread), with its metadata from the manifest too, so nothing is instantiated to make it; each instance declares the same metadata when it starts, or its start fails; that plugin is then the name's. Its plugin is named `guest:<plugin>@<marketplace>`, which sets a guest apart from the built-in rows in the registries and in the log.
- **The process is the Agent's.** A program guest's spawner reserves an owner and starts the process through the instance's `ExecutorManager`, as a reserved pipe executor that hands its pipes to the guest bridge; the bridge ends the process only through its receipt, and the executor is released once its end is confirmed. The process is in the instance's owner group, recorded in `process-groups.json`, swept at the instance's stop and reaped at the next start ([Processes](/docs/internals#plugin-guests)).
- **What a start needs.** For a program, what the manifest asks for must be granted (`install.json`, or a linked package's `linked.json`, keeps the grant, which `grant_package_permissions` records); and the package must still have the content hash its install recorded (checked at every spawn, or once before a module is compiled). A guest waiting for its grant is `blocked`; a package whose content changed fails its start. A linked package has no hash to keep: it starts as its directory is, under the same grant and sandbox profile.
- **Linked packages follow their directory.** While the guest host runs, it watches the directory of every linked package that is on (code or not), on a thread of the instance's contained worker group. Once one has changed and then been quiet for 500 ms, that package's revision counts one more and the guest host signals; the `plugins` row then runs the facade's reload of the packages in the background, the same one `reload_packages` runs, so the package's Skills, MCP servers, hooks and roles are read again and its guest, newly named, starts anew ([Plugin guests](/docs/internals#plugin-guests)).
- **A module reaches nothing.** Its only imports are the guest ABI's host functions (`view` and `invoke` limited as a program's), so it has no files, network, clock or environment: its manifest's `permissions` are ignored with an issue, it needs no grant (`AgentPackageGuest::ungranted` is `None`) and no sandbox, and it starts on every platform. Its limits (`runtime.limits`) bound each export: fuel, time by epoch interruption (by default as long as its longest call may take; each call's own deadline too) and its linear memory (256 MiB by default).
- **The plugin profile.** The process starts with an empty environment but its granted `env` variables, `PLUGIN_ROOT` and `PLUGIN_DATA` (on Windows also `SystemRoot`), in its data directory, confined by the sandbox's plugin profile (`SandboxPolicy::Plugin`): it reads the platform's system directories and its package, writes only its data directory, reaches the workspace as granted (`none`, `read` or `write`) and the network only if granted. Linux (Landlock) and macOS (Seatbelt) enforce the reads; Windows's restricted token cannot deny them, so there a guest reads what its user can and `workspace: "none"` is not enforced. Guests use the platform's sandbox whatever `[windows] sandbox` says (that setting is the model's commands'); where there is none (a program that did not call `helper_dispatch`, a Linux kernel without Landlock), a guest does not start.
- **Its state** is the guest host's: `starting`, `running`, `restarting`, `failed`, `stopped` or `blocked`, with why, its last exit report (exited, killed or disposed, the reason, the status) and the last 16 KiB of its stderr. `packages()` shows it with the asked and granted permissions (`AgentPackageStatus.guest`).
- **Restarts.** A guest that fails after it ran (its process exited or was killed, a call outlived its deadline, it broke the protocol or sent a frame over 4 MiB; a module trapped, ran out of fuel or time, or would grow its memory past its limit, which `GuestHost::call` tells from the call's error) fails its fiber, Kardia's `Failed`; the guest host then restarts it under the restart policy (after 2 s, 10 s and 30 s, three times within 10 minutes) by updating the failed fiber, which writes no configuration. A fourth fault in the window leaves it `failed` until `retry_package`. A start that fails is not restarted. Being stopped by faults is not being off: none of it reaches `[plugins]`.

- **Contributions through proxies.** What a guest contributes is what its manifest declares (`contributes`), never what the guest says: when its fiber becomes active the guest host registers proxies as that fiber's effects (a tool source, a context contributor and renderer per section kind, a prompt renderer, a tool lifecycle and a continuation hook, an observer), so they retire with every failure, stop or restart and come back with the next start. Each calls one method of the guest's `plugin` service within a deadline shorter than the kernel's own, so a hung guest is killed and restarts while the kernel still gets the call's error path in time: a tool error, a section or fragment left out, a hook with no say, a dropped event. The prompt fragments go through one contributor of the guest host, because a step's prepared values are keyed by type. Approval rules and turn admission are not offered. The rules and the protocol are in [Plugin rules](/docs/plugin-rules#code-plugins-rules).
- **What a guest reaches, and its settings.** Beside each guest's loader entry, a host-services entry (`<id>#host`) provides `workspace` and `settings` in a realm the two share by label, which the guest's entry declares; checked access finds nothing else a guest can `view` or `invoke`, and kardia-hmr refuses a guest any service to provide but its `plugin` (the refusal is the guest's error). Its settings, `[plugins."<id>"].settings`, are both entries' configuration, so `set_package_settings` (checked against the manifest's `configSchema`) restarts it with them.
- **Writing one.** `plugins new` scaffolds a code plugin, `plugins validate` checks it as the guest host would run it (with `--run`, starting it in a throwaway home), `plugins dev` installs it again after each change, and `plugins link` links its directory, which a running Agent follows; the package, the manifest, the SDKs and the wire are in [Writing plugins](/docs/writing-plugins).

## MCP [#mcp]

`McpManager` (`hanafubuki-agent-mcp`) owns the connections (stdio and Streamable HTTP transports, OAuth, catalogs, liveness, reconnect, leases); the `mcp` plugin is only a tool source over it, plus three resource tools. Each step, the source binds the connected servers' catalogs (as its plan lease) and contributes one tool per catalog entry.

- **The catalog is built tool by tool**; one bad tool costs only itself, and names are sanitized per character to `[A-Za-z0-9_-]`.
- **Annotations are hints, never a grant.** A tool with `readOnlyHint` and without `destructiveHint: true` is `ConcurrentRead` and `ReadOnly` (offered in Plan mode); every other is `Exclusive` and `Mutating`. Approval reads only the server's or tool's policy and the destructive hint, a missing one counting as destructive.
- **Liveness and reconnect.** When the server's side ends a connection, the server becomes `Failed` with the reason, its entry is retired (its tools leave the next plan), and the manager reconnects it under the restart policy with the configuration and secrets it was opened with.
- **The connection is the catalog revision.** A step keeps the connection it was planned with, so a call can be stale only when its connection closed; it then returns `McpError::CatalogChanged` without asking for approval, and the model searches or retries. A counter would fail calls on a connection a user's refresh retired but that still runs, breaking the guarantee that a step keeps its connection.
- **One fault owner per server, not a child fiber per server.** A named child fiber would fault under a name the host's fault handler does not know, so it would only be logged and would panic again on every call; an unnamed one faults as `mcp` and stops the whole plugin. Catching at the call isolates the server, and all servers share one process anyway.

## The model API [#the-model-api]

`hanafubuki-agent-model-api` implements three protocols, Responses, Chat Completions and Anthropic Messages: encoding, streaming decode, tool lowering and the model listing. It names a model as the Agent reaches it with `ModelRouteKey` (in an endpoint's `ModelEndpointKey`), whose endpoint is the SHA-256 of the canonical base URL rather than the URL, since a key is logged and persisted and a base URL's query may hold a credential. It knows no plugin and no context section kind, and does not depend on the plugin API. A Provider's stream is external input, decoded tolerantly: empty tool arguments are `{}`; unparseable ones `{}` plus an `argument_error`; a missing usage count is 0; a stream without a finish reason ends with `end_turn` unknown; Responses `response.incomplete` keeps the completed items and the text streamed so far, and fails only when nothing was produced. Every protocol sends a reasoning effort, each in its own field (`responses/encode.rs`, `chat_completions/reasoning.rs`, `anthropic_messages/thinking.rs`; the table is in [Providers and models](/docs/providers-models#reasoning)); Anthropic's form, adaptive or a budget, is read from the model id, since the two families refuse each other's. Wire bodies are logged only as the [content-logging rule](/docs/contributing#content-logging) allows: at `trace`, truncated.

## The terminal interface and the command line [#the-terminal-interface-and-the-command-line]

- **`hanafubuki-agent-cli`** is the `hanafubuki-agent` binary, above the facade and depending on nothing else of the workspace. Every command composes the runtime from its global flags and installs the panic hook and the log file; the commands that read or write the configuration (`config`, `providers list`, `mcp list`, `roles`, `doctor` offline) never start the Agent, so they work beside a running one; `roles` and `doctor` read the installed plugins' roles with the store's read-only listing (`PackageStore::read_installed`: no staging sweep, no quarantine, no write, no lock). `exec` brings its own sinks: the turn's `AgentEventSink` and the slot's status sink feed one channel the command's thread reads, so the events it prints are the facade's own (`--json` serializes `AgentEvent` as it is). See [CLI reference](/docs/cli-reference).
- **`hanafubuki-agent-tui`** is Codex's terminal interface (`rust-v0.93.0`) ported over the facade, on upstream ratatui 0.30 and crossterm 0.29 (Codex patches them with git forks, which crates.io cannot take). An inline viewport sits at the bottom of the terminal, and the transcript goes into the terminal's own scrollback. One adapter (`agent_bridge`) maps the turn's `AgentEvent`s onto what the chat widget shows and the interface's requests onto the facade; one loop, one channel: the terminal reader and the Agent's sinks send to the same channel, and a facade call that waits runs as a task of the Agent's runtime and reports back on it, so the loop never blocks on the Agent. See [Terminal interface](/docs/terminal-interface).

### What the port of the terminal interface changed [#what-the-port-of-the-terminal-interface-changed]

Every file in `crates/tui` derived from Codex carries a marker line saying so ([Licence](/docs/contributing#licence)). The port changed Codex's terminal interface as follows:

- **Upstream ratatui and crossterm.** Codex patches ratatui and crossterm with git forks, which crates.io cannot take; the port uses upstream ratatui 0.30 (its `scrolling-regions` feature grows the viewport) with crossterm 0.29 through ratatui's re-export, and drops the terminal palette query for the fixed theme Codex falls back to without it.
- **Over the facade.** `agent_bridge` stands where Codex has its `ConversationManager` and `CodexConversation`. Tool events carry neither arguments nor output, so a finished call's output (and for `apply_patch` the patch read by the Agent's own parser, `preview_patch`) comes from the turn's committed history (`read_turn_page`); the diff has no line numbers, since that reading has none. The slash commands map onto facade calls; `/diff` runs `git diff` in the first workspace root as the interface's own short-lived process, not a tool call of the Agent's, so the Agent's process ownership does not cover it.
- **`@` file mentions** come from Codex's `file-search` crate, ported as the interface's `file_search` module rather than a crate of its own, since only the interface uses it. crates.io's `nucleo` 0.5 has no accessor for the match scores Codex's pinned git revision reads, so the matches carry none (nothing showed them); the matcher waits on a std channel with a deadline where Codex selects over `crossbeam` channels; the locks are `parking_lot`'s.
- **Restoring the terminal.** The terminal is restored on every return (a drop guard) and on a panic that ends the process: the interface's hook restores the terminal, then runs the Agent's. A contained panic leaves the interface running.
- **Slash commands as isolated modules.** Codex's flat `SlashCommand` matches became one table (`commands`): each command's spec (name, aliases, description, whether it takes inline arguments, whether it runs during a turn or needs a session) and its dispatch, from which the popup, the lookup of `/name args` and the dispatch come. Each dispatch, and each view a command pushes (its key handling and its drawing), runs inside `hanafubuki_agent::panic::catch_panic`: a command that panics loses its view and is turned off for the rest of the run, with an error in the conversation, while the session, the composer and the other commands go on. The chat itself (composer, transcript, streaming) is not a module, so a panic there still ends the process.
- **A configuration center.** `/config` opens a full-screen, searchable list of every configuration domain with its effective value. Each domain is edited as a whole typed form, through `AgentSettingsPatch`, the standalone writer or `AgentTuiPreferencesPatch`, or opens the editor that owns it; the layers page lists the files and warnings, and a write a profile, project or `-c` shadows says so. Providers and MCP keep their revision-gated editors and say they are unlayered owner-only files.
- **Messages sent while the Agent works.** Codex's input queue (Enter steers, Tab queues, Esc interrupts and sends the waiting steers, Shift+Left edits the last queued message) lives in the chat, one per conversation, over the kernel's steering: the chat sends steers one at a time so the turn takes them in order, keeps each one's text until the turn's `SteeringConsumed` covers the sequence it was accepted under, and settles a turn's end only once every steer has its answer, since the kernel drops what a cancelled or failed turn had not read and refuses a steer that arrives late. A message typed with Tab that names a command runs at once instead of waiting, and Shift+Left puts the message before the draft rather than over it.
- **No session until it is needed.** Codex starts a thread at launch; here the bridge holds no session until the first message, or a command that needs one, creates it (what is asked meanwhile waits for it), and `/new` drops back to none. A failed creation (no default Provider) is an error in the conversation, not an exit.
- **Syntax highlighting and the status surfaces.** `render/highlight` keeps Codex's syntect and two-face set (Oniguruma grammars, the 32 bundled themes, custom `.tmTheme` files) without Codex's own model-named themes, and with no terminal palette query its default is two-face's `ansi` theme, which colors with the terminal's palette, in place of Codex's choice between Catppuccin Mocha and Latte by the queried background. The theme picker previews on a sample diff beside or under the list. The status line and the title drop Codex's account, rate-limit, cost and version items and add the permission mode and the goal; the session's values come from the facade's session snapshot when an event changes them, and the Git branch is read from `.git/HEAD`, not from a `git` process. Codex leaves the terminal's title as it last set it; here the title is pushed on the terminal's title stack and popped at exit.
- **Not ported:** the transcript pager's live tail and backtracking, custom prompts, Skill and app mentions and image attachments in the composer, the status card's account and rate limits, the search field of the status line's and the title's setups, and Codex's incremental highlighter for streamed code (a streamed answer is rendered again whole at each completed line, its code with it).

## Design choices [#design-choices]

Choices a reader might otherwise undo, and why they stand:

- **No streaming dispatch** (above).
- **One fault owner per MCP server**, and **the connection is the catalog revision** (see [MCP](#mcp)).
- **A Skill's body as `SkillContext`, not as tool output.** Compaction keeps neither, so it did not decide; the `$mention` path has no tool output, and `SkillContext` is the typed record the once-per-turn check reads, so the body has one form however a Skill is selected.
- **MCP tools are always `PollutesContribution`**, read-only or not: a read-only tool's output is still external content, like a web fetch.
- **`module_faults` off and automatic restarts on for the plugin host.** That flag is about the application's module fault sink, which plugin faults never use; they reach the Agent's host through its `PluginFaults`.
- **Renderers are data**, and **registration refuses, planning renames** (above).
- **Turn limits are not model-visible.** History has no item for a failed turn's reason; the user reads the turn's error message, and nothing needs the model to see one.
- **The sandbox rewrites the argv; the process crate does not know it.** `sandbox` turns a command into the command line of a helper, the Agent's own binary selected by its first argument (`--hanafubuki-agent-sandbox`, as Codex selects its other helpers), which confines itself and then executes the command in place. The `ExecutorManager` spawns, owns and reaps that process like any other, in pipe and PTY mode alike, so `process` (the twin of Hanafubuki's) is unchanged; Codex's argv[0] selection would have needed it to set `arg0`. Where it sits: a turn freezes the session's sandbox settings (`SandboxSettings`, an extension the facade adds when it prepares the turn), `plugin-execution` hands them to `execution` with the command, and `execution` resolves them over its workspace roots and wraps the approved command just before the spawn. On Linux the helper uses Codex's Landlock pipeline rather than its bubblewrap default: no user namespace (which many distributions restrict), no bundled `bwrap` built from C, and nothing Codex left Landlock for (its app-server's Unix sockets, denied carve-outs) applies here. On macOS there is no helper: the command line is `/usr/bin/sandbox-exec` with Codex's Seatbelt policy, its writable roots and read-only carve-outs (`.git`, which Landlock cannot make) passed as parameters (`-D`) rather than spliced into the policy's text. A mode the machine cannot enforce fails the command, never runs it unconfined ([Permissions](/docs/permissions#sandbox-unavailable)).
- **`hierarchical` is a built-in strategy, not a plugin.** As a plugin it would need a new registry the kernel calls for every request, so every request would depend on code a plugin can replace ([composition rule 1](/docs/plugin-rules#composition-rules)), and the contracts cannot name the model API's types. Instead the algorithm is a pure crate (no I/O, no async, production code that does not panic, checked as a plugin's is) and the kernel calls it under `catch_panic`: a failure there costs a request's projection or one tool call, never the session, which is what a plugin's isolation would have given.
- **Not built:** code mode (JS over all tools), cross-session MCP connection pooling, deferring every MCP tool whatever the catalog's size, MCP prompts, subscriptions, sampling and roots, Skill-registered tools or `allowed-tools` enforcement, installing a Skill on its own from the Agent (a Skill is installed with the [plugin](/docs/plugins) that carries it, or copied into a Skill root by hand), and an out-of-process Agent.

Compared with Codex (`codex-rs`), which the Agent's mechanisms were checked against:

| Area             | Codex                                                                             | hanafubuki-agent                                                                                                                                   |
| ---------------- | --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tool snapshot    | a tool router per step                                                            | a tool plan per step, with plan leases                                                                                                             |
| Names            | `{namespace, name}`, lookup only                                                  | the same; one wire-name table per request, fitted per protocol                                                                                     |
| Deferred tools   | `tool_search`; selection lives in history                                         | the same, through `ToolSelection` items until compaction                                                                                           |

## Known limits [#known-limits]

- The file tools' policy roots are fixed when the Agent is built; only the Skill roots and the context sections follow the workspace per read.
- A session's window is resolved again only as a turn starts: a window learned while a turn runs is taken at the session's next turn, and a reported window the model metadata no longer knows at all is kept until the session's model is selected again.
- An MCP reconnect reuses the secrets the connection was opened with, so an expired OAuth token fails it until the user connects by hand.
- The Skill watcher watches only the roots that exist at start; later roots, an enabled package's among them, rely on the stamp each read takes.
- A hand edit of `[plugins]` takes effect at the next start or reload; the Agent reloads its packages after its own settings writes only.
- On Windows a program guest's sandbox does not restrict its reads.
- A WebAssembly guest's failed instance is found only by a call whose caller waited for it: a guest stopped in a call its caller gave up on (a cancelled turn) is failed by its next call, which fails. Each set of limits in use keeps one engine, and one thread that advances its epoch every 10 ms.
- The built-in context windows cover only families whose limits are published (GPT, o-series, Claude, Gemini 2.5); any other model needs the Provider's listing or the setting before it compacts automatically.
- The command sandbox exists on Linux and macOS only; Windows (a restricted token, its elevated setup) has none yet, so an unset `sandboxMode` is full access there. The macOS sandbox is checked by its tests on macOS only.
- Not verified off Linux: the `notify` watcher's macOS and Windows backends, Windows paths in the directories the Skill catalog shows, the MCP stdio exit reason and a dead child's disposal on Windows, and the memory artifact install rename on Windows.
