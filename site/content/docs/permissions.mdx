模型想要执行有副作用的操作（运行命令、修改文件、调用 MCP 工具）时，Agent 先根据**权限模式**决定是否需要你的同意。

## 权限模式 [#modes]

| 模式         | `--permission-mode` | `config.toml` 中的值 | 行为                                               |
| ------------ | ------------------- | -------------------- | -------------------------------------------------- |
| 手动（默认） | `manual`            | `"manual"`           | 需要审批的操作都等你回答                           |
| 自动审查     | `auto-review`       | `"auto_review"`      | 由模型审查需要审批的操作，判断是否允许，不再询问你 |
| 完全访问     | `full-access`       | `"full_access"`      | 需要审批的操作直接允许                             |

设置方式：

```sh
hanafubuki-agent config set permissionMode auto_review   # 以后都使用
hanafubuki-agent --permission-mode full-access exec "..." # 只对这次运行
```

也可以写在配置档中，例如 `[profiles.review] permissionMode = "auto_review"`，再用 `-p review` 选择。权限模式在每个回合开始时确定。在终端界面中，`/permissions` 可以为本会话修改它（见下文），`/status` 会显示生效的模式。

### 单个会话的模式 [#session-mode]

一个会话可以使用与配置不同的模式，直到会话结束，不改变 `permissionMode`。在终端界面中用 `/permissions` 设置：从三种模式的列表中选择（Full access 需要确认），或用 `/permissions 模式` 直接设置（[终端界面](/docs/terminal-interface#permissions)）。嵌入的宿主用 `set_session_permission_mode` 设置它（[嵌入 Agent](/docs/embedding#permissions)）。

- 随时可以修改。正在运行的回合保持开始时的模式，会话的下一个回合使用新模式。
- 只属于这个会话：其他会话，以及从它分叉出的会话，仍使用配置的模式。
- 只保存在内存中：重启后，会话回到 `permissionMode`。

## 沙箱 [#sandbox]

权限模式决定由谁批准一个命令；**沙箱**决定获得批准的命令能触及什么。两者互相独立：完全访问模式下不经询问就运行的命令，仍在沙箱中运行。

| `sandboxMode`                                  | 模型运行的命令可以                                                                                                                                                                                               |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `"read-only"`                                  | 读取你的用户能读的所有文件；除 `/dev/null` 和 `/dev/tty` 外不能写入；不能使用网络                                                                                                                                |
| `"workspace-write"`（Linux 上的默认值）        | 读取所有文件；只能写入[工作区根目录](/docs/tools#workspace)、`/tmp`、Agent 的临时目录（`TMPDIR`）和 `sandboxWorkspaceWrite.writableRoots` 之下；只有 `sandboxWorkspaceWrite.networkAccess = true` 时才能使用网络 |
| `"full-access"`（macOS 和 Windows 上的默认值） | 你的用户能做的一切：没有沙箱                                                                                                                                                                                     |

```sh
hanafubuki-agent config set sandboxMode read-only
hanafubuki-agent config set sandboxWorkspaceWrite.networkAccess true
```

它们就是 Codex 的 `sandbox_mode` 和 `[sandbox_workspace_write]`；Codex 的默认预设是不带网络的 workspace-write。这些键见[配置参考](/docs/config-reference#sandbox)。和权限模式一样，一个回合的沙箱在回合开始时确定。

### 平台 [#sandbox-platforms]

- **Linux**：Landlock 限制文件系统（Linux 5.13 或更新，且启用了 Landlock），seccomp 限制网络（x86_64 和 aarch64）。沙箱中的命令会再次启动 `hanafubuki-agent` 程序作为辅助进程，它先限制自身，再变成那个命令，所以命令仍是 Agent 所拥有的那个进程。这是 Codex 的 Landlock 流程；Codex 自己现在优先使用 bubblewrap，它需要许多系统都会限制的用户命名空间，以及一个随附的 `bwrap`。
- **macOS 和 Windows**：暂时没有沙箱（计划使用 macOS 的 Seatbelt 和 Windows 的受限令牌）。在这些平台上，未设置的 `sandboxMode` 即 full-access；设为其他模式会让每个命令都失败，见下文。

`hanafubuki-agent doctor` 会报告当前生效的沙箱模式，以及这台机器能否提供它。

### 沙箱不可用时 [#sandbox-unavailable]

需要沙箱、而这台机器无法提供的命令**不会运行**：Agent 绝不会改为不受限地运行它。这个工具调用在请求任何人审批之前就失败，模型会读到原因：

```text
the command was not run: it needs the workspace-write sandbox, which is unavailable (this kernel has no Landlock (Linux 5.13 or later, with Landlock enabled)); set sandboxMode to "full-access" to run commands without a sandbox
```

在这样的机器上，设置 `sandboxMode = "full-access"` 即可重新运行命令，不受限制。嵌入 Agent 的程序必须让自己的程序文件充当辅助进程，否则每个沙箱中的命令都会这样失败（[嵌入 Agent](/docs/embedding#sandbox-helper)）。

### 它不涵盖的内容 [#sandbox-limits]

- 只有模型运行的命令（`exec_command`，以及它们留在后台运行的终端）在沙箱中。文件工具受工作区根目录和审批约束；你配置的 MCP 服务器和[钩子](/docs/configuration#hooks)在沙箱之外运行。
- 读取不受限制。
- 可写根目录之下没有任何内容保持只读，包括 `.git`：Landlock 只能授予权限，所以 Codex 把工作区中的 `.git` 设为只读的做法没有移植。
- 没有网络访问时，除 Unix 套接字外的所有套接字都会被拒绝，连接任何套接字也会被拒绝，包括 Unix 套接字（SSH agent、Docker 的套接字）。有网络访问时，只有虚拟机套接字仍被拒绝。两种情况下，可以绕过过滤器打开套接字的 `io_uring` 都会被拒绝。
- 在终端（PTY）命令中，`/dev/stdout` 和 `/dev/stderr` 指向终端的 `/dev/pts` 设备，它不可写：请直接写到输出，或写到可写的 `/dev/tty`（命令自己的终端）。
- 在早于 6.2 的内核上，截断可写根目录之外的文件不受限制（Landlock 第 3 版之前的 ABI 做不到）。
- 没有提升权限的途径：与 Codex 不同，模型不能请求在沙箱之外运行某个命令。需要时请改变模式。
- 模型不会被告知沙箱模式；被沙箱拒绝的写入或连接，会以操作系统报告的错误失败（`Permission denied`、`Operation not permitted`）。

### 单个会话的沙箱 [#session-sandbox]

和权限模式一样，一个会话可以有自己的沙箱模式，直到会话结束，不改变 `sandboxMode`（`set_session_sandbox_mode`，见[嵌入 Agent](/docs/embedding#permissions)）。会话的下一个回合使用它；它只保存在内存中；分叉出的会话不带它，子代理沿用父会话的。`sandboxWorkspaceWrite` 仍取自配置。

## 哪些操作需要审批 [#what-asks]

| 操作                                           | 是否需要审批                                         | 风险等级                             |
| ---------------------------------------------- | ---------------------------------------------------- | ------------------------------------ |
| 运行命令（`exec_command`）                     | 每次都需要                                           | 严重（critical）                     |
| 向运行中的命令输入、调整终端大小               | 不需要                                               |                                      |
| 修改文件（`apply_patch`）                      | 需要                                                 | 高；修改工作区目录以外的文件时为严重 |
| 移动、删除文件（`move_path`、`delete_path`）   | 需要                                                 | 高；递归删除为严重                   |
| 读取文件、列出目录、搜索文本                   | 不需要                                               |                                      |
| 网页搜索和抓取                                 | 不需要                                               |                                      |
| MCP 工具                                       | 取决于服务器的审批策略，见 [MCP](/docs/mcp#policies) | 高；工具声明有破坏性时为严重         |
| MCP 资源、记忆工具、Skill 列表和读取、查看图片 | 不需要                                               |                                      |
| 启用或停用 Skill                               | 总是询问你                                           | 严重                                 |
| `git clone`                                    | 总是询问你                                           | 严重                                 |

- 没有“安全命令”白名单：即使是 `ls` 或 `git status` 也需要审批。
- 读取文件不受工作区目录限制，模型可以读取你的用户能读取的任何文件。
- **总是询问你**的操作（启用或停用 Skill、`git clone`）即使在自动审查和完全访问模式下也会询问，并且只能允许一次。

## 回答审批 [#answering]

  <Tab value="终端界面">
    审批框显示操作类型、摘要和风险等级。按 `y` 允许一次，按 `a` 在本会话内允许（可用时），按 `n` 或
    Esc 拒绝。Ctrl-C
    拒绝当前请求及排在后面的所有请求。见[终端界面](/docs/terminal-interface#approvals)。
  </Tab>
  <Tab value="exec">
    `--approve` 决定如何回答：`deny`（默认，全部拒绝）、`ask`（在终端上询问你）或
    `allow:工具[,工具…]`（列出的工具允许，其他拒绝）。见 [exec](/docs/exec#approvals)。
  </Tab>
</Tabs>

- **允许一次**只允许这一个操作。
- **本会话内允许**（`a`）在会话剩下的时间里，同一个工具的请求不再询问，不论是什么命令或路径。这个允许只保存在内存中：重启、或者工具发生变化（例如 MCP 服务器的设置或凭据改变了）后会重新询问；只是重新连接的 MCP 服务器会保留它。总是询问你的操作不提供这个选项。
- **拒绝**后，模型会收到“被拒绝”的结果，通常会换一种做法，或者向你说明为什么需要这个操作。
- 审批最多等待 15 分钟，超时视为拒绝。

## 自动审查 [#auto-review]

自动审查模式下，需要审批的操作交给**会话自己的模型和 Provider** 审查。审查请求不带工具，只包含操作本身和对话的摘录，模型要给出风险等级、你是否授权过这个操作、允许或拒绝，以及理由。

- 允许时直接执行；拒绝时模型会收到理由。
- 连续三次拒绝会停止回合，避免模型反复尝试。
- 审查超时（90 秒）或失败时拒绝这个操作。
- 审查过程记录在会话历史中，`exec --json` 中是 `permission_review_*` 事件。
- 审查拒绝的操作可以由你批准，见下文。

自动审查会增加模型请求，也依赖模型的判断。它适合日常的、可以撤销的工作。

### 批准被拒绝的操作 [#approve-denied]

审查拒绝了一个你确实需要的操作时，可以批准它：在终端界面中，`/approve` 列出本会话的拒绝供你选择（[终端界面](/docs/terminal-interface#permissions)）；嵌入的宿主调用 `approve_denied_action`（[嵌入 Agent](/docs/embedding#permissions)）。只能批准会话最近十次拒绝中的一次，回合或压缩运行期间不能批准。

批准不会执行这个操作，也不会开始回合。它在会话历史中加入一条说明，模型从下一次请求起读到它：

```text
The user has manually approved a specific action that automatic permission review previously denied.

Treat this as approval to perform that exact action in the same context in which it was originally requested.
Do not assume this also authorizes similar operations with different payloads.

Approved action:
<操作的摘要>
```

- 模型把这条说明视为可信的上下文，你让它继续时，它可以再次尝试这个操作。
- 重试**仍然要经过审查**。审查模型在你自己的消息中看到这条说明，标记为 `user approval`，并被告知它只授权这个确切的操作。其他操作，或参数不同的同一操作，照常判断。
- 这条说明保存在会话历史中，重启后仍在。[压缩](/docs/providers-models#compaction)既不保留这条说明，也不保留拒绝记录：压缩之后，这次批准就不再有效。

## 完全访问 [#full-access]

完全访问模式下，需要审批的操作直接允许，不再询问。仍然有效的限制：

- [沙箱](#sandbox)：命令按 `sandboxMode` 的规定受限运行。
- 总是询问你的操作（启用或停用 Skill、`git clone`）。
- 被直接拒绝的调用，例如 MCP 服务器设置为 `deny` 的工具、无法解析的命令或路径。
- [计划模式](/docs/plan-mode)仍然只提供只读工具。

## 评审中 [#review]

[评审](/docs/sessions#reviews)会话是只读的，代替 Codex 评审时所用的只读沙箱：

- 只读的工具（文件、目录、文本搜索、网页、图片、MCP 资源）和其他地方一样运行。
- 命令只有在是 `git --no-pager` 加 `status`、`diff`、`show`、`log`、`blame`、`rev-parse`、`merge-base`、`ls-files` 之一和普通参数时才运行：没有引号、变量、重定向、管道或第二个命令，也没有 `--output` 或 `--ext-diff`。它通过 POSIX shell 或 PowerShell 运行，从不经过 `cmd.exe`（后者会先运行工作目录中的 `git.cmd`）。必须带 `--no-pager`，这样不会有分页器在终端上等待输入。
- 其他需要审批的操作（其他命令、修改文件、需要审批的 MCP 工具、Skill）都**不经询问直接拒绝**，原因作为工具的错误。不需要审批的照常运行：服务器策略不经询问允许的 MCP 工具（`allow` 且不是破坏性的），以及计划、目标等 Agent 自己的工具。
- 评审的回合以完全访问模式运行，所以允许的操作不经询问直接运行（Codex 的“从不询问”）。之后你在评审会话上开始的回合按你的模式运行，仍然是只读的。
- 这条规则属于 `review` 插件：插件关闭时不能开始评审，之前的评审会话也不再保持只读。

## 其他控制 [#other-controls]

- [沙箱](#sandbox)限制获得允许的命令能写入和访问的内容。
- [计划模式](/docs/plan-mode)让模型只能使用只读工具，与权限模式无关。
- MCP 服务器有自己的审批策略（`allow`、`ask`、`deny`），见 [MCP](/docs/mcp#policies)。
- `disabledPlugins` 可以整个去掉某类工具，例如 `["execution"]` 让模型无法运行命令，见[配置参考](/docs/config-reference#general)。
- 模型会被告知当前的权限模式，以便据此规划。
